## Core job and dispatch

| Feature                           | Status    | Current behavior and limits                                                                                                                                                                                                                                                 |
| --------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stable job identity               | Supported | One `job` UUID persists across debounce replacements, attempts, events, runtime, and outcome.                                                                                                                                                                               |
| JSON payload and named type       | Supported | Payload and type become immutable when dispatch starts; pending debounce may replace them first. Optional `QueueOptions.contracts` validate versioned payloads and results, persist canonical JSON size limits, and redact configured top-level fields from operator reads. |
| Job tags                          | Supported | Jobs accept up to 20 non-empty tags of at most 100 characters; a GIN index supports overlap and containment filters.                                                                                                                                                        |
| Named queues                      | Supported | Enqueue and claim accept queue names.                                                                                                                                                                                                                                       |
| Queue pause/resume and purge      | Supported | `set_queue_paused_v1` suppresses claims per queue via `queue_control`; `purge_queue_v1` removes scheduled and ready work atomically.                                                                                                                                        |
| Strict-priority ordering          | Supported | Ready runtimes order higher integer priorities first, then preserve FIFO among equal-priority jobs with a monotonic sequence. Batch-ready jobs receive sequences in input order; promotion and retry assign a new ready sequence.                                           |
| Immediate and delayed enqueue     | Supported | Due jobs enter ready runtime; future jobs enter scheduled runtime.                                                                                                                                                                                                          |
| Atomic batch enqueue              | Supported | Up to 1,000 mixed requests share one classification timestamp, return IDs in order, and roll back together.                                                                                                                                                                 |
| Transactional application enqueue | Supported | An active `Queryable`/`PoolClient` controls the transaction.                                                                                                                                                                                                                |
| Persisted enqueue retry policy    | Supported | `retryPolicy` accepts fixed, exponential, or decorrelated-jitter configuration and is validated and normalized by PostgreSQL.                                                                                                                                               |
| Notification-assisted dispatch    | Supported | One process-local listener per node-postgres pool routes commit-delivered queue and wildcard wake hints to matching workers. Reconnects wake every subscriber; jittered bounded polling remains authoritative.                                                              |
| Bounded promotion                 | Supported | `promote_v1` uses the selective scheduled index and `FOR UPDATE SKIP LOCKED`.                                                                                                                                                                                               |
| Multi-worker claim                | Supported | `claim_v1` atomically enforces durable queue and optional queue-scoped key budgets, then changes one bounded priority-ordered candidate to active.                                                                                                                          |
| Fleet-wide concurrency policies   | Supported | Namespaced desired-state policies limit unexpired active work across workers. Keyed admission uses bounded lookahead, and capacity release sends a queue wake hint.                                                                                                         |
| Fleet-wide rate-limit policies    | Supported | Namespaced queue and optional per-key token buckets consume one durable token per start. PostgreSQL owns refill time, competing claims serialize consumption, and bounded status reports tokens, throttled work, and next eligibility.                                      |
| Single mutable live row           | Supported | Scheduled, ready, and active state are mutually exclusive shapes in `job_runtime`.                                                                                                                                                                                          |
| Selective dispatch indexes        | Supported | Separate partial indexes cover ready, scheduled, and active-expiry access paths.                                                                                                                                                                                            |
| Declarative recurring jobs        | Supported | Namespaced definitions synchronize into the target database. Worker-owned cadence calls PostgreSQL's shared evaluator and fires jobs through the normal Workhorse protocol.                                                                                                 |
| Schedule revision fencing         | Supported | Changed definitions increment a revision; stale cron commands become no-ops instead of running new payloads at an old cadence.                                                                                                                                              |
| Schedule occurrence deduplication | Supported | One durable `(namespace, schedule, second)` key prevents duplicate enqueue for the same supplied or observed fire second.                                                                                                                                                   |
| Persisted schedule retry policy   | Supported | Recurring job definitions persist the same optional policy and copy it to every fired job identity.                                                                                                                                                                         |
| Enqueue idempotency               | Supported | Optional `options.idempotency` uses PostgreSQL scoped ownership. Equivalent retained requests return the same job ID without duplicate durable/FIFO/notify effects; mismatches roll back with safe structured conflict details.                                             |
| Keyed debounce                    | Supported | Optional `options.debounce` keeps one pending identity per scoped key. PostgreSQL replaces its accepted definition and either resets or preserves its run time, with structured outcomes and lifecycle events.                                                              |
| Debounce lifecycle boundary       | Supported | Active, terminal, incompatible-key, and elapsed pending work is non-replaceable. Purged identities and keys whose windows elapsed after dispatch can accept fresh work.                                                                                                     |
| Keyed throttle                    | Supported | Optional `options.throttle` accepts one equivalent job per scoped PostgreSQL-owned window. Later requests return the retained identity as `coalesced` without duplicate event, FIFO, or notification effects.                                                               |
| Throttle lifecycle boundary       | Supported | Ready, scheduled, active, and terminal jobs coalesce until expiry. Window expiry or purge permits a fresh identity, while material changes and retained cross-mode keys reject.                                                                                             |
| Idempotency bounds and defaults   | Supported | Scope defaults to `default`, TTL defaults to 24 hours, keys are limited to 512 UTF-8 bytes, scopes to 256 bytes, and TTL is 1 ms through 365 days.                                                                                                                          |
| Idempotency request equivalence   | Supported | Queue, type, payload, sorted tags, max attempts, normalized retry policy, TTL, and explicit `runAt` are material. Omitted keyed `runAt` remains omitted so immediate retries replay.                                                                                        |
| Idempotency expiry and purge      | Supported | Expired bindings permit key reuse. Housekeeping removes expired bindings before terminal identity pruning, and queued/scheduled purge releases bindings.                                                                                                                    |
| Unkeyed enqueue compatibility     | Supported | Omitting `idempotency`, `debounce`, and `throttle` preserves the prior non-deduplicating behavior and creates a new identity for every accepted request.                                                                                                                    |
| Immediate cancellation            | Supported | Ready, future-scheduled, and durable-wait continuations atomically leave runtime and create one immutable `canceled` outcome. Never-started jobs do not invent attempt history.                                                                                             |
| Recurring occurrence cancellation | Supported | Canceling a fired occurrence affects only its job. The schedule definition remains enabled and later occurrences fire independently.                                                                                                                                        |

## Ownership, retry, and failure

| Feature                             | Status    | Current behavior and limits                                                                                                                                                                                                                                                                                              |
| ----------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Lease ownership                     | Supported | Active runtime stores worker, fence, acquisition, heartbeat, and expiry.                                                                                                                                                                                                                                                 |
| Global fencing                      | Supported | Each claim allocates a monotonic fence; stale generations cannot mutate a newer lifecycle.                                                                                                                                                                                                                               |
| Heartbeat                           | Supported | `heartbeat_v1` returns ownership status directly, including accepted, cancellation, deadline, timeout, and stale outcomes.                                                                                                                                                                                               |
| Active cancellation delivery        | Supported | Active cancellation is a durable request delivered through heartbeat status and handler `AbortSignal`; the exact worker/fence acknowledges it cooperatively.                                                                                                                                                             |
| Cancellation expiry materialization | Supported | If an active handler ignores the signal until lease expiry, bounded recovery creates `canceled` instead of retrying.                                                                                                                                                                                                     |
| Absolute job deadlines              | Supported | Enqueue can persist a finite deadline; expired work cannot enter a new claim, active expiry is cooperatively signaled, and deadline termination never retries.                                                                                                                                                           |
| Per-attempt execution timeouts      | Supported | Each attempt can have a bounded active-execution budget; durable waits pause it, timeout evidence is distinct, and remaining retry budget schedules a later attempt.                                                                                                                                                     |
| Late-write fencing                  | Supported | Completion, failure, heartbeat, checkpoint, and wait writes cannot overwrite a committed deadline or execution-timeout transition.                                                                                                                                                                                       |
| Expiry recovery                     | Supported | Bounded cooperative recovery locks expired active runtimes and requeues, terminally fails, or materializes a requested cancellation.                                                                                                                                                                                     |
| Centralized maintenance             | Supported | Advisory-lock-coordinated workers run the fast tick plus independently due partition, history-retention, and terminal-storage tasks off the claim hot path.                                                                                                                                                              |
| Immediate/delayed retry             | Supported | `fail_v1` increments attempt and CAS-updates the same runtime to ready or scheduled.                                                                                                                                                                                                                                     |
| Built-in retry policies             | Supported | Fixed `{delayMs}`, exponential `{initialDelayMs,multiplier,maxDelayMs}`, and decorrelated jitter `{baseDelayMs,maxDelayMs}` apply to handler failure and lease recovery.                                                                                                                                                 |
| PostgreSQL-owned selection          | Supported | PostgreSQL validates policy, selects delay, performs the transition, persists jitter state, and records policy, selected delay, and source in lifecycle events.                                                                                                                                                          |
| Deterministic decorrelated jitter   | Supported | Selection derives from stable job identity, attempt, and persisted previous delay; replay and `Queue` recreation do not change it.                                                                                                                                                                                       |
| Retry-policy bounds                 | Supported | Delays are integers from 0 through 31,536,000,000 ms; multiplier is an integer from 1 through 100; maximum must be at least initial/base.                                                                                                                                                                                |
| Omitted-policy compatibility        | Supported | Handler failure retains legacy Sidekiq-inspired random backoff; expired-lease recovery remains immediate.                                                                                                                                                                                                                |
| Manual retry-delay override         | Supported | Numeric `Queue.fail`, `WorkerOptions.retryDelayMs`, and explicit recovery delays take precedence while PostgreSQL still enforces the attempt budget.                                                                                                                                                                     |
| Retry budget                        | Supported | Exhaustion atomically removes runtime and creates failed outcome.                                                                                                                                                                                                                                                        |
| Terminal success                    | Supported | Completion atomically removes runtime and creates succeeded outcome plus attempt/event history.                                                                                                                                                                                                                          |
| Terminal failure                    | Supported | Handler exhaustion or lease exhaustion creates immutable failed outcome.                                                                                                                                                                                                                                                 |
| Terminal cancellation               | Supported | Immediate, acknowledged, or expiry-materialized cancellation creates one immutable canceled outcome. Attempt history is added only when a logical attempt started.                                                                                                                                                       |
| Cancellation race ownership         | Supported | Cancellation, completion, and failure serialize on runtime. First commit wins; stale completion, failure, heartbeat, checkpoint, wait, and acknowledgement writes fail.                                                                                                                                                  |
| Cancellation request idempotency    | Supported | Repeated active or terminal requests return retained evidence without duplicate request events, terminal events, outcomes, or attempt rows.                                                                                                                                                                              |
| Immutable terminal materialization  | Supported | Terminal jobs occupy `job_outcome`, not dispatch indexes.                                                                                                                                                                                                                                                                |
| Dead-letter views and redrive       | Supported | `list_dead_letters_v1`/`Admin.listDeadLetters` page and filter cold failed outcomes. Audited single or oldest-first bounded bulk redrive creates fresh ready identities, supports exact request replay and dry-run, clears the old absolute deadline, preserves immutable source outcomes, and records retained lineage. |
| Retry policy exposure               | Supported | Enqueue and schedule definitions accept `retryPolicy`; claims and `JobSnapshot` return the normalized persisted value.                                                                                                                                                                                                   |

## Durable execution boundaries

These primitives make selected handler boundaries durable while preserving Workhorse's restart-from-entry execution model. They do not persist a JavaScript stack or provide a workflow graph.

| Feature                              | Status    | Current behavior and limits                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Named checkpoint execution           | Supported | `context.checkpoint(name, operation)` reuses a completed name on replay; otherwise it runs the operation and persists its JSON result under the current lease. Overlapping same-name calls in one activation are coalesced.                                                                                                                            |
| Checkpoint reads                     | Supported | Handlers expose `getCheckpoint`; `Admin.getCheckpoint` and `listCheckpoints` provide low-level reads with attempt, fence, worker, and creation-time provenance. The existing demo task drawer renders the same immutable outputs as checkpoint-backed interim artifacts.                                                                               |
| Checkpoint immutability and fencing  | Supported | `Queue.saveCheckpoint` accepts only the exact active, unexpired worker/fence generation. Reusing a name with materially different JSON raises `CheckpointConflictError`; stale ownership raises `CheckpointLeaseLostError`.                                                                                                                            |
| Checkpoint value limits              | Supported | Names contain 1 to 200 characters and each PostgreSQL-canonical JSONB value is limited to 1 MiB. The external-effect-to-checkpoint crash window remains at least once and requires application idempotency.                                                                                                                                            |
| Relative durable timer               | Supported | `context.sleep(name, durationMs)` stores the first relative duration and PostgreSQL-computed wake target, releases ownership into the scheduled index, and suspends without consuming the logical attempt.                                                                                                                                             |
| Absolute durable timer               | Supported | `context.sleepUntil(name, wakeAt)` persists an immutable absolute target. Reusing the name with a different mode or target raises `WaitConflictError`.                                                                                                                                                                                                 |
| Timer replay and inspection          | Supported | A due timer is promoted and reclaimed with a new fence in the same logical attempt. `context.getWait`, `Admin.getWait`, and `listWaits` expose the committed boundary and provenance. Handler code restarts from entry on every claim.                                                                                                                 |
| Timer bounds and lease safety        | Supported | Wait names contain 1 to 200 characters; each job retains at most 1,000 waits; first targets are limited to a 365-day future horizon. Stale ownership and wait-limit failures have typed errors.                                                                                                                                                        |
| Durable lifecycle history            | Supported | Checkpoint creation and timer scheduling, elapsed reclaim, and replay append explicit lifecycle events. One finalized attempt-history row spans all timer suspensions in that logical attempt.                                                                                                                                                         |
| Linked child fan-out and result join | Supported | `context.runChild` and `context.runChildren` create fenced named children and block the parent without holding a lease. Set joins return tagged success, failure, and cancellation outcomes by default; explicit all-success operations propagate rejected outcomes. Retry, cancellation, redrive, and retention preserve bounded lineage evidence.    |
| Durable health visibility            | Supported | Queue health reports sleeping jobs, overdue waits, and the next durable wake target. The demo dashboard separately shows immutable checkpoint outputs, durable waits, and the latest mutable progress projection.                                                                                                                                      |
| Human decision waits                 | Supported | `context.waitForHuman` stores bounded operator context and releases the lease. The dashboard lists pending decisions and completes one with authenticated attribution; `Queue.completeHumanWait` exposes the same idempotent transition to applications.                                                                                               |
| Signals and workflow DAGs            | Partial   | Named signal and human waits support idempotent delivery, caller-selected bounded timeout, job-deadline timeout, cancellation fencing, safe parent retention, and bounded operational diagnostics. Bounded dependencies and linked child fan-out are supported, while a deterministic workflow runtime and persisted continuation stack remain absent. |

## History, reads, and observability

| Feature                           | Status    | Current behavior and limits                                                                                                                                                                                                                                         |
| --------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lifecycle events                  | Supported | Durable lifecycle and definition changes append `job_event`. Throttle coalescing changes no durable job data, so it emits process telemetry without amplifying history.                                                                                             |
| Closed attempt history            | Supported | Success, terminal failure, cancellation after an attempt starts, retry, and lease expiry append one immutable row per logical attempt; `started_at` spans timer suspensions and `claimed_at` records the final activation.                                          |
| Daily history partitions          | Supported | UTC-daily partitions are precreated for today plus three future days; maintenance independently retires fully expired event and attempt days plus bounded default rows.                                                                                             |
| Current/terminal lookup           | Supported | `Admin.getJob(id)` coalesces the sole live runtime or terminal outcome into the stable `JobSnapshot` shape.                                                                                                                                                         |
| Latest mutable progress           | Supported | Exact active ownership may replace one 64-KiB latest-value row at most once per 100 ms per fence. Revisions retain attempt, fence, worker, and timestamps; identical values are no-ops; accepted changes append value-free `progress_updated` telemetry.            |
| Cross-state job listing           | Supported | `Admin.listJobs()` pages a dedicated operator projection by queue, type, lifecycle states, and a half-open creation-time range. Immutable signed cursors are filter/projection-bound; cross-page membership is intentionally weakly consistent.                     |
| Bounded payload projection        | Supported | Listing omits payload by default. PostgreSQL applies up to 50 unique top-level redaction keys before enforcing a caller-selected 1-byte through 1-MiB response ceiling and reports `omitted`, `included`, or `too_large`.                                           |
| Merged lifecycle timeline         | Supported | `Admin.getJobTimeline()` returns retained events and closed attempts in one latest-first cursor stream. Event and attempt retention remain independent, so known jobs can have partial or empty timelines.                                                          |
| Terminal result inspection        | Supported | Terminal outcomes and their JSON results persist in `job_outcome`; the demo task drawer exposes result or terminal failure evidence alongside immutable attempt history.                                                                                            |
| Queue health                      | Supported | One snapshot reports schema version 1, bounded counts, and lifecycle pressure. It includes external waits, recent delivery rejections, retention, partitions, evaluated status reasons, and separate PostgreSQL observations.                                       |
| Crash-boundary harness            | Supported | Worker failpoints model process loss before and after handler/completion boundaries.                                                                                                                                                                                |
| Job/outcome retention             | Supported | Configurable 14-day defaults drive bounded terminal-only deletion. A retained-history watermark prevents identity cleanup from outrunning event or attempt retention.                                                                                               |
| Event and attempt retention       | Supported | Independent configurable windows drop only fully expired completed daily partitions and bounded-delete expired fallback rows.                                                                                                                                       |
| Rolling statistics rollups        | Supported | Per-minute `(queue, job type)` aggregates derive from history, then complete hours and days derive from the finer tier. Job/attempt grain stays separate, recent recomputation is idempotent, and excess groups fold into an overflow type.                         |
| Stitched statistics read path     | Supported | `stat_buckets_v1` selects minute, hour, or day rows for the window, then evaluates the same aggregation for its live edge. Operator windows are correct immediately, and a lagging rollup costs a longer tail rather than a wrong answer.                           |
| Rollup retention interlock        | Supported | History retention clamps its event and attempt cutoffs to the rollup watermark; a stalled rollup holds history and surfaces through `QueueHealth.statistics.lagMs` and retention lag instead of creating silent gaps.                                               |
| Statistics retention              | Supported | A sixth configurable retention category, bounded per pass and deliberately outside the identity chain so aggregates may outlive the history they were derived from. Defaults to 14 days; null keeps buckets forever.                                                |
| Storage and rollup visibility     | Supported | The system page reports per-relation size and row counts with daily partitions folded into their parent, plus rollup watermark, lag, bucket count, and covered span. A stalled rollup degrades page health.                                                         |
| Long-horizon statistics tiers     | Supported | Hour and day tiers retain mergeable logarithmic wait sketches. Production-shaped benchmarks keep worker and tag dimensions on bounded live queries because materializing either would remove the aggregate row bound.                                               |
| Cold history export               | Planned   | Optional provider packages may export finalized history after rollup safety is established; PostgreSQL-only operation remains the default.                                                                                                                          |
| Checkpoint retention              | Supported | Checkpoints intentionally follow safe parent-identity deletion; independent removal is rejected because it could make a retry repeat a completed step.                                                                                                              |
| Wait retention                    | Supported | Named timer rows intentionally follow safe parent-identity deletion. Retention is supported; signal delivery and operator early wake remain separate unsupported capabilities.                                                                                      |
| Redrive lineage retention         | Supported | A retained descendant protects its source identity. Target pruning removes the inbound edge, after which ancestors become eligible under the normal terminal identity policy.                                                                                       |
| Consistent health snapshot        | Supported | Every correctness-sensitive value is read in one SQL statement and stamped `capturedAt`; history scans are size-capped with explicit lower-bound flags; lagging PostgreSQL statistics are separated under `observations`.                                           |
| OpenTelemetry tracing and metrics | Supported | Vendor-neutral core records lifecycle spans, bounded W3C context propagation, task- and queue-attributed metrics, logs, and queue observations. The free `@stablemates/workhorse-otel` adapter uses host-owned OpenTelemetry API peers after explicit registration. |

| Versioned SQL API                       | Supported     | Schema version 1 is the preproduction contract. | SQL protocol conformance fixtures       | Supported     | `protocol/v1` defines compatibility ranges, canonical enqueue requests, lifecycle scenarios, runtime behavior, and structured errors. A language client can run the shared fixtures against PostgreSQL and reject an incompatible schema before mutation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Graceful worker stop                    | Supported     | Stop prevents further claims and waits for in-flight work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Worker pause/resume                     | Supported     | `Worker.pause()`/`resume()` stop new claims locally while active jobs finish and heartbeats continue. `Admin.setWorkerPaused()` records a durable operator pause that reaches workers in any process; it is cooperative, applied at the next registration refresh, and cannot be overridden by a local `resume()`. It is scoped to a process incarnation through `worker_registry.instance_id`, so a restarted or replaced worker comes back running; durable "stop this work" is queue pause. `actor` is attribution only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Worker concurrency                      | Supported     | `WorkerOptions.concurrency` is an integer from 1 through 100 and defaults to 1. `queues` lets one identity rotate across several queues under that shared slot budget; `queue` remains the single-queue option. Claims are serial and bounded by free slots, handlers overlap per job, and an all-queues-empty pass stops filling. One worker timer batches every active fence renewal. `worker.concurrency` is readonly and `runtimeState()` exposes local slot, pause, and drain state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Batch handler delivery                  | Supported     | `Worker.handleBatch` groups one queue and type up to a validated size, dispatches full groups immediately and partial groups after a bounded linger, and accepts one explicit success or failure outcome per member. Every member preserves its lease, context, priority order, retry budget, timeout, cancellation, and fenced settlement. PostgreSQL admits and accounts for policy capacity per job before the process-local rendezvous.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Worker fleet registration               | Supported     | TypeScript, Python, and Go workers upsert `workhorse.worker_registry` on their configured registry cadence and read back the operator pause flag in the same round trip. The worker owns reported concurrency, slot use, and draining; PostgreSQL owns pause. Registration failures do not stop dispatch and preserve the last remote-pause decision. Graceful shutdown deregisters; a killed worker ages out and is pruned by `prune_worker_registry_v1`. The registry is never consulted by the claim path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Project scaffolding and schema CLI      | Supported     | `workhorse init` detects ORM, framework, and package manager and writes one worker configuration file, editing nothing it does not own. `workhorse schema install`/`status` expose clean-install and version reporting, including separate JSON fields for schema drift and PostgreSQL support. The single `workhorse` binary also owns the strict `health` subcommand. `workhorse dashboard` serves the operator console as its own process against any database, binding loopback and read-only by default; the dashboard package is an optional runtime dependency loaded on demand.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Built-in dashboard authentication       | Supported     | The standalone dashboard accepts one environment-configured administrator, including bounded previous-credential rotation and container secret files. It throttles login failures, protects HTML, assets, private reads, and same-origin mutations with a bounded secure cookie session, ignores untrusted proxy headers, and refuses an unauthenticated remote listener.
