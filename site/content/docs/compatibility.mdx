Before you use a task queue, you must know two things. Does it run on your stack? And what does the
word "supported" prove? Workhorse has five SDKs: TypeScript, Python, Go, Rust, and Ruby. All five
use one PostgreSQL schema. A version is supported only if continuous integration (CI) runs the full
test suite with it. Workhorse can run on other versions, but no test shows that it is correct there.

Check your runtime and your PostgreSQL version in the table below.

## The tested matrix

| Runtime    | Supported      | Minimum | End of life                                                    | Notes                                                           |
| ---------- | -------------- | ------- | -------------------------------------------------------------- | --------------------------------------------------------------- |
| Node.js    | 22, 24         | 22      | 22: 2027-04-30, 24: 2028-04-30                                 | Even-numbered releases only. `engines.node` is `>=22`.          |
| Python     | 3.12–3.14      | 3.12    | 3.12: 2028-10, 3.13: 2029-10, 3.14: 2030-10                    | `stablemates-workhorse` ships one `py3-none-any` wheel.         |
| Go         | 1.25 and newer | 1.25    | No date; Go supports its two most recent releases              | pgx v5.11.0 is the minimum and the tested version.              |
| Rust       | 1.89 and newer | 1.89    | No date; Rust supports only its latest stable release          | Tokio with `tokio-postgres` 0.7 and `deadpool-postgres`.        |
| Ruby       | 3.3, 3.4, 4.0  | 3.3     | 3.3: 2027-03-31, 3.4: not announced, 4.0: not announced        | `pg` 1.6 alone, behind `connection_pool`, or Active Record.     |
| Active Job | 8.0, 8.1       | 8.0     | 8.0: 2026-11-07, 8.1: 2027-10-10                               | The Rails adapter. Rails dates are the end of security support. |
| PostgreSQL | 15, 16, 17, 18 | 15      | 15: 2027-11-11, 16: 2028-11-09, 17: 2029-11-08, 18: 2030-11-14 | No extension beyond the default `plpgsql` is installed.         |

Your application needs one language runtime from this table, and a PostgreSQL server at or above
its minimum. It does not need the other runtimes. For example, a Python service needs only Python.
Node.js is necessary in one other place: the machine that runs the schema step of your deployment.
The schema tools are in the TypeScript package.

The End of life column shows the retirement date of each version. The upstream project of each
runtime publishes this date, and Workhorse copies it. A version stays in the table until its date
passes. Thus, you can plan an upgrade before a release removes the version.

- Go and Rust have no date. Their policies refer to their current release, not to a calendar.
- The Python developer guide publishes only a month until a version retires.
- Ruby publishes the end date of a branch only when the branch starts security maintenance. Until
  then, the table says "not announced".
- The Active Job dates are the end of security support for each Rails release.

CI runs the tests at two levels:

- Pull requests and pushes run each language suite one time, for fast feedback. Node.js, Python,
  and Ruby use their newest version. Go uses its minimum, and Rust uses its pinned version. All of
  them use the newest PostgreSQL.
- The weekly run tests each Node.js, Python, and Ruby version with each PostgreSQL version. It runs
  Go and Rust with each PostgreSQL version.

A regression on a supported version blocks the release.

The runtime also exports these limits for tools, so that a script does not have to read this page:
`MINIMUM_NODE_MAJOR`, `MINIMUM_POSTGRES_MAJOR`, `SUPPORTED_NODE_MAJORS`, and
`SUPPORTED_POSTGRES_MAJORS`. A test in the repository compares the CI matrix, the package `engines`
fields, these constants, and the rows of this table with one support file. If they disagree, the
test fails. The Rust row is the exception, because the support file has no Rust entry.

## Check the PostgreSQL server at runtime

Your application can check the connected server when it runs.

- `readPostgresSupport` reports if the server is tested, newer than the tested versions, or below
  the minimum.
- `assertSupportedPostgres` stops if the server is below the minimum. Thus, the schema installation
  does not fail later with an unclear error.

```ts
import { readPostgresSupport } from "@stablemates/workhorse";

const support = await readPostgresSupport(pool);
console.log(support); // { major: 17, version: "17.2 …", supported: true, tested: true }
```

If the server is newer than the tested versions, Workhorse reports it as supported but not tested.
It does not refuse the server. A refusal would stop your application after each PostgreSQL upgrade,
because a release cannot know a version that did not exist when it was published.

## Plan for a minimum that rises

A minimum is the oldest supported version of a runtime. Workhorse raises a minimum only in a minor
release. It does so only after the version reaches its end of life at its upstream project. The
Node.js, Python, Go, Ruby, Rails, and PostgreSQL projects decide this date, not Workhorse. If a
version is still supported upstream, it stays in the table, also if its removal makes the matrix
shorter.

Before the minor release that removes a version, the changelog of at least one published minor
release tells you. PostgreSQL gets the notice in two published minor releases, not one. A
PostgreSQL major upgrade is a database migration that you must plan, not a package update.

A release that you already installed does not change. It continues to run with the database that
you built it for. A runtime that Workhorse no longer supports gets no future releases.

The dependency ranges of `pg`, Psycopg, asyncpg, and pgx follow the same rule. Each change is a
minor release. A change can widen a range for a new upstream major, or narrow it to remove a retired
one.

## Use plain PostgreSQL with no extensions

Workhorse needs only standard PostgreSQL with its default procedural language. It installs no
extension. Thus, it runs on managed services, for example RDS, Cloud SQL, Neon, and Supabase. You
do not have to ask the provider to allow an extension.

The published TypeScript packages are ESM, with TypeScript declarations. Plain JavaScript uses the
same runtime. Workhorse does not support CommonJS loading.

## Schema tooling ships in the TypeScript package

All SDKs read and write the schema. Only `@stablemates/workhorse` installs and migrates it. These
commands are in that package:

- `workhorse schema install`
- `workhorse schema migrate`
- `workhorse schema contract`
- `workhorse schema status`

A Python, Go, Rust, or Ruby deployment runs these commands with `npx`, at the SDK version of its
application. Thus, the machine that runs your deployment needs Node.js, also if your application
does not.

This is a decision, not a missing feature. Migration is the code that has the most effect on
safety, so it exists one time, not one time for each SDK. It runs as one deployment step, not from
processes that deploy on many nodes. [Installation](/docs/installation) gives the two forms of the
command. [Limitations](/docs/limitations) states this limit with the other limits.

## Let a client accept a newer schema

The PostgreSQL schema is the durable protocol between all processes that use the queue. A client
accepts the schema version that it was built for, and each later version. This is safe because a
migration only adds:

- A migration can add a function, a view, a column, a table, or an index.
- To replace a function, a migration adds a new function next to the old one.

A client refuses an installed schema that is below its minimum version. It also refuses a schema
that no longer serves the protocol of the client. A major release does not stop serving a protocol.
The schema stops serving it only when you run the contract step, after all of your processes use
the new release. The contract step is the one migration that removes old functions and protocols.

The minimum with no maximum inside a major line makes a rolling upgrade possible:

1. Your pipeline migrates the schema first.
2. Each process that still runs continues to work, because the schema only got larger.
3. The new release rolls out at its own speed.

Assert compatibility when a process starts, before it claims or changes work. Use
`assertSchemaCompatible` in TypeScript, `assert_schema_compatible` in Python,
`AssertSchemaCompatible` in Go, and `assert_compatible` in Rust and Ruby.
[Installation](/docs/installation) shows each call and the errors of a refusal.

`workhorse schema migrate` applies forward-only steps that never change, from the supported
baseline. Each step commits one version in its own transaction, behind an advisory lock. If a step
fails, its transaction rolls back. A development schema at a version from before the baseline has
no migration history. You must reset it.

## Use one protocol in all SDKs

Python, Go, Rust, and Ruby use the versioned SQL functions and the JSON fixtures in `protocol/v1/`
as their compatibility limit. The fixtures make sure that each client refuses an incompatible schema
or protocol before it changes data. Then they check canonical requests, results, transitions, and
structured errors.

The dashboard transport has its own contract, `dashboard/v1`. The TypeScript, Python, Go, Rust, and
Ruby backends use its shared procedure schemas, HTML placeholders, request order, and HTTP fixtures.

- To give operators access, embed a shipped backend.
- For application operations, use `Queue`.
- For operator integrations, use `Admin`.

The contract version belongs to the SDK artifacts, not to the HTTP path. Each SDK release binds its
backend to the matching dashboard contract and browser bundle. A release that moves to
`dashboard/v2` ships the new pair together. Its release notes give operators the transition steps.
An existing installation keeps its current pair until you upgrade it. The backend does not
negotiate more than one contract version, so `Deprecation` and `Sunset` response headers do not
apply.

### Use the Python package

The Python `stablemates-workhorse` package uses Psycopg in synchronous or asynchronous mode, and
asyncpg in asynchronous mode. Each worker runtime lets the versioned PostgreSQL functions evaluate
cron schedules, with the stored IANA timezone of each definition.

The release test of the package installs the built wheel and the source distribution. It installs
each one in three ways: bare, with the compatibility `psycopg` extra, and with the `asyncpg` extra.
It runs the public examples. Then it checks the active Python and PostgreSQL versions against the
declared matrix.

The package declares no peer range on the TypeScript packages, because the schema and SQL protocol
versions define its compatibility. Its version number is still the same as theirs, because all
lines release from one commit.

### Use the Rust crate

The Rust `workhorse` crate runs on Tokio, with `tokio-postgres` and `deadpool-postgres`. Add it with
`cargo add workhorse`. Two optional features add the remaining surface:

- `dashboard` embeds the dashboard backend as a `tower::Service`.
- `opentelemetry` connects core telemetry to an OpenTelemetry provider that the host owns.

To use them, run `cargo add workhorse --features dashboard,opentelemetry`. A build without
`dashboard` compiles no HTTP dependency. As with the Python package, the crate declares no range on
the TypeScript packages, and its version is the same as theirs.

### Use the Ruby gem

The Ruby `stablemates-workhorse` gem runs on the `pg` gem. It accepts a single connection, a
`connection_pool`, or an Active Record connection through `ActiveRecordExecutor`. Telemetry starts
when the application loads the OpenTelemetry API gems. The gem declares no dependency on them. A
Rails application can also run jobs through the [Active Job adapter](/docs/active-job).

## Know the limits of Bun and Deno

Bun and Deno have a smoke-tested tier, not support. On pull requests, pushes to `main`, and weekly
runs, CI does one enqueue, claim, and complete round trip with each. It uses the built package, the
latest release of each runtime, and PostgreSQL. `SMOKE_TESTED_JS_RUNTIMES` exports the tier for
tools.

A successful lane shows only three things: the driver connects, the schema installs, and one task
completes. The full test suites run only under Node.js, so Workhorse makes no stronger claim. The
[compatibility matrix](https://github.com/stablemates/workhorse/blob/main/docs/compatibility.md)
records the known problems for each runtime.

Serverless platforms have a separate matrix for lifetime and connectivity. Read
[Serverless and edge](/docs/serverless) before you choose where producers and worker processes run.
Connection poolers have a separate matrix for session state. Read [the pooler guide](/docs/pgbouncer)
and [PgCat](/docs/pgcat) before you put a pooler between Workhorse and PostgreSQL.

## Release each package line from its own changelog

Core and its integration packages release together. Keep their versions the same, so that adapters,
dashboard contracts, and exported types describe the same source revision. The
[changelog](https://github.com/stablemates/workhorse/blob/main/CHANGELOG.md) records breaking
changes and the schema version that each release needs.

Each release publishes one version to npm, PyPI, the Go module proxy, crates.io, and RubyGems, from
one source commit. The current release is `0.7.1`. Earlier beta versions stay on the registries.
Each changelog gives their dates and their source commits. [Releases](/docs/releases) shows the
current version of each line, its date, and whether it still gets fixes.

A 0.x minor release can change behaviour, so read the changelog before you upgrade. You do not have
to make your database again. The schema upgrades in place, because a release ships ordered
migrations, and a migration inside a major line only adds. If your installation runs cold export,
stop the exporters during that upgrade. [Export history before retention deletes
it](/docs/maintenance#export-history-before-retention-deletes-it) gives the procedure.

The dashboard and core can use different patch releases in the same minor line. The dashboard
server reads versioned views and functions that core owns. Thus, a core patch stays compatible if
its migration keeps those contracts.

The shared browser bundle carries no SDK version. The TypeScript, Python, Go, Rust, or Ruby host
supplies its own published version when it renders the application. Thus, the dashboard reports the
package that serves it, and a release that changes only the version does not change the bundle.

### Check the release gate of the TypeScript packages

The lockstep TypeScript packages release from the tag `vX.Y.Z`, after the tagged commit passes
public CI. Their release gate checks the version contract, the generated package assets, lint,
dependencies, types, and unit behavior. It builds each tarball one time. It installs and tests
those exact files with PostgreSQL. Then it gives the unchanged tarballs to protected npm
publication, with provenance.

### Check the release gate of the Python package

`stablemates-workhorse` releases from its own tag `python/vX.Y.Z`, after the tagged commit passes
public CI. Its release gate checks the version, the embedded dashboard bundle, the Python format,
lint, types, dependencies, and the full test suite with PostgreSQL. It builds and tests a source
distribution and a universal wheel one time. It makes PEP 740 attestations for those files. Then
PyPI trusted publishing uploads the unchanged files and the attestations.

### Check the release of the Go module

The Go module records its versions in `go/CHANGELOG.md`. It uses the same version as the other
lines. The release script of the repository runs the full gate. Then it creates and pushes the
matching tag `go/vX.Y.Z`.

### Check the release gate of the Rust crate

The `workhorse` crate records its versions in `rust/CHANGELOG.md`. It publishes from the same tag
`vX.Y.Z` as the TypeScript packages. Its release gate packages the crate, builds a clean consumer
from that archive, and enqueues one task. After npm publishes, crates.io trusted publishing uploads
the crate if its version matches the tag.

### Check the release gate of the Ruby gem

The Ruby gem records its changes in `ruby/CHANGELOG.md`. It publishes from the same tag `vX.Y.Z` as
the TypeScript packages, and its first release was 0.6.0. Its release gate builds the gem one time,
installs that archive in a clean consumer project, and enqueues one task. After npm publishes,
RubyGems trusted publishing uploads the gem if its version matches the tag.

### Check the CI runs and the publication approval

The repository is public, and these paths run. Pull requests and pushes to `main` run the suite of
each language one time. The weekly schedule runs the full compatibility matrix, each suite
variation, and the packed-install and package checks. Branch protection requires the stable
`CI / required` check. The protected npm, PyPI, crates.io, and RubyGems environments require a
second person to approve publication.

Support shows correctness under the tested matrix. It does not promise a throughput level for your
database, payloads, handlers, or deployment topology.
