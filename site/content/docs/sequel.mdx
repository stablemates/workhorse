---
title: How do I enqueue inside a Sequel transaction?
description: A tested Ruby recipe that commits an application write and a task on the native PostgreSQL connection of Sequel.
---

Sequel is a database toolkit for Ruby. Your application write and its task must both commit, or
both must roll back. The native PostgreSQL adapter of Sequel gives a `PG::Connection` to the block
of `Database#transaction`. Build the existing `Stablemates::Workhorse::Queue` on that connection,
inside the block. You need no extra gem and no Workhorse executor.

## Enqueue a task in a Sequel transaction

The application table `sequel_orders` has a text primary key `id` and a non-null text column
`email`. In this code, `database` is your Sequel database and `server` is its selected server.
`queue_name` identifies the queue. `order_id` and `email` are the business values to insert.

```ruby
database.transaction(server: server) do |connection|
  database[:sequel_orders].server(server).insert(id: order_id, email: email)
  Stablemates::Workhorse::Queue.new(connection, default_queue: queue_name)
    .enqueue("order.accepted", {"orderId" => order_id, "email" => email})
end
```

When the block ends, Sequel commits both writes or rolls back both writes. An independent
connection cannot see either write before the commit.

Do not use `after_commit` for this enqueue. It creates a second transaction, and the two writes are
then not atomic.

## Install the gems and the schema

Add `stablemates-workhorse`, `sequel`, and `pg` to the Gemfile of your application. Use the native
`postgres` adapter of Sequel. Do not use JDBC or another PostgreSQL driver.

Install the Workhorse schema in the same database before you enqueue a task. Sequel does not own
Workhorse migrations. [Installation](/docs/installation) describes the schema lifecycle.

## Run the example

The [standalone example](https://github.com/stablemates/workhorse/blob/main/ruby/examples/sequel.rb)
creates the business table and prints the task identifier. It needs an existing Workhorse schema.
It inserts a new order, and Sequel disconnects after the block. From a source checkout, run it
against your development database:

```sh

WORKHORSE_DATABASE_URL="$APPLICATION_DATABASE_URL" pnpm exec tsx scripts/with-env.ts \
  sh -c 'cd ruby && bundle exec ruby -Ilib examples/sequel.rb'
```

To run the isolated regression suite, run `pnpm ruby:test:sequel`. The suite creates scratch
databases from the test database of the checkout and removes them after the run.

## Keep the queue inside the transaction block

Sequel owns the transaction, savepoints, pool checkout, and connection lifecycle. Workhorse does
not begin, commit, roll back, release, reset, or close the connection that Sequel gives to the
block.

- Do not cache the queue.
- Do not give the queue to another thread or fiber.
- Do not use the queue after Sequel returns the connection to the pool.

The SDK does not make a checkout last longer. It also does not detect a connection that Sequel
returned but that is still open. The tests prove that a Sequel disconnect makes the borrowed
executor unusable. They do not make use outside the block safe.

## Roll back an inner write with a savepoint

A savepoint is a named point inside a transaction. You can roll back to it and keep the outer
transaction. With `savepoint: true`, Sequel keeps both writes under the same savepoint.

If that savepoint rolls back, Sequel removes its business write and its task. The outer transaction
stays. A released savepoint does not commit either write independently of the outer transaction.

## Let an error leave the transaction block

Workhorse errors are not Sequel errors. Do not rescue only `Sequel::DatabaseError` around the
enqueue. Let an error leave the transaction block, so Sequel rolls back.

To recover inside an outer transaction, let the error leave an inner `savepoint: true` block first.
If you rescue a statement error without a rollback, the PostgreSQL transaction stays aborted.

## Disconnect after a connection loss

Raw `pg` calls do not go through the query error wrappers of Sequel. Workhorse does not tell the
Sequel pool to discard a broken connection. It also does not send the failed statement again.

**Example.** The connection breaks during an enqueue.

1. Workhorse raises a transport error from the raw `pg` call.
2. The Sequel pool does not see a Sequel error, so it can keep the broken connection.
3. Your code lets the error leave the transaction block.
4. Your code calls `database.disconnect`, and Sequel clears the failed connections.
5. Your code uses the pool again.

After a confirmed connection loss, leave the transaction and call `database.disconnect` before you
use the pool again. The Workhorse error alone can fail to start the automatic discard of Sequel. The
specs cover this action. They also cover the separate disconnect detection of Sequel when its own
commit fails.

A transport failure can have no SQLSTATE. It can also leave the commit result unknown. Reconcile
the state before you try the business operation again.

## Use the same server for all writes

Use the same Sequel database, execution context, and server for the transaction and for each
business dataset write. To use the configured server `orders`, select the transaction with
`server: :orders`. Select the dataset with `.server(:orders)`.

- Install the Workhorse schema on each writable shard that you enqueue into.
- Validate the server name against your configuration. For an unknown name, Sequel can use the
  default server.
- Do not rely on implicit routing to a read replica.
- Do not use a second Sequel database object for the business write.

The tests use two independent scratch databases. They prove that only the selected shard gets the
business row and the task.

<details>
<summary>Reference: server and adapter limits</summary>

**Not supported by this recipe.** Unknown server names, writes to a replica, transactions across
servers, and distributed atomicity.

**Not verified.** JDBC, `postgres-pr`, other adapters, and changed thread or fiber pool behavior.

More detail: [ADR 0075: Connection model](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0075-shape-the-ruby-sdk-as-one-gem-with-an-active-job-adapter.md#connection-model).

</details>

## Run workers in a separate process

This recipe only enqueues tasks. Run workers in a [dedicated process](/docs/worker-processes) with
their own `ConnectionPool` of PostgreSQL connections.

- Do not give a worker this transaction connection.
- Do not use the Sequel pool as a Workhorse worker pool.

Each shard needs workers that use its own database. Workers do not see uncommitted tasks.
