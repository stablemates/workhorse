---
title: Can a PydanticAI tool wait for durable approval?
description: Resume one deferred local tool from the message history that your application keeps, without a change to the execution model of PydanticAI.
---

Yes, for the bounded Python recipe on this page. A PydanticAI tool can ask for approval before it
runs. This recipe keeps that request in PostgreSQL and waits for a reviewer through a Workhorse
human wait. A human wait suspends a task until a person sends a decision.

This is a tested local recipe. It is not a durable backend for PydanticAI, and it is not a general
provider integration. PydanticAI does not get Workhorse persistence automatically.

## Run the local proof

The repository example uses Python 3.12 or later, `pydantic-ai-slim==2.53.0`, and the Psycopg
driver of the Python SDK. The local proof uses Psycopg 3.3.6, psycopg-pool 3.3.2, and PostgreSQL
18.6. PydanticAI is a development dependency. It is not a dependency of the installed Workhorse SDK.

Configure the checkout with its pinned tools and a local PostgreSQL. Then run:

```sh
pnpm example:pydanticai-approval
```

The command creates a loopback scratch database from the `DATABASE_URL_TEST` of this checkout. It
applies the current Workhorse schema and the application tables of the example. At the end, it drops
only that scratch database. It starts no demo and no container. Never point this fixture at a
production database.

The example uses `FunctionModel`, one allowed `credit` tool, and a fixed local reviewer. It sets
`pydantic_ai.models.ALLOW_MODEL_REQUESTS=False`. The example uses no provider extras, native model,
network tool, model credential, or paid request. Its tool adds credit to a local PostgreSQL account.
A denied request changes no account.

The maintained test file is `python/tests/test_pydanticai_approval.py`. The existing
`pnpm python:test` discovery runs it one time. The tests also use a `TestModel` with an explicitly
restricted tool list. By default, `TestModel` can call every registered tool.

## Follow one approval from request to result

**Example.** The Agent asks to run the `credit` tool for a local account.

1. The handler stores the history and the pending tool request. Then it stores the
   `agent-history-receipt` checkpoint.
2. The worker registers the `credit-approval` human wait, and Workhorse suspends the task.
3. The fixed reviewer approves, and Workhorse commits the decision.
4. A new worker activation reads the decision and stores it.
5. A new `Agent.run` call runs the tool from the stored history and returns the result.

The initial Agent accepts `str` or `DeferredToolRequests` as its output. Its `credit` tool uses
`requires_approval=True`. A deferred response goes back to the caller. No live process waits for
the reviewer.

`ModelMessagesTypeAdapter` serializes the history that the application keeps. To resume, the handler
gives that history and the validated `DeferredToolResults` to a **new** `Agent.run` call. The
conversation ID stays the task ID. The Agent run ID changes. If a call reuses a run ID that is
already in the history, the call fails.

## Give each owner its own state

The application owns these PostgreSQL tables:

- `pydanticai_conversation` keeps the admitted request, the serializer version, the histories, the
  identity and arguments of the pending tool, the decision, the result, the stop record, and the
  request count of the conversation.
- `pydanticai_effect` records the operation key and its arguments, which do not change.
- `pydanticai_account` records the local business effect in the same transaction as its operation
  ledger.

Workhorse owns task admission, durable retries, leases, human waits, and fenced context writes. A
checkpoint is a named piece of handler code whose result Workhorse stores. The
`agent-history-receipt` and `agent-result-receipt` checkpoints contain only the conversation ID.
They contain no framework snapshot. They do not wrap an Agent run or a tool effect.

## Enqueue the task and the conversation in one transaction

The producer calls the `admit` function of the example inside an explicit caller transaction. That
transaction enqueues the task and inserts its conversation row together. Another session sees
neither row before the commit. A rollback removes both rows.

The handler never reconstructs a missing conversation. This is also true before the first queue
receipt exists.

## Store the state before the receipt

**Example.** The handler stores the pending request, and the process stops.

1. The handler stores the serialized initial history and the pending request.
2. The process stops before Workhorse stores the `agent-history-receipt` checkpoint.
3. Workhorse runs the task again.
4. The handler loads the stored request. It does not make a new draft.

The pending record contains the tool name, the `tool_call_id`, and the arguments from the history
that the server owns. The handler validates all three against the admitted request, which does not
change.

The worker registers `credit-approval` with that context and a 60-second timeout. The registration
suspends the task and releases the application writer. The completion function of the example
refuses a request until the matching queue wait is committed.

After the completion, `wait_for_human` returns the decision during a later activation. The handler
stores that decision before it starts the resumed Agent turn.

The application saves the result history and the result before the `agent-result-receipt`
checkpoint. If that receipt is lost, a retry returns the stored result. It does not call the model
or the tool again. The original pending history stays available for an approval audit and for a
duplicate completion.

## Exclude competing and stale writers

Each activation opens a direct Psycopg connection without a pool. It takes a session advisory lock
that the recipe derives from the task ID. The **same connection** writes the histories, the
decisions, and the local effect ledger. The connection never reconnects. If the writer session
stops, the activation loses the lock and every application writer.

Queue concurrency alone does not exclude a stale application driver. Before each of these actions,
the handler makes a new public `AsyncHandlerContext.set_progress` call:

- the Agent entry
- a model request
- an application write
- a tool effect

That fenced write rejects an activation whose queue lease or cancellation authority has changed. A
replayable checkpoint is not a new fence check.

Every application driver must use this lock and fence discipline. Transaction pooling does not
satisfy it. A separate connection for the lock only does not satisfy it. If a driver fails or finds
the lock in use, Workhorse retries the task. The driver does not replace the lock, and it does not
reconnect its writer.

<details>
<summary>Reference: progress fence</summary>

`set_progress` calls `update_progress_v1`. It accepts only the exact unexpired worker and fence
generation, and it rejects a write after a cancellation request. A stale write raises
`ProgressLeaseLostError`.

More detail: [Data model: `task_progress`](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#task_progress).

</details>

## Reconcile uncertain local effects

The operation key is `(task_id, tool_call_id)`. Its arguments must match the stored approval and
any ledger entry that exists. The tool inserts that entry and adds the credit in one PostgreSQL
transaction. Both commit, or both roll back.

**Example.** The tool adds the credit, and the process exits.

1. The tool transaction commits the ledger entry and the credit.
2. The process exits before PydanticAI returns the tool result.
3. Workhorse runs the task again, and the handler repeats the approved tool from the initial
   history.
4. The ledger verifies the arguments and returns. It does not add the credit again.

The same recovery applies if the process exits before the application saves the result history.
The tests use an actual process exit and a new interpreter for this case.

This guarantee covers only this local transactional tool. An HTTP request, a payment, an email, or
another external action needs its own provider idempotency or reconciliation contract. No
checkpoint or message history gives an external effect that occurs exactly one time. Cancellation
cannot undo a committed credit.

## Keep model repair apart from task retry

The PydanticAI `ModelRetry` asks a model to repair a response within its configured retry limit. A
Workhorse task retry starts the handler again and loads the durable application state again. These
two retries have different budgets. The tests run a successful model repair and a retry exhaustion,
apart from the task retry.

The recipe allows one approval only. An approved tool that raises `ModelRetry` can make a new
deferred request with changed arguments. The request can even have the same tool call ID. The
handler rejects that output. Support for another request needs a separate approval lifecycle. That
lifecycle must never reuse an earlier decision only because an ID matches.

The application permits a maximum of four model requests in the conversation, including lost turns.
It reserves each request in PostgreSQL before the model runs. It checks that budget **before** a
resumed tool runs. The PydanticAI usage check for the next request is not sufficient alone, because
a resumed deferred tool can run before the next model request.

The history limit is 32,768 serialized bytes.

## Observe cancellation and deadlines

An active handler sends the cooperative cancellation token of Workhorse to the separate
`CancellationToken` of PydanticAI. A native token cancellation raises `RunCancelled`. An external
asyncio cancellation stays `CancelledError`. For the `RunCancelled` path,
`RunCancelled.from_cancellation` gives the messages that it kept. Neither path automatically stores
the interrupted history. Neither path rolls back an effect that is already committed.

A suspended Agent has no live run to cancel. After Workhorse reports `failed` or `canceled`, an
application observer calls `reconcile_terminal`. The function holds the same application lock. It
records a stop, and it does not delete the history or the approval context.

Workhorse has the authority over task deadlines, the execution timeout, and the human wait timeout.
If the queue authority is missing, reconcile the task manually. Do not start a new run.

## Authorize each reviewer on the server

This example authorizes only the literal `local-reviewer` actor. It is not an authentication
system. A real application gets the actor from authenticated server state. Before it calls the
completion function, it checks the scope of the conversation and the permission of the reviewer.
Attribution is not authorization.

A client can send an opaque approval reference and a decision. A client must not send message
histories, call IDs, arguments, or tool results. The server loads all approval context again from
its own rows. Protect those rows from client writes. Protect the stored prompts and histories, for
example with encryption, as your confidentiality requirements specify.

## Keep the application state until reconciliation ends

Keep these records until you can reconcile every accepted task and every late approval:

- the conversation history
- the pending request
- the decision
- the operation ledger
- the queue receipts

If stored state is missing, the recipe fails closed. If you delete an operation ledger, the business
effect can occur again. A purge of the queue context does not give permission to reconstruct an old
conversation.

## Migrate the stored histories explicitly

The stored recipe marker is `local-credit-v1`, and the serializer marker is `2.53.0`. If a marker
does not match, you must migrate explicitly. The handler does not guess the compatibility.

Before you upgrade the framework, test the serialized histories and the tool schemas. Tool
authorization and defense against prompt injection stay the responsibility of the application. This
is also true if a model asked for the action.

## What this recipe does not establish

This recipe does not establish any of these:

- a graph
- a replacement for a checkpointer
- a generic durable backend
- a new core state machine
- a framework package
- provider support
- compatibility with a live model
