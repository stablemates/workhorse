---
title: Can I use Workhorse with my web framework?
description: Make the three decisions that a web framework changes, with one question that answers each decision for any framework.
---

When you add Workhorse to a web application, you make three decisions. They are where the worker
runs, where your code gets the `Queue`, and how you mount the dashboard. None of these needs a
framework package, so Workhorse publishes none. Make the three decisions in the order of this page.
The first decision sets the shape of your deployment. The other two change only one file each.

A Rails application can also keep its job classes through the
[Active Job adapter](/docs/active-job) of the Ruby gem.

## Run the worker in its own process

A Workhorse worker is a continuous process. It holds a PostgreSQL pool, renews leases, and sends
heartbeats. After a termination signal, it drains its tasks. A web framework controls the lifecycle
of a request, not the lifecycle of a worker.

Run each worker as its own process. Use `defineWorkerProcess`, `startWorkerProcess`, or the
`workhorse worker` command. [Worker processes](/docs/worker-processes) shows the shape of the
process.

This rule is not a style preference. If web replicas start workers, these problems occur:

- When you scale the web tier for HTTP traffic, you also multiply the worker capacity and the
  database connections. Nothing tells you about it.
- When a deploy drains HTTP traffic, it also drains your queue.

## Get the queue from the dependency injection of your framework

A `Queue` is an ordinary object over a database handle. Supply it the same way that your framework
supplies other objects. For example, use a module-scoped constant, a container binding, a
request-scoped provider, or a plugin decoration.

The source of the `Queue` is not important. The important rule is the transaction: the enqueue must
use the transaction that writes the data of your application. Then a request that rolls back leaves
no task. [Enqueue](/docs/enqueue) explains this rule. Each [ORM adapter](/docs/integrations) shows
how its transaction type gets to the queue.

## Mount the dashboard in one of two shapes

To mount the dashboard, ask one question about your route handler: **does it receive a Fetch
`Request`, or a Node `req`/`res` pair?**

- **A Fetch `Request`.** Call `host.handle(request)`. If the call resolves to `null`, continue to
  your next route.
- **A Node `req`/`res` pair.** Wrap the same host in `dashboardNodeMiddleware(host)`. The middleware
  passes each request that it does not own to `next()` without a change.

This question has an answer for every framework. This includes a framework that no page describes.
Thus this page asks the question and does not list vendors. [Dashboard](/docs/dashboard) explains both
shapes and names the frameworks that were checked with each shape.

Some frameworks convert between the two shapes. For example, Fastify gets Connect middleware through
`@fastify/middie`, and some Node frameworks run on a Fetch server. Use the object that your handler
receives, not the object that the framework advertises.

## Use the core package, not a framework package

Framework packages once combined two parts: queue access in a request, and worker startup and
shutdown. The lifecycle part encouraged the mistake that
[Run the worker in its own process](#run-the-worker-in-its-own-process) prevents. The request part
was a package around a dependency injection call. Each framework already does that call better.

Thus a framework needs its own page only if its request adapter is unusual. If you find an adapter
that the two dashboard shapes do not cover, report it. It is the only part of this page that can be
incomplete.
