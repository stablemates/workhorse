---
title: Enqueue and transactions
description: Accept immediate, delayed, batched, or transactional tasks that commit or roll back with your application data.
---

Your code inserts an account, then enqueues "send a welcome email". If the insert and the enqueue
commit separately, one of them will eventually happen without the other: an account with no email,
or an email for an account that rolled back.

Workhorse closes that gap because a task is a row in your own PostgreSQL database. Enqueue inside
your open transaction, and PostgreSQL commits the account and the task together, or rolls both back
together. There is no outbox table to build and no window where only one exists. This page covers
what an enqueue can do: run now, run later, join a transaction, batch, and choose a queue and
priority.

Rust SQLx applications can use the optional [SQLx enqueue transport](/docs/sqlx) with their exact mutable PostgreSQL transaction.
Rust worker drivers remain unchanged.

## Enqueue immediate or delayed work

> **Example.** An app server handles one request that needs two tasks.
>
> 1. **At 0 s** it enqueues `email.send` without a run time. Workhorse places the task in `ready`,
>    and a worker can claim it at once.
> 2. **Also at 0 s** it enqueues `invoice.remind` on the `billing` queue, with `runAt` set three
>    days ahead. Workhorse places that task in `scheduled`.
> 3. **Three days later** the run time passes. Promotion, a regular background pass, moves the task
>    to `ready`.
> 4. **At that moment** an operator has paused `billing`. The task stays ready until the queue
>    resumes, and a worker claims it then.

`queue.enqueue(type, payload, options?)` turns a type and JSON payload into a durable task and
returns its ID. `runAt` is a not-before boundary, not an appointment. If someone pauses the queue,
or workers become unavailable, a worker claims the task later than the boundary, never earlier.

## Join an application transaction

This is the option that replaces an outbox. A signup request creates account `acc-7` and asks for
an `account.created` task.

1. **The transaction opens.** The app server begins a transaction and inserts the `acc-7` row.
2. **The enqueue.** The app server enqueues `account.created` through the same transaction.
   Workhorse writes the task's rows in that transaction. No worker can see them yet, because they
   are not committed.
3. **The commit.** The app server commits. The account row and the task become visible at the same
   moment. PostgreSQL delivers the wake-up notification to listening workers only now, and a worker
   claims the task.

Now take the same request, but a later statement fails after step 2. The app server rolls back.
PostgreSQL discards the account row and the task together. No worker ever sees the task, so no email
goes out for an account that does not exist.

Compare two separate commits. The app server commits `acc-7`, then its process dies before the
enqueue. The account exists, and nothing will ever send its email.

The rule: pass the open transaction to the enqueue call, and commit once. Each language hands it
over differently. TypeScript passes the transaction client as the fourth argument to `enqueue`.
Python builds a `Queue` on the connection whose transaction is open. Go wraps the transaction in an
executor and builds a `Queue` around that. Rust builds a `Queue` on the open `tokio_postgres`
transaction. Ruby builds a `Queue` on the connection that `transaction` yields.

    await client.query("INSERT INTO account (id, email) VALUES ($1, $2)", [id, email]);

  </Tab>
  <Tab value="Go">
    ```go
    func createAccount(ctx context.Context, pool *pgxpool.Pool, id, email string) error {
    	tx, err := pool.Begin(ctx)
    	if err != nil {
    		return err
    	}
    	defer tx.Rollback(ctx)

    	if _, err := tx.Exec(ctx, "INSERT INTO account (id, email) VALUES ($1, $2)", id, email); err != nil {
    		return err
    	}
    	queue := workhorse.NewQueue(workhorse.NewPGXExecutor(tx), "default")
    	if _, err := queue.Enqueue(ctx, "account.created", map[string]any{"accountId": id}); err != nil {
    		return err
    	}
    	return tx.Commit(ctx)
    }
    ```

In TypeScript, `Queue.enqueue` accepts your open transaction client as its final argument.
Anything with a pg-compatible `query` method works, such as a `pg` `PoolClient` inside an explicit
transaction. `Queue.enqueueMany` takes the same transaction argument, so a fan-out created by one
request commits or rolls back as a unit with the row that caused it.

Python has no transaction argument. `Queue` binds the connection you give it, and the transaction
belongs to that connection. Open `connection.transaction()`, enqueue through `Queue(connection)`,
and the two writes share it. If the block raises, Psycopg rolls back, and the task goes with your
row.

Python's `Worker` takes a Psycopg `ConnectionPool` of autocommit connections, not a single
connection. `AsyncWorker.from_psycopg` and `AsyncWorker.from_asyncpg` take the matching async pools.
A worker also [reserves pool connections of its own](/docs/pgbouncer#connection-budgets), so size
the pool for them. Your enqueue code can borrow a connection
from that pool and open its transaction there. Autocommit and an explicit transaction are not in
conflict: `connection.transaction()` opens a real transaction block on an autocommit connection.

Go has no transaction argument either. An executor wraps whatever you already hold.
`NewPGXExecutor` accepts a `pgx.Tx` as readily as a pool, and `NewSQLExecutor` accepts a
`*sql.Tx`. When any step fails, the function returns before `Commit`. The deferred `Rollback` then
discards the account row, and no task exists without it.

Rust's `Queue::new` accepts a `tokio_postgres` client or `Transaction`, or their
`deadpool_postgres` counterparts. If an error returns before `commit`, dropping the transaction
rolls it back, and the task goes with your row.

Ruby's `Queue.new` accepts a `PG::Connection`, a `ConnectionPool` of them, or the connection inside
`transaction`. If the block raises, the `pg` gem rolls the transaction back. A Rails application
can pass an `ActiveRecordExecutor` around a model class instead, and the queue joins the open
Active Record transaction.

- `NOTIFY workhorse_tasks` is delivered at commit. It is coalesced to one notification per distinct
  queue that gained ready work.
- A batch holds at most 1,000 requests. Any invalid member rolls back the entire batch.
- No Workhorse client commits, rolls back, or closes a transaction, connection, or pool it was

### ORM adapters and recipes

If your TypeScript application talks to PostgreSQL through an ORM, use that ORM's Workhorse package
instead of managing a raw client next to it. Each provider wraps the database object you already
own and exposes `forTransaction`. That method returns a `Queue` bound to your open transaction.
The TypeScript `Queue.enqueue` and `Queue.enqueueMany` methods accept a `PoolClient` directly or a
client produced by `forTransaction`. If the ORM transaction callback throws, the ORM rolls back, and
the task disappears with your data.

The ORM integrations are `createDrizzleAdapter` from `@stablemates/workhorse-drizzle`,
`createPrismaAdapter` from `@stablemates/workhorse-prisma`, `createTypeOrmAdapter` from
`@stablemates/workhorse-typeorm`, and `createKyselyAdapter` from `@stablemates/workhorse-kysely`.
For Knex and Objection, use the [Knex adapter](/docs/knex) and [tested Objection recipe](/docs/objection) with the exact model-write transaction.
[MikroORM PostgreSQL](/docs/mikroorm) uses the shipped Kysely adapter with the callback-local EntityManager executor.

The queue does not `close` a connection or transaction supplied by its caller. An adapter closes
nothing it did not create. Your database, pool, or client stays open until you close it yourself.
You can also hand the adapter a `close` callback and call `close` on the adapter.

Other languages pass their own connection or transaction, as the examples above show. Sequel's
native PostgreSQL adapter yields that same `PG::Connection`; use the [tested Sequel transaction recipe](/docs/sequel).
For Go's Bun ORM, pass the embedded `tx.Tx`, not the Bun wrapper, to `NewSQLExecutor`.
The [Go Bun recipe](/docs/go-bun) explains native bindings, savepoints, and the hooks this path bypasses.
[sqlc (Go)](/docs/sqlc) shares a pgx transaction with generated business queries.
[Go sqlx](/docs/go-sqlx) passes its underlying `*sql.Tx` to the existing Go executor; it is not Rust SQLx.

- An adapter closes nothing it did not create.
- `WorkhorseAdapter.close()` invokes the configured `close` callback at most once, however many
  times it is called. Without a `close` callback, `close()` does nothing.

### Synchronous SQLAlchemy with Psycopg

SQLAlchemy applications using its Psycopg dialect can reach that same driver connection through
`sqlalchemy_connection.connection.driver_connection`. Build the queue inside SQLAlchemy's own
transaction so it cannot outlive the application write:

```python
from sqlalchemy import create_engine, text

from workhorse import Queue

engine = create_engine("postgresql+psycopg://localhost/application")

with engine.begin() as sqlalchemy_connection:
    sqlalchemy_connection.execute(
        text("INSERT INTO account (id, email) VALUES (:id, :email)"),
        {"id": account_id, "email": email},
    )
    psycopg_connection = sqlalchemy_connection.connection.driver_connection
    Queue(psycopg_connection).enqueue("account.created", {"accountId": account_id})
```

`driver_connection` is the Psycopg connection already enlisted in this transaction. SQLAlchemy
still owns the commit, rollback, and pool checkout.

### Asynchronous SQLAlchemy with Psycopg

To enqueue through SQLAlchemy's async engine, install `SQLAlchemy[asyncio]` and use
`postgresql+psycopg`. The `asyncio` extra installs the required `greenlet` bridge.
Workhorse does not install SQLAlchemy or manage its engine.

Inside an `AsyncConnection` transaction, use
`(await connection.get_raw_connection()).driver_connection` with `AsyncQueue.from_psycopg`.
An enqueue can be the first statement or follow an application write. Both stay invisible
to other connections until SQLAlchemy commits. SQLAlchemy also owns savepoints and rollback.

With `AsyncSession`, flush pending ORM writes before obtaining its enlisted connection:

```python
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

from workhorse import AsyncQueue

engine = create_async_engine("postgresql+psycopg://localhost/application")
sessions = async_sessionmaker(engine)

async with sessions.begin() as session:
    session.add(account)
    await session.flush()
    connection = await session.connection()
    raw = await connection.get_raw_connection()
    driver = raw.driver_connection
    await AsyncQueue.from_psycopg(driver).enqueue("account.created", {"accountId": account.id})
```

Await each ORM and queue operation in sequence. Never share a session or enlisted connection
between concurrent tasks. If enqueue fails or the task is canceled, let the exception escape
the transaction context so SQLAlchemy rolls back. Catch a recoverable failure outside
`connection.begin_nested()` so its savepoint rolls back before continuing the outer transaction.

The queue and driver reference last only as long as that enlisted transaction and checkout.
Do not retain them after completion. Never commit, roll back, change autocommit, enter a driver
transaction, or close the driver or raw proxy yourself. Do not use `AsyncEngine.raw_connection()`:
it can check out another connection instead of joining the application transaction.
Dispose the engine when the application stops, not while a transaction is running.

The runnable `python/examples/sqlalchemy_async_enqueue.py` creates an example table and commits
an account with its task. Against an already installed local Workhorse schema, run:

```bash
pnpm exec tsx scripts/with-env.ts sh -c \
  'uv run --project python python python/examples/sqlalchemy_async_enqueue.py "$DATABASE_URL_TEST"'
```

The repository's existing Python CI suite collects `python/tests/test_sqlalchemy_async.py`.
It proves backend and transaction identity, both statement orders, independent invisibility,
joint commit and rollback, session flush, savepoints, structured idempotency errors, cancellation,
and pool reuse. The fixture tests locked SQLAlchemy `2.1.1`, Psycopg `3.3.6`, and greenlet `3.5.6`.
SQLAlchemy stays a development dependency; applications install their own ORM and driver.

### SQLAlchemy's asyncpg dialect is not supported

The discriminator uses SQLAlchemy `2.1.1` and asyncpg `0.31.0`; it reproduces two distinct boundaries.
A logical `connection.begin()` does not start asyncpg's physical transaction.
After unwrapping without an ORM statement, `driver.is_in_transaction()` is false.
Raw enqueue commits immediately, is visible to an independent observer, and survives the
application transaction's later rollback.

A public ORM statement starts the physical transaction. The tests then prove shared identity,
invisibility, and nested savepoint completion. This does not establish general compatibility:
SQLAlchemy installs JSON and JSONB decoders that return Python values, unlike asyncpg's default text codecs.
Workhorse's asyncpg reader decodes string-valued JSON again. A `"plain"` payload raises
`JSONDecodeError` on `AsyncAdmin.get_task`; `"123"` becomes a number, and a quoted string changes value.
Object, array, numeric, boolean, and null payloads pass the same discriminator.
A custom `json_deserializer` also changes the payload Workhorse reads.

Do not work around these failures with private `_start_transaction()`, a competing driver
transaction, or changing codecs on SQLAlchemy's connection. Workhorse publishes no asyncpg
SQLAlchemy recipe until physical enlistment and codec compatibility both pass executable proof.
This limit does not withdraw support for independently owned asyncpg connections and pools.

SQLAlchemy documents the [async accessor and session lifecycle](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#sqlalchemy.ext.asyncio.AsyncConnection.get_raw_connection)
and its [asyncpg JSON codecs](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#asyncpg).

### GORM

Inside `db.Transaction`, Go applications can adapt `tx.Statement.ConnPool` with
`NewSQLExecutor` and `NewQueue`. Use that same `tx` for business writes and return enqueue errors.
The [GORM recipe](/docs/gorm) covers the pinned PostgreSQL driver, prepared-statement wrappers,

Inside `transaction.atomic(using=alias)`, Django lends its enlisted Psycopg connection to a

For `@task` and `.enqueue()`, use the bounded [Django Tasks backend](/docs/django-tasks).

### What the transaction covers

In the signup example, the commit made the `account.created` task durable together with `acc-7`.
It did not send the email. A worker sends it later, outside any application transaction. If that
worker crashes after sending and before completing, another worker sends it again. So the handler's
external effects still need their own idempotency, which [delivery guarantees](/docs/concepts)
describe. The transaction covers durable acceptance only.

## Enqueue a batch

A newsletter goes out to every subscriber of the `mail` queue.

1. **At 0 s** the app server builds one `email.digest` request per recipient and passes the list
   to `queue.enqueueMany`.
2. **In one statement** Workhorse validates every request and writes the whole group.
3. **One request is invalid.** Workhorse rejects the whole call, and no task from the group exists.
   With every request valid, the group commits together, and the returned IDs follow input order.

If a single operation produces many tasks, such as a fan-out or an import, use `queue.enqueueMany`.
It also accepts a transaction as its second argument. Split very large input into several bounded
calls. If a caller may repeat part of the batch, give each request an idempotency key so the repeat
converges instead of duplicating.

<details>
<summary>Reference: batch limits</summary>

- A batch holds at most 1,000 requests.
- `enqueue_batch_v1` validates every request against one timestamp.
- Any invalid member rolls back the entire batch.
- Returned IDs preserve input order. Input ordinality also controls ready sequence allocation.
- `Queue.enqueueManyWithResults` returns one result per request. `Queue.enqueueMany` returns only
  the task IDs.

More detail: [Task lifecycle: Batch validation](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#batch-validation).

## Prioritize work within a queue

Queue `billing` holds a backlog of ordinary reminders, all ready. Its workers are busy.

1. **At 0 s** your app enqueues one urgent `invoice.remind` with a higher `options.priority`.
2. **At 1 s** a worker slot frees up. The worker claims the urgent reminder first.
3. **After that** the ordinary reminders run in the order they became ready.

`new Queue(pool, "billing")` sets the client default queue; `options.queue` overrides one task. A
`Worker` claims only from its configured queue set, rotating across those queues under one identity
and one concurrency budget.

Set `options.priority` when urgent ready work should run before ordinary work in the same queue.
Workhorse dispatches higher-priority tasks first, and it keeps FIFO order among tasks with the same
value. Priority is strict, so a sustained stream of urgent work can delay lower-priority tasks.

Use separate queue names when work needs independent capacity or worker policy. Priority changes
dispatch order within one queue; it does not reserve capacity for lower-priority work.

Whole-queue controls belong to `Admin`, and every mutation carries audit identity:

Use `options.concurrencyKey` when a synchronized policy should also limit one application-defined
group, such as one tenant or one destination host. Keys are scoped to their queue and remain part
of idempotent enqueue identity.

<details>
<summary>Reference: priority values and claim order</summary>

| Option                    | Rule                                                       |
| ------------------------- | ---------------------------------------------------------- |
| `EnqueueOptions.priority` | An integer from 0 to 100 (`MAX_TASK_PRIORITY`). Default 0. |

Claim orders ready rows by:

1. `priority`, descending;
2. `sequence`, the FIFO ready sequence, ascending;
3. `task_id`.

Priority dispatch has no aging or fair-share control. `pauseQueue` and `resumeQueue` write the
queue's pause state through the audited `set_queue_paused_v1`.

More detail: [Data model: Priority, payload reads, and retry policy](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#priority-payload-reads-and-retry-policy).

</details>
