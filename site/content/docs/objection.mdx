Objection is an ORM that runs on Knex. This recipe commits an Objection model write and its task
together in one Knex transaction. Objection accepts Knex transactions, so use the
[Knex adapter](/docs/knex). You do not need another package.

## Install the packages

The tested versions are Objection 3.1.5, Knex 3.3.0, and pg 8.23.1.

```bash
pnpm add @stablemates/workhorse @stablemates/workhorse-knex objection@3.1.5 knex@3.3.0 pg@8.23.1
```

## Commit a model write and a task together

Migrate your application tables separately from the Workhorse schema. Give each table name its
schema, such as `public.account`, so that the table stays outside the Workhorse schema.

```ts
import knex from "knex";
import { Model } from "objection";
import { createKnexAdapter } from "@stablemates/workhorse-knex";

class Account extends Model {
  static tableName = "public.account";
  declare id: number;
  declare email: string;
}

const database = knex({ client: "pg", connection: process.env.DATABASE_URL });
const workhorse = createKnexAdapter(database);
await database.transaction(async (transaction) => {
  const account = await Account.query(transaction)
    .insert({ email: "a@example.com" })
    .returning("*");
  await workhorse.forTransaction(transaction).enqueue("account.created", { accountId: account.id });
});
await database.destroy();
```

Give the `transaction` of the callback to `Model.query(transaction)` and to
`forTransaction(transaction)`. Other connections do not see the account or the task before the
commit. If the transaction rolls back, the IDs that it returned identify no row and no task.

Your application commits or rolls back the transaction, and it destroys Knex. If you do not give a
`close` callback, `adapter.close()` does neither of these.

## Keep the pool queue out of the transaction

The default queue of the adapter, `workhorse.queue`, uses the Knex pool. It does not join your
transaction.

**Example.** A callback enqueues through the default queue by mistake.

1. The callback inserts an account through `Account.query(transaction)`.
2. The callback enqueues a task through `workhorse.queue`.
3. The pool queue commits the task immediately on another connection.
4. The callback throws an error, and Knex rolls back the account.
5. The task stays, but its account does not exist.

In the callback, enqueue only through `forTransaction(transaction)`.

## Roll back the model write and the task together

If the callback throws an error, Knex rolls back both writes. A later model write that fails also
rolls back both writes, together with the tasks that the transaction enqueued.

A nested Knex transaction uses a savepoint.

**Example.** An outer transaction writes account A, and an inner transaction writes account B.

1. The outer transaction inserts account A and enqueues its task.
2. The inner transaction inserts account B, enqueues its task, and throws an error.
3. Knex rolls back to the savepoint. Account B and its task are removed.
4. The outer transaction commits. Account A and its task commit.

If the outer transaction rolls back, Knex also removes the writes of an inner transaction that
completed.

## Enqueue from a model hook

In a model hook, use the `transaction` of the hook context. Do not use a pool queue that you kept
from outside the hook. Await the enqueue. If the enqueue fails, let the error leave the hook. In the
fixture, an `$afterInsert` hook that throws an error rolls back both writes.

The adapter does not support the response transformation hooks of Knex. It requires native object
rows.

## Handle errors

Objection errors keep their own `nativeError`. Adapter failures throw `KnexQueryError`. This error
gives the SQLSTATE in `code` and keeps the original error in `cause`.

## Run workers in a separate process

Run workers in a separate process with their own node-postgres pool and the core `Queue`. Do not run
them in a request process. Do not give them an Objection or Knex transaction session. Your
application owns the models and Knex. The workers own their pool and its shutdown.

A worker module can use the core adapter. It does not need to load Objection or Knex.

```ts
import { createWorkhorseAdapter, defineWorkerProcess, Pool } from "@stablemates/workhorse";

export default defineWorkerProcess({
  adapter() {
    const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 4 });
    return createWorkhorseAdapter({ database: pool, close: () => pool.end() });
  },
  workers: [
    {
      configure(worker) {
        worker.handle<{ accountId: number }>("account.created", async (payload) => ({
          accountId: payload.accountId,
        }));
      },
    },
  ],
});
```

Connect the pool to the same database, which has the Workhorse schema and your application schema.
In the fixture, the worker cannot claim a task before the commit. It handles the task after the
commit.

## Run the tested recipe

The [maintained recipe](https://github.com/stablemates/workhorse/blob/main/typescript/examples/objection.ts)
runs against a real PostgreSQL fixture in the TypeScript database lane of CI. This recipe does not
certify other versions, other drivers, custom parsers, or patched query execution.
