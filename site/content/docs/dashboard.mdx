---
title: Dashboard
description: Mount the operator interface behind application authorization, or run it standalone with a built-in administrator login.
---

The dashboard is the web interface that operators use to examine and change queue state. It shows
tasks, attempts, checkpoints, schedules, queues, workers, failures, and health, so you do not have
to build an admin page. Every host reads PostgreSQL through the versioned `dashboard/v1` contract.
Thus, the dashboard shows workers on all machines, even if its own process runs no workers.

Because it can cancel, release, and pause work, only operators must reach it. An embedded dashboard
uses the login of your application. The standalone dashboard can own one administrator login.

## Protect an embedded dashboard with your application login

**Example.** Dana is an operator. Dana's application has an admin login, and it mounts the
dashboard at `/workhorse`.

1. Dana opens `/workhorse`. The dashboard calls the `authorize` callback before it serves anything.
2. The callback reads the session of the application. It returns a principal that names `dana`.
3. The dashboard checks that the installed schema is compatible. It does not install or change the
   schema.
4. Dana cancels a task. The dashboard records `dana` as the operator who asked.

A principal is the identity that the `authorize` callback returns. If the callback refuses the
request, the dashboard serves nothing. Each language has its own host. Use the host for the
language of your application.

<Tabs items={["TypeScript", "Python", "Go", "Rust", "Ruby"]}>
  <Tab value="TypeScript">
    In TypeScript, `createDashboardHost` takes a database pool that you own. It returns a handler
    for Fetch requests.

    ```ts
    import { createDashboardHost } from "@stablemates/workhorse-dashboard/server";

    const host = createDashboardHost({
      path: "/workhorse",
      database: pool,
      environment: "production",
      authorize: (request) => {
        const session = applicationAdminSession(request);
        return session ? { actor: session.username } : false;
      },
    });
    ```

  </Tab>
  <Tab value="Python">
    In Python, `DashboardHost` is a WSGI application over a synchronous Psycopg connection that
    you own. The connection must use autocommit, so that one request cannot keep a transaction
    open.

    ```python
    import os

    import psycopg
    from workhorse.dashboard import DashboardHost, DashboardPrincipal

    connection = psycopg.connect(os.environ["DATABASE_URL"], autocommit=True)

    def authorize(environ):
        username = environ.get("REMOTE_USER")
        return DashboardPrincipal(actor=str(username)) if username else False

    dashboard = DashboardHost(
        connection,
        path="/workhorse",
        environment="production",
        authorize=authorize,
    )
    ```

    Mount `dashboard` with the WSGI router that your application uses.

  </Tab>
  <Tab value="Go">
    In Go, `dashboard.NewHandler` returns a standard `net/http` handler over a Workhorse executor
    that you own.

    ```go
    import (
    	"net/http"

    	workhorse "github.com/stablemates/workhorse/go"
    	"github.com/stablemates/workhorse/go/dashboard"
    )

    operator, err := dashboard.NewHandler(dashboard.HandlerOptions{
    	Executor:    workhorse.NewPGXExecutor(pool),
    	Path:        "/workhorse",
    	Environment: "production",
    	Authorize: func(request *http.Request) dashboard.Authorization {
    		username, ok := applicationAdminSession(request)
    		if !ok {
    			return dashboard.Authorization{}
    		}
    		return dashboard.Authorization{
    			Principal: &dashboard.Principal{Actor: username},
    		}
    	},
    })
    if err != nil {
    	return err
    }
    http.Handle("/workhorse/", operator)
    ```

  </Tab>

    own. Turn on the `dashboard` feature of the crate.

    ```rust
    use workhorse::dashboard::{self, Authorization, DashboardOptions, Principal};

    let authorize = dashboard::authorize(|request| {
        let session = application_admin_session(request);
        async move {
            match session {
                Some(username) => Authorization::Principal(Principal { actor: username }),
                None => Authorization::Unauthenticated,
            }
        }

    let mut options = DashboardOptions::new(pool, authorize);
    options.path = "/workhorse".into();
    options.environment = "production".into();
    let operator = dashboard::handler(options)?;
    let app = axum::Router::new().nest_service("/workhorse", operator);
    ```

    In Ruby, `Stablemates::Workhorse::Dashboard` is a Rack application over a connection or a pool

    ```ruby
    dashboard = Stablemates::Workhorse::Dashboard.new(
      pool,
      authorize: lambda do |env|
        username = application_admin_session(env)
        username ? Stablemates::Workhorse::Dashboard::Principal.new(actor: username) : false
      end,
      path: "/workhorse",
      environment: "production",
      allowed_hosts: ["ops.example.com"]

    ```

All five hosts serve the same browser bundle and the same `dashboard/v1` procedures. Only the HTTP
adapter changes with the language. PostgreSQL keeps the operator behavior the same in each host.

A workspace is one named database that a dashboard serves. If the TypeScript host serves more than
one workspace, `authorize` also receives the name of the workspace. Thus, your application can give
an operator access to one workspace and not to the others. See
[Serve several databases as workspaces](#serve-several-databases-as-workspaces).

Do not configure the built-in login together with `authorize`. If you configure both,
`createDashboardHost` rejects the configuration. It does not guess which login owns the request.

- `createDashboardHost` accepts exactly one of `authorize` and `singleAdmin`. It rejects both or
  neither.
- The callback runs before the interface, the assets, the compatibility check, and every RPC

- In workspaces mode, TypeScript calls `authorize(request, workspace)` with the resolved workspace
  name. It passes null in single-workspace mode and outside every workspace.
- The Python host rejects a connection without `autocommit=True`.
- A non-empty `allowedHosts` list answers `421` for any other host, before `authorize` runs.

## Connect the TypeScript host to your web framework

The TypeScript host handles Fetch requests. Connect it to your framework in one of two ways.

A Fetch framework, such as Hono, Next.js route handlers, SvelteKit, or Nitro, calls
`host.handle(request)`. If the result is `null`, the dashboard does not own the request. Send the
request to the next route:

```ts
app.all("/workhorse/*", async (c) => {
  const response = await host.handle(c.req.raw);
  return response ?? c.notFound();
});
```

A Connect framework, such as Express, Connect, or Fastify with `@fastify/middie`, uses the
middleware:

```ts
import { dashboardNodeMiddleware } from "@stablemates/workhorse-dashboard/server";

app.use(dashboardNodeMiddleware(host));
```

The middleware sends each request that the dashboard does not own to `next()` without a change.
Thus, the dashboard does not take requests from other routes.

<details>
<summary>Reference: framework adapters</summary>

- `host.handle(request, context)` returns a `Response`, or `null` when the path is not under the
  mount path.
- The middleware from `dashboardNodeMiddleware` passes unowned requests to `next()`.
- `dashboardNodeMiddleware` passes `request.socket.remoteAddress` as `clientAddress`, or the
  forwarded client of a peer that its `trustedProxies` option names.

More detail: [Dashboard: Login rate limit](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#login-rate-limit)
and [Dashboard: Standalone server](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#standalone-server).

</details>

## Record who changes queue state

Workhorse records an actor for each change that an operator makes. An actor is the name that the
history of the task shows for the person who asked. The server sets the actor. The browser cannot
set it.

**Example.** Dana opens a task in the embedded dashboard.

1. Dana selects Cancel.
2. The browser sends the request with an actor name in it.
3. The server discards the actor name from the browser.
4. The server records `dana`, the actor of the principal that `authorize` returned.

The server takes the actor from one of these sources:

- With the built-in login, the server records the configured username.
- In an embedded host, the server records the actor of the principal that `authorize` returns.
- If `authorize` returns only `true`, the server records its configured audit actor.

A principal always has priority over the audit actor. The TypeScript, Python, and Ruby hosts accept
a `true` result, so they have an audit actor option. The Go and Rust callbacks must return a
principal, so those hosts have no audit actor option.

A mutation is a request that changes queue state. Each mutation must have an `Origin` header that
matches the origin of the dashboard. Thus, a valid session cookie alone cannot let a form or a
script from a different site change queue state.

The `auditActor` and `requestedBy` fields record who acted. They do not decide who can act. To
send a mutation through a service of your application, use the controller options in TypeScript.
In Python, Go, Rust, or Ruby, use the procedure extensions of the host.

<details>
<summary>Reference: mutations and attribution</summary>

| Source                       | Recorded actor                                                        |
| ---------------------------- | --------------------------------------------------------------------- |
| Single-admin session         | The configured username, as `DashboardRpcContext.authenticatedActor`. |
| Principal, every host        | The principal's `actor`.                                              |
| TypeScript `true`            | `auditActor`, default `dashboard`.                                    |
| Python `True` or Ruby `true` | `audit_actor`, default `dashboard`.                                   |

- `auditWithOccurredAt` replaces the browser's `audit.actor` before any operator controller runs.
- `rejectCrossOriginMutation` requires an `Origin` header whose origin exactly matches the request
  URL origin. The Python, Go, Rust, and Ruby hosts make the same check.
- `BoundaryTimeline` shows `details.requested_by` beside each operator event's reason.

More detail: [Dashboard: Mutations and attribution](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#mutations-and-attribution).

</details>

## Serve several databases as workspaces

The TypeScript host and the standalone command can serve more than one Workhorse database. Each
database is a named workspace, and the browser can change between them.

**Example.** Dana's team runs a production database and a staging database. The team wants one
dashboard for both.

1. The team configures the TypeScript host with `workspaces`, not `database`. Each entry has its
   own connection.
2. Dana opens `/workhorse/staging`. The host finds the `staging` workspace and gives that name to
   `authorize`.
3. The callback gives Dana access to staging only. The host refuses Dana's request for
   `/workhorse/production`.
4. In a second browser tab, a colleague views `/workhorse/production`. A link into each workspace
   stays valid to share.

```ts
const host = createDashboardHost({
  path: "/workhorse",
  workspaces: {
    production: { database: productionPool, environment: "production" },
    staging: { database: stagingPool, environment: "staging" },
  },
  defaultWorkspace: "production",
  authorize: (request, workspace) => isOperator(request, workspace),
});
```

Each workspace entry can override the host options, such as `environment`, `operator`, and the
controllers. The host does not own the pool size, the shutdown order, the reconnection, or the TLS
of any connection. The Python, Go, Rust, and Ruby hosts serve one database for each host.

The standalone command serves workspaces too. Repeat `--workspace name=url`, or give a JSON file
to `--config`. Each file entry names a `url`, or a `urlEnv` environment variable. Use `urlEnv` to
keep credentials out of the file.

<details>
<summary>Reference: workspace routing</summary>

- `createDashboardHost` accepts exactly one of `database` and `workspaces`.
- A workspace mounts at `{path}/{name}`, such as `/workhorse/production` and `/workhorse/staging`.
  Its endpoint is `{path}/{name}/rpc`.
- The mount path redirects to `{path}/{defaultWorkspace}/tasks`. `defaultWorkspace` defaults to
  the first configured workspace.
- A first segment that names no workspace answers `404`.
- `authorize(request, workspace)` receives the resolved workspace name. It receives null in
  single-workspace mode and outside every workspace.
- Each workspace entry can override `environment`, `configuredWorkers`, `maintenanceLoops`,
  `operator`, the five controllers, and `projectDurability`. An omitted override uses the
  host-level option.
- `databaseHost` and `databaseName` are optional labels for the workspace switcher. The host never
  derives them from the connection.
- The Go, Python, Rust, and Ruby hosts serve one workspace each.
- The standalone command takes repeated `--workspace name=url`, or `--config` with entries that
  name `url` or `urlEnv`. A `--workspace` entry overrides a file entry with the same name.
  Workspaces cannot be combined with `--database-url`.
- Single-admin authentication stays host-wide at `{path}/login` and `{path}/logout`.

More detail: [Overview: Workspaces](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#workspaces)
and [Overview: Workspace routing](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#workspace-routing).

</details>

## Run the standalone dashboard

The `workhorse dashboard` command serves the dashboard without an application. Use it for a quick
local view of a database, or as a separate service with the built-in login.

**Example.** Dana wants to look at a local database. Dana has no web server to mount the dashboard
in.

1. Dana runs `workhorse dashboard` in a project that has only the core package. The command names
   the missing dashboard package. It stops before it opens a listener.
2. Dana installs the dashboard package and runs the command again. It listens on loopback, port
   3000, in read-only mode.
3. Dana starts it again on a public interface without a login. The command refuses, because a
   listener without a login must use loopback or a Unix socket.

The command serves the same packaged application as the hosts. Thus, it needs the dashboard
package next to the core package. An installation for workers only does not include React or the
browser bundle.

```bash
npm install @stablemates/workhorse-dashboard
npm exec --no -- workhorse dashboard --port 3000
```

The command is read-only by default. To allow changes, add `--allow-mutations`. The command then
warns that attribution is not authorization.

The standalone server owns the login session, the logout, the password rotation, the origin
checks, and the login limits. The next sections tell how each one works. If you need more than one
user, roles, single sign-on, or tenant isolation, use an embedded host and its `authorize`
callback.

<details>
<summary>Reference: standalone CLI defaults</summary>

| Option                  | Default         | Rule                                                   |
| ----------------------- | --------------- | ------------------------------------------------------ |
| `--port`                | `3000`          | A positive integer.                                    |
| `--host`                | `127.0.0.1`     | Cannot be combined with `--socket`.                    |
| `--socket`              | none            | Listens on a Unix socket. Excludes `--host`, `--port`. |
| `--public-origin`       | none            | HTTPS origin for a remote authenticated listener.      |
| `--allow-mutations`     | off             | Enables queue, task, and worker mutations.             |
| `--reveal-error-stacks` | off             | Shows worker stack traces on a remote listener.        |
| `--actor`               | `workhorse-cli` | The actor recorded for mutations.                      |

- Without `WORKHORSE_DASHBOARD_USERNAME` and `WORKHORSE_DASHBOARD_PASSWORD_HASH`, the listener is
  limited to loopback or a Unix socket.
- A remote authenticated listener requires `WORKHORSE_DASHBOARD_PUBLIC_ORIGIN` with HTTPS.
- With `--allow-mutations`, the command warns that attribution is not authorization.
- A listener that is not loopback, or that has a remote public origin, omits worker stack traces
  unless `--reveal-error-stacks` is set.

More detail: [Dashboard: Standalone server](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#standalone-server),
[Dashboard: CLI integration](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#cli-integration),
and [Dashboard: Error-stack redaction](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#error-stack-redaction).

</details>

## Turn on the built-in login

The standalone dashboard is the `workhorse dashboard` command. It can own one administrator login.
The server keeps only a hash of the password, so its configuration never contains the password.

**Example.** Dana runs `workhorse dashboard` on a host behind `https://ops.example.com`.

1. Before the start, Dana sets `WORKHORSE_DASHBOARD_USERNAME` to `dana`.
2. Dana sets `WORKHORSE_DASHBOARD_PASSWORD_HASH` to a versioned hash of the password.
3. At the start, the server reads the hash.
4. At login, Dana types the password into the login form. The browser sends it to the server over
   TLS.
5. The server compares the password with the hash. It does not keep the password.

In a container, mount each value as a secret file. Then set the matching `_FILE` variable, not the
direct variable.

The login page uses the light or dark color scheme of the browser. After login, the header of the
dashboard shows the administrator and a sign-out action.

<details>
<summary>Reference: credentials</summary>

| Variable                            | Rule                                             |
| ----------------------------------- | ------------------------------------------------ |
| `WORKHORSE_DASHBOARD_USERNAME`      | 1 to 256 characters.                             |
| `WORKHORSE_DASHBOARD_PASSWORD_HASH` | `scrypt-v1$<base64url-salt>$<base64url-digest>`. |

- Each value can come from its `_FILE` variant, with one trailing line ending removed.
- A direct value and its file variant are mutually exclusive.
- The username and the hash must be configured together.

| Hash setting       | Value                   |
| ------------------ | ----------------------- |
| scrypt (version 1) | `N=16384`, `r=8`, `p=1` |
| salt               | at least 16 bytes       |
| digest             | exactly 32 bytes        |

The server compares the derived digest with `timingSafeEqual`. A password longer than 1,024
characters never matches.

More detail: [Dashboard: Credentials](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#credentials).

</details>

## Control how long a login session lasts

A login session is the period in which the browser can use the dashboard without a new login. The
server keeps each session in its memory and gives the browser only a random token.

**Example.** Dana logs in at 09:00.

1. At 09:00, the server makes a random token. It keeps the token and its expiry in its memory.
2. The browser receives the token in a cookie. The token does not contain the password.
3. During the day, each request sends the cookie. The server compares the token with its record.
4. At 17:00, the session expires. Dana's dashboard tab is still open.
5. The next request from the tab fails. The dashboard shows the login page.

If the session expired, the browser cannot read the dashboard HTML, the assets, or the RPC
responses. To end a session before it expires, send a `POST` request to the logout path. The server
deletes its record. After that, the cookie does not work, even if the browser keeps it.

<details>
<summary>Reference: sessions</summary>

| Setting          | Value                                                                   |
| ---------------- | ----------------------------------------------------------------------- |
| Cookie           | `__Host-workhorse-dashboard-session`                                    |
| Cookie flags     | `Path=/`, `Max-Age`, `Secure`, `HttpOnly`, `SameSite=Strict`            |
| Token            | 32 random bytes                                                         |
| Session lifetime | Default 28,800 seconds (8 hours). An integer from 60 through 86,400 s.  |
| Sessions kept    | At most 16 per process. Login evicts the oldest record past that bound. |

**Requests without a valid session**

| Request                         | Answer                  |
| ------------------------------- | ----------------------- |
| `GET` for a page                | `302` to `{path}/login` |
| RPC, asset, or any other method | `401`                   |

**Login and logout.** A successful login answers `303` to the mount path. `POST /logout` (at
`{path}/logout`) deletes the server record, expires the cookie, and answers `303` to the login page.
Another method on `/logout` answers `405`. After a `401`, `createDashboardClient()` calls
`window.location.replace(loginUrl)` once.

More detail: [Dashboard: Sessions](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#sessions),
[Dashboard: Login page and client](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#login-page-and-client), and
[Dashboard: Credentials](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#credentials).

</details>

## Run one process for the built-in login

The built-in login keeps its sessions in the memory of one standalone server process. Other
processes cannot read them.

**Example.** Dana is logged in. At 11:00, Dana restarts the dashboard process to install an update.

1. Before the restart, Dana's session is only in the memory of the old process.
2. The new process starts with no session records.
3. Dana's cookie matches no record, so Dana logs in again.

A restart ends every session. A second replica does not know the sessions of the first replica. If
you run more than one replica, use an embedded host with the shared login of your application.

<details>
<summary>Reference: process boundary</summary>

- Built-in authentication supports one standalone server replica.
- A restart revokes every session.
- Replicated deployments use host-owned authorization, or an identity-aware proxy with its own
  shared session boundary.
- [ADR 0032](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0032-keep-single-admin-authentication-process-local.md) records this
  boundary.

More detail: [Dashboard: Process boundary](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#process-boundary).

</details>

## Stop repeated password guesses

The built-in login limits the number of failed logins from one client. A client is the network
address that a login comes from. The limit stops a person who tries many passwords.

**Example.** A person at `203.0.113.7` tries to guess Dana's password.

1. In less than one minute, the person sends some wrong passwords. Each gets the same invalid-login
   page.
2. The server stops the login check for `203.0.113.7`. It tells the client to try again later. It
   does not check the password.
3. At the same time, Dana logs in from a different address. The server checks Dana's password.
4. The oldest failed attempt leaves the time window. The server accepts logins from `203.0.113.7`
   again.

The server identifies a client by the address of the network connection. It ignores proxy headers
by default, because a client can write these headers. A successful login clears the count of that
client.

Each password check uses much processing time on purpose. Thus, the server checks only a small
number of passwords at the same time.

<details>
<summary>Reference: login rate limit</summary>

1. The server keeps at most five login reservations per client in a rolling 60-second window.
2. The client is the transport peer address. When the peer is a trusted proxy, the client is the
   rightmost hop of `X-Forwarded-For` or `Forwarded` that is not a trusted proxy. An IPv6 address
   shares its /64 prefix with its neighbors. A request without an address uses one shared key.
3. Each form submission reserves capacity before scrypt begins. Concurrent requests therefore cannot
   bypass the bound.
4. An invalid submission keeps its reservation and returns the generic `401` page.
5. Further submissions from that client return `429` with `Retry-After` until its oldest
   reservation leaves the window.
6. A successful login clears that client's reservations.
7. At most `MAX_CONCURRENT_PASSWORD_HASHES` (2) password checks run at once. Another submission
   gets `429` with `Retry-After: 1` and reserves nothing.

**Login body.** The login body may be at most `MAX_LOGIN_BODY_BYTES` (4,096 bytes). A larger or
malformed declared length gets `413` before the form is read. The body must be
`application/x-www-form-urlencoded`, or the server answers `415`.

More detail: [Dashboard: Login rate limit](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#login-rate-limit) and
[Dashboard: Login body limit](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#login-body-limit).

</details>

## Count login failures behind a reverse proxy

A reverse proxy is a server that receives requests and sends them to the dashboard. Behind a
reverse proxy, each connection comes from the proxy. Thus, all clients of the proxy share one count
of failures. To prevent this, name the proxy as a trusted proxy.

**Example.** Dana's server is behind a proxy at `10.0.0.2`. Dana sets
`WORKHORSE_DASHBOARD_TRUSTED_PROXIES` to `10.0.0.2` before the start.

1. The person at `203.0.113.7` sends a login. The request has a false `X-Forwarded-For` entry with
   Dana's address.
2. The proxy adds `203.0.113.7` to the right of that entry.
3. The connection comes from a trusted proxy, so the server reads the header.
4. The server takes the rightmost address that is not a trusted proxy. It counts the failure for
   `203.0.113.7`.
5. Dana's logins count for Dana's own address.

The server reads a forwarding header only from a proxy that you name. A request from a different
connection keeps the address of that connection. The headers do not change it. If an entry in the
setting is not valid, the server does not start.

<details>
<summary>Reference: trusted proxies</summary>

The list is empty by default, so `dashboardNodeMiddleware` passes the socket address and reads no
forwarding header.

- `--trusted-proxy`, repeatable, or the comma-separated `WORKHORSE_DASHBOARD_TRUSTED_PROXIES` names
  addresses and CIDR ranges. Any flag replaces the whole variable.
- A trusted proxy's request that carries both `X-Forwarded-For` and `Forwarded`, or neither, keeps
  the proxy's address. So does a `Forwarded` header whose quoted string never closes.
- An unparseable hop ends the walk at the trusted proxy that wrote it.
- A malformed entry, or a non-empty list on a Unix socket listener, stops the server at startup.

[ADR 0093](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0093-key-single-admin-login-throttling-by-transport-peer.md) and
[ADR 0094](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0094-read-the-login-throttle-client-through-trusted-proxies.md) record this
model.

More detail: [Dashboard: Login rate limit](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#login-rate-limit).

</details>

## Rotate the password

To change the password, you can accept the old password for a limited time. Thus, other operators
have time to change to the new password.

**Example.** Dana changes the password on Monday. Two other operators still use the old password.
Dana gives them until Friday 18:00 UTC.

1. On Monday, Dana configures the new hash as the current hash.
2. Dana configures the old hash as the previous hash, with a cutoff time of Friday 18:00 UTC.
3. Until the cutoff, both passwords log in.
4. A session from the old password expires at the cutoff or before it, even if its lifetime is
   longer.
5. At Friday 18:00 UTC, the old password stops working. Each session that it made stops working at
   the same time.

<details>
<summary>Reference: password rotation</summary>

| Variable                                                | Meaning                            |
| ------------------------------------------------------- | ---------------------------------- |
| `WORKHORSE_DASHBOARD_PREVIOUS_PASSWORD_HASH`            | The old hash, in the same format.  |
| `WORKHORSE_DASHBOARD_PREVIOUS_PASSWORD_HASH_EXPIRES_AT` | The cutoff, an ISO 8601 timestamp. |

- Both variables must be configured together. Each has a `_FILE` variant.
- They map to `previousPasswordHash` and `previousPasswordHashExpiresAt`.
- Before the cutoff, either hash authenticates.
- A previous-hash session expires at the earlier of the session lifetime and the cutoff.
- At and after the cutoff, the previous hash and every session it created fail authentication.

More detail: [Dashboard: Password rotation](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#password-rotation).

</details>

## Publish the standalone dashboard behind a proxy

A listener is the network address or the Unix socket where the dashboard accepts connections.
Without a login, the standalone dashboard must use a loopback address or a Unix socket. A remote
listener must have the
built-in login and an HTTPS public origin. The public origin is the scheme and host name that the
browser uses.

If a proxy decrypts TLS and sends plain HTTP to the server, the server sees an HTTP request. The
server ignores forwarded protocol headers, so a proxy cannot change its cookie or origin decisions.
Thus, you must give the public origin to the server.

To publish the dashboard behind a proxy, do these steps:

1. Turn on the built-in login.
2. Set `WORKHORSE_DASHBOARD_PUBLIC_ORIGIN` to the origin that the browser uses, for example
   `https://ops.example.com`.
3. Name the proxy as a trusted proxy, so that each client gets its own count of login failures.
4. Start `workhorse dashboard` on an address that the proxy can reach.

<details>
<summary>Reference: listener exposure</summary>

- The CLI maps `--public-origin` and `WORKHORSE_DASHBOARD_PUBLIC_ORIGIN` to `publicOrigin`, and
  `--socket` to `socketPath`.
- The unauthenticated bypass accepts only `127.0.0.0/8`, `::1`, or a Unix socket.
- A remote TCP listener without authentication fails before `listen`.
- An unauthenticated local listener rejects a non-loopback `publicOrigin`.
- An authenticated remote TCP listener requires an HTTPS `publicOrigin`.
- `dashboardNodeMiddleware` ignores `Forwarded` and `X-Forwarded-*` when it builds the request URL.

More detail: [Dashboard: Listener exposure](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#listener-exposure).

</details>

## Set the browser security headers

Security headers tell the browser which content a page can load and show. The standalone dashboard
owns all of its origin, so it sends a content security policy and other browser protections on
each response.

An embedded host shares its origin with the pages of your application. If two content security
policies apply to one response, the browser applies both, and each policy limits the other. Thus,
an embedded host sends no security headers. Copy the documented policy into the headers of your
application.

<details>
<summary>Reference: standalone headers</summary>

`startDashboardServer` sets these headers on every response:

- `content-security-policy`
- `x-content-type-options: nosniff`
- `referrer-policy: strict-origin-when-cross-origin`
- `x-frame-options: DENY`
- `x-robots-tag: noindex, nofollow, noarchive`

`createDashboardHost` sets none of them. `typescript/dashboard-server/README.md` states the policy
an embedder copies.

More detail: [Dashboard: Browser security headers](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#browser-security-headers).

</details>

## Find a task in the task listing

The task listing shows the tasks that match your filters, one page at a time. It moves between
pages with a cursor, so a page does not have to count all matching tasks. A cursor is a value that
marks the position of a page in the listing.

**Example.** Dana filters the task listing to failed tasks.

1. Dana selects Next two times. The dashboard shows each page without a count of all failed tasks.
2. The URL holds the filters and the cursor. Dana sends the URL to a colleague, who sees the same
   page.
3. Dana opens a task and then selects Back in the browser. The browser shows the saved position
   again.
4. While Dana reads, a task changes state. The task can move to a different page.

The listing does not keep a snapshot between requests. Thus, a change of state can move a task
between pages. A task link in the sidebar starts at the first page. An old link with a page number
still works.

The listing shows tags in a separate column, and the actions of each task at the left edge of the
table. Task details has the same actions, with the same confirmation steps. A status indicator
shows the full state, the waits, the blockers, and the timing. It shows them on hover, on keyboard
focus, or on touch.

<details>
<summary>Reference: task browsing</summary>

- The task listing uses cursor navigation, with Previous and Next controls.
- A page does not count the full matching selection by default.
- The URL carries the filters and the navigation cursor. Browser Back restores the saved position.
- The pager has a first-page control that drops the cursor. It keeps every filter, the sort, the
  page size, the chart settings, and the open drawer.
- A sidebar task link starts a fresh page.
- A legacy page-number link still resolves. The dashboard walks forward from the first page to
  the requested page or the last available page.
- Concurrent state changes can move tasks between pages.

More detail: [Dashboard: Cursor task listing](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#cursor-task-listing).

</details>

## Read task details and events

Task details and the Events page show what happened to a task. They also show which keyed mode
accepted the task. A keyed mode is [enqueue idempotency](/docs/idempotency),
[debounce](/docs/debounce), or [throttle](/docs/throttle).

The task listing labels each task Idempotency, Debounce, or Throttle. A tooltip tells how each mode
handles a repeated request. An older host shows only the general label Keyed. The enqueue menu
shows the three modes under Enqueue behavior.

Task details shows one section for the accepted mode. The section shows the scope, the key digest,
and the window or retention settings. If Workhorse refuses a debounce request, Task history shows
the refusal. The refusal does not change the mode that task details shows.

The Events page can filter by worker and by text in the selected time window. One successful
execution can make two records: a task lifecycle record and an attempt record. The status tooltips
show the source of each record. Event details has a control that copies the task ID.

<details>
<summary>Reference: enqueue modes and events</summary>

- The listing's optional `enqueueMode` is `idempotency`, `debounce`, `throttle`, or null. It comes
  from the initial `enqueued` event. The UI falls back to Keyed for an older host that only
  supplies `keyed`.
- `TaskEnqueueSection` renders one accepted mode. It reads `scope`, `key_digest`, `key_length`,
  `window_ms`, `schedule`, and `expires_at` from `details.debounce` or `details.throttle`.
- Rejected proposals remain visible in Task history and never establish the accepted mode.
- The event listing accepts `worker` and `search`. `search` is a case-insensitive literal
  substring match over task ID, queue, type, event name, worker, and recorded details or error
  message.

More detail: [Dashboard: Enqueue mode section](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#enqueue-mode-section),
[Dashboard: Listing enqueue mode](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#listing-enqueue-mode),
and [Dashboard: Event feed](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#event-feed).

</details>

## Change queue state and settings from the dashboard

The dashboard can change queue state only through controllers that the host gives it. A controller
is an object that does one group of operator actions. With the controllers, the dashboard can do
these actions:

- Cancel a task, run a scheduled task now, or redrive a dead letter.
- Pause or resume a queue, a schedule, or a worker.
- Purge a queue.
- Change the maintenance policy.

The Settings page changes the maintenance policy through `DashboardSettingsController`. It shows
the retention windows and the cleanup limits read-only, because a shorter window can delete stored
history permanently. It also shows the values that each worker process owns, read-only. To change
those values, change the worker configuration and deploy again.

If the host did not authorize settings changes, the Settings page is read-only.

<details>
<summary>Reference: controllers and settings</summary>

| Controller                    | Methods                                                                                                    |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `DashboardTaskController`     | `runTaskNow`, `cancelTask`, `signalTask`, `completeHumanWait`, `redriveTask`, `redriveDeadLetters`         |
| `DashboardQueueController`    | `setQueuePaused`, `purgeQueue`                                                                             |
| `DashboardScheduleController` | `setSchedulePaused`                                                                                        |
| `DashboardWorkerController`   | `setWorkerPaused`                                                                                          |
| `DashboardSettingsController` | `overrideMaintenancePolicy`, `revertMaintenancePolicy`, `overrideRetentionPolicy`, `revertRetentionPolicy` |

- `dashboard_settings_v1` sets `editable` only when the host is writable and has a
  `DashboardSettingsController`.
- Policy mutation requires `operator.mode === "writable"` and a `DashboardSettingsController`.
  Each call carries actor, reason, request ID, and server-assigned occurrence time.

More detail: [Dashboard: Controller types](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#controller-types),
[Dashboard: Settings page](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#settings-page),
and [Overview: Operator dashboard](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#operator-dashboard).

</details>

## Render the dashboard in your React application

You can render the dashboard components in your own React tree. Thus, you do not have to fork the
dashboard.

1. Wrap `Dashboard` in `WorkhorseThemeProvider`.
2. Connect the components to the host with `createDashboardClient`.
3. Import the packaged stylesheet for the tokens and the layout.

Two host options change what the dashboard shows. `configuredWorkers` names the worker processes
that you expect, for example `mailer` and `billing`. The Workers page shows them before they
register for the first time. `projectDurability` changes the stored checkpoint evidence into names
from your domain. It does not change the stored queue data.

<details>
<summary>Reference: customization points</summary>

| Name                                          | Where                                     | Purpose                                          |
| --------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| `configuredWorkers`                           | `createDashboardHost` options             | Worker names expected before they register.      |
| `projectDurability`                           | `createDashboardHost` options             | A `DashboardDurabilityProjector` for step names. |
| `createDashboardClient`                       | `@stablemates/workhorse-dashboard/client` | The browser client for the dashboard RPC.        |
| `Dashboard`, `WorkhorseThemeProvider`         | `@stablemates/workhorse-dashboard`        | The React components.                            |
| `@stablemates/workhorse-dashboard/styles.css` | Stylesheet                                | Required when rendering the components directly. |

More detail: [Dashboard: Public subpaths](https://github.com/stablemates/workhorse/blob/main/docs/architecture/dashboard.md#public-subpaths).

</details>

## Refresh the data on the page

The dashboard refreshes the open page at the interval that you select. It does not make more
requests when the number of tasks increases.

**Example.** Dana keeps the task listing open with automatic refresh on.

1. At each interval, the browser reads only the open page.
2. A refresh is still loading at the next interval. The dashboard does not start the same read
   again.
3. Dana cancels a task. The dashboard then reads the committed result.
4. Dana goes to the third page. Automatic refresh pauses, because updates move tasks out of that
   page.
5. Dana selects manual refresh. The dashboard reads the third page again.

The dashboard is a view for operators, not a transaction snapshot. PostgreSQL statistics and
worker registry rows can be behind the processes that they describe.

<details>
<summary>Reference: refresh behavior</summary>

- The browser polls only the active page, at the selected cadence.
- An automatic refresh does not start while the same read is still loading.
- After an operator action, the dashboard fetches the committed result.
- Auto refresh pauses while a task listing is pinned to a cursor or to a page beyond the first.
  Returning to the first page resumes the configured cadence.
- Manual refresh works on every page.
- PostgreSQL statistics and worker registry rows can lag their processes.

More detail: [Operations: Dashboard refresh and build reuse](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#dashboard-refresh-and-build-reuse)
and [Task lifecycle: Read models and health](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#read-models-and-health).

</details>
