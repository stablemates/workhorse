Workhorse publishes six release lines from one source commit:

- ten npm packages, which release together with one version,
- one Python distribution,
- one Go module,
- one Rust crate,
- one Ruby gem,
- three JVM artifacts on Maven Central for Java, Kotlin, and Spring Boot, which release together
  with one version.

The four .NET packages `Workhorse`, `Workhorse.Hosting`, `Workhorse.EntityFrameworkCore`, and
`Workhorse.AspNetCore` join the same release train. NuGet does not serve them yet, so the .NET row
of the table shows no version.

Every release publishes all six lines at one version, before and after 1.0.0. This page shows the
current version of each line. You need it to apply the support policy below.

The site build reads each version on this page from the changelog of its line. Nobody types a
version into this page, so the page always agrees with the release that it describes.

## Upgrade to the current line to get a fix

Workhorse ships a fix only on the highest published minor release of the current major, for each
line that the defect affects. Workhorse has no maintenance branches, no backports, and no long-term
support version. An older version continues to work, but it keeps the defect. To get the fix,
upgrade to the current line.

Each fix ships in a release train. A release train publishes the artifacts of all lines from one
commit, in one controlled release window. The location of the defect decides which lines change:

- If the defect is in the SQL schema or in the protocol that the SDKs share, each line gets the fix.
- If the defect is in one SDK, the fix ships in a release train like any other release. Each other
  line publishes the same version with no change, a version-only release.

This policy works because each upgrade is an ordinary rolling deployment. A minor release only adds,
and a major release also only adds. The one destructive action is the contract step, which you run
when you decide. Thus, a fix costs a package update and a `workhorse schema migrate` that only adds.
Each other release uses the same procedure.

## Report a vulnerability privately

Report a vulnerability through the private advisory form of GitHub. Do not use an issue, a pull
request, or a discussion. [`SECURITY.md`](https://github.com/stablemates/workhorse/blob/main/SECURITY.md)
is the full policy. It tells you:

- where to report,
- what the maintainers do after a report,
- the fix target for each severity,
- the embargo,
- what a reporter can safely test.

GitHub shows `SECURITY.md` next to the report button. This page does not copy it, because a second
copy can become out of date.
