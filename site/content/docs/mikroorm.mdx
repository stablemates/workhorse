title: MikroORM
description: Enqueue a task through the shipped Kysely adapter in the same PostgreSQL transaction as your MikroORM entity writes.

MikroORM is an ORM for TypeScript. Your application often writes an entity and enqueues a
follow-up task for it. The entity and the task must commit together, or both must roll back. The
shipped `@stablemates/workhorse-kysely` adapter gives you this guarantee with MikroORM, and you need
no other integration package.

This page is a tested PostgreSQL recipe. It is not a separate MikroORM adapter, and it does not
cover every MikroORM version. The [integration catalog](/docs/integrations) puts recipes in its
**documented** tier. This recipe also has a maintained real-database fixture in TypeScript CI.
Workhorse owns its schema lifecycle. Keep the `workhorse` schema out of your ORM's entity
definitions and migrations.

## Install the tested packages

The fixture pins the MikroORM packages to one version. The PostgreSQL package of MikroORM brings
its own versions of the SQL package, Kysely, and node-postgres. Install the same versions in your
application:

```bash
pnpm add @stablemates/workhorse @stablemates/workhorse-kysely \
  @mikro-orm/core@7.2.3 @mikro-orm/postgresql@7.2.3 kysely@0.29.6 pg@8.23.0
```

Use a Node.js version that MikroORM accepts and that is also a Workhorse
[supported runtime](/docs/installation).

[MikroORM 7.1 introduced transaction-aware `getKysely()`](https://mikro-orm.io/blog/mikro-orm-7-1-released#getkysely-now-binds-to-the-active-transaction).
This feature makes the recipe possible, but it does not define a supported version range. The
recipe tests only the pinned version. When you upgrade, keep all MikroORM packages at the same
version. Run the fixture again before you use a version outside the tested scope.

## Write the entity and enqueue the task in one callback

Initialize MikroORM with your application entities. Use the same database that holds the Workhorse
schema. Then write the entity and enqueue the task inside one `transactional()` callback:

```ts
import { createKyselyAdapter } from "@stablemates/workhorse-kysely";

const workhorse = createKyselyAdapter(orm.em.fork().getKysely());

const accepted = await orm.em.fork().transactional(async (transactionalEm) => {
  const order = transactionalEm.create(MikroOrder, { reference: "order-42" });
  await transactionalEm.flush();
  const executor = transactionalEm.getKysely();
  const taskId = await workhorse.forTransaction(executor).enqueue("order.accepted", {
    orderId: order.id,
  });
  return { orderId: order.id, taskId };
});
```

The runnable example declares `MikroOrder` with an integer primary key and a unique `reference`.
The entity uses the table `public.mikro_order`. The example sets the `search_path` of the
PostgreSQL connection to `public`. Workhorse queries name their own schema, so the ORM table names
stay out of `workhorse`.

If the task payload needs a generated identifier, flush before you enqueue the task. The
`transactional()` wrapper of MikroORM flushes the remaining entity changes before it commits. If
that final flush fails after the enqueue, MikroORM rolls back both writes. Workhorse does not flush
entities, and it does not commit or roll back the application transaction.

`accepted.orderId` is a number, and `accepted.taskId` is a string. The task ID is provisional until
`transactional()` resolves. An enclosing transaction can still roll it back. An independent
connection cannot see the entity or the task before the outer commit.

## Use only the executor of the callback

The initial executor of the adapter uses the pool. Only `forTransaction(executor)` joins the
transaction of the callback.

**Example.** A developer passes a pool executor that the code captured earlier.

1. The callback writes the order entity and flushes it in the MikroORM transaction.
2. The callback enqueues `order.accepted` through the captured pool executor.
3. That enqueue runs on another connection and commits immediately.
4. The callback throws an error, and MikroORM rolls back the order.
5. The task stays in the database, but its order does not exist.

To prevent this result:

- Get `executor` from the EntityManager that MikroORM gives to that callback.
- Call `getKysely()` with its default options.
- Do not use a captured pool executor.
- Do not use the default queue of the adapter.
- Do not use `transactionalEm.fork().getKysely()`.

The fixture runs both the captured pool executor and the callback fork as negative controls.

Let every failure leave the callback. Do not change an enqueue failure into a successful business
commit.

## Roll back an inner write with a savepoint

A savepoint is a named point inside a transaction. You can roll back to it and keep the outer
transaction. To nest `transactional()` calls with savepoints, use
`TransactionPropagation.NESTED`. In each callback, get the `getKysely()` executor of that callback.
Give it to `forTransaction` again.

If the inner callback rolls back, MikroORM removes its entity and its task. The outer transaction
can continue. A released savepoint does not commit. If the outer transaction rolls back, it also
removes the writes of the released savepoint. The fixture proves both results on the same physical
PostgreSQL connection.

Obey these limits:

- Do not disable transactions for this recipe.
- Do not use a propagation that suspends the transaction.
- Do not keep a transaction-bound queue or executor after its callback ends.
- Keep the `getKysely()` options at their defaults. The fixture does not cover custom naming,
  conversion, or hook plugins.

## Read raw query results

The Kysely adapter sends parameterized SQL without changes. It returns a core `QueryResult` with
the raw values of the driver. The adapter does not supply PostgreSQL field metadata, and it does
not hydrate entities.

The MikroORM default parsers give these value types. A raw `timestamptz` value is a string, not a
`Date` instance. Do not declare raw timestamps as `Date`. Do not expect the same values as a
node-postgres pool that you configure directly.

<details>
<summary>Reference: result shape and value types</summary>

| `QueryResult` field | Value                                                              |
| ------------------- | ------------------------------------------------------------------ |
| `rows`              | The raw driver values, in result order                             |
| `rowCount`          | The number of returned rows, not affected rows without `RETURNING` |
| `command`           | An empty string                                                    |
| `oid`               | Zero                                                               |
| `fields`            | An empty array                                                     |

| PostgreSQL type | Value with MikroORM default parsers |
| --------------- | ----------------------------------- |
| `integer`       | Number                              |
| `bigint`        | String                              |
| `jsonb`         | Object                              |
| `timestamptz`   | String, not a `Date` instance       |

The fixture checks the instant of a `timestamptz` string when it parses the string explicitly.

More detail: [Overview: What an adapter must guarantee](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#what-an-adapter-must-guarantee).

</details>

## Handle database errors

If a statement fails, the adapter raises a Workhorse error that keeps the original error and its
SQLSTATE. If the final MikroORM flush fails, you get an ORM error, not a Workhorse error. MikroORM
still rolls back the task.

<details>
<summary>Reference: errors</summary>

| Failure                               | Error              | Fields                                                      |
| ------------------------------------- | ------------------ | ----------------------------------------------------------- |
| A database failure in the adapter     | `KyselyQueryError` | `cause` holds the original error; `code` holds its SQLSTATE |
| A unique violation in the final flush | ORM error          | SQLSTATE `23505`; the task rolls back                       |

The fixture checks a missing relation (`42P01`) and an enqueue in an aborted transaction
(`25P02`).

More detail: [Overview: Kysely queryable](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#kysely-queryable).

</details>

## Close the ORM in your application

By default, the adapter never destroys a Kysely executor that it borrows. For this request-side
recipe, do not set the `close` option of the adapter. Your application calls `orm.close()` after
the requests drain.

- Do not call `destroy()` on the pooled or transaction-bound Kysely objects of MikroORM.
- If your application creates a separate Kysely instance, your application also destroys it.

## Run workers in a separate process

Use a dedicated worker process with its own node-postgres pool. Do not give a worker the
EntityManager or the transaction of a request. The pool supplies the dedicated heartbeat and
notification connections of the worker.

Compile this configuration to JavaScript. Start it with
`workhorse worker --config ./dist/worker.js`.

```ts
import { createWorkhorseAdapter, defineWorkerProcess, Pool } from "@stablemates/workhorse";

export default defineWorkerProcess({
  adapter() {
    const pool = new Pool({ connectionString: process.env.DATABASE_URL });
    return createWorkhorseAdapter({
      database: pool,
      adaptTransaction: (transaction) => transaction,
      close: () => pool.end(),
    });
  },
  workers: [
    {
      configure(worker) {
        worker.handle<{ orderId: number }>("order.accepted", async (payload) => ({
          orderId: payload.orderId,
        }));
      },
    },
  ],
});
```

## Run the maintained fixture

From a configured checkout, run `pnpm test:integration:mikroorm`. The command creates and drops a
scratch database through the repository harness. It never resets an application database. The
TypeScript CI lane finds the fixture in its database suite and runs it one time for each change.

The fixture imports and runs the business write and enqueue function of the runnable example. It
also runs the example CLI. Then it checks the committed entity and task after the application
closes its ORM.

To run the example CLI yourself:

1. Build the runtime with `pnpm build:runtime:dev`.
2. Use a disposable database that already has the Workhorse schema and no `public.mikro_order`
   table.
3. Run the CLI:

```bash
DATABASE_URL="$DISPOSABLE_DATABASE_URL" pnpm exec tsx scripts/with-env.ts \
  tsx typescript/adapter-conformance/examples/mikroorm.ts
```

The CLI creates the example table. It is not an application migration command.
