---
title: Payload contracts
description: Version payload and result validators, bound durable JSON, and keep sensitive fields out of operator views.
---

A queue accepts whatever producers send it. Without a gate, a malformed payload becomes a durable
task that fails in a handler hours later, and a payload carrying an access token becomes a row an
operator can read on a dashboard. Payload contracts close both gaps: they reject the malformed
value before anything is written, and they carry a redaction policy with every accepted task.

## Define contracts where you create the queue

Pass `contracts` through the third `Queue` constructor argument, or through an adapter's
`queueOptions`. Each task type names a `currentVersion` for newly accepted tasks and retains every
version that live or redrivable tasks may still carry.

Call `queue.syncContracts()` during application startup. Python, Rust, and Ruby expose
`sync_contracts`, and Go exposes `SyncContracts`. PostgreSQL inserts an immutable document for every version and keeps
the current version in a separate policy row, so an operator override survives the next deploy.

After synchronization, the TypeScript, Python, and Go clients cache the selected document for each
task type. If an operator changes the selected version, the cached document can go stale in two
ways. A payload the cached document accepts reaches PostgreSQL, which reports the stale selection. A
payload the cached document rejects never reaches PostgreSQL, so the client reloads the selection
once before it reports the rejection. Either way, the client validates the enqueue again against the
current document.

Workhorse accepts the shared JSON Schema profile only. Bundled references work inside one document,
formats stay annotations, and Workhorse rejects remote references or custom keywords before
compilation.

Every SDK compiles each schema the profile allows. TypeScript does not add Ajv's stricter lint
rules, so a union type, `properties` without an object type, or an open `prefixItems` array compiles
there as it does in the other SDKs. Ajv still rejects a schema that is not valid JSON Schema.

## Rejection is safe by construction

A schema mismatch produces a `TaskContractValidationError` that names the task type, version, and
whether the payload or result failed. Workhorse does not copy the rejected value or the library's
diagnostic into that error, so a rejected payload cannot leak through the failure report.

The two directions fail differently:

- **Payload failures prevent enqueue.** The queue validates before writing, so an invalid task
  never exists.
- **Result failures follow the retry path.** The worker validates a handler's return value before
  completion; an invalid result is a failed attempt, not a committed success.

Size ceilings work the same way. `defaultMaxPayloadBytes` and `defaultMaxResultBytes` set
queue-wide limits, and a contract version can override them with `maxPayloadBytes` and
`maxResultBytes`. PostgreSQL measures its canonical JSON representation before the durable write,
so clients cannot disagree about the accepted size — an oversized value throws
`TaskValueSizeLimitError` with the actual and allowed byte counts.

The TypeScript, Go, Python, and Ruby workers measure a handler result the same way before they send
its completion. An oversized result fails that attempt with `TaskValueSizeLimitError`, or
`ValueSizeLimitError` in Ruby, and follows the retry path. In Python, a `NaN` or infinite number fails the attempt with `ValueError` the same way.
Either failure stays local to its task, so the worker keeps claiming other work.

## Hide sensitive fields from operators

`sensitivePayloadKeys` and `sensitiveResultKeys` name top-level object fields. The split is
between execution and observation: when a worker claims a task, PostgreSQL returns the raw payload
to its handler, because the handler needs the token to do its work. Task lookup, listing, dead
letters, and dashboard detail remove the persisted sensitive keys, because an operator does not.

When a contract names sensitive fields, Workhorse also replaces handler error details before
tracing or persistence — a thrown error that embeds the payload cannot smuggle it into telemetry.

## Deploy a new version

Contracts are versioned because tasks outlive deployments. Each task stores the version selected
when PostgreSQL accepted it. A worker loads that immutable document and caches it by task type and
version, so a new deployment finishing an old task uses the old contract.

To change a shape: add the new version, move `currentVersion` to it, and keep old versions
configured until no live or redrivable task can still carry them. A worker that claims a task whose
version is no longer configured fails safely with `TaskContractUnavailableError` instead of
guessing.

Operator reads never run validators, so historical JSON stays readable even after the application
stops accepting that shape for new tasks.

TypeScript applications provide the versioned registry through `QueueOptions.contracts`, so both
enqueue validation and worker result validation use the same configured documents.
