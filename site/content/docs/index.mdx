---
title: What is Workhorse?
description: A durable task queue that keeps its data in PostgreSQL, so your tasks commit with your data.
---

Most applications have work that must continue after a request ends. For example, the application
sends an email, charges a card, or builds a report. If a separate broker holds this work, you have
two systems that can disagree. An order can exist without its task, or a task can exist for an order
that rolled back.

Workhorse removes the second system. It is a durable task queue that uses PostgreSQL tables and
versioned SQL functions. It has supported SDKs for TypeScript, Python, Go, Rust, and Ruby. It needs
no broker, no Redis, and no PostgreSQL extension. One database holds your business data, your
queued work, the state of each task, and the record of what occurred.

## Commit a task with your data

Workhorse can enqueue a task in the transaction of your application. Thus, the task and your data
commit together, or roll back together.

**Example.** An application takes an order. It inserts the order row and enqueues an
`order.fulfill` task in one transaction.

1. The application opens a transaction and inserts the order row.
2. It calls `Queue.enqueue` and gives the open transaction as the last argument.
3. If the transaction commits, the order and the task both exist.
4. If the transaction rolls back, PostgreSQL removes the order and the task together.

Thus, the order and the task cannot exist one without the other.

```ts
import { Pool, Queue } from "@stablemates/workhorse";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const queue = new Queue(pool);

const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("INSERT INTO orders (id) VALUES ($1)", [orderId]);
  await queue.enqueue("order.fulfill", { orderId }, {}, client);
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

## Keep the work when a worker stops

A worker runs the task. If the process of the worker stops, another worker runs the task again. A
checkpoint stores the result of a part of the handler, so that part does not run again.

**Example.** A worker runs the `order.fulfill` task. Its process stops while the handler runs.

1. A `Worker` claims the task. The claim gives the worker a lease and a fence token.
2. The worker runs the handler that you registered with `Worker.handle`. The handler charges the
   card, and `ctx.checkpoint` stores the result of the charge.
3. The process stops while the handler prints the label.
4. The lease expires, and another worker claims the task. The fence token stops the old worker from
   writing old results.
5. The handler starts again from the top. `ctx.checkpoint` returns the stored result, so the card
   is not charged again. Then the handler prints the label.

A handler runs outside a database transaction. Thus, Workhorse runs each task at least one time, and
a handler can run two times after a crash. A checkpoint cannot commit the response of an external
service in the same transaction. If the process stops after the service succeeds but before the
checkpoint is stored, the call can occur again. For effects such as a card charge, give the provider
an idempotency key that does not change between attempts.

```ts
import { Worker } from "@stablemates/workhorse";

type OrderPayload = { orderId: string };

const worker = new Worker(queue).handle<OrderPayload>("order.fulfill", async (payload, ctx) => {
  // These application helpers must use stable provider idempotency keys.
  const charge = await ctx.checkpoint("charge", () => chargeCard(payload.orderId));
  // Once the checkpoint is saved, a retry reuses the charge result.
  const label = await ctx.checkpoint("label", () => printLabel(payload.orderId));
  return { chargeId: charge.chargeId, labelId: label.labelId };
});
await worker.run();
```

Workhorse also has retries with a backoff policy and durable sleeps that free the worker slot. It
has cron schedules, idempotent enqueue, and dead letters that you can run again. It keeps an
immutable history that you can read with `Admin.getTask` and `Admin.getTaskTimeline`.

## Decide if Workhorse fits your application

Use Workhorse if your application uses PostgreSQL and needs reliable background work. Choose the
TypeScript, Python, Go, Rust, or Ruby SDK. [Compatibility](/docs/compatibility) gives the supported
versions of PostgreSQL and of each runtime.

Workhorse is a public beta. You can use it for evaluation and for early production use. A minor
release can change behavior, so read the changelog before you upgrade. A minor release does not make
you create your database again. Migrations are ordered, and inside a major line a migration only
adds. Thus, a running deployment upgrades in place. The upgrade from 0.4.x to 0.5.0 is the one
exception. [Installation](/docs/installation) gives its offline procedure.

Workhorse supports strict priority, dependency fan-in, child tasks, external signals, and human
decisions. You write the orchestration as application code, not as a separate workflow definition.
External calls still need provider idempotency keys. If the queue must scale separately from the
database, use a dedicated broker.

## Choose your packages

- `@stablemates/workhorse` gives `Queue`, `Admin`, `Worker`, schema tools, process orchestration, and the CLI.
- `stablemates-workhorse` on PyPI gives synchronous and asynchronous Python queue clients and workers.
- `github.com/stablemates/workhorse/go` gives Go queue clients and workers over pgx or `database/sql`.
- The `workhorse` crate gives the Rust queue client, `Admin`, and workers.
- The `stablemates-workhorse` gem gives the Ruby queue client, `Admin`, and workers.
- `@stablemates/workhorse-dashboard` gives the operator interface and its server host, which works with each framework.
- `@stablemates/workhorse-drizzle` connects Drizzle databases and transactions to the core `Queryable` protocol.
- `@stablemates/workhorse-prisma` connects Prisma clients and interactive transactions.
- `@stablemates/workhorse-typeorm` connects TypeORM data sources and transactional entity managers.
- `@stablemates/workhorse-kysely` connects Kysely databases and transactions.
- `@stablemates/workhorse-knex` connects Knex instances and transactions.
- `@stablemates/workhorse-otel` connects Workhorse telemetry to OpenTelemetry.

A TypeScript application starts with `@stablemates/workhorse`, which includes its default PostgreSQL
driver. Python includes Psycopg and has an `asyncpg` extra. Go includes pgx. A TypeScript application
adds an adapter if it enqueues in an ORM transaction.
