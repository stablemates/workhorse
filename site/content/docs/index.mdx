title: What is Workhorse?
description: A durable task queue that lives inside PostgreSQL, so your tasks commit with your data.
---

Every application eventually needs work that outlives a request: send the email, charge the card,
rebuild the report. The moment that work moves to a separate broker, you have two systems that can
disagree — an order row without its task, or a task for an order that rolled back.

Workhorse removes the second system. It is a durable task queue built from PostgreSQL tables and
versioned SQL functions, with supported SDKs for TypeScript, Python, Go, Rust, and Ruby. There is
no broker, no Redis, and no PostgreSQL extension — one database owns your business data, your queued
work, your execution state, and the evidence of what happened.

## The core promise

An application takes an order and wants it fulfilled in the background. It inserts the order row and
enqueues an `order.fulfill` task in one transaction.

1. **The transaction opens.** The application inserts the order row.
2. **It calls `Queue.enqueue`** and passes its open transaction as the last argument.
3. **If the transaction commits**, the order and the task both exist.
4. **If it rolls back instead**, PostgreSQL removes the business write and the task together.

So no window exists where one committed and the other did not.

```ts
import { Pool, Queue } from "@stablemates/workhorse";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const queue = new Queue(pool);

const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("INSERT INTO orders (id) VALUES ($1)", [orderId]);
  await queue.enqueue("order.fulfill", { orderId }, {}, client);
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

Now a worker runs that task, and its process dies partway through.

1. **The claim.** A `Worker` claims the task and runs the handler you registered with
   `Worker.handle`. The claim grants a temporary lease and a fence token.
2. **The charge.** The handler charges the card, and `ctx.checkpoint` saves that stage's result.
3. **The crash.** The process dies while it prints the label.
4. **Recovery.** The lease expires, and another worker recovers the task. The fence token blocks the
   dead worker from writing stale results.
5. **The rerun.** The handler restarts from the top. `ctx.checkpoint` replays the stored charge
   result instead of charging again, and the label stage runs.

Handlers run outside database transactions, so delivery is at least once: a handler can run twice
after a crash. A checkpoint cannot atomically commit an external service's response. If the process
dies after the service succeeds but before the checkpoint is saved, the call can repeat. Use a stable
provider idempotency key for effects such as charging a card.

```ts
import { Worker } from "@stablemates/workhorse";

type OrderPayload = { orderId: string };

const worker = new Worker(queue).handle<OrderPayload>("order.fulfill", async (payload, ctx) => {
  // These application helpers must use stable provider idempotency keys.
  const charge = await ctx.checkpoint("charge", () => chargeCard(payload.orderId));
  // Once the checkpoint is saved, a retry reuses the charge result.
  const label = await ctx.checkpoint("label", () => printLabel(payload.orderId));
  return { chargeId: charge.chargeId, labelId: label.labelId };
});
await worker.run();
```

Beyond checkpoints, tasks get retries with configurable backoff, durable sleeps that release the
worker slot, cron-style schedules, idempotent enqueue, dead letters with redrive, and immutable
history you can query with `Admin.getTask` and `Admin.getTaskTimeline`.

## When to use it

If your application already runs on PostgreSQL and needs reliable background work, Workhorse fits.
Choose its TypeScript, Python, Go, Rust, or Ruby SDK and connect it to PostgreSQL 15 or newer.

Workhorse is a public beta. It is usable for evaluation and early production adoption. A minor
release may change behaviour, so read the changelog before you upgrade. It will not ask you to
recreate your database: migrations are ordered, and inside a major line a migration only adds, so a
running deployment upgrades in place.

Workhorse supports strict priority, dependency fan-in, child tasks, external signals, and human
decisions. Orchestration remains application code rather than a separate workflow definition.
External calls still need provider idempotency keys. If the queue must scale independently of the
database, use a dedicated broker.

## Which package do I need?

- `@stablemates/workhorse` provides `Queue`, `Admin`, `Worker`, schema tools, process orchestration, and the CLI.
- `stablemates-workhorse` provides synchronous and asynchronous Python queue clients and workers.
- `github.com/stablemates/workhorse/go` provides Go queue clients and workers over pgx or `database/sql`.
- `@stablemates/workhorse-dashboard` provides the operator interface and its framework-neutral server host.
- `@stablemates/workhorse-drizzle` adapts Drizzle databases and transactions to the core `Queryable` protocol.
- `@stablemates/workhorse-prisma` adapts Prisma clients and interactive transactions.
- `@stablemates/workhorse-typeorm` adapts TypeORM data sources and transactional entity managers.
- `@stablemates/workhorse-kysely` adapts Kysely databases and transactions.

TypeScript applications start with `@stablemates/workhorse`, which includes its default PostgreSQL
driver. Python includes Psycopg by default and offers an asyncpg extra, while Go includes pgx.
TypeScript applications add an adapter when they want to enqueue inside an ORM transaction.

If you are integrating Workhorse with an AI coding agent, start with the
[agent documentation index](/llms.txt) or the [agent integration guide](/docs/for-ai-agents).
