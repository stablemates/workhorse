description: Run durable background tasks from the PostgreSQL database that your application already uses, with workers in eight languages and no broker.

Workhorse runs background tasks from the PostgreSQL database that your application already uses.
You add a library, not a service.

Most applications have work that must continue after a request ends. For example, the application
sends an email, charges a card, or builds a report. If a separate broker holds this work, you have
two systems that can disagree. An order can exist without its task, or a task can exist for an order
that rolled back.

Workhorse removes the second system. It keeps each task in PostgreSQL tables, and versioned SQL
functions make each change to a task. A task that you enqueue in a transaction commits or rolls back
with your data. Workhorse needs no broker, no Redis, and no PostgreSQL extension. Workers in
TypeScript, Python, Go, Rust, Ruby, Java, Kotlin, and C# use the same SQL protocol and the same
dashboard.

## Run a task that waits, shares a limit, and survives a crash

A real task often waits for another system, shares a limited resource with other tasks, and must
continue after a worker stops. Workhorse keeps all three in PostgreSQL. Thus, the handler stays
ordinary code.

**Example.** A SaaS application onboards each new account. Each tenant can have three onboardings
active at a time, so one large tenant does not use all the workers. The onboarding creates a
workspace, waits until the user verifies their email address, and then sends a welcome email.

1. The application stores a concurrency policy of three active tasks for each tenant. It enqueues
   `account.onboard` with the concurrency key `tenant-42`.
2. A worker claims the task. The handler creates the workspace, and the `workspace` checkpoint
   stores it.
3. The handler waits for the signal `email-verified`. Workhorse releases the worker, and the waiting
   task does not count against the limit of `tenant-42`.
4. An hour later, the user clicks the link in the email, and the application sends
   `email-verified`. A worker runs the handler again from its first line. The `workspace`
   checkpoint returns the stored workspace, so the handler does not create a second one.
5. The handler sends the welcome email, and the task succeeds.

If a worker stops at any step, its lease expires. Then another worker claims the task and continues
it in the same way.

    // Step 1: allow three active onboardings per tenant, across all workers.
    // PostgreSQL applies this limit when a worker claims a task.
    await queue.syncConcurrencyPolicies("accounts", [
      { queue: "onboarding", maxActive: 20, maxActivePerKey: 3 },
    ]);

    // Enqueue the task. The tenant is the concurrency key.
    await queue.enqueue(
      "account.onboard",
      { accountId, email },
      { queue: "onboarding", concurrencyKey: tenantId },
    );

    worker.handle(
      "account.onboard",
      async ({ accountId, email }: { accountId: string; email: string }, ctx) => {
        // Step 2: create the workspace. The checkpoint stores it.
        // On a later run, it returns the stored workspace, and the handler
        // does not create a second one.
        const workspace = await ctx.checkpoint("workspace", () =>
          workspaces.create(accountId, { idempotencyKey: `workspace:${accountId}` }),
        );

        // Step 3: wait until the user verifies the email address. The task
        // releases its worker, and it does not count against the tenant limit.
        await ctx.waitForSignal("email-verified");

        // Step 4: the signal arrived. The handler ran again from its first line,
        // and the "workspace" checkpoint gave back the stored workspace.

        // Step 5: send the welcome email.
        await ctx.checkpoint("welcome", () => mailer.welcome(email, workspace.url));
        return { workspaceId: workspace.id };
      },
    );

A handler runs outside a database transaction. Thus, Workhorse runs each task at least one time, and
a handler can run two times after a crash. If the process stops after the workspace exists but
before Workhorse stores the checkpoint, the next run asks for the workspace again. Thus, the example
gives the workspace service an idempotency key that does not change between attempts. Then the
service returns the first workspace.

<details>
<summary>Reference: the core promise</summary>

| Boundary                                         | Owner                                                                  |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| `Queue.enqueue(type, payload, options, client)`  | Your transaction. The task commits or rolls back with it.              |
| `Queue.syncConcurrencyPolicies(namespace, list)` | PostgreSQL. It applies `maxActive` and `maxActivePerKey` at claim.     |
| `Worker.handle(type, handler)`                   | The worker. It claims under a lease and a fence token.                 |
| `ctx.checkpoint(name, operation)`                | The task. A saved stage replays on a later attempt.                    |
| `ctx.waitForSignal(name)`                        | The task. The wait releases the lease and keeps the attempt.           |
| `Queue.sendSignal(taskId, name, payload)`        | The sender. Workhorse accepts the first delivery and resumes the task. |
| `Admin.getTask` and `Admin.getTaskTimeline`      | The immutable record of what happened.                                 |

- A concurrency policy counts only active tasks whose lease has not expired. A task that waits for
  a signal holds no lease.
- After a signal, the handler runs again from its first line. A completed checkpoint returns its
  stored result.

| Setting (TypeScript) | Default   | Effect                                      |
| -------------------- | --------- | ------------------------------------------- |
| `leaseMs`            | 30,000 ms | How long a claim lasts without a heartbeat. |

[Workers](/docs/workers) gives the lease setting of each SDK. [Concurrency
policies](/docs/concurrency-policies) and [Signals](/docs/signals) give the call of each SDK.

## Decide if Workhorse fits your application

Workhorse fits an application that meets these conditions:

- The application uses PostgreSQL. [Compatibility](/docs/compatibility) gives the supported
  versions of PostgreSQL and of each runtime.
- Its handlers can accept that a task runs more than one time.
- Its deployment can upgrade the schema in a deployment step.

Use a different tool in these cases:

- If the queue must scale separately from the database, use a dedicated broker.
- If you must define and deploy a workflow separately from the application code, use a workflow
  tool. Workhorse supports child tasks, signals, and human decisions, but you write the workflow as
  handler code.
- If a worker must stop a running handler by force, run that work in a process that you can stop.

[Limitations](/docs/limitations) gives each limit and its workaround.

Workhorse is a public beta for evaluation and early production use. A minor release can change
behavior, but inside a major line a migration only adds. The upgrade from 0.4.x is the one
exception, and [Installation](/docs/installation#upgrade-a-04x-database-offline) gives its offline
steps. Before you upgrade, read the changelog.

## Move from the queue that you use now

The reason to move depends on the type of system that you use now.

| You use now                               | What changes with Workhorse                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| A task queue on Redis or a message broker | The task commits in your transaction, and you operate one service fewer.                              |
| Another task queue in a SQL database      | Your transactional enqueue stays. Compare checkpoints, durable waits, and workers in eight languages. |
| A workflow platform with its own server   | Your tasks and their checkpoints stay in your database. Workhorse has no separate workflow runtime.   |

[Compare](/docs/compare) gives the facts for each product, with a source for each fact.
[Migrate](/docs/migrate) moves one task type at a time, while the old system empties its queue.
