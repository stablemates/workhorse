---
title: Can I run my Rails jobs on Workhorse?
description: Run the Active Job jobs of a Rails app on Workhorse, start their worker, and move a job to the native API for more features.
---

Active Job is the job interface of Rails. The Ruby gem of Workhorse has an Active Job adapter, so a
Rails application can run its existing job classes on Workhorse. The adapter keeps the call sites,
the retries, and the callbacks of Active Job. It does not give the features that need a handler
context, because `perform` never receives one. If a job needs those features, move it to a native
handler. Its callers do not change.

The adapter requires Active Job 8.0 or later.

## Select the adapter

Name the adapter in `config/application.rb` or in one environment file.

```ruby
config.active_job.queue_adapter = :stablemates_workhorse
```

`require "stablemates/workhorse"` registers the adapter when Active Job loads. The adapter enqueues
through the connection of `ActiveRecord::Base`. Thus the web process needs no pool for it.

<details>
<summary>Reference: adapter class and loading</summary>

- The adapter class is `ActiveJob::QueueAdapters::StablematesWorkhorseAdapter`.
- `require "stablemates/workhorse"` registers an `ActiveSupport.on_load(:active_job)` hook that
  loads the adapter.
- If Active Job is older than 8.0, the load raises `LoadError`.
- `StablematesWorkhorseAdapter.new(executor = nil)` enqueues through
  `ActiveRecordExecutor.new(ActiveRecord::Base)` when `executor` is nil.

More detail: [Schema and protocol: Active Job adapter](https://github.com/stablemates/workhorse/blob/main/docs/architecture/schema-and-protocol.md#active-job-adapter).

</details>

## Choose a default job or a typed job

A default job is a job class without a task type. Workhorse stores it as an `active_job` task. The
payload of that task is the serialized job. Only the Ruby worker can run it, and every argument type
of Active Job works.

A typed job is a job class that names its own task type. To make one, include the options module
one time in `ApplicationJob`.

```ruby
class ApplicationJob < ActiveJob::Base
  include Stablemates::Workhorse::ActiveJob::Options
end
```

Then declare the task type on the job class.

```ruby
class ClassifyImageJob < ApplicationJob
  queue_as :ml
  workhorse_options task_type: "images.classify", max_attempts: 5

  def perform(payload)
    Classifier.run(payload["blob_id"], model: payload["model"])
  end
end
```

A typed job takes exactly one argument: a JSON `Hash` with String keys. That `Hash` is the task
payload. Thus a Python, Go, TypeScript, or Rust worker can also handle the same task type. If the
job gets a different argument list, the adapter raises `ArgumentError` before it writes anything.

`workhorse_options` accepts four keys:

- `task_type` makes the class a typed job.
- `max_attempts` sets the attempt budget of the task.
- `tags` adds tags to the two tags that the adapter adds: `active_job:<class>` and
  `active_job_id:<job_id>`.
- `concurrency_key` is a String or a callable that receives the job.

If the class uses a different key, `workhorse_options` raises `ArgumentError` when the class loads.

<details>
<summary>Reference: `workhorse_options` keys</summary>

| Key               | Accepts                                                         |
| ----------------- | --------------------------------------------------------------- |
| `task_type`       | A non-empty String of at most 256 bytes other than `active_job` |
| `max_attempts`    | An Integer from 1 through 100                                   |
| `tags`            | At most 18 Strings of 1 to 100 characters                       |
| `concurrency_key` | A non-empty String, or a callable that receives the job         |

A payload key such as `_aj_globalid` stays a plain key in a typed job.

More detail: [Schema and protocol: Default and typed jobs](https://github.com/stablemates/workhorse/blob/main/docs/architecture/schema-and-protocol.md#default-and-typed-jobs).

</details>

## Enqueue as you already do

The adapter maps `perform_later`, `set(wait:)`, `set(wait_until:)`, `queue_as`, and
`set(priority:)` to the task.

```ruby
ClassifyImageJob.perform_later({"blob_id" => 42, "model" => "v3"})
ClassifyImageJob.set(wait: 10.minutes).perform_later({"blob_id" => 43, "model" => "v3"})
ClassifyImageJob.set(priority: 90).perform_later({"blob_id" => 44, "model" => "v3"})
SyncInventoryJob.perform_later("sku-1")
```

`perform_all_later` enqueues its jobs in atomic chunks.

A priority must be nil or an Integer from 0 through 100. If the priority has a different value, the
adapter raises `ActiveJob::EnqueueError`. Active Job records that error as the `enqueue_error` of
the job.

<details>
<summary>Reference: enqueue mapping</summary>

- The adapter prepends the tags `active_job:<class name>` and `active_job_id:<job_id>`. It omits the
  class-name tag when that tag is longer than 100 characters.
- `queue_as` sets the task queue.
- `set(wait:)` and `set(wait_until:)` set `run_at`.
- `enqueue_all` enqueues in atomic chunks of `MAX_ENQUEUE_BATCH_SIZE`. It skips a job whose priority
  it refuses, and sets the `enqueue_error` of that job. It returns the number of jobs that it
  enqueued. It clears `enqueue_error` first, so each job reports only the error of the current call.

More detail: [Schema and protocol: Enqueue mapping](https://github.com/stablemates/workhorse/blob/main/docs/architecture/schema-and-protocol.md#enqueue-mapping).

</details>

## Enqueue a job in your transaction

The adapter enqueues through Active Record. Thus, if you enqueue inside a transaction, the task
commits and rolls back with that transaction. Rails can also defer the enqueue until after the
commit. The adapter cannot change that choice. Rails does not defer through version 8.1, and
`load_defaults "8.2"` turns on deferral.

If a job must commit atomically with the rows of its caller, turn off deferral for that job.

```ruby
class ReceiptJob < ApplicationJob
  self.enqueue_after_transaction_commit = false

  def perform(order_id)
    Mailer.receipt(order_id)
  end
end
```

Then the receipt task exists only if the order update commits.

```ruby
ActiveRecord::Base.transaction do
  Order.find(order_id).update!(status: "paid")
  ReceiptJob.perform_later(order_id)
end
```

## Run the worker from `bin/workhorse`

The web process never runs jobs. Start the worker as its own process from a script, such as
`bin/workhorse`. Write the script in this sequence:

1. Require `../config/environment`, so that the application and its job classes load.
2. Make a worker over its own connection pool.
3. Register the handlers.
4. Run the worker process.

```ruby
pool = ConnectionPool.new(size: 6) { PG.connect(ENV.fetch("DATABASE_URL")) }
worker = Stablemates::Workhorse::Worker.new(pool, queues: %w[default ml], concurrency: 5)
Stablemates::Workhorse::ActiveJob.handle(worker, jobs: [ClassifyImageJob])
worker.handle("invoice.charge") { |payload, _context| Billing.charge(payload["invoice_id"]) }
Stablemates::Workhorse.run_worker_process(worker)
```

`ActiveJob.handle` registers one handler for all default jobs. It also registers one handler for
each typed job in `jobs:`. The same worker can run native handlers next to the Active Job jobs.

`run_worker_process` handles the termination signals. When the worker stops, an Active Job
continuation stops at a step boundary. [Worker processes](/docs/worker-processes) shows the shape of
the process.

<details>
<summary>Reference: handlers</summary>

- `Stablemates::Workhorse::ActiveJob.handle(worker, jobs: [])` registers the `active_job` handler
  and one handler for each typed class in `jobs`.
- `handle` raises `ArgumentError` for a listed class without a task type. It also raises
  `ArgumentError` for two classes that declare the same task type.
- The default handler calls `ActiveJob::Base.execute` with `provider_job_id` set to the task ID.
- The typed handler builds the job from the payload and sets `executions` to the attempt number
  minus 1. It calls `perform_now` inside the `execute` callbacks. Its `job_id` comes from the
  `active_job_id:` tag, or is the task ID for a task that another SDK enqueued.
- `StablematesWorkhorseAdapter#stopping?` returns `Worker#stopping?` for the worker that runs the
  current job. Thus an Active Job continuation stops at a step boundary and continues as a new task.

More detail: [Schema and protocol: Handlers](https://github.com/stablemates/workhorse/blob/main/docs/architecture/schema-and-protocol.md#handlers).

</details>

## List every typed job in `jobs:`

A worker can claim a task of a type that it has no handler for. Then Workhorse releases the task.
Thus a typed job that is not in `jobs:` never runs. Workhorse releases its task again on each poll.

List every typed job in `jobs:`. Do not depend on Rails to load the job classes for you. In
development, Rails does not load job classes eagerly.

<details>
<summary>Reference: tasks without a handler</summary>

- A claim has no task-type filter.
- Each SDK releases a task of an unregistered type through `release_owned_v1` and records the
  `released` handler outcome. The release does not use an attempt.
- A pass whose claims were all unrunnable counts as empty for the poll backoff. Thus a task that no
  deployed worker handles is claimed again on the poll cadence, not in a loop.

More detail: [Task lifecycle: Owned release](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#owned-release).

</details>

## Decide who owns the retries

Active Job and Workhorse both retry. A default job gets both retries:

- `retry_on` stays in Active Job. It enqueues a new task with the same `job_id`, and the current
  task succeeds.
- `discard_on` completes the task.
- If an exception escapes Active Job, the attempt fails. Then Workhorse retries the task in its own
  attempt budget.
- If a worker stops during a job, the worker loses its lease. Then Workhorse runs the job again.

**Example.** `SyncInventoryJob` has `retry_on Timeout::Error, attempts: 3` and the default
Workhorse attempt budget.

1. `Inventory.sync` raises `Timeout::Error` on the first two runs. Each time, `retry_on` enqueues a
   new task.
2. On the third run, `Inventory.sync` raises the error again. `retry_on` has no more attempts and no
   block, so Active Job raises the error again.
3. The error escapes Active Job, so the Workhorse attempt fails.
4. Workhorse retries the task in its own attempt budget. Each retry runs the job again.

Thus the job retries in two places: first in Active Job, then in Workhorse. The default Workhorse
budget is large.

If you want Active Job to own every retry, let Workhorse make only one attempt.

```ruby
class SyncInventoryJob < ApplicationJob
  workhorse_options max_attempts: 1
  retry_on Timeout::Error, wait: 5.seconds, attempts: 3

  def perform(sku)
    Inventory.sync(sku)
  end
end
```

With `max_attempts: 1`, a crash makes the task fail. Workhorse does not run it again.
An operator can still redrive the job from the dashboard. If you prefer crash recovery to a possible
double retry, keep the default budget.

A typed job gives every retry to Workhorse. Thus its retries are the same in every language. If a
typed job calls `retry_job`, the call raises `ArgumentError` and the attempt fails.

<details>
<summary>Reference: retry ownership</summary>

| Event in a default job                | Result                                                |
| ------------------------------------- | ----------------------------------------------------- |
| `retry_on` retries                    | Enqueues a new task and completes the current task.   |
| `discard_on` discards                 | Completes the task.                                   |
| Active Job raises the exception again | Fails the attempt under the retry policy of the task. |
| The worker stops during the job       | The lease expires, and Workhorse runs the job again.  |

- The default `max_attempts` is 25. A value of 0 or nil selects that default.
- A typed job's `retry_job` raises `ArgumentError`. The attempt fails, and no second task exists.

More detail: [Schema and protocol: Handlers](https://github.com/stablemates/workhorse/blob/main/docs/architecture/schema-and-protocol.md#handlers) and [Data model: Priority and attempts](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#priority-and-attempts).

</details>

## Review each priority when you migrate from Solid Queue

Workhorse runs a higher priority first. Solid Queue runs a lower number first. The adapter does not
change the number, so the dashboard and every SDK show the value that the job set. Thus, when you
migrate a Solid Queue application, examine each `priority` and change it if necessary.

## Know what stays native-only

`perform` receives no handler context. Thus an Active Job job cannot use these features:

- durable checkpoints, durable timers, and waits for a signal or a human decision;
- child fan-out and result joins, progress reports, and batch delivery;
- persisted retry policies, deadlines, and execution timeouts;
- enqueue idempotency, debounce, and throttle;
- task dependencies, recurring schedules, and cancellation that a running job can observe.

Payload contracts apply only to typed jobs. No Active Job job stores a result.

## Move a job to the native API

Move a job if it needs one of the features above, or if a different language must run it. Do these
steps:

1. Make the job a typed job, if it is a default job. Its arguments then change to one `Hash`.
2. Remove the job from `jobs:`.
3. Register a native handler for the same task type.

```ruby
worker.handle("images.classify") do |payload, context|
  features = context.checkpoint("features") { Classifier.extract(payload["blob_id"]) }
  context.checkpoint("label") { Classifier.label(features, model: payload["model"]) }
end
```

The payload of a typed job is already the task payload. Thus `ClassifyImageJob.perform_later`
continues to enqueue the same task, and no call site changes.
