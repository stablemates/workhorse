The `@stablemates/workhorse-kysely` package connects Workhorse to Kysely. With it, your application
enqueues a task in the same transaction as its Kysely writes. The row and the task then commit
together, or neither commits.

This prevents two errors. Without a shared transaction, a task can exist for a row that rolled back.
Also, a row can commit and its task can be lost, and no error shows this. Kysely owns your tables.
Workhorse owns its own schema and its versioned SQL functions.

## Create the adapter

Install the integration together with Kysely and node-postgres.

```bash
pnpm add @stablemates/workhorse-kysely kysely pg
```

Give the Kysely database to `createKyselyAdapter`. The `PostgresDialect` of Kysely holds a
node-postgres pool, but Kysely does not make this pool available. If the same process runs workers,
give that pool as the `pool` option. The worker takes its heartbeat connection and its listen
connection from this pool. A listen connection waits for notifications about new tasks.

```ts
import { createKyselyAdapter } from "@stablemates/workhorse-kysely";
import { Pool } from "@stablemates/workhorse";
import { Kysely, PostgresDialect } from "kysely";

interface AppDatabase {
  account: { id: string; email: string };
}

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = new Kysely<AppDatabase>({ dialect: new PostgresDialect({ pool }) });
const workhorse = createKyselyAdapter(database, {
  pool,
  close: () => database.destroy(),
});
```

The adapter is a `WorkhorseAdapter`. It has `database`, `queue`, `admin`, `forTransaction`,
`adminForTransaction`, `createWorker`, and `close`. Your request handlers, operator tools, and
worker processes use this one adapter.

## Enqueue a task in a Kysely transaction

Call `forTransaction` with the transaction that Kysely gives to your callback. The queue that it
returns runs its compiled SQL through that transaction. Thus the task commits or rolls back with
your Kysely writes.

```ts
await database.transaction().execute(async (transaction) => {
  const account = await transaction
    .insertInto("account")
    .values({ email })
    .returning("id")
    .executeTakeFirstOrThrow();

  await workhorse.forTransaction(transaction).enqueue("account.created", {
    accountId: account.id,
  });
});
```

If the callback throws an error, Kysely rolls back the account and the task. Other connections do
not see the account or the task before the commit.

To enqueue a task that is not part of a transaction, use `workhorse.queue`. This queue does not join
the transaction of the caller.

## Run a worker without a pool

If you do not give `pool`, a worker does not start unless you set `sharedHeartbeats`. With this
setting, the worker sends its heartbeats through the queries of Kysely. It then finds new tasks by
bounded polling.

<details>
<summary>Reference: worker connections</summary>

- `createKyselyAdapter` accepts the option `pool`. Give the pool that `PostgresDialect` uses.
- A dedicated heartbeat connection needs a pool of at least 3 connections. If the pool is smaller,
  the worker does not start unless you set `sharedHeartbeats`.

## Handle database errors

If a database statement fails, the adapter throws `KyselyQueryError`. The error keeps the
statement, the original error, and the PostgreSQL error code.

Typed Workhorse conflicts keep their core error classes. Examples are idempotency, checkpoint, and
wait conflicts.

<details>
<summary>Reference: errors and statements</summary>

| `KyselyQueryError` field | Content                                                |
| ------------------------ | ------------------------------------------------------ |
| `statement`              | The SQL statement.                                     |
| `code`                   | The SQLSTATE that PostgreSQL reported, or `undefined`. |
| `cause`                  | The original error.                                    |

- `KyselyQueryError` extends `QueryError`.
- `kyselyQueryable` builds a `CompiledQuery.raw` from the statement and its values. It then calls
  `executeQuery` on a `Kysely` database or a `Transaction`.

More detail: [Overview: Kysely queryable](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#kysely-queryable).

</details>

## Close the database that the adapter owns

The adapter does not destroy a database that the caller owns unless you give a `close` callback.
Give this callback only when the adapter owns the database. `adapter.close` can run when the process
stops or when startup fails.

## Install the Workhorse schema with the Workhorse tools

Install the Workhorse schema with the deployment tools of the core package, not with a Kysely
migration. The Workhorse schema is a versioned protocol, not a set of application tables.
