GORM is an ORM for Go. When your application accepts an order, the order row and its fulfillment
task must commit together, or both must roll back. In the `db.Transaction` callback of GORM, give
`tx.Statement.ConnPool` to the existing SQL executor of Workhorse. You need no GORM adapter package
and no second database connection.

## Enqueue a task in a GORM transaction

Install `github.com/stablemates/workhorse/go`, `gorm.io/gorm`, and `gorm.io/driver/postgres` in your
application. Install the Workhorse schema separately from your application migrations. The runnable
example needs an application table `orders` with `id text PRIMARY KEY` and
`email text NOT NULL`.

```go
package application

import (
	"context"

	workhorse "github.com/stablemates/workhorse/go"
	"gorm.io/gorm"
)

type Order struct {
	ID    string `gorm:"primaryKey"`
	Email string `gorm:"not null"`
}

func acceptOrder(ctx context.Context, tx *gorm.DB, order Order) (string, error) {
	if err := tx.WithContext(ctx).Create(&order).Error; err != nil {
		return "", err
	}
	queue := workhorse.NewQueue(workhorse.NewSQLExecutor(tx.Statement.ConnPool), "orders")
	return queue.Enqueue(ctx, "order.accepted", map[string]any{"orderId": order.ID})
}

func createOrder(ctx context.Context, db *gorm.DB, order Order) (string, error) {
	var taskID string
	err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		var err error
		taskID, err = acceptOrder(ctx, tx, order)
		return err
	})
	if err != nil {
		return "", err
	}
	return taskID, nil
}
```

Follow these rules in the callback:

- Use `tx`, not the outer `db`, for each business write.
- Return each enqueue error, including client-side validation errors. Then GORM can roll back the
  business row.
- Give the task ID to the caller only after the transaction succeeds.

The complete executable and its setup commands are in
[`go/examples/gorm`](https://github.com/stablemates/workhorse/tree/main/go/examples/gorm). The
example opens the PostgreSQL dialector with `PrepareStmt: true`. It prints the task ID after the
commit.

## Let GORM own the transaction

GORM starts, commits, and rolls back the transaction. It also owns savepoints and the return of the
connection. Workhorse only sends statements through the connection pool interface of the callback.

- Do not get another connection for the enqueue.
- Do not keep the queue after the callback ends.
- Do not close the GORM pool through an executor.

Nested `Transaction` callbacks use savepoints, unless you enable `DisableNestedTransaction`. If the
enqueue fails or the context is cancelled, the callback must return an error. Do not let the
callback commit.

## Keep Workhorse tables out of GORM models

Workhorse sends its statements directly, with positional parameters. Its task writes do not go
through GORM model hooks, associations, or model SQL generation. Connection pool wrappers and
driver wrappers can still intercept these raw statements. Your business writes still use GORM
normally.

Do not put Workhorse tables into `AutoMigrate` or into the model lifecycle of your application.

## Run workers in a separate process

A request transaction accepts a task. It does not run the handler. Run a
[dedicated worker process](/docs/worker-processes) with its own pgx pool.

- Do not give a request transaction to a worker.
- Do not run a worker in the web request process.

A handler runs later, so its external effects need their own idempotency.

## Check the tested scope

This page is a tested recipe, not a separately published adapter package. The
[integration catalog](/docs/integrations) therefore puts it in the **documented** tier. The
**verified** tier stays limited to packages.

The maintained fixture pins one GORM version, one PostgreSQL dialector version, and one pgx
version. The tests do not prove support for another driver, dialect, pooler, or GORM version. An
actual command run verifies the executable, not only a copied snippet.

CI runs the fixture in the Go and PostgreSQL lane of the repository. The fixture runs with both
`*sql.Tx` and the GORM `*gorm.PreparedStmtTX`, which `PrepareStmt` enables.

The fixture proves:

- physical transaction identity
- invisibility to an independent connection before the commit
- joint commit and rollback
- nested savepoint rollback
- cancellation
- JSONB bindings, UUID decoding, and nullable decoding
- ordered batch results
- structured SQLSTATE errors

Lifecycle guards prove that the executor does not begin, commit, roll back, or close the resources
of the caller.
