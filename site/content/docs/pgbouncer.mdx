---
title: Can I run Workhorse behind a connection pooler?
description: Which Workhorse operations survive each PgBouncer and PgCat pool mode, and which need a dedicated session.
---

Yes, in every pool mode — with one caveat that costs latency rather than correctness. Enqueue,
claim, heartbeat, settle, schema installation, and migration all work through `pool_mode =
session` and `pool_mode = transaction` on both PgBouncer and PgCat, because every statement
Workhorse sends is self-contained and every advisory lock the schema takes is transaction-scoped.
The exception is the worker's wake-hint listener, which needs a dedicated session — and a pooler
that actually relays notifications.

## The pool-mode matrix

| Operation                                              | Direct | PgBouncer session | PgBouncer transaction          | PgCat session                 | PgCat transaction              |
| ------------------------------------------------------ | ------ | ----------------- | ------------------------------ | ----------------------------- | ------------------------------ |
| Enqueue, claim, settle, heartbeat, operator reads      | Yes    | Yes               | Yes                            | Yes                           | Yes                            |
| Transactional enqueue in your own transaction          | Yes    | Yes               | Yes                            | Yes                           | Yes                            |
| Schema install and migrate                             | Yes    | Yes               | Yes                            | Yes                           | Yes                            |
| Maintenance tick and transaction-scoped advisory locks | Yes    | Yes               | Yes                            | Yes                           | Yes                            |
| `LISTEN`/`NOTIFY` wake hints                           | Yes    | Yes               | Accepted but never delivered   | Buffered until the next query | Buffered until the next query  |
| Session-level advisory locks                           | Yes    | Yes               | Unsafe — no exclusion, leaks   | Yes                           | Unsafe — no exclusion, leaks   |
| Session state (`SET`, `PREPARE`, temporary tables)     | Yes    | Yes               | Unsafe — leaks between clients | Yes                           | Unsafe — leaks between clients |

The conformance suite runs each pooler and mode as a separate lane in CI. The matrix above is the
verified result, not a reading of either manual.

## The silent `LISTEN` failure

Transaction-mode PgBouncer accepts `LISTEN workhorse_tasks` and returns success, then releases the
server connection when the statement ends. PgCat accepts it in every mode, then holds the
notification until the client sends another query — which an idle listener never does. Either way
nothing errors: the worker believes it is listening while dispatch runs entirely on its fallback
poll. That fallback is the correctness mechanism, so tasks still run; wake-up is just slower.

To keep wake hints, give the listener a connection that reaches PostgreSQL directly or through
session-mode PgBouncer:

- The Drizzle and TypeORM adapters use the ORM's own node-postgres pool for listening; point that
  pool at a session-mode alias.
- The Prisma and Kysely adapters take a `pool` for exactly this. Give it a session-pooled PgBouncer
  or direct pool.
- A `Queue` built on a queryable without `connect()` has no listener, so its worker polls and logs
  one warning when it starts.

## Connection budgets

A notification-capable pool holds one connection for the listener no matter how many `Queue` or
`Worker` objects share it, so a listening pool needs room for the listener plus claims. A pool
capped at one connection polls instead of listening. Behind any pooler that cannot deliver
notifications the listener slot is held without delivering anything — budget for it on both
sides, or drop the capability.

Heartbeats need headroom too. If handlers hold every pooled connection, a heartbeat queued behind
them never runs and every lease lapses at once. TypeScript workers therefore keep one dedicated
heartbeat connection per pool, shared the way the listener is, so budget it on top of the listener
and your handlers. If the pool cannot spare it, or states no size, the worker refuses to start and
says why. Set `sharedHeartbeats` to send heartbeats through the shared pool instead, and accept
that busy handlers can then delay renewal. The heartbeat connection runs only self-contained
statements, so it works in every pool mode. Go workers still heartbeat through the shared pool. A Python worker opens its own
heartbeat connection only when you pass it a `heartbeat_connection_factory`.

## What is unsafe

Two configurations fail quietly. Giving a worker a pool behind transaction-mode PgBouncer or PgCat
accepts `LISTEN` and delivers nothing. And session-level advisory locks — `pg_advisory_lock`,
not the transaction-scoped forms Workhorse uses — stop excluding across clients under transaction
pooling, because each statement may land on a different server session and a grant outlives the
client that took it. Any `SET` left behind lands on the next client to borrow that backend.

One PgCat-only detail: `pgcat.toml` names each pool statically, so a client URL's database name
must match a configured pool — a PgCat deployment cannot forward a database it was not configured
for, unlike PgBouncer's wildcard entries.
