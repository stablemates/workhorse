Workhorse is a durable task queue for PostgreSQL. It makes three claims. You enqueue a task inside
your own transaction. A handler that stops during a task continues after its completed checkpoints.
Workers in eight languages use one SQL protocol and one dashboard.

Other products put background work in one of three places. A database task queue keeps tasks in a
SQL database, often the database of the application. A Redis or broker queue keeps them in a second
service beside the database. A workflow platform runs a server that records each step, or offers a
cloud service. Each place gives different guarantees, so compare the approach first, then the
product.

## When Workhorse fits

Workhorse fits these cases:

- Your application uses PostgreSQL, and you do not want to run a second service.
- A task must commit in the same transaction as your data.
- A task has steps that are slow or costly to repeat.
- A task waits for a timer, a signal, or a person.
- More than one language must run workers on the same queue.

## When another approach fits

Another approach fits these cases:

- Your application does not use PostgreSQL. Workhorse needs PostgreSQL.
- Your application runs in one language, and a retry that runs the whole handler again is
  acceptable. A database task queue for that language can be sufficient.
- You already run Redis, and your application has no PostgreSQL database.
- You must define and deploy a workflow separately from the application code. Workhorse has no
  separate language to define workflows. Read [Limitations](/docs/limitations).
- Your workflows run for weeks or months and change while they run. Some workflow platforms keep
  each running workflow compatible with its history. Workhorse detects only some changes, such as a
  changed checkpoint input.
- A client must read the state of a running workflow and get a reply. A Workhorse signal delivers
  data to a waiting task and returns no value.
- You do not want to operate the database yourself. Some workflow platforms offer a managed
  service. Workhorse uses your PostgreSQL database, and you operate that database.

In each approach, a checkpoint or a recorded step does not make an external effect run one time
only. If a worker stops after the effect and before the record commits, the effect runs again. Thus
the effect must be idempotent.

## How this page stays correct

Each fact comes from the documentation or the source code of the product, at the version on its
page. The facts give no performance numbers. A person checks each product page every quarter
against the newest release. If you find a fact that is not correct, open an issue in the
[Workhorse repository](https://github.com/stablemates/workhorse). To move work from another queue,
read [Migrate to Workhorse](/docs/migrate).
