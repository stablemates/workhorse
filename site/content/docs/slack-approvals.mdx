---
title: Can a Slack user approve a Workhorse task?
description: A signed Slack approval recipe that registers a committed human wait, accepts each click durably, and settles the decision in a separate process.
---

This recipe lets a Slack user approve or reject a Workhorse human decision with two buttons. A
human decision is a human wait: it suspends a task until a person sends a decision. Workhorse keeps
the result that has the authority. Slack is not an approval backend, and it is not a worker host.

The runnable [TypeScript recipe](https://github.com/stablemates/workhorse/blob/main/typescript/examples/slack-approvals.ts)
and its [application schema](https://github.com/stablemates/workhorse/blob/main/typescript/examples/slack-approvals.sql)
use the current SDK, the crypto and HTTP primitives of Node, PostgreSQL, and `fetch`. They use no
Slack SDK and no framework wrapper.

## Follow one decision through the processes

Each process does one job. A decision goes through these steps:

1. The task handler stores its authorization scope in a checkpoint. Then it registers
   `waitForHuman("approval", context)`.
2. The notifier finds committed waits through `Admin.listHumanWaits` and posts the buttons.
3. The receiver verifies the raw signed action. It commits the first authorized decision before it
   replies.
4. The decision worker reads that durable inbox. It calls `completeHumanWait` with the stored key
   and actor.

The receiver never starts a worker, posts a Slack message, or waits for the business action to
complete.

The handler returns only the decision. If your application adds an external action, that action
must be safe to replay by itself.

## Configure the Slack app with the least privilege

1. Enable interactivity in an app that is installed in one workspace.
2. Send its HTTPS request URL to `/slack/actions` on the receiver. The receiver listens locally on
   `127.0.0.1:3010`.
3. Keep the exact raw request bytes and the Slack signature headers through your ingress.
4. Grant the bot only `chat:write`.
5. Invite the bot to the selected channel.

Do not deserialize the JSON or rebuild the form body before the verification.

The recipe does not need these scopes: public-channel posting, message history, directory lookup,
or impersonation. Configure the workspace, app, channel, and authorized user IDs explicitly. Do not
use display names. Organization-wide installations, ephemeral messages, dialogs, and modals are
outside this example.

Only the notifier gets `SLACK_BOT_TOKEN`. Only the receiver gets `SLACK_SIGNING_SECRET`. Keep the
secrets in a secret environment. Do not put them in source control, command arguments, logs, or
request captures.

## Run the recipe

Install Workhorse normally. Then apply `slack-approvals.sql` to the same application database.

To run the maintained proof without credentials, use a configured checkout:

```bash
pnpm build:runtime:dev
pnpm test:slack-approvals
```

That proof uses real PostgreSQL transactions and mocked Slack effects. It does not provision a
workspace, and it sends no live messages.

For an explicitly authorized evaluation, use the separate modes: `schema`, `enqueue`, `worker`,
`notifier`, `receiver`, and `decision-worker`.

```bash
pnpm exec tsx scripts/with-env.ts tsx --tsconfig tsconfig.source-paths.json typescript/examples/slack-approvals.ts schema
pnpm exec tsx scripts/with-env.ts tsx --tsconfig tsconfig.source-paths.json typescript/examples/slack-approvals.ts enqueue
```

Run each long-lived mode in its own process. Use the guarded `DATABASE_URL_PRIMARY` configuration of
the checkout that owns the data. Outside the repository, the recipe imports `@stablemates/workhorse`.
There, give it the database environment of your application.

The [complete setup reference](https://github.com/stablemates/workhorse/blob/main/docs/recipes/slack-approvals.md)
lists each process, credential boundary, command, storage field, limit, and verification seam.

## Accept a click before the Slack deadline

Slack requires HTTP 200 within three seconds. The receiver allows 2,500 ms from the HTTP arrival for
the acceptance.

The receiver limits the raw body size and verifies the HMAC-SHA256 signature. It rejects a timestamp
outside the replay window. It binds the random reference to these values:

- the task and the wait generation
- the workspace, the app, the user, and the channel
- the Slack message
- the expiry time

An opaque reference alone does not give permission. The receiver derives the actor on the server
from the authorized workspace and user IDs.

The receiver serializes clicks with a PostgreSQL row lock. It returns HTTP 200 only after the
acceptance commits, or for the same receipt that is already committed. A competing actor or decision
gets a conflict. An invalid signature, an unauthorized user, or a closed wait fails without
acceptance. If the budget expires, the receiver returns a failure, not an early success.

Controlled tests prove these boundaries. They do not prove the latency of your production network
or database.

| Other route                                                           | `404` |

## Know what HTTP 200 means

HTTP 200 confirms a durable receipt. It does not confirm a successful approval or a task completion.

**Example.** A user clicks "Approve", and an operator cancels the task at the same time.

1. The receiver commits the approval and replies HTTP 200.
2. The operator cancels the task before the decision worker settles the approval.
3. The decision worker calls `completeHumanWait`.
4. Workhorse keeps the cancellation. The decision worker records the status `stale`.

The same rule applies to a timeout or another Workhorse operator. The decision worker records the
status that Workhorse returns: `completed`, `duplicate`, `already_completed`, `stale`,
`not_waiting`, or `not_found`. It does not use its own authority in place of the Workhorse result. It commits the Workhorse settlement and its local
receipt on the same PostgreSQL connection, in the same transaction.

Keep the receiver clock synchronized. Before production use, measure your actual latency for the
ingress, the pool acquisition, the commit, and the response.

A timeout or a lost response can leave a committed receipt. Inspect the stored state before you ask
for another click. Do not assume that interactive actions get the retry guarantees of the Events
API.

## Expect orphan prompts

The recipe does not deliver each prompt exactly one time. An orphan prompt is a Slack message that
has no committed reference.

**Example.** The notifier posts a prompt for a wait.

1. Slack accepts the post.
2. The notifier crashes before the reference transaction commits.
3. The prompt stays visible in the channel, but no reference exists for it.
4. A later pass posts a new prompt with a new reference.

Only the stored reference can accept a decision. A click that arrives before the local reference
commits can also fail. The person can then click again. The test fixture injects this failure
window.

The notifier posts a maximum of one Slack message in each pass. It obeys the Slack `Retry-After`
header for rate limits. If you run more than one notifier process, they need a shared rate policy
for the channel.

The discovery is bounded. An overdue wait can stay visible until maintenance closes it. The
receiver checks the real deadline with the PostgreSQL clock, not with the visibility alone.

## Treat `response_url` as a bearer credential

The Slack `response_url` can bypass the channel posting permissions. The recipe does not store it
and does not follow it. Keep it out of logs, traces, proxy captures, and analytics.

## Define orphan reconciliation and retention before production use

The recipe does not use `trigger_id`. It does not reconcile Slack messages automatically. It does
not give a daemon that cleans the inbox.

Before production use, define these two procedures:

- an orphan reconciliation that a person reviews
- a receipt retention policy

Never delete unsettled decisions to hide a failure.
