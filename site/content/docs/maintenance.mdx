title: Maintenance and retention
description: Workers keep PostgreSQL tidy automatically — promotion, recovery, partitions, and evidence retirement — while you set policy and watch for lag.
---

A durable queue accumulates: delayed tasks waiting to become ready, leases that expired with their
workers, history partitions filling up, and evidence that eventually outlives its usefulness.
Workhorse handles all of it as bounded background work that workers drive automatically. PostgreSQL
coordinates the passes with advisory locks, so scaling from one worker to fifty never multiplies
destructive work — one worker wins each due phase, the rest get cheap no-ops. TypeScript, Python,
Go, Rust, and Ruby workers all call `run_maintenance_v1`, which keeps the slow phase order in
PostgreSQL.
A deployment therefore needs no TypeScript worker to replenish partitions, roll up statistics,
retire history, or prune terminal and worker records.

## The phases, and how to watch them

`run_maintenance_v1` calls the same versioned SQL functions you can call yourself:

- `queue.tick` promotes due tasks to ready and recovers expired leases.
- `queue.prepareHistoryPartitions` creates future time partitions before data arrives.
- `queue.rollupStatistics` folds raw history into minute summaries, then derives hour and day tiers.
- `queue.retainHistory` retires history the statistics rollup no longer needs.
- `queue.pruneTerminalStorage` removes expired idempotency bindings, then terminal task bundles.
- `queue.pruneWorkerRegistry` removes registrations whose processes stopped refreshing them.

Direct calls are for controlled scripts and tests; in production the workers already make them.
To observe each pass, give any worker an `onMaintenance` callback:

```ts
const worker = new Worker(queue, {
  onMaintenance(telemetry) {
    metrics.record("workhorse.maintenance", {
      phase: telemetry.phase,
      rows: telemetry.rowsAffected,
      durationMs: telemetry.durationMs,
    });
  },
});
```

The `WorkerMaintenanceTelemetry` result names the phase, affected rows, duration, lock outcome,
and any error — enough to chart cleanup throughput in whatever monitoring you already run.

PostgreSQL retains recent execution history for the maintenance routines shown on the Schedules
page. Expand a routine there to inspect outcomes, duration, affected rows, phase timings, and error
details. Slow routines record each eligible execution; the fast tick records work and failures but
omits successful idle polls.

## Set retention policy

Retention decides how long evidence lives. `queue.syncRetentionPolicy` stores your application's
defaults as a deploy step:

```ts
await queue.syncRetentionPolicy({
  taskIdentityRetentionDays,
  terminalOutcomeRetentionDays,
  taskEventRetentionDays,
  attemptHistoryRetentionDays,
  scheduleOccurrenceRetentionDays,
  statisticsRetentionDays,
});
```

Sync updates only values an operator has not overridden, so a deploy never silently reverts an
incident-time decision. During an incident, `queue.overrideRetentionPolicy` changes selected
values without a deploy, and `queue.revertRetentionPolicy` restores the application defaults for
the settings you name. `queue.getRetentionPolicy` shows the effective policy.

Before any destructive change, preview it:

```ts
const impact = await queue.previewRetentionPolicy({ terminalOutcomeRetentionDays });
console.log(impact.eligible.terminalTasks, impact.capped.terminalTasks);
```

The preview counts currently eligible rows per category, size-capped with an explicit `capped`
flag. The dashboard settings page runs the same preview before applying a change.

Statistics use progressively coarser summaries inside that policy window, so long windows keep
totals and mergeable wait percentiles without retaining the finest detail forever.

PostgreSQL guards the dependency order: it rejects any `RetentionPolicyDefinition` that could
remove a task's identity before its retained evidence, and a retained `task_redrive` descendant
keeps its source identity available for lineage. A retained source does not hold up cleanup:
terminal pruning steps past it to eligible younger tasks, including the descendant that releases
it. A fast-tier task usually has no events or
attempts, so its outcome row stands in for its history and waits for both windows.

Delete terminal data through the retention functions rather than deleting `task` rows directly.
Direct deletion cascades into retained history, so it can remove evidence before the configured
windows expire or statistics consume it.

## Set maintenance cadence

`queue.syncMaintenancePolicy` stores one set of scheduling defaults for the database, including
an IANA timezone, a local wall-clock time for the daily history retention pass, and the
statistics rollup interval, group limit, and recompute window. Setting the rollup interval to
zero opts the whole fleet out of statistics.
`queue.overrideMaintenancePolicy` and `queue.revertMaintenancePolicy` follow the same
override-and-revert model as retention, and the dashboard settings page shows each value's
source. Workers check eligibility at different moments, but the database owns the shared due
state — extra replicas change nothing.

## Detect lag before it hurts

Cleanup that silently stalls becomes a full disk weeks later. `queue.health` budgets exactly this:
a stalled statistics rollup, late retention, or a missing history partition each produces a
`status.reasons` entry with a stable code.

Only the daily history pass deletes schedule runs, so runs expire between passes by design.
Workhorse reports late schedule runs when the latest pass left late rows behind. It also reports
them when the next pass is overdue and expired runs remain. `retentionLagMs` still shows the raw
time past the window.

```ts
const health = await queue.health();
if (health.status.level !== "healthy") {
  for (const reason of health.status.reasons) alert(reason.code, reason.observed);
}
```

For continuous export rather than polling, Workhorse emits OpenTelemetry metrics. In TypeScript,
core stays silent until a telemetry provider is registered, even when your application configures
an SDK. Configure the SDK first, then call `registerOpenTelemetry()` from
`@stablemates/workhorse-otel` once during startup; [OpenTelemetry](/docs/operations#opentelemetry)
covers the setup. Database-wide gauges — queue depth, ready-work age, expired leases, fleet
capacity — come from a dedicated observer:

```ts
import { WorkhorseMetricsObserver } from "@stablemates/workhorse";
import { registerOpenTelemetry } from "@stablemates/workhorse-otel";

const unregisterTelemetry = registerOpenTelemetry();
const observer = new WorkhorseMetricsObserver(pool, {
  onError: (error) => logger.error({ error }, "workhorse metrics collection failed"),
}).start();

// During service shutdown, stop the observer before unregistering telemetry:
observer.stop();
unregisterTelemetry();
```

Run exactly one observer per database, beside a long-lived service — every replica sees the same
queues, so multiple observers export duplicate gauges. `registerQueueMetrics` and
`queue.queueMetricSnapshot` are the lower-level pieces if you integrate by hand.

## Export history before retention deletes it

Retention is the right window for a database whose job is dispatch, and the wrong window for an
auditor. Cold export copies each finished UTC day of events (`task_event`), attempts
(`attempt_history`), and [fast-tier](/docs/fast-tier) outcomes (`fast_task_outcome`) to a store you own, and
history retention then waits for that copy: while export is enabled, a day above the export
watermark is never deleted, so an exporter that falls behind holds history instead of leaving a
hole in the archive. Export is off by default.

Workhorse ships the ledger and the four SQL functions an exporter drives: claim a day, read it in
ordered pages, complete it with a SHA-256 checksum and counts, or report a failure so the
day is handed out again. The exporter itself is a small program you run on your own schedule, and
no exporter ships in this release. Enable export only once one is ready, because enabling it with
nothing to drain it holds history indefinitely:

```ts
await queue.setColdExportPolicy({ enabled: true });
console.log(await queue.getColdExportStatus());
```

Object names derive from the day, so a crashed export resumes by rewriting the same object.

A day is always a UTC day: a segment starts at a UTC midnight and lasts one UTC day, whatever time
zone the exporter's session uses. Earlier releases stepped a calendar day in the session time zone,
so across a daylight-saving change two segments could share a UTC date and one object name, and the
later export overwrote the earlier day's object. The schema upgrade that adds the UTC-day rule
repairs such a ledger.

Before you run that upgrade, stop every exporter and let each finish its object and manifest
uploads. Keep export enabled, so retention still waits for the export. The repair fences an earlier
exporter out of the ledger, but it cannot stop an upload already in flight, and that upload would
overwrite the corrected day's object with the old range. The repair then does this:

- It waits for any running retention pass and holds off new ones until it commits, so no pass that
  read the old watermark deletes history the repair exports again. An exporter that claims or
  completes a day meanwhile waits for it too.
- When a dataset lost a completed day to a short or long segment, it moves the watermark back to
  the first day that segment may have overwritten, so the exporter writes those days again.
  Retention keeps those days until the export has copied them.
- A damaged segment that starts at a UTC midnight at or after the new watermark becomes one UTC day
  and is exported again, with its attempt count raised so its earlier exporter cannot complete it.
- It drops every other segment that is not one UTC day. Their objects stay in your store, but the
  ledger no longer names them. It warns per dataset with the counts and ranges.
- The rewind reaches only history still in PostgreSQL. If retention already removed some of those
  days, the watermark stops at the oldest retained day, and a second warning names the days that
  cannot be written again. Treat their archive objects as suspect and restore them from another
  copy if you have one.
- Retention can also remove part of a day, as the fast tier does row by row. The rewind stops after
  the last completed day whose source now holds fewer rows than its archive recorded, so it never
  overwrites a complete object with a smaller one. The same warning names those days.

`queue.getColdExportStatus()` reports the watermark, the segment being exported, and the last
error. Read exports back with a JSON-lines tool such as DuckDB, or `COPY` a day into a scratch
schema as `jsonb` lines; never load it into the live `workhorse` schema.
