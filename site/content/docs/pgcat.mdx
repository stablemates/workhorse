---
title: Can I run Workhorse behind PgCat?
description: Run every Workhorse operation behind PgCat in both pool modes, and know that PgCat never delivers a LISTEN notification on its own.
---

PgCat is a PostgreSQL connection pooler. Workhorse works correctly behind PgCat in
`pool_mode = "session"` and in `pool_mode = "transaction"`. Each Workhorse statement is
self-contained, and each Workhorse lock is transaction-scoped. Two behaviors of PgCat change your
deployment:

- PgCat never pushes a notification to an idle client.
- `pgcat.toml` names each pool statically.

## Check which operations work in each pool mode

| Operation                                              | Session mode                  | Transaction mode               |
| ------------------------------------------------------ | ----------------------------- | ------------------------------ |
| Enqueue, claim, settle, heartbeat, operator reads      | Yes                           | Yes                            |
| Transactional enqueue in your own transaction          | Yes                           | Yes                            |
| Schema install and migrate                             | Yes                           | Yes                            |
| Maintenance tick and transaction-scoped advisory locks | Yes                           | Yes                            |
| `LISTEN`/`NOTIFY` wake hints                           | Buffered until the next query | Buffered until the next query  |
| Session-level advisory locks                           | Yes                           | Unsafe — no exclusion, leaks   |
| Session state (`SET`, `PREPARE`, temporary tables)     | Yes                           | Unsafe — leaks between clients |

<details>
<summary>Reference: verification</summary>

- `typescript/core/test/integration-pooling.test.ts` runs PgCat in `pool_mode = session` and in
  `pool_mode = transaction` as separate lanes.
- The schema rows cover `installSchema`, `migrateSchema`, and `contractSchema`.
- The advisory lock rows cover every SQL `pg_(try_)advisory_xact_lock` and the session-level
  `pg_advisory_lock`/`pg_advisory_unlock`.
- The rows were verified on 2026-09-11 against PgCat 1.2.0 and PostgreSQL 18.6.

More detail: [Compatibility: PostgreSQL connection poolers](https://github.com/stablemates/workhorse/blob/main/docs/compatibility.md#postgresql-connection-poolers).

</details>

## Give the worker a direct pool to keep wake hints

A wake hint is a PostgreSQL notification that tells an idle worker about a new task. Behind PgCat,
wake hints do not arrive in either pool mode.

**Example.** A worker listens for wake hints through PgCat, and the queue is empty.

1. The worker sends `LISTEN workhorse_tasks`. PgCat accepts it, and no error occurs.
2. The worker waits. It sends no query.
3. Your application enqueues a task, and PostgreSQL sends a notification.
4. PgCat buffers the notification until the worker sends a different query. The idle worker never
   sends one.
5. The fallback poll of the worker finds the task and runs it.

The worker reports that it listens, but the fallback poll does all the dispatch. Polling is the
mechanism that makes Workhorse correct, so all tasks still run. Only the wake-up is slower.

To keep wake hints, give the worker a pool that connects to PostgreSQL directly or through
session-mode PgBouncer. The Prisma and Kysely adapters take a `pool` for this purpose. Drizzle and
TypeORM use the pool of the ORM.

<details>
<summary>Reference: listener behavior</summary>

- PgCat, in either pool mode, relays a buffered notification only with the result of the next query
  of the client.
- `Queue.supportsTaskNotifications()` and the `isListening()` of the subscription still report the
  capability.
- `TypeOrmAdapterOptions` and `DrizzleAdapterOptions` omit `pool`.

More detail: [Overview: `LISTEN` notifications](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#listen-notifications) and [Compatibility: PostgreSQL connection poolers](https://github.com/stablemates/workhorse/blob/main/docs/compatibility.md#postgresql-connection-poolers).

</details>

## Name each pool after its database

PgCat routes a connection by the pool name in `pgcat.toml`, not only by the real database name.
The database name in a client URL must match a configured `[pools.<name>]` entry. Each entry names
the database that it routes to. PgCat cannot forward a database that you did not configure. In this
respect PgCat is different from the wildcard entries of PgBouncer. Name each pool after the
database that it serves.

## Do not use session state under transaction pooling

Under transaction pooling, each statement can go to a different server session. Thus session state
is unsafe:

- A session-level advisory lock stops the exclusion between clients. Workhorse uses only the
  transaction-scoped forms.
- A grant of a session-level lock stays after the client that took it.
- A `SET` that a client leaves applies to the next client that borrows that backend.

The listener connection that receives no notifications still counts against the client limit of
PgCat. Except in Rust, it also counts against the client pool.

<details>
<summary>Reference: locks and connection budget</summary>

- The session-level lock functions are `pg_advisory_lock`, `pg_advisory_unlock`, and
  `pg_try_advisory_lock`.
- Every Workhorse advisory lock is transaction-scoped: `pg_advisory_xact_lock`,
  `pg_try_advisory_xact_lock`, and `pg_advisory_xact_lock_shared`. This includes the
  schema-migration lock.
- The Rust worker opens its listener with `notifications::listen` from
  `WorkerOptions::listen_config`, outside the pool. The other languages take the listener connection
  from the pool.

More detail: [Overview: Advisory locks](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#advisory-locks) and [Overview: Connection budgets per language](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#connection-budgets-per-language).

</details>
