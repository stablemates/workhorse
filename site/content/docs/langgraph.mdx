---
title: Can a LangGraph approval use a Workhorse human wait?
description: A tested Python recipe that keeps the LangGraph replay in PostgreSQL and accepts one committed approval with only one graph driver.
---

This recipe lets a LangGraph graph wait for a reviewer through a Workhorse human wait. A human wait
suspends a task until a person sends a decision. Workhorse admits the task and keeps the wait.
LangGraph keeps its own persistent graph. Neither system replaces the other.

The tested recipe contains one deterministic draft, one approval interrupt, and one local PostgreSQL
tool. It calls no model provider, and it does no external action.

## Run the bounded example

The source is
[`python/examples/langgraph_approval.py`](https://github.com/stablemates/workhorse/blob/main/python/examples/langgraph_approval.py).
It uses the released `langgraph==1.2.12` and `langgraph-checkpoint-postgres==3.1.2`. These are
development dependencies. They are not dependencies of the Workhorse Python distribution.

Use a local development database that has the Workhorse schema. In a configured checkout of the
repository, do these steps:

1. Install the pinned tools.
2. Run the example.

```sh
uv sync --project python --locked
pnpm example:langgraph-approval
```

The command uses the `DATABASE_URL_PRIMARY` of the checkout through `scripts/with-env.ts`. It
installs separate schemas for the application and for the checkpointer. It does not reset Workhorse.

The example runs a limited number of worker passes. It verifies the committed human wait, approves
it as a fake reviewer, and returns a receipt. It is not a worker that runs in a request process. It
is not an observer service that runs all the time.

The recipe needs a direct PostgreSQL connection or a proxy that keeps the session. For the graph
session, do not use a transaction pooler, a connection pool for the checkpointer, or a driver that
reconnects.

## Give each owner its own state

Each system owns a different part of the state:

| Owner                     | Owns                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------ |
| Workhorse                 | Admission, leases, retry policy, and the `langgraph-approval` human wait             |
| LangGraph `PostgresSaver` | Graph state, replay, and the actual `Interrupt.id`                                   |
| Your application          | Graph-driver coordination, receipt storage, reviewer authorization, tool idempotency |

The thread ID is `workhorse:{task_id}`, and it does not change. The bridge is the application code
between Workhorse and the graph. It keeps the interrupt identity, the original approval context, the
decision, and the resume identity.

The Workhorse checkpoints contain bridge receipts, not a graph snapshot. A checkpoint is a named
piece of handler code whose result Workhorse stores. The handler never puts a full graph call inside
one `checkpoint` call.

## Recover the graph after a crash

**Example.** The handler resumes the graph after an approval, and the process stops.

1. The local tool commits its effect.
2. The process stops before LangGraph saves the graph checkpoint.
3. Workhorse runs the task again. The application reads `get_state` before it continues.
4. The graph replays the tool node against the deterministic local ledger.
5. The ledger finds an equal effect and gives back its receipt.

After a crash, the application gets back the interrupt that exists. It does not start the thread
again. If the replay finds a conflicting effect, the recipe fails closed. This is not exactly-once
execution of an arbitrary external action.

## Do not use queue concurrency to coordinate the graph

A handler can continue to run after its Workhorse lease ends. A queue concurrency policy alone
cannot stop it from becoming a second graph driver.

For this reason, the recipe holds a session advisory lock for the thread. The lock, the
checkpointer, the bridge writes, and the local tool use the same Psycopg connection. That connection
does not reconnect. If the session stops, each old graph writer and tool writer loses its
connection, and the lock goes with it. A separate connection for the lock would leave an unsafe
writer behind.

Before the graph starts and before each node, the handler makes a new fenced `set_progress` call.
The handler does not use a cached checkpoint or an old cancellation token in place of that check.

If another session holds the lock, the handler gets `DriverBusy`. Workhorse then retries the task
without a call to the graph. While the committed human wait suspends the task, the handler releases
the application lock.

<details>
<summary>Reference: progress fence</summary>

`set_progress` calls `update_progress_v1`. It accepts only the exact unexpired worker and fence
generation, and it rejects a write after a cancellation request. A stale write raises
`ProgressLeaseLostError`.

More detail: [Data model: `task_progress`](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#task_progress).

</details>

## Commit the approval before the graph resumes

**Example.** The graph reaches the approval interrupt.

1. LangGraph saves the interrupt. The bridge keeps the original context.
2. Workhorse commits the human wait and suspends the task.
3. A reviewer approves, and Workhorse commits the response. The task becomes runnable.
4. The handler resumes the graph with `Command(resume={interrupt_id: decision})`.

Only a committed approval can resume the graph. An approval that is not committed cannot authorize a
tool.

The application accepts exactly `{"approved": true}` or `{"approved": false}`. It rejects extra
fields, tools that a prompt selects, and a conflicting reuse of an approval identity.

Authenticate and authorize each reviewer before you call `Queue.complete_human_wait`. The
`requested_by` value records an actor. It does not authenticate that actor.

<details>
<summary>Reference: human wait completion</summary>

| Request                  | Result                                     |
| ------------------------ | ------------------------------------------ |
| Equal retry              | Returns `duplicate`                        |
| Changed same-key request | Raises `HumanWaitIdempotencyConflictError` |
| Another key              | Returns `already_completed`                |

More detail: [Data model: Completing a human wait](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#completing-a-human-wait).

</details>

## Send terminal outcomes to the graph

The example waits a maximum of 60,000 milliseconds for an approval. A Workhorse timeout or
cancellation does not automatically cancel a LangGraph interrupt that the graph keeps.

After Workhorse records a terminal task, your observer must call
`reconcile_terminal(database_url, task_id)` from the example. The recipe gives that function. It
does not install an observer or a scheduler.

Reconciliation uses the same application lock. It verifies the terminal state of the task that
Workhorse keeps. It stops the pending approval or tool, and it keeps the review context and the
original decision.

Reconciliation does not undo a committed tool effect. It does not replace an outcome that the graph
already completed. Cancellation is cooperative. It cannot revoke an effect that occurred after an
ownership check.

<details>
<summary>Reference: timeout and cancellation</summary>

`reconcile_terminal` accepts only a task in the `canceled` or `failed` state. It records
`cancelled`, `failed`, or `timed_out`. It records `timed_out` when the task error is
`DeadlineExceeded`.

More detail: [Data model: Timeout, cancellation, and retention](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#timeout-cancellation-and-retention).

</details>

## Keep the history until recovery and audit end

Keep these records until recovery and audit no longer need them:

- graph checkpoints
- bridge receipts
- tool receipts
- Workhorse history

Each record has its own cleanup lifecycle. This recipe gives no retention service. If a bridge row
loses its graph, the driver does not create the interrupt again. If the terminal task history is
missing, the observer does not infer a permission.

## Test the threads before you change the graph

Test the threads that you keep before you change the graph code, the interrupt placement, the
dependency pins, or the serializer configuration. The version check of the bridge fails closed. The
migrations of the checkpointer do not migrate the definition of the application. This proof covers
only this graph and the synchronous saver. It does not cover another framework or provider.

## Protect the boundary

- Keep the database credentials on the server.
- Treat drafts, prompts, approval input, and tool output as untrusted data.
- Keep secrets out of the approval context.
- Restrict direct table writes, so that a caller cannot bypass authorization, fencing, or the
  application lock.

The serializer disables the pickle fallback and module reconstruction. The driver disables ambient
LangSmith tracing. A live tool needs its own design for retries, idempotency, credentials, and
cancellation.

## Run the recipe tests

`python/tests/test_langgraph_approval.py` tests the real PostgreSQL saver and Workhorse workers in
scratch databases. The existing Python CI suite collects these tests one time. The tests cover these
cases:

- the graph saves before the bridge saves
- the graph resumes before the Workhorse checkpoint
- local tool replay
- duplicate and concurrent resume
- fencing of a stale driver
- session loss
- timeout and cancellation
- the retained context

The integration catalog calls this a documented, tested recipe. It is not a published adapter, and
it is not verified against a live provider.
