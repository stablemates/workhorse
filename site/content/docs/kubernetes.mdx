---
title: How do I deploy Workhorse on Kubernetes?
description: Apply a schema Job, worker Deployment, and dashboard Service with correct drain and connection budgets.
---

Kubernetes can run Workhorse as ordinary workloads: one schema Job, one worker Deployment, and one
dashboard Deployment with its Service. This page gives reference manifests that drain workers
correctly and keep the dashboard internal. Workhorse does not publish a Helm chart, an operator,
or a custom resource definition.

Your deployment system controls images, Secrets, ingress, authentication, and resource sizing.
The manifests on this page were applied to a k3s v1.34.1+k3s1 cluster on 2026-09-12. They use only
standard `batch/v1`, `apps/v1`, and `v1` resources.

## Prepare one application image

Replace `registry.example.com/acme/workhorse-app:1.2.3` with one immutable application image. The
image must contain the Workhorse CLI. It must also contain `/app/dist/workhorse.worker.js`, the
compiled worker definition from [Worker processes](/docs/worker-processes).

The worker definition must start the probe listener on port 9090. Set its `hostname` to `0.0.0.0`,
because the default `127.0.0.1` does not accept probes from Kubernetes.

## Supply secrets by reference

Create two Secrets with your secret manager or deployment system.

- `workhorse-database` supplies the `url` key.
- `workhorse-dashboard-auth` supplies the `username` and `password-hash` keys.

The manifests only refer to these keys. Do not put a credential in Git or on a command line.

## Run the schema Job first

The schema Job migrates the schema one time from the release image. Then it verifies that the
release accepts the schema. This step occurs before a new worker or dashboard process starts.

Give each release a new Job name, because the Pod template of a Job is immutable.

```yaml title="workhorse-schema-job.yaml"
apiVersion: batch/v1
kind: Job
metadata:
  name: workhorse-schema-migrate-1-2-3
  labels:
    app.kubernetes.io/name: workhorse
    app.kubernetes.io/component: schema
    app.kubernetes.io/version: "1.2.3"
spec:
  backoffLimit: 1
  template:
    metadata:
      labels:
        app.kubernetes.io/name: workhorse
        app.kubernetes.io/component: schema
        app.kubernetes.io/version: "1.2.3"
    spec:
      restartPolicy: Never
      containers:
        - name: schema
          image: registry.example.com/acme/workhorse-app:1.2.3
          imagePullPolicy: IfNotPresent
          command: ["/bin/sh", "-ec"]
          args:
            - |
              workhorse schema migrate
              workhorse schema status --json
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: workhorse-database
                  key: url
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
```

```sh
kubectl apply -f workhorse-schema-job.yaml
kubectl wait --for=condition=Complete job/workhorse-schema-migrate-1-2-3 --timeout=10m
kubectl logs job/workhorse-schema-migrate-1-2-3
```

If the Job fails, stop the release. Do not migrate in the init container of each worker. That
change makes one deliberate deployment step into concurrent migration attempts.

## Deploy the worker tier

This Deployment runs two worker replicas, so one Pod is not the only worker process. Each replica
adds task concurrency and a database pool. Set the replica count from your availability and
capacity requirements.

The resource requests below only help Kubernetes schedule the Pods. They are not sizing advice.
Replace them with values that you measure for your handlers.

```yaml title="workhorse-worker.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: workhorse-worker
  labels:
    app.kubernetes.io/name: workhorse
    app.kubernetes.io/component: worker
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: workhorse
      app.kubernetes.io/component: worker
  template:
    metadata:
      labels:
        app.kubernetes.io/name: workhorse
        app.kubernetes.io/component: worker
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: worker
          image: registry.example.com/acme/workhorse-app:1.2.3
          imagePullPolicy: IfNotPresent
          command: ["workhorse"]
          args:
            - worker
            - --config
            - /app/dist/workhorse.worker.js
            - --shutdown-timeout-ms
            - "110000"
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: workhorse-database
                  key: url
          ports:
            - name: probes
              containerPort: 9090
              protocol: TCP
          readinessProbe:
            httpGet:
              path: /readyz
              port: probes
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /livez
              port: probes
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
```

`/readyz` returns 200 only while the workers can claim tasks. It returns 503 when the drain starts.
`/livez` returns 200 while handlers drain. It reports the process lifecycle, not the health of the
database, the queue, or a handler.

Make the Pod grace period longer than the Workhorse shutdown deadline. This manifest sets a grace
period of 120 seconds and a deadline of 110 seconds. The Kubernetes default grace period is 30
seconds. When the grace period ends, Kubernetes sends `SIGKILL`, so the default stops this drain
too early. A `preStop` hook uses the same grace period, so this manifest has no hook.

## Keep the dashboard internal

The dashboard Deployment binds beyond loopback, so the standalone CLI requires authentication. This
manifest reads the credentials from the Secret. It exposes the dashboard only through an internal
`ClusterIP` Service.

1. Point your authenticated HTTPS ingress at the Service.
2. Change `--public-origin` to your public HTTPS origin.

```yaml title="workhorse-dashboard.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: workhorse-dashboard
  labels:
    app.kubernetes.io/name: workhorse
    app.kubernetes.io/component: dashboard
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: workhorse
      app.kubernetes.io/component: dashboard
  template:
    metadata:
      labels:
        app.kubernetes.io/name: workhorse
        app.kubernetes.io/component: dashboard
    spec:
      containers:
        - name: dashboard
          image: registry.example.com/acme/workhorse-app:1.2.3
          imagePullPolicy: IfNotPresent
          command: ["workhorse"]
          args:
            - dashboard
            - --host
            - 0.0.0.0
            - --port
            - "3000"
            - --public-origin
            - https://workhorse.example.com
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: workhorse-database
                  key: url
            - name: WORKHORSE_DASHBOARD_USERNAME
              valueFrom:
                secretKeyRef:
                  name: workhorse-dashboard-auth
                  key: username
            - name: WORKHORSE_DASHBOARD_PASSWORD_HASH_FILE
              value: /run/secrets/workhorse/password-hash
          ports:
            - name: http
              containerPort: 3000
              protocol: TCP
          readinessProbe:
            tcpSocket:
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            tcpSocket:
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
          volumeMounts:
            - name: dashboard-auth
              mountPath: /run/secrets/workhorse
              readOnly: true
      volumes:
        - name: dashboard-auth
          secret:
            secretName: workhorse-dashboard-auth
            items:
              - key: password-hash
                path: password-hash
---
apiVersion: v1
kind: Service
metadata:
  name: workhorse-dashboard
  labels:
    app.kubernetes.io/name: workhorse
    app.kubernetes.io/component: dashboard
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: workhorse
    app.kubernetes.io/component: dashboard
  ports:
    - name: http
      port: 80
      targetPort: http
      protocol: TCP
```

Keep one standalone dashboard replica, because its sessions exist only in that process. If your
application embeds the dashboard, use shared application authorization before you add replicas.

## Count connections before you add replicas

Let `R` be the number of worker replicas. Let `P` be the maximum of each node-postgres pool. The
worker tier can open `R × P` client connections.

- Notification-assisted dispatch reserves one connection in each pool for `LISTEN`.
- Heartbeats reserve one more connection in each pool, unless you set `sharedHeartbeats`.
- So `R` replicas leave at most `R × (P - 2)` worker-pool slots for queries.

**Example.** Two worker replicas each use a pool with `max: 10`.

1. The worker tier can open 20 client connections.
2. Two connections stay on `LISTEN`, one in each replica.
3. Two connections stay on heartbeats, one in each replica.
4. 16 connections remain for claims, handlers, and maintenance.

Add the dashboard, producer, and migration pools to this total. Then compare the total with the
client limit of your database or pooler.

Transaction-mode PgBouncer keeps queue operations correct, but it breaks the session that `LISTEN`
needs. Do one of these steps:

- Connect the notification pool directly to PostgreSQL.
- Connect the notification pool through session-mode PgBouncer.
- Turn off notifications and use bounded polling.

Supavisor has the same boundary. Transaction mode breaks `LISTEN`, but session mode and native mode
keep it. Supavisor recommends native mode or direct mode for migrations.

## Roll forward, then roll back only the processes

Use this order for a release:

1. Apply the schema Job and wait until it succeeds.
2. Apply both Deployments with the same image.
3. Wait until both rollouts are complete.

```sh
kubectl apply -f workhorse-worker.yaml
kubectl apply -f workhorse-dashboard.yaml
kubectl rollout status deployment/workhorse-worker
kubectl rollout status deployment/workhorse-dashboard
```

If a rollout fails after the migration, undo the Deployment revision. Do not reverse the schema
migration. Migrations within a major release only add, so the previous release accepts the newer
schema.

```sh
kubectl rollout undo deployment/workhorse-worker
kubectl rollout undo deployment/workhorse-dashboard
kubectl rollout status deployment/workhorse-worker
kubectl rollout status deployment/workhorse-dashboard
```

`workhorse schema migrate` stops before a contract step. Apply a contract step separately, and only
after every old worker and producer has left the fleet.

## Test the manifests locally

Run `pnpm test:kubernetes` on a computer with Docker, k3d, and kubectl. The test applies the YAML
on this page to a temporary k3s cluster. It checks the migration, dashboard access, worker probes,
and a graceful task drain. When the test ends, it removes the cluster and the fixture images.
