Before infrastructure becomes important to your application, you must know what it does not do.
This page lists each limit of Workhorse. If a limit has a workaround, the page gives it.

Workhorse fits an application that uses PostgreSQL. The handlers of the application must accept
that a task can run more than one time. The schema upgrades in a deployment step, not by itself.

Workhorse is a public beta. A public beta is a usable 0.x release for evaluation and early
production use. A minor release can change behaviour, so read the changelog before you upgrade. You
do not have to make your database again. Migrations are ordered, and inside a major line a migration
only adds. Thus, a running deployment upgrades in place.

## Write workflows in handler code

Workhorse supports task dependencies, fan-in policies, child tasks, external signals, and human
decisions. It does not have a separate language to define workflows, or a model to deploy a graph.

Workaround: write these durable steps in ordinary handler code. If you must define and deploy a
workflow separately from the application code, use a separate workflow tool. You can use it together
with Workhorse or in its place.

## Make handlers stop when a cancellation arrives

A worker never stops a running handler by force, because that is not safe. A cancellation, a
deadline, or an execution timeout sends a request to the handler. The handler continues until it
reads the request or until the worker loses the task. When a process shuts down, it also lets the
handlers complete. It does not stop them by force.

Each SDK gives the request to the handler in its own way:

- TypeScript aborts `context.signal`.
- Python cancels `context.cancellation`.
- Go cancels the standard context of the handler.
- Rust reports the request through `context.cancellation()`.
- Ruby reports the request through `context.cancellation`.

Workaround: give the cancellation signal to each operation that can stop. Check the signal between
the units of work. If work must stop by force, run it in a process that you can stop. Make its
effects recoverable.

## Make external effects safe to repeat

PostgreSQL cannot commit an HTTP call, an email, or a payment in the same transaction as the
completion of a task. A worker can do the effect and stop before it records the success. Then the
effect can occur again.

An idempotency key of the enqueue removes duplicate tasks. It cannot make one accepted handler run
exactly one time. A redrive also runs the handler at least one time.

Workaround: this is the designed model. Put each effect in a named `checkpoint`, so that a completed
step does not run again. Also give the provider an idempotency key, for example the task ID or a
domain ID. The key covers the short time between the effect and the save of the checkpoint.

## Run the schema tools from the TypeScript package

Python, Go, Rust, and Ruby have transactional queue clients, complete worker runtimes, and `Admin`
operator clients. All of them use the shared SQL protocol. Schema installation and migration, the
`workhorse` admin CLI, and the TUI are only in the TypeScript package. Thus, a deployment with many
languages keeps that package available for these operations.

This is a decision, not a missing feature. No component can migrate the schema when it starts,
because no component runs as a single instance. The dashboard and each worker deploy on many nodes.
If each component migrated itself, many migrations would run at the same time. Also, the migration
runner is the code that has the most effect on safety, so it exists only one time.

This limit stays at 1.0.0. In the stable line, schema installation, migration, the `workhorse` CLI,
and the TUI stay in the TypeScript package only. The 1.0.0 release makes two promises:

- Each language gets the same operator capability through its own `Admin` client.
- Each language refuses to start with a schema that it cannot use.

The 1.0.0 release does not promise a second migration runner in each language.

Workaround: run the CLI as a deployment step. Pin it to the SDK version of your application. Before
the first new process starts, check the schema with `workhorse schema status --json`.
[Installation](/docs/installation) gives the two forms of the command. For a development database
without Node.js, each release attaches `schema.sql`, which you can apply with `psql -f`.

## Enqueue from your own API routes

Workhorse does not accept tasks over HTTP. A producer needs a database connection and the SDK.

Workaround: enqueue from your own API routes. There, you can also enqueue in the same transaction
as your business data.

## Reset a retired development schema

`migrateSchema` applies ordered, forward-only migrations from the supported baseline. A schema at a
version that retired before that baseline has no migration history. Thus, an operator must reset
such a development schema. It cannot upgrade.

Workaround: keep schema changes in the deployment path. Before you start a new runtime, run
`workhorse schema migrate`. Each language uses this command. A TypeScript application can call
`migrateSchema` in code. The changelog records the schema version that each release needs.

## Put the dashboard behind your own authentication

The standalone dashboard has one administrator login. It has sessions that expire, logout,
credential rotation, and a limit on login attempts. It does not have more than one user, roles,
single sign-on (SSO), or tenant isolation.

Workaround: put the dashboard behind the existing authentication of your application. Return the
verified operator from `authorize`.

## Give each isolated tenant its own database

Workhorse keeps tenants apart only when they use different databases. In one database, a task
identifies its tenant with three values: a concurrency key, a budget name, and a tag. These give a
fair share, a limit for each tenant, and reads that you can filter.

Inside one database, these limits apply:

- Nothing checks that the three values agree.
- The retention windows are the same for each tenant.
- An administrator sees all tasks of all tenants and can act on them.
- Workhorse cannot limit operator access to one tenant, and it has no roles for this.

Workaround: if a tenant needs separate data or its own retention windows, give it its own database.
For the shared database, follow the [multi-tenancy](/docs/multi-tenancy) page.
