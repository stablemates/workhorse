A worker process is a process that runs only workers. Your web servers and your workers fail in
different ways, scale differently, and need different amounts of memory. A dedicated worker process
keeps them apart: web replicas serve requests, worker replicas run tasks, and the two meet only in
PostgreSQL. Workhorse gives the full process lifecycle: startup, signals, drain, and probes. Thus, a
worker deployment needs one configuration file and one command.

If your web tier runs in a function or an edge isolate, use the
[serverless and edge matrix](/docs/serverless) to check its enqueue path. The worker still runs in
a process that runs continuously and has its own lifecycle.

## Define the worker process

Use `defineWorkerProcess` to write the configuration. The function checks the types of the
configuration and returns it unchanged. The definition owns its adapter, and through the adapter,
its database pool. It also has one entry for each worker.

```ts title="src/workhorse.worker.ts"
import { createWorkhorseAdapter, defineWorkerProcess, Pool } from "@stablemates/workhorse";
import { generateReport, sendEmail } from "./tasks.js";

export default defineWorkerProcess({
  adapter() {
    const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 10 });
    return createWorkhorseAdapter({
      database: pool,
      adaptTransaction: (transaction: typeof pool) => transaction,
      close: () => pool.end(),
    });
  },
  workers: [
    {
      options: { concurrency: 8 },
      configure(worker) {
        worker.handle("email.send", sendEmail);
        worker.handle("report.generate", generateReport);
      },
    },
  ],
  shutdownTimeoutMs: 25_000,
  probes: { hostname: "0.0.0.0", port: 9090 },
});
```

To run the process:

1. Compile the configuration module to JavaScript.
2. Run its default export with the packaged CLI:

```bash
workhorse worker --config ./dist/workhorse.worker.js
```

The CLI does not include a TypeScript loader. It imports only JavaScript that the current Node.js
process can read. Thus, production must run compiled output. To change the drain deadline for one
deployment, use `--shutdown-timeout-ms`.

If your app already supervises its processes, you do not need the CLI. Use one of these functions:

- `startWorkerProcess(definition)` starts the workers. It does not install global signal handlers.
- `runWorkerProcess(definition, options)` also adds the Node.js process lifecycle: signal handling,
  exit codes, and a forced exit.

<details>
<summary>Reference: process entry points</summary>

| Entry point                             | Behavior                                                     |
| --------------------------------------- | ------------------------------------------------------------ |
| `defineWorkerProcess(definition)`       | Type-checks and returns a configuration.                     |
| `startWorkerProcess(definition)`        | Starts workers without global signal handlers.               |
| `runWorkerProcess(definition, options)` | Adds the standalone Node.js process lifecycle.               |
| `workhorse worker --config <module>`    | Loads the default export and calls the standalone lifecycle. |

- `RunWorkerProcessOptions.shutdownTimeoutMs` and `--shutdown-timeout-ms` override the deadline of
  the definition.
- At startup, the process validates the definition, creates one adapter, creates and configures
  every `Worker`, starts the optional probe server, and starts every run loop. It reports readiness
  only after every worker starts.

More detail: [Worker process lifecycle](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#worker-process-lifecycle).

</details>

## Stop a worker process without losing work

When a worker process stops, it lets its active tasks finish. A drain is the time in which the
process waits for its active tasks to finish and takes no new tasks.

**Example.** A deployment replaces a worker process that runs 3 tasks.

1. The platform sends `SIGTERM` to the process.
2. The process sets readiness to false and calls `Worker.stop` on each worker.
3. The workers stop asking PostgreSQL for tasks. The 3 active tasks keep their leases.
4. Two tasks finish. The third task is still running when the 25-second deadline ends.
5. The process exits. Another worker recovers the third task after its lease expires.

If a claim was already in progress when the signal arrived, that claim can still commit. The
process then owns that lease, so it also drains that task.

`shutdownTimeoutMs` sets the drain deadline. If the deadline ends, the process exits. The remaining
leases stay in PostgreSQL. After a lease expires, the fenced recovery of Workhorse gives the task to
another worker. Thus, each task finishes in this process or in another worker.

Two limits apply:

- Process shutdown does not abort `HandlerContext.signal`, and it does not record a cancellation.
  If the task itself must stop, call `queue.cancel`.
- Set the drain deadline shorter than the termination window of your platform. A second signal
  makes the process exit immediately. Thus, a handler must be safe to recover after a forced stop.
  A handler that uses checkpoints and is idempotent is safe.

The [Kubernetes deployment reference](/docs/kubernetes) uses a 110-second process deadline and a
120-second Pod grace period. It also connects the two probe endpoints to a worker Deployment.

<details>
<summary>Reference: shutdown, deadline, and exit codes</summary>

- The first `SIGINT` or `SIGTERM` marks readiness false and calls `stop()` on every `Worker`.
  Later claim requests stop. Active handlers and the heartbeat batch of the worker continue.
  Adapter resources close only after every run loop settles.
- A claim transaction that is in flight can commit after shutdown starts. The worker drains that
  lease.
- Process termination does not abort a handler and does not cancel a task.
- `shutdownTimeoutMs` is a safe integer from 1 to 3,600,000. The default is 25,000 ms.

| Event                          | Exit                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------- |
| Clean drain                    | Code 0                                                                       |
| Second `SIGINT`                | Code 130                                                                     |
| Second `SIGTERM`               | Code 143                                                                     |
| Missed deadline                | Code 1                                                                       |
| Unexpected worker-loop failure | Stops sibling workers, applies the same bounded drain, and exits with code 1 |

A hard exit leaves active leases for the usual fenced recovery after lease expiry.

More detail: [Graceful shutdown](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#graceful-shutdown)
and [Shutdown deadline and failure](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#shutdown-deadline-and-failure).

</details>

## Connect the probes to your orchestrator

The probe server is an optional HTTP server that tells an orchestrator the state of the process. It
has two endpoints:

- Liveness (`/livez`) reports success while the process runs or drains.
- Readiness (`/readyz`) reports success only while the workers can ask for tasks.

Readiness fails as soon as the drain starts. Thus, a rolling deployment sends no work to a process
that stops.

The probe server does not serve your application. It shows no task data, no queue data, and no
metrics, and it accepts no changes. You can bind it where your orchestrator needs it.

If startup fails, the process closes each resource that it already created. If a worker loop stops
unexpectedly, the process stops the other workers and exits. Your supervisor then restarts the full
process. The process does not continue with only some of its workers.

<details>
<summary>Reference: probe listener</summary>

| Endpoint      | Running | Draining or failing |
| ------------- | ------: | ------------------: |
| `GET /livez`  |     200 |                 200 |
| `GET /readyz` |     200 |                 503 |

- `probes.livenessPath` and `probes.readinessPath` change the two paths. `HEAD` is supported.
  Other paths and methods return 404.
- `probes.hostname` defaults to `127.0.0.1`. Bind `0.0.0.0` only if the orchestrator must reach the
  pod or container network address.
- `probes.port` is an integer from 0 to 65,535.

More detail: [Probe listener](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#probe-listener).

</details>

## Give each process its own pool

Give each worker process its own database pool. Let the `close` function of the adapter close the
pool after the last worker drains. Plan the total number of connections across all replicas.

Some connections stay reserved in each pool:

- The notification listener holds one connection.
- The heartbeat connection holds one connection, unless you set `sharedHeartbeats`.
- Claims, handler queries, and routines share the other connections.

Each worker also registers itself in PostgreSQL at each `registryIntervalMs`. Thus, a dashboard on
another machine can see the workers. See [Operations](/docs/operations).

<details>
<summary>Reference: connection budget</summary>

- Notification-assisted dispatch reserves one shared listener connection for each node-postgres
  pool.
- Heartbeats reserve one more connection unless `sharedHeartbeats` is set.
- Claims, handler queries, and maintenance use the remaining pool capacity.
- By default, each worker upserts `workhorse.worker_registry` on its `registryIntervalMs` cadence.
  `registryIntervalMs: 0` turns registration off.

More detail: [Connection budgets per language](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#connection-budgets-per-language).

</details>
