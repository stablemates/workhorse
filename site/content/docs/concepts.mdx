Most queue bugs are really model bugs: you assumed a task runs once, or that a dead worker's writes
stop mattering, or that finished tasks slow down the queue. This page gives you the model that makes
Workhorse's behavior predictable — where a task lives, who may touch it, and what remains afterward.

## A task is three kinds of row

Workhorse splits every task across three relations, one per kind of fact.

`task` stores the stable ID and the accepted definition: queue, type, payload, attempt budget, and
policy. A pending [keyed debounce](/docs/debounce) may replace that definition while preserving the
ID. Dispatch or another non-replaceable state freezes the accepted definition.

`task_runtime` is the live row. It exists only while the task is `scheduled`, `blocked`, `ready`,
or `active`, and it is the only mutable lifecycle relation — workers and SQL functions change it as the task
becomes eligible, gains an owner, or returns for another attempt.

`task_outcome` is the terminal row. When the task becomes `succeeded`, `failed`, or `canceled`,
PostgreSQL deletes the runtime row and inserts the outcome in the same transaction.

A committed task therefore has one runtime row or one outcome row, never both. No reader can observe
a task as live and terminal at the same time. Terminal tasks leave the indexes workers search. This
isolates the ready scan from lifetime completed work, so dispatch is designed to scale with live work.

## The seven states

```
blocked ──▶ scheduled ──▶ ready ──▶ active ──▶ succeeded
   │                        ▲ ▲        │  └───▶ failed
   └────────────────────────┘ └(retry)─┘  └───▶ canceled
```

- `blocked`: the task waits on prerequisite tasks; its dependency policy decides whether it is
  released or terminally settled when they finish.
- `scheduled`: the task has a future `runAt`, a retry delay, or a durable sleep in progress.
- `ready`: the task is eligible and waiting for a worker slot, in queue-local FIFO order.
- `active`: one worker owns the task under a lease and is running its handler.
- `succeeded`, `failed`, `canceled`: terminal. Result, error, or cancellation envelope is stored.

`Admin.getTask` returns a snapshot with `state`, `currentAttempt`, `result`, and `error`, whichever
side of the split the task is on.

```ts
const admin = new Admin(pool);
const task = await admin.getTask(taskId);
console.log(task?.state, task?.currentAttempt, task?.result);
```

## Who owns active work

When a `Worker` has free slots, it calls `claim_many_v1` with that count. PostgreSQL applies the
`claim_v1` queue-policy transition to each member, then records the worker ID, a lease expiry, and a fence token on `task_runtime`. The worker
sends every active lease through `heartbeat_many_v1` while handlers run.

If heartbeats stop, recovery closes the old attempt and makes the task eligible again. Every
semantic write carries the worker ID and fence token, so a stale worker cannot complete, fail, or
change a task after a newer worker has claimed it — the full mechanics live in
[Workers](/docs/workers).

## Why a handler can run twice

The handler runs outside the transaction that grants ownership. A process can finish an external
effect — the email sent, the card charged — and die before PostgreSQL records success. Recovery
cannot tell that apart from a crash before the effect, so it must run the handler again.

That is at-least-once delivery, and it shapes how you write handlers:

- If a stage must not repeat within a task, wrap it in `HandlerContext.checkpoint`. A completed
  checkpoint replays its stored result on the next run instead of executing again.
- If an external call must not repeat across systems, give the provider a stable idempotency key.
  Checkpoints narrow the duplicate window; only the provider can close it.

```ts
worker.handle("invoice.send", async (payload: { invoiceId: string }, ctx) => {
  return ctx.checkpoint("send", () =>
    emailProvider.send({ idempotencyKey: `invoice:${payload.invoiceId}` }),
  );
});
```

[Durable execution](/docs/durable-execution) covers checkpoints, durable sleeps, and their rules.

## Where history goes

Execution leaves append-only evidence, kept off the dispatch path so audits never compete with
claims.

`task_event` records every lifecycle change; `attempt_history` records how each logical attempt
closed. `Admin.getTaskTimeline` merges both into one cursor stream, so you can answer "what happened
to task X" from SQL-backed records rather than log lines. Every history row has a UUIDv7 identity
that remains stable in an archive or across Workhorse installations.

`task_query` is a separate bounded routing projection for operator reads. `Admin.listTasks` pages
through its immutable creation order, then reads each task's current state from `task_runtime` or
`task_outcome`. Claims and other lifecycle changes don't rewrite the projection or maintain broad
state indexes on `task_runtime`. Both history relations are partitioned by day and retired by
retention policy, independently of live dispatch.

Inside a handler, `HandlerContext.checkpoint` records a named completed stage.
The shorter `context.checkpoint` form in examples refers to that same durable boundary.
