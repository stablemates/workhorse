Most queue bugs are model bugs. Someone assumed a job runs exactly once, or that a dead worker
stops writing, or that finished jobs pile up and slow everything down. None of those are true here,
and each one is cheap to understand up front and expensive to discover in production.

This page covers four things: where a job lives, who is allowed to touch it, why a handler can run
twice, and what survives after it finishes.

## A job moves between two tables, never both

Think of a job as having a **live** form and a **finished** form.

While a job is waiting or running, it has a live row. The moment it ends, PostgreSQL deletes that
live row and writes a finished row in the same transaction. One or the other, never the two
together.

This has a consequence you will feel: **finished jobs cost nothing to skip**. A worker looking for
work only ever searches live rows, so a million completed jobs do not slow down the next claim.

Underneath, that is three relations:

- **`job`**: who the job is. Queue, type, payload, attempt budget, policy. Written once, never
  semantically changed.
- **`job_runtime`**: the live row. Exists only while the job is waiting or running, and it is the
  only row that changes.
- **`job_outcome`**: the finished row. Holds the result, the error, or the cancellation.

## The states, and what moves a job between them

```
scheduled ──▶ ready ──▶ active ──▶ succeeded
                ▲          │  └───▶ failed
                └──(retry)─┘  └───▶ canceled
```

- **`scheduled`**: not yet. The job has a future start time, a retry delay, or a durable sleep
  running.
- **`ready`**: eligible, waiting for a free worker slot, in queue order.
- **`active`**: one worker owns it and the handler is running.
- **`succeeded`**, **`failed`**, **`canceled`**: over. The result, error, or cancellation is stored.

Ask any job where it is:

```ts
const job = await queue.getJob(jobId);
console.log(job?.state, job?.currentAttempt, job?.result);
```

## One worker owns a job at a time, and PostgreSQL enforces it

A worker with a free slot asks PostgreSQL for work. PostgreSQL hands back the job with two things
attached: a **lease**, which is a deadline for finishing, and a **fence token**, which is a number
that increases every time the job is claimed.

The worker sends a heartbeat while it works. If the heartbeats stop, because the process crashed or
the machine vanished, the lease expires and the job becomes available again.

Here is the part that matters. When the old worker wakes up and tries to write its result, its
fence token is now stale, and PostgreSQL rejects the write. A zombie process cannot overwrite the
work of the worker that replaced it. You do not have to detect this yourself.

[Workers](/docs/workers) has the full mechanics.

## A handler can run twice, and no setting changes that

The handler runs *outside* the transaction that granted ownership. So a process can send the email,
then die before PostgreSQL records that it succeeded. Recovery cannot tell that apart from a crash
that happened *before* the email. It has to assume the work did not happen and run the handler
again.

That is **at-least-once delivery**. Two tools make it safe, and they solve different halves:

- **Inside your process**, wrap the step in `ctx.checkpoint`. A finished step returns its stored
  result next time instead of running again.
- **Outside your process**, pass the provider a stable idempotency key. A checkpoint narrows the
  window where a duplicate is possible. Only the provider can close it.

```ts
worker.handle("invoice.send", async (payload: { invoiceId: string }, ctx) => {
  return ctx.checkpoint("send", () =>
    emailProvider.send({ idempotencyKey: `invoice:${payload.invoiceId}` }),
  );
});
```

[Checkpoints](/docs/durable-execution) covers the rules.

## Everything that happened is still there

Execution writes an append-only trail, and it is kept off the path workers use to claim jobs, so
reading history never slows down running work.

- **`job_event`** records every lifecycle change.
- **`attempt_history`** records how each attempt ended.
- **`job_query`** is a separate projection that operator screens page through.

`Queue.getJobTimeline` merges the first two into one stream, so "what happened to job X" is a
database query, not a log search. Both history tables are partitioned by day and cleaned up by
retention policy, on their own schedule.
