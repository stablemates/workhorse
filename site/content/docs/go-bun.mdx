[Bun](https://bun.uptrace.dev/) is an ORM for Go. When your application accepts an order, the
business row and its follow-up task must commit together. A Bun transaction contains the
`database/sql` transaction that gives this guarantee. Give its embedded `tx.Tx` to the existing
`NewSQLExecutor` of Workhorse.

This page is about the Go ORM, not the JavaScript Bun runtime. It is a tested recipe, not another
Workhorse package. The [integration catalog](/docs/integrations) puts it in the **documented**
tier, because the **verified** tier requires a dedicated integration package. A PostgreSQL fixture
in the Go suite checks the recipe continuously.

## Enqueue a task in a Bun transaction

Create Bun over `sql.Open("pgx", databaseURL)` with `pgdialect.New()`. Import
`github.com/jackc/pgx/v5/stdlib` to register the driver. At startup, call `AssertSchemaCompatible`
with `NewSQLExecutor(database)` on the `*sql.DB` of your application. Then create the queue inside
the transaction callback:

```go
err := db.RunInTx(ctx, nil, func(ctx context.Context, tx bun.Tx) error {
	if _, err := tx.NewInsert().Model(accepted).Exec(ctx); err != nil {
		return err
	}
	queue := workhorse.NewQueue(workhorse.NewSQLExecutor(tx.Tx), "orders")
	_, err := queue.EnqueueWithResult(ctx, "order.accepted", map[string]any{
		"orderId": accepted.ID, "customer": accepted.Customer, "receipt": accepted.Receipt,
	}, workhorse.EnqueueOptions{Tags: []string{"orders"}})
	return err
})
```

If the callback returns an error, Bun rolls back both writes. Bun owns commit, rollback, and the
return of the connection to the pool. Workhorse borrows the embedded transaction. It does not get a
new connection, and it does not end the transaction.

- Do not return, cache, or keep this queue after the callback.
- After the commit or the rollback, the underlying transaction returns `sql.ErrTxDone`.
- Run workers as [separate processes](/docs/worker-processes), never inside this request callback.

## Install the packages and the schema

Install the Go SDK and the pinned ORM in your application:

```bash
go get github.com/stablemates/workhorse/go
go get github.com/uptrace/bun@v1.3.0 github.com/uptrace/bun/dialect/pgdialect@v1.3.0
go get github.com/jackc/pgx/v5@v5.11.0 github.com/google/uuid@v1.6.0
```

Install the Workhorse schema one time, outside the application, with the matching schema tool.
Read [installation](/docs/installation) and [compatibility](/docs/compatibility) before you serve
requests. Bun owns your business tables. Workhorse owns its schema and its versioned SQL functions.

The runnable example needs this application table. Your application migration must create it:

```sql
CREATE TABLE bun_order (
  id uuid PRIMARY KEY,
  customer text NOT NULL,
  receipt jsonb NOT NULL
);
```

## Give Workhorse the embedded transaction, not the Bun wrapper

Use `NewSQLExecutor(tx.Tx)`. Do **not** use `NewSQLExecutor(tx)`. The `bun.Tx` type satisfies the Go
interface, so the wrong call compiles.

**Example.** A developer gives the `bun.Tx` wrapper to `NewSQLExecutor`.

1. Workhorse sends an enqueue statement with `$1`, `$2`, and more positional arguments.
2. The `QueryContext` method of `bun.Tx` formats the SQL through the Bun formatter.
3. Bun calls the embedded transaction, but it does not forward the bind arguments.
4. The statement fails, or its text changes.

Workhorse statements need native `$1`, `$2`, and later positional arguments. The embedded `tx.Tx`
keeps them.

## Supply hook guarantees separately

The raw path skips Bun SQL formatting and Bun query hooks for Workhorse statements. It also does not
call Bun model hooks, because Workhorse SQL uses no Bun model query. Business writes through
`tx.NewInsert()` still use the normal Bun formatting and hooks.

If your hooks do routing, authorization, or mandatory auditing, supply these guarantees separately
before you use this path. Do not expect your Bun hook to see Workhorse queries.

## Read raw results with the tested driver

`database/sql` gives JSONB results as bytes. It gives array results in the SQL representation of
the driver, not as Bun model values. The fixture decodes arrays with PostgreSQL `to_jsonb`. The
recipe does not promise a Bun slice decoder for raw result rows.

Use the tested driver configuration, or make an equal proof for your configuration.

## Roll back an inner write with a savepoint

A savepoint is a named point inside a transaction. You can roll back to it and keep the outer
transaction. The `tx.RunInTx` method of Bun creates a savepoint on the same embedded `*sql.Tx`. In
the nested callback, give `nested.Tx` to Workhorse.

- If the nested callback returns an error, Bun rolls back its business row and its task. The
  successful outer writes stay.
- A released savepoint does not make either row visible to an independent connection.
- If the outer transaction rolls back, it also removes the writes of a released savepoint.

Nested transaction options do not create another isolation boundary. Bun ignores these options for
savepoints.

## Return cancellation errors to Bun

Give the request context to the business writes and to the enqueue. Return cancellation errors and
deadline errors to Bun. Do not catch them and report success.

The fixture checks an enqueue with a context that is cancelled before the call. It also cancels a
raw statement while it runs, after both writes. In both cases, the two writes roll back together,
and the pool of the caller stays usable.

## Run the maintained fixture

From a configured checkout, run the focused fixture:

```bash
WORKHORSE_REQUIRE_DATABASE=1 \
  pnpm exec tsx scripts/with-env.ts go -C go test -count=1 -v ./examples/bun
```

The [maintained fixture](https://github.com/stablemates/workhorse/blob/main/go/examples/bun/transaction_test.go)
creates scratch databases from the test database of the checkout. It drops them at teardown.
`pnpm go:test` finds the fixture, so CI needs no second test step.

**Method.**

- The fixture limits the Bun pool to one connection and uses a separate observer pool.
- Backend IDs, transaction IDs, and the `xmin` of both rows prove physical transaction identity.
- Observer reads prove invisibility before the commit, and joint commit or rollback after it.
- Hooks, savepoints, native bindings, errors, cancellation, and the runnable example get real

- In the Go database CI lane, `WORKHORSE_REQUIRE_DATABASE=1` makes a missing database URL a
