Go's `github.com/jmoiron/sqlx` adds query helpers to `database/sql`. Its transaction contains the
same `*sql.Tx` that the existing `NewSQLExecutor` of Workhorse accepts. Thus your business write and
your task can commit together. This page is about **Go sqlx, not Rust SQLx**. It is a tested recipe,
not a new package and not a claim about Rust. The [transactional enqueue](/docs/enqueue) page owns
the shared ownership rules.

## Enqueue a task in a sqlx transaction

`BeginTxx` returns a `*sqlx.Tx`. Its embedded `Tx` field is the underlying `*sql.Tx`. Use the query
helpers of sqlx for business writes. Give `tx.Tx` directly to Workhorse.

```go
tx, err := database.BeginTxx(ctx, nil)
if err != nil {
	return err
}
defer func() { _ = tx.Rollback() }()

if _, err := tx.NamedExecContext(ctx,
	"INSERT INTO recipe_order (id, details, note) VALUES (:id, :details, :note)",
	map[string]any{"id": orderID, "details": `{"source":"sqlx"}`, "note": nil},
); err != nil {
	return err
}
queue := workhorse.NewQueue(workhorse.NewSQLExecutor(tx.Tx), "recipes")
if _, err := queue.Enqueue(ctx, "order.accepted", map[string]any{"orderId": orderID}); err != nil {
	return err
}
return tx.Commit()
```

The [runnable example](https://github.com/stablemates/workhorse/tree/main/go/examples/sqlx) contains
the complete setup and the error path.

## Set up the driver and the business table

Add `github.com/jmoiron/sqlx` to your application. Register pgx stdlib with its blank import. The
recipe dependency is in the Go module of the repository. The core source of Workhorse does not
import sqlx.

```go
import (
	_ "github.com/jackc/pgx/v5/stdlib"
	"github.com/jmoiron/sqlx"
)
```

Open the database with `sqlx.Open("pgx", databaseURL)`. Apply the business migration
`go/examples/sqlc/schema.sql` from the companion sqlc example to a disposable database. That database
must already have the Workhorse schema. The two examples use the same application table, so you can
compare their transaction behavior. Neither example owns the Workhorse schema lifecycle.

## Send Workhorse statements without changes

Workhorse supplies PostgreSQL positional parameters through pgx stdlib. Do not change its SQL.

- Do not wrap the executor with the sqlx `Named` or `Rebind` helpers.
- Do not wrap the executor with a query formatter.
- Do not enqueue through `database.DB`. It can get another connection and commit independently.

## Own the transaction in your application

Your application owns commit, rollback, savepoints, and database shutdown.

- Return client-side validation errors and database errors before the commit.
- Do not keep the queue after its transaction ends.
- Do not give a request transaction to a worker.
- Run a dedicated worker with its own pgx pool.

## Roll back an inner write with a savepoint

In this recipe, sqlx does not supply a nested transaction feature. Use explicit PostgreSQL
savepoints on `tx`. A savepoint is a named point inside a transaction. You can roll back to it and
keep the outer transaction. The fixture tests two nested levels.

If you roll back an inner savepoint, PostgreSQL removes both inner writes. A released savepoint
never commits the outer transaction. After an ordinary SQL error, roll back to a savepoint before
you continue.

## Keep the context alive until the commit

Keep the context that you give to `BeginTxx` alive until the commit or the rollback. If that context
is cancelled, `database/sql` rolls back the transaction. Workhorse does not do this rollback.

The fixture tests two cases separately. In the first case, the context is cancelled before the
query starts. In the second case, a real enqueue waits for a database lock and the context is
cancelled.

If a cancellation occurs while a query runs, discard the transaction and use a new one. Do not
expect the connection to stay usable. The recipe does not promise recovery to a savepoint after the
wire protocol cancels a query.

## Run the maintained fixture

From a configured checkout, run this command:

```sh
WORKHORSE_REQUIRE_DATABASE=1 pnpm exec tsx scripts/with-env.ts \
  go -C go test -count=1 -v ./examples/sqlx
```

The fixture creates and drops an isolated scratch database. It installs both schemas and runs the
actual CLI. The Go CI suite of the repository compiles and runs the fixture, so no additional
integration suite is necessary.

To run the example manually, follow the example README. The example uses a fixed UUID, so run it one
time against a new disposable business schema.

The fixture proves:

- the same backend PID, transaction identity, and task `xmin`
- invisibility to an independent connection, joint commit and rollback, and executor lifecycle
  ownership
- JSONB, UUID, nullable text, nullable enqueue reasons, batch order, nested savepoints,
  cancellation, and recovery in a new transaction

pgx stdlib keeps native SQLSTATE errors. `Queue` translates `P1001` into its structured idempotency
conflict error. Ordinary `22012` errors and aborted-transaction `25P02` errors stay native
`*pgconn.PgError` values.

No maintained proof targets lib/pq, another sqlx driver, Rust SQLx, a hosted provider, or a pooler.
This local proof does not certify other sqlx drivers, providers, or poolers.
