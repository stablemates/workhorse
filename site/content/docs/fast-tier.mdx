---
title: Fast tier
description: Let a high-volume queue skip the records of durable execution, keep one outcome row for each task, and record history only where you need it.
---

A tier is a queue setting. It sets how much Workhorse records for each task of the queue. The full
tier is the default. It records everything that durable execution needs, so a handler can stop and
continue later on a different worker.

Some queues run short handlers at a high volume, for example handlers that send an email or call a
webhook. These handlers never stop to wait. The fast tier removes the records that only durable
execution needs. But a fast-tier queue cannot use a known set of features.

## Choose the fast tier for handlers that never wait

**Example.** The queue `emails` sends a welcome email for each new user. The handler calls the mail
provider and returns after a few milliseconds. It never waits. On a full-tier queue, each task still
makes these writes:

1. A worker claims the task. Workhorse changes the runtime row of the task and adds a `claimed`
   event.
2. The handler returns. Workhorse deletes the runtime row and writes an outcome row. It also adds an
   event and writes an attempt row.
3. If the provider fails, the retry also changes the runtime row, adds an event, and writes an
   attempt row.

These records let a task use checkpoints, durable waits, signals, and child tasks. With them, a task
can stop for days and continue on a different worker. The welcome email never stops, so these
writes give it nothing.

The tier of the queue decides if its tasks make these writes. A full-tier queue keeps the complete
record and supports every feature. A fast-tier queue keeps only the records that claims and outcomes
need.

Thus, choose the fast tier for a queue if all of its handlers only do work and return.

<details>
<summary>Reference: what each tier writes</summary>

| Transition                  | Full tier                                                                          | Fast tier                                           |
| --------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------- |
| Live task                   | `task_runtime` row                                                                 | `fast_task_runtime` row                             |
| Claim                       | `task_runtime` change and `task_event` row                                         | `fast_task_runtime` change                          |
| Retry                       | `task_runtime` change, `task_event` row, `attempt_history` row                     | `fast_task_runtime` change                          |
| Completion or final failure | `task_runtime` delete, `task_outcome` row, `task_event` row, `attempt_history` row | `fast_task_runtime` delete, `fast_task_outcome` row |

- Both tiers share the stable `task` identity row.
- After a committed transition, a fast-tier task has exactly one of `fast_task_runtime` and
  `fast_task_outcome`, and neither `task_runtime` nor `task_outcome`.
- A fast-tier queue writes claim events and `attempt_history` rows only when it opts in. Two audit
  paths always write `task_event` rows: batch evidence (`batch_dispatched`) and redrive
  (`redriven`, `redrive_created`).

More detail: [Fast tier: Fast tier](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#fast-tier).

</details>

## Move a queue to the fast tier

Each queue starts on the full tier. An operator must move a queue to the fast tier. The queue must
have no live task when the tier changes.

**Example.** An operator moves the queue `emails` to the fast tier. At that time, 300 emails wait in
the queue.

1. The operator calls `Admin.setQueueTier`. Workhorse refuses the change, because the queue has live
   tasks.
2. The operator stops the producers.
3. The workers send the 300 emails. The queue is now empty.
4. The operator calls `Admin.setQueueTier` again. Workhorse changes the tier.
5. New tasks in `emails` are fast-tier tasks.

`Admin.setQueueTier` records who asked for the change and why:

```ts
const admin = new Admin(pool);

await admin.setQueueTier("emails", "fast", {
  actor: "ops@example.com",
  reason: "email handlers never suspend",
  requestId: crypto.randomUUID(),
});
```

From a shell, `workhorse admin set-tier` does the same change. The CLI checks the target and asks
for a confirmation first. The Queues page of the dashboard shows the tier of each queue.

Workhorse refuses a tier change while the queue has a live task in either tier. Thus, a task never
moves between tiers, and its record stays in one place. Workhorse also refuses a move to the fast
tier while a concurrency policy or a rate-limit policy names the queue.

Finished tasks stay in the tier where they finished. After a tier change, the old outcomes of the
queue stay readable. Retention and cold export include the outcomes of both tiers.

<details>
<summary>Reference: changing the tier</summary>

`set_queue_tier_v1(p_queue_name, p_tier, p_requested_by, p_reason)` takes the exclusive tier lock
of the queue, then:

1. returns at once when the tier is unchanged;
2. raises `P1007` with feature `tier change` when the queue holds a live task in either runtime
   table;
3. raises `P1007` with feature `concurrency policies` or `rate-limit policies` when moving to
   `fast` while such a policy names the queue;
4. otherwise upserts `queue_control.tier`, `updated_by`, `reason`, and `updated_at`.

- `queue_control.tier` defaults to `full`. A queue without a `queue_control` row is full-tier.
- `p_requested_by` is 1 to 200 characters, and `p_reason` is 1 to 2,000.
- The function changes neither `paused` nor the history switches.
- TypeScript `Admin.setQueueTier(queueName, tier, { actor, reason, requestId })` passes only
  `actor` and `reason`, and emits the `workhorse.queue.tier_set` log event.
- The CLI command is `workhorse admin set-tier <queue> --tier <fast|full>`.
- `redrive_v1` copies a task into the current tier of its queue, not the tier it closed in.
- Retention prunes `fast_task_outcome`, and cold export has a `fast_task_outcome` dataset.

More detail: [Fast tier: Changing the tier](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#changing-the-tier).

</details>

## Check which features the fast tier supports

The fast tier removes the features that need durable execution or coordination state for each
task. For example, the team of the queue `emails` plans two new handlers:

- The first handler calls the mail provider and returns. It can use the fast tier.
- The second handler sends an email, then waits for a bounce signal. A fast-tier task cannot wait
  for a signal. Thus, this handler must use a full-tier queue, such as `reports`.

The table shows each feature. For each feature that the fast tier does not have, it gives the
reason.

| Feature                                                           | Full   | Fast              | Why the fast tier does not have it                                                                                                      |
| ----------------------------------------------------------------- | ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Leases, fences, and heartbeats                                    | Yes    | Yes               |                                                                                                                                         |
| Priority and delayed runs                                         | Yes    | Yes               |                                                                                                                                         |
| Retry policies, `maxAttempts`, deadlines, and execution timeouts  | Yes    | Yes               |                                                                                                                                         |
| Idempotency keys                                                  | Yes    | Yes               |                                                                                                                                         |
| Cancellation, pause, purge, run-now, and redrive                  | Yes    | Yes               |                                                                                                                                         |
| Combined completion and next claim                                | No     | Yes, every worker |                                                                                                                                         |
| `claimed` events and attempt history                              | Always | Opt-in per queue  | Each write is a part of the cost that the tier removes.                                                                                 |
| Checkpoints                                                       | Yes    | No                | A checkpoint is durable execution state. A fast-tier task does not keep this state.                                                     |
| Progress                                                          | Yes    | No                | A progress write checks the attempt against a `task_runtime` row. A fast-tier task has no such row.                                     |
| Durable sleeps, signal waits, and human waits                     | Yes    | No                | A wait stops the task. A fast-tier task is only ready or active, so it cannot stop.                                                     |
| Task dependencies, in either direction                            | Yes    | No                | A fast-tier task cannot stay blocked on a prerequisite. A finished fast-tier task never releases its dependents.                        |
| Child tasks, as parent or child                                   | Yes    | No                | A parent waits for its children, and a fast-tier task cannot wait. A fast-tier child never releases its parent.                         |
| Concurrency keys, budgets, and concurrency or rate-limit policies | Yes    | No                | The full claim admits one task at a time against each policy. The fast claim takes many tasks in one statement, with no admission step. |
| Debounce                                                          | Yes    | No                | While its window is open, debounce changes the `task_runtime` row of the pending task. No fast-tier path changes a pending row.         |
| Throttle                                                          | Yes    | No                | No reason is recorded yet. Throttle only decides if Workhorse accepts an enqueue request.                                               |

The full tier does not combine a completion with the next claim. The project measured this
combination only on the fast tier.

Thus, if a handler only does work and returns, use the fast tier. If a handler must stop and
continue later, keep its queue on the full tier.

<details>
<summary>Reference: supported features and combined completion</summary>

**Supported on the fast tier.** Priority, delayed runs, and idempotency keys. Retry policies,
deadlines, and execution timeouts. Heartbeats and cancellation. Redrive, pause, purge, and run-now.

**Rejected.** Every other feature in the table raises SQLSTATE `P1007` through
`reject_fast_feature_v1`. A full-tier task that names a fast-tier task as a prerequisite is also
rejected, with feature `dependencies` and no `queue` key.

**Combined completion.** `complete_many_and_claim_v1` serves only fast-tier queues. On a full-tier
queue it raises `P1007` with feature `batched completion` and the message
`queue <name> is not a fast-tier queue`. ADR 0077 measured fused completion only on the fast tier.

More detail: [Fast tier: Rejected features and `P1007`](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#rejected-features-and-p1007).

</details>

## Handle a request for a missing feature

If code asks a fast-tier queue for a feature that the tier does not have, Workhorse rejects the
request. The error names the queue and the feature.

**Example.** The queue `emails` is now fast-tier. Two incorrect calls reach it.

1. A producer enqueues a task with `concurrencyKey: "acme"`. Workhorse rejects the enqueue and
   creates no task.
2. The SDK raises `FastTierUnsupportedError` with the queue `emails` and the feature
   `concurrency keys`.
3. A handler calls `ctx.checkpoint("render", …)`. The handler context rejects the call with the
   same error and the feature `checkpoints`.
4. The handler fails. The retry policy of the task applies, as for each handler failure.

The handler context rejects a call for durable execution before the call goes to PostgreSQL. If an
operator adds a concurrency policy or a rate-limit policy to a fast-tier queue, Workhorse rejects it
with the same error.

In Ruby, some argument checks occur before the tier check. If a checkpoint, wait, signal, human
wait, or child name is not valid, Ruby raises `ArgumentError` first. Ruby also checks the type and
the size of a child set before its names.

<details>
<summary>Reference: rejections and errors</summary>

`reject_fast_feature_v1` raises SQLSTATE `P1007` with the message
`fast-tier queue <name> does not support <feature>` and `DETAIL` JSON `{ queue, feature, ordinal? }`.
`ordinal` names the position of the rejected request in a batch.

| Feature text                                  | Raised by                                                       |
| --------------------------------------------- | --------------------------------------------------------------- |
| `concurrency keys`, `budgets`                 | `enqueue_batch_v1`, and `redrive_v1` into a fast queue          |
| `dependencies`, `prerequisite tasks`          | `enqueue_batch_v1`                                              |
| `debounce`, `throttle`                        | `enqueue_debounce_v1`, `enqueue_throttle_v1`, `enqueue_many_v1` |
| `child tasks`                                 | `create_single_child_v1` and `create_children_v1`               |
| `concurrency policies`, `rate-limit policies` | Policy synchronization and `set_queue_tier_v1`                  |
| `tier change`                                 | `set_queue_tier_v1` while live tasks exist                      |
| `batched completion`                          | `complete_many_and_claim_v1` on a full-tier queue               |

**SDK errors**

| SDK        | Error                                                         |
| ---------- | ------------------------------------------------------------- |
| TypeScript | `FastTierUnsupportedError(queue, feature, ordinal?)`          |
| Python     | `FastTierUnsupportedError`                                    |
| Go         | `*FastTierUnsupportedError` matching `ErrFastTierUnsupported` |
| Rust       | `Error::FastTierUnsupported { queue, feature, ordinal }`      |

**Handler context rejections.** The handler context raises `FastTierUnsupportedError` before any
statement reaches PostgreSQL. The rejection is a handler failure, so the retry policy of the task
applies.

| Call                                        | Feature text    |
| ------------------------------------------- | --------------- |
| `setProgress`                               | `progress`      |
| `checkpoint`                                | `checkpoints`   |
| `sleep`, `sleepUntil`                       | `durable waits` |
| `waitForSignal`                             | `signal waits`  |
| `waitForHuman`                              | `human waits`   |
| `runChild`, `runChildren`, `runChildrenAll` | `child tasks`   |

**Ruby order.** An invalid checkpoint, wait, signal, human wait, or child name raises
`ArgumentError` first. `run_children` and `run_children_all` check the set before its names. A set
that is not an Array of `ChildTaskRequest` raises `ArgumentError`. A set of more than 100 children
raises `LimitExceededError`.

More detail: [Fast tier: Rejected features and P1007](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#rejected-features-and-p1007), [Fast tier: Handler context rejections](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#handler-context-rejections), and [Fast tier: Ruby argument validation order](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#ruby-argument-validation-order).

</details>

## Read what a fast-tier task records

A fast-tier task keeps fewer records than a full-tier task. But the core guarantees do not change,
and Workhorse keeps the errors of recent failed attempts.

**Example.** A new user signs up. The app enqueues the task `welcome-17` in the fast-tier queue
`emails`.

1. Workhorse writes one `fast_task_runtime` row in the state `ready`. It writes no `enqueued` event.
2. Worker A claims the task. The worker gets a lease and a fence token, as on the full tier.
3. Attempt 1 fails, because the mail provider times out. Workhorse adds the error to a list of
   recent errors in the runtime row. The row goes back to `ready`, with a later run time.
4. Attempt 2 succeeds. Workhorse deletes the runtime row and writes one `fast_task_outcome` row.
5. The outcome row keeps the list of recent errors. Thus, the failure of attempt 1 stays readable.

A claim still gives a lease and a fence token. Thus, a worker with an old lease cannot change the
result of a newer attempt. [Leases and fences](/docs/workers) explains these terms.

The list of recent errors has a size limit. When the list is full, Workhorse removes the oldest
entry and counts the removal. Thus, a reader knows that the list is not complete. If a lease, a
timeout, or a deadline closes the task, the column `closed_as` of the outcome names that cause.

A fast-tier task is only ready or active. A delayed task is a ready row with a run time in the
future. Thus, the fast tier has no `scheduled` state and no step that moves scheduled tasks to
ready.

<details>
<summary>Reference: runtime row, error list, and outcome</summary>

**`fast_task_runtime`**

- `state` is `ready` or `active`. A ready row with a future `run_at` counts as `scheduled` in the
  dashboard and in `queue_health_v1`.
- The row keeps no heartbeat time, no execution budget across releases, and no wait name.
- The execution timeout restarts on every claim.
- The tier has no separate scheduled state and no promotion pass.

**`errors` list.** `fast_retry_v1` appends one entry per closed attempt, with `attempt`,
`fence_token` as text, `worker_id`, `claimed_at`, `finished_at`, `outcome`, and `error`. The
`outcome` is `retry`, `timeout`, or `lease_expired`. The list holds at most 10 entries. At the cap,
`fast_retry_v1` drops the oldest entry and increments `errors_dropped`.

**`fast_task_outcome`**

| Column           | Values                                                               |
| ---------------- | -------------------------------------------------------------------- |
| `state`          | `succeeded`, `failed`, or `canceled`                                 |
| `closed_as`      | Null, `canceled`, `deadline_exceeded`, `timeout`, or `lease_expired` |
| `errors`         | Carried over from the runtime row                                    |
| `errors_dropped` | Carried over from the runtime row                                    |

If the handler itself fails the task for the last time, `closed_as` stays null.

More detail: [Fast tier: The errors list](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#the-errors-list) and [Fast tier: `fast_task_outcome`](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#fast_task_outcome).

</details>

## Run workers with no tier configuration

The tier belongs to the queue. It never belongs to a worker or to a task. Thus, the worker
configuration does not name a tier. The worker finds the tier of each queue itself.

**Example.** Worker W serves two queues: `emails` is fast-tier, and `reports` is full-tier.

1. W starts and tries a fast claim on each queue. On `emails`, the fast claim succeeds.
2. On `reports`, Workhorse rejects the fast claim. W marks `reports` as full-tier for some time.
3. W claims from `reports` with the full claim. Later, W tries a fast claim on `reports` again.
4. An `emails` handler returns. W sends one statement that completes the task and claims new
   `emails` tasks for the free slots.

If a worker has an old belief about a tier, the result is still correct. Workhorse sends each claim
to the current tier of the queue. Thus, an old belief costs one round trip and no correctness.

### Combine a completion with the next claim

On a fast-tier queue, each worker combines a completion with the next claim. A slot is the capacity
of a worker to run one handler. One statement closes the finished tasks and gives new tasks to their
slots. This saves one round trip for each task.

The combination has a cost. Handlers that finish at the same time wait together for that statement.
Their slots do no work during the round trip. Thus, a busy worker divides its slots into cohorts. A
cohort is a group of slots that combines only its own completions. While one cohort waits for
PostgreSQL, the handlers of another cohort continue to run.

A worker with more slots uses more cohorts, up to a limit. Each cohort uses its own connection from
the pool. Thus, a worker with a small pool uses fewer cohorts. If the database is far away or has
little CPU, set the cohort count with the `cohorts` option (`Cohorts` in Go).

### Expect one large result to fail only its own attempt

A combined completion sends many results in one statement. If one result is larger than its size
limit, Workhorse fails only that attempt. The retry policy of that task applies. Workhorse completes
the other tasks if their leases are still live, and the next claim still runs.

The SDK workers check the size of each result before they send it. Thus, a worker sends a result
that is too large only because of a defect. On the full tier, a result that is too large makes the statement of the caller fail.

<details>
<summary>Reference: tier probe, combined completion, and cohorts</summary>

**Tier probe.** A worker probes a queue with a fast claim through `complete_many_and_claim_v1`. A
`P1007` answer marks the queue full-tier for 30 seconds. The worker then claims through
`claim_many_v1` until the next probe.

| SDK        | Probe interval constant        |
| ---------- | ------------------------------ |
| TypeScript | `TIER_PROBE_INTERVAL_MS`       |
| Python     | `_TIER_PROBE_INTERVAL_SECONDS` |
| Go         | `fastTierProbeInterval`        |
| Rust, Ruby | `TIER_PROBE_INTERVAL`          |

**Combined completion.** `complete_many_and_claim_v1` completes up to 100 tasks and claims up to
`p_limit` more from one fast-tier queue. `p_limit` is 0 to 100. `p_lease_ms` is 100 to 86,400,000,
with a default of 30,000. The combined claim of a worker asks for its free slots plus one. A
`batched completion` rejection sends the worker back to `complete_v1`.

**Oversized results.** `fast_complete_many_v1` passes each result larger than the
`result_max_bytes` of its row to `fast_fail_v1` with a `TaskValueSizeLimitError` error. It then
reads the clock again, completes the rest of the batch whose leases are still live, and the
combined claim still runs. On the full tier, `complete_v1` raises for an oversized result, and the
statement or transaction of the caller rolls back. The TypeScript, Go, Python, Ruby, and Rust
workers measure results before they call, so they reach this path only through a bug.

**Cohorts.** Without an explicit count, `defaultDispatchCohorts(concurrency, spareConnections)`
gives:

- 1 below concurrency 8;
- otherwise `ceil(concurrency / 8)`, clamped to 2 through 8;
- then capped at the spare connections, and never below 1.

Spare connections are the pool size minus the pooled connections that the worker keeps for its
listener and its heartbeats. Each SDK reads its own pool settings. In TypeScript, pools of 3, 4, 6,
and 10 connections give a concurrency-64 worker 1, 2, 4, and 8 cohorts.

| SDK        | Option                   | Rule                                           |
| ---------- | ------------------------ | ---------------------------------------------- |
| TypeScript | `WorkerOptions.cohorts`  | 1 through `concurrency`                        |
| Python     | `Worker(cohorts=...)`    | 1 through `concurrency`                        |
| Go         | `WorkerOptions.Cohorts`  | 1 through `Concurrency`; 0 selects the default |
| Rust       | `WorkerOptions::cohorts` | `Option<usize>`, 1 through `concurrency`       |
| Ruby       | `Worker.new(cohorts:)`   | 1 through `concurrency`                        |

An explicit count is never capped.

More detail: [Fast tier: Workers on a fast-tier queue](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#workers-on-a-fast-tier-queue), [Fast tier: `complete_many_and_claim_v1`](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#complete_many_and_claim_v1), and [Fast tier: Oversized results](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#oversized-results).

</details>

## Record history for a fast-tier queue

By default, a fast-tier queue writes no attempt history and no claim events. The dashboard still
shows each fast-tier task. It makes the timeline and the attempt list from the runtime row and the
outcome row. But it cannot show the records that the tier did not write.

**Example.** The task `welcome-17` fails twelve times and then succeeds. An operator opens the task
in the dashboard.

1. The list of recent errors keeps only ten entries. Workhorse removed the two oldest entries and
   counted them.
2. The attempt list shows the last ten failed attempts and the final attempt.
3. The timeline shows a claim event only for the final attempt.

Two switches add these records for one queue. Set them with `Admin.setQueueHistory`:

```ts
await admin.setQueueHistory("emails", { recordAttempts: true, recordClaims: false });
```

- `recordAttempts` writes an `attempt_history` row for each closed attempt. The row replaces the
  entry in the list of recent errors.
- `recordClaims` writes a `claimed` event for each claim.

From a shell, `workhorse admin set-history` sets the same switches. The Queues page of the dashboard
shows the history that each queue records.

Each switch adds back a part of the cost that the tier removes. Keep the switches off by default.
Set a switch only when you need its records.

<details>
<summary>Reference: history switches</summary>

| Switch           | Column            | Default | Writes                                                                              |
| ---------------- | ----------------- | ------- | ----------------------------------------------------------------------------------- |
| `recordAttempts` | `record_attempts` | `false` | One `attempt_history` row per closed attempt; `started_at` = `claimed_at`           |
| `recordClaims`   | `record_claims`   | `false` | One `claimed` `task_event` per claim, with `worker_id`, `fence_token`, `expires_at` |

- `set_queue_history_v1(p_queue_name, p_record_attempts, p_record_claims)` sets the switches. A null
  argument keeps the current value.
- The function does not check the tier. The settings take effect when the queue is fast-tier.
- A change applies to claims and completions that start after it commits.
- TypeScript `Admin.setQueueHistory(queueName, settings)`, Python `Admin.set_queue_history`, Go
  `Admin.SetQueueHistory`, and Rust `set_queue_history` wrap it.
- The CLI command is `workhorse admin set-history <queue>` with `--record-attempts <on|off>` and
  `--record-claims <on|off>`. An omitted flag keeps its setting.

**Derived dashboard rows.** `dashboard_attempt_history_v1` derives one row per `errors` entry and
one for the final attempt. `dashboard_task_event_v1` derives an `enqueued` event, a `claimed` event
unless a recorded one exists, and a terminal event named `COALESCE(closed_as, state)`.

More detail: [Fast tier: Changing the history switches](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#changing-the-history-switches) and [Fast tier: Fast read models](https://github.com/stablemates/workhorse/blob/main/docs/architecture/fast-tier.md#fast-read-models).

</details>

## What this means for you

- Choose the fast tier for a high-volume queue whose handlers never wait.
- Make sure that the queue is empty before you change its tier.
- Expect `FastTierUnsupportedError` when code asks a fast-tier queue for a feature that it does not
  have. In Ruby, a name that is not valid raises `ArgumentError` first.
- Set the history switches only for the records that you need.
