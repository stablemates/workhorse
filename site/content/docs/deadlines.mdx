---
title: Deadlines and timeouts
description: End a whole task at a fixed time with a deadline, or end one attempt with an execution timeout.
---

A task can take too long in two different ways, and Workhorse gives a different limit for each. A
deadline ends the whole task at a fixed time. An execution timeout ends one attempt that runs too
long. If you use the wrong limit, the task can stop too early or run after it is useful.

## Stop a task at a fixed time

**Example.** A `price.quote` task calculates the price of a quote. The quote expires at 20:00. Your
app enqueues the task at 18:00 with a deadline of 20:00 and an exponential retry policy.

1. At 18:00, attempt 1 fails because the pricing provider is down. Workhorse schedules attempt 2.
2. Until 19:40, attempts 2 and 3 fail. Each wait is longer than the wait before it, so attempt 4
   waits until 20:05.
3. At 20:00, the deadline passes. The task is `scheduled`, and no worker holds it.
4. Soon after 20:00, the maintenance of a worker finds the passed deadline. Workhorse ends the task
   as failed, and attempt 4 does not start.

Thus, a deadline ends the task even if the attempt budget has attempts left.

To set a deadline, give `deadline` when you enqueue the task. The deadline is a time, not a
duration.

<Tabs items={["TypeScript", "Python", "Go", "Rust", "Ruby"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.enqueue("price.quote", { quoteId }, { deadline: quoteExpiresAt });
    ```
  </Tab>
  <Tab value="Python">
    ```python
    queue.enqueue(
        "price.quote",
        {"quoteId": quote_id},
        EnqueueOptions(deadline=quote_expires_at),
    )
    ```
  </Tab>
  <Tab value="Go">
    ```go
    _, err := queue.Enqueue(ctx, "price.quote", map[string]any{
    	"quoteId": quoteID,
    }, workhorse.EnqueueOptions{Deadline: &quoteExpiresAt})
    ```
  </Tab>
  <Tab value="Rust">
    ```rust
    queue
        .enqueue(
            "price.quote",
            &json!({ "quoteId": quote_id }),
            EnqueueOptions { deadline: Some(quote_expires_at), ..Default::default() },
        )
        .await?;
    ```
  </Tab>
  <Tab value="Ruby">
    ```ruby
    queue.enqueue("price.quote", {"quoteId" => quote_id}, deadline: quote_expires_at)
    ```
  </Tab>
</Tabs>

The time to the deadline continues to pass while the task is pending, retrying, in a durable wait,
or running. After the deadline, PostgreSQL does not let a worker claim the task. Workhorse ends the
task as failed and starts no new attempt. A retry of expired work only makes the failure later.

If a handler runs when the deadline passes, the worker aborts `ctx.signal`. Then the task ends as
failed. If a cancellation request came first, the task ends as canceled.

Use a deadline for work that is not useful after a time. Examples are a reminder for an event, a
price quote that expires, and a batch that must finish before a cutoff.

If you [redrive](/docs/dead-letters) a failed task, the new task has no deadline. Workhorse does not
copy the old deadline, because it is in the past. A copy makes the new task fail at once.

<details>
<summary>Reference: deadline</summary>

| SDK        | Option                          | Rule                        |
| ---------- | ------------------------------- | --------------------------- |
| TypeScript | `EnqueueOptions.deadline: Date` | A finite absolute timestamp |
| Python     | `deadline: datetime`            | A finite absolute timestamp |
| Go         | `EnqueueOptions.Deadline`       | A finite absolute timestamp |
| Rust       | `EnqueueOptions.deadline`       | A finite absolute timestamp |
| Ruby       | `deadline:`                     | A finite absolute timestamp |

The deadline is optional. Workhorse stores it as `deadline_at`.

| Where the task is                  | What settles a passed deadline                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- |
| Enqueued with a past deadline      | `enqueue_batch_v1` settles it in the same call.                                                 |
| `ready`, `scheduled`, or `blocked` | Claim skips it. `recover_expired_v1`, from each worker's `tick_v1`, settles a bounded batch.    |
| `active`                           | The owning worker's local timer calls `expire_owned_v1`. Heartbeats return `deadline_exceeded`. |

`terminalize_deadline_v1` writes:

- a `failed` outcome with a deadline error envelope;
- a `deadline_exceeded` attempt-history row, only when an attempt had started;
- a `deadline_exceeded` event whose `started` field says whether an attempt had started.

If a cancellation was requested first, it writes a `canceled` outcome instead, with event
`source = deadline_reaper`.

`redrive_v1` clears the old absolute deadline.

More detail: [Task lifecycle: Deadlines and execution timeouts](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#deadlines-and-execution-timeouts) and [Data model: redrive_v1](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#redrive_v1).

</details>

## Stop one attempt that runs too long

**Example.** A `report.build` task builds a report. It has an execution timeout of 2 min.

1. At 0 s, a worker claims the task. The handler calls a reporting service, and the call does not
   return.
2. At 2 min, the attempt has used its full budget. PostgreSQL closes attempt 1 as timed out.
3. Attempt 1 was below the attempt budget, so PostgreSQL uses the normal
   [retry rules](/docs/retries) and schedules attempt 2.
4. The worker aborts the signal of the handler.
5. Attempt 2 starts with a full budget of 2 min.

Thus, a timeout ends one attempt, and the task can continue with a new attempt.

To set the timeout, give `executionTimeoutMs` when you enqueue the task. The timeout limits how long
the handler can run in one attempt. It does not set when the task must end. Use it if one attempt
must stop, but a later attempt can succeed. For example, an HTTP call stops responding.

<Tabs items={["TypeScript", "Python", "Go", "Rust", "Ruby"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.enqueue("report.build", { reportId }, {
      executionTimeoutMs: attemptTimeoutMs,
      maxAttempts: attemptBudget,
    });
    ```
  </Tab>
  <Tab value="Python">
    ```python

        "report.build",
        {"reportId": report_id},
        EnqueueOptions(
            execution_timeout_ms=attempt_timeout_ms,
            max_attempts=attempt_budget,
        ),
    )
    ```
  </Tab>
  <Tab value="Go">
    ```go

    	"reportId": reportID,
    }, workhorse.EnqueueOptions{
    	ExecutionTimeoutMS: attemptTimeout,
    	MaxAttempts:        attemptBudget,
    })
    ```
  </Tab>
  <Tab value="Rust">
    ```rust

                execution_timeout_ms: Some(attempt_timeout_ms),

    ```
  </Tab>
  <Tab value="Ruby">

  </Tab>
</Tabs>

Only the time that the handler runs uses the budget. If a handler runs for 1 min and then sleeps for
a day in a [durable wait](/docs/durable-execution), the wait releases the lease. Then no worker
holds the task, and the time does not count. After the wait, the same attempt has 1 min of budget
left.

When the budget is used, Workhorse closes the attempt as timed out and applies the retry rules. If
attempts are left, the task gets another attempt. If not, the task fails. Thus, a timeout usually
starts another attempt, but a deadline always ends the task. The history of the task shows a timeout
differently from a thrown error. Thus, an operator can see if a handler was slow or broken.

<details>
<summary>Reference: execution timeout</summary>

| SDK        | Option                              | Rule                                   |
| ---------- | ----------------------------------- | -------------------------------------- |
| TypeScript | `EnqueueOptions.executionTimeoutMs` | An integer from 1 to 31,536,000,000 ms |
| Python     | `execution_timeout_ms`              | An integer from 1 to 31,536,000,000 ms |
| Go         | `EnqueueOptions.ExecutionTimeoutMS` | The same budget                        |
| Rust       | `execution_timeout_ms`              | The same budget                        |
| Ruby       | `execution_timeout:`                | The same budget, in seconds            |

The timeout is optional.

**Accounting**

- Each claim sets `attempt_timeout_at` to the claim time plus `execution_timeout_ms` minus
  `execution_used_ms`.
- A timer wait, a signal wait, a child suspension, or an owned release adds the active time to
  `execution_used_ms`. It clears `attempt_timeout_at`.
- A retry resets `execution_used_ms` to zero.

**`timeout_owned_v1`**

- It writes a `timeout` attempt-history row and an `execution_timed_out` event. The event names
  the next state.
- With attempts left, `retry_delay_v1` selects the delay. With no policy, the delay is 0.
- With no attempts left, it writes a `failed` outcome.
- A pending cancellation request wins. The function then changes nothing.

When the deadline and the timeout have both passed, the earlier one settles the attempt. On a tie,
the deadline wins.

More detail: [Task lifecycle: Deadlines and execution timeouts](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#deadlines-and-execution-timeouts) and [Data model: Retry delay selection](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#retry-delay-selection).

</details>

## Use a deadline and a timeout together

You can set the two limits on the same task. Each attempt then has its own execution budget, and the
whole task ends at the deadline. The deadline applies even if attempts are left.

Set `deadline` with `executionTimeoutMs` in TypeScript. Set `deadline` with `execution_timeout_ms`
in Python or Rust. Set `Deadline` with `ExecutionTimeoutMS` in Go. Set `deadline:` with
`execution_timeout:` in Ruby. The Ruby timeout is in seconds.

## Keep each handler short

**Example.** An attempt of the `report.build` task waits for a call that does not return.

1. At 30 s, a rolling deploy stops the worker process. The worker claims no new tasks and waits for
   its running handlers.
2. The drain period ends, and the handler still waits for the call.
3. The process exits, and the handler stops with it.
4. Later, the lease of the attempt expires, and recovery returns the task.

Thus, a handler that runs longer than the drain period ends without a result, and recovery must
return its task. The drain period is the time that a stopping worker process waits for its running
handlers. When a worker process stops, it does not cancel a task or create a deadline or a timeout.

Make each handler end well before the drain period of your deployment ends. For long work, do not
set a longer timeout. Divide the work into idempotent stages, with a
[checkpoint](/docs/durable-execution) after each stage. Use a durable wait where the handler only
waits. Then each short stage can start again without the stages before it.

<details>
<summary>Reference: handler duration</summary>

- Ordinary handlers should complete within 110 seconds. That leaves rolling deployments practical
  drain headroom.
- The recommendation is not a database limit, because deployment grace periods vary.
- On the first `SIGINT` or `SIGTERM`, a worker process stops claiming. Active handlers and their
  heartbeats continue.
- Process termination does not create a durable cancellation or abort a handler.
- `shutdownTimeoutMs` bounds that drain. The default is 25,000 ms. A missed deadline exits the
  process with code 1.
- Hard termination leaves active leases for ordinary expiry recovery.
- Set execution timeouts deliberately rather than relying on an unbounded handler.

More detail: [Task lifecycle: Deadlines and execution timeouts](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#deadlines-and-execution-timeouts), [Operations and CLI: Graceful shutdown](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#graceful-shutdown), and [Operations and CLI: Shutdown deadline and failure](https://github.com/stablemates/workhorse/blob/main/docs/architecture/operations.md#shutdown-deadline-and-failure).

</details>

## Know what a handler does after a timeout

**Example.** The handler of the `report.build` task waits for a call that does not return.
The attempt has an execution timeout of 2 min.

1. At 2 min, the local timer of the worker calls `expire_owned_v1` with the worker ID and the fence
   token.
2. PostgreSQL closes the attempt and schedules the retry in the same call. It does not wait for the
   lease to expire.
3. The worker aborts `ctx.signal`. Cancellation uses the same signal with a different reason.
4. At 3 min, the call returns, and the handler tries to complete the task. The attempt is already
   closed, so Workhorse refuses the completion.

Thus, a limit does not stop JavaScript code. The worker asks PostgreSQL to close the attempt, and
then it aborts the signal of the handler. If PostgreSQL answers that the limit is not yet due, the
handler continues, and the worker asks again later.

If the handler does not obey the signal, its code can continue. But the fence token of the attempt
is no longer current, so Workhorse refuses each later write of the handler. Heartbeats and
maintenance close the attempt if the process or the timer cannot do it. For the signal, see
[cancellation](/docs/cancellation).

<details>
<summary>Reference: local timers and abort reasons</summary>

The worker sets one local timer at the earlier of `deadline_at` and `attempt_timeout_at`.

| Boundary          | Abort reason (TypeScript)                | `expire_owned_v1` status |
| ----------------- | ---------------------------------------- | ------------------------ |
| Deadline          | `DeadlineExceededError(taskId)`          | `deadline_exceeded`      |
| Execution timeout | `ExecutionTimeoutError(taskId, attempt)` | `timeout_exceeded`       |

`expire_owned_v1(p_task_id, p_worker_id, p_fence_token)` returns one of `not_due`,
`cancel_requested`, `deadline_exceeded`, `timeout_exceeded`, or `stale`. After `not_due`, the
handler keeps running under its lease, and the worker asks again.

- The completed transition fences every late completion, failure, heartbeat, checkpoint, or wait
  write.
- Heartbeats and bounded maintenance remain fallbacks for process loss and races.
- Races between cancellation, completion, deadline, timeout, and lease expiry are row-lock ordered.
  The first transaction to commit wins.

More detail: [Task lifecycle: Local timers](https://github.com/stablemates/workhorse/blob/main/docs/architecture/lifecycle.md#local-timers).

</details>
