---
title: Schedules
description: Synchronize named cron definitions during deployment and let any matching worker fire them safely.
---

Some work runs on a clock: a nightly report, an hourly sync, a weekly cleanup. The usual costs are
a separate scheduler process to deploy and keep alive, and a duplicate-firing problem the moment
you run more than one of them. Workhorse has neither. Schedules are cron definitions stored and
evaluated in PostgreSQL, declared by your deployment, and offered by the workers you already run.
Any number can offer the same namespace while PostgreSQL still creates exactly one task.

## Synchronize the namespace

Call `queue.syncSchedules` during deployment with every definition the namespace should contain.
It is a desired-state call, like a migration: definitions you list are created or updated, and
with pruning enabled — the default — definitions you dropped from the list are disabled.

<Tabs items={["TypeScript", "Python", "Go"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.syncSchedules("billing-production", [{
      name: "invoice-run",
      schedule: nightlyCron,
      timezone: "America/New_York",
      task: { type: "invoice.generate", queue: "billing", payload: { scope: "due" } },
    }]);
    ```
  </Tab>
  <Tab value="Python">
    ```python
    queue.sync_schedules(
        "billing-production",
        [ScheduleDefinition(
            name="invoice-run",
            schedule=nightly_cron,
            timezone="America/New_York",
            task=ScheduledTask(
                type="invoice.generate", queue="billing", payload={"scope": "due"}
            ),
        )],
    )
    ```
  </Tab>
  <Tab value="Go">
    ```go
    err := queue.SyncSchedules(ctx, "billing-production", []workhorse.ScheduleDefinition{{
    	Name: "invoice-run", Schedule: nightlyCron, Timezone: "America/New_York",
    	Task: workhorse.ScheduledTask{
    		Type: "invoice.generate", Queue: "billing", Payload: map[string]any{"scope": "due"},
    	},
    }}, workhorse.SyncSchedulesOptions{Prune: true})
    ```
  </Tab>
</Tabs>

Disabled, not deleted: the old definition stays, so tasks it fired in the past still have something
to point at.

Each `ScheduleDefinition` names the occurrence (`name`, `schedule`, optional `timezone` and `enabled`) and
describes the task every occurrence creates — its `type`, `payload`, and optionally `queue`,
`concurrencyKey`, `maxAttempts`, and `retryPolicy`.

The namespace keeps one service's schedules apart from another's, so two deployments sharing a
database cannot prune each other's definitions. Cron validation happens before the write; one
invalid expression fails the call rather than leaving a partial deployment. Pass
`{ prune: false }` only when you deliberately want an additive update — the normal deployment path
supplies the complete namespace so code remains the owner of intent.

`ScheduleDefinition.enabled` records deployment intent. The dashboard's Pause action records a
separate durable operator override, so a later deployment cannot silently resume incident-paused
work. The pause survives definition updates, removal, and re-addition until an operator chooses
Resume. The Schedules page labels definitions disabled by code as **Config off**, separately from
operator-paused definitions.

## Let workers offer schedule namespaces

There is no scheduler process and no PostgreSQL extension. A `Worker` offers the namespaces listed
in `WorkerOptions.scheduleNamespaces` as part of its normal maintenance cadence. PostgreSQL then
evaluates and fires each due definition through `fire_due_schedules_v2`, so every SDK uses one
parser and one stored IANA timezone.

<Tabs items={["TypeScript", "Python", "Go"]}>
  <Tab value="TypeScript">
    ```ts
    const worker = new Worker(queue, { scheduleNamespaces: ["billing-production"] });
    ```
  </Tab>
  <Tab value="Python">
    ```python
    worker = Worker(pool, schedule_namespaces=["billing-production"])
    ```
  </Tab>
  <Tab value="Go">
    ```go
    worker, err := workhorse.NewWorker(pool, workhorse.WorkerOptions{
    	ScheduleNamespaces: []string{"billing-production"},
    })
    ```
  </Tab>
</Tabs>

A worker with an empty list fires nothing. Point at least one worker at each namespace you
synchronize, or its schedules sit idle.

Workers offer namespaces rather than private schedule copies. PostgreSQL stores the current
definitions, so workers that offer the same namespace evaluate the same desired state. The
Schedules page reports how many live workers offer each namespace.
Open an application schedule's run count to view tasks of that type in a new browser tab.

The page also lists Workhorse maintenance beside application schedules. Maintenance runs directly
in PostgreSQL instead of creating a task, and its last-run value records that direct execution.
Expand a maintenance row to inspect recent outcomes, durations, affected rows, phase timings, and
errors. The row reports the retained total while the expanded history identifies its recent subset.
It also states that Workhorse samples successful task-changing ticks and records tick errors
immediately. Workhorse records every eligible slow-routine execution.

The synchronous Python `Worker` provides the same participation through `schedule_namespaces` and
`schedule_catchup_limit`. Go uses `WorkerOptions.ScheduleNamespaces` and
`WorkerOptions.ScheduleCatchupLimit`. Every runtime offers its configured namespaces on the
maintenance cadence. PostgreSQL coordinates each namespace, so workers with different namespace
sets do not depend on the same maintenance-tick winner.

## Why competing workers create one task

Several workers notice the same occurrence is due. Each firing writes a durable key built from
the namespace, schedule name, and planned occurrence time. The first worker claims the key; every
other call converges on the task that already exists. No leader election, no single scheduler — any
number of workers can race and the outcome is one task.

Rolling deployments are covered the same way. Every definition carries a revision that increments
on change. PostgreSQL reads that revision while evaluating the namespace, then requires the same
revision when it reserves the occurrence. If a deployment changes or disables the definition
between those operations, the fire becomes a no-op.

Evaluation runs on PostgreSQL's clock rather than each worker's, so a worker whose clock drifts
neither fires early nor moves a schedule's position backwards. When another transaction already
holds an occurrence, Workhorse defers that occurrence and everything after it to the next tick
instead of stepping over it, so a manual fire that rolls back loses no occurrence.

If the whole fleet is down, nothing fires. Workhorse skips missed occurrences by default when
workers return. Set `catchupPolicy` to `latest` when one current task can replace the missed work,
or to `all` when every occurrence must create a task. The worker's catch-up limit bounds each
`all` pass, and later passes continue until the schedule catches up. Schedules provide durable
recurring work, not hard real-time alarms; prefer UTC unless the schedule follows local civil time. If local clocks skip a scheduled time, Workhorse fires after
the clock advances. If clocks repeat a time, Workhorse fires its first occurrence only. Hashed `H`
fields choose a stable offset across TypeScript, Python, and Go workers, so every runtime fires the
same occurrence. If several cron fields land on one instant, Workhorse creates one occurrence.

## What happens after firing

The occurrence creates an ordinary task with the definition's queue, payload, attempt budget, and
retry policy. From there the usual rules apply — at-least-once delivery, retries, cancellation.
Canceling one fired task does not pause its definition; tomorrow's occurrence still runs. Use the
dashboard to pause future occurrences, or change `ScheduleDefinition.enabled` and synchronize the
namespace when the deployment should own the change.

Three related calls round out the API:

- `Admin.schedules` reads stored definitions and their last occurrence, for operator
  tools.
- `Admin.runTaskNow` releases one scheduled task immediately with the actor, reason,
  and request identity used by operator controls.
- `Queue.fireSchedule` exposes the revision-fenced firing
  operation itself, for tests and controlled integrations.
