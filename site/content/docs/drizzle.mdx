The `@stablemates/workhorse-drizzle` package connects Workhorse to Drizzle ORM on node-postgres.
With it, your application enqueues a task in the same transaction as its Drizzle writes. The row and
the task then commit together, or neither commits.

This prevents two errors. Without a shared transaction, a task can exist for a row that rolled back.
Also, a row can commit and its task can be lost, and no error shows this. Drizzle owns your tables.
Workhorse owns its own schema and its versioned SQL functions.

## Create the adapter

Install the integration together with the Drizzle and node-postgres packages that your application
uses.

```bash
pnpm add @stablemates/workhorse-drizzle drizzle-orm pg
```

Give the Drizzle database to `createDrizzleAdapter`.

```ts
import { createDrizzleAdapter } from "@stablemates/workhorse-drizzle";
import { Pool } from "@stablemates/workhorse";
import { drizzle } from "drizzle-orm/node-postgres";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const db = drizzle({ client: pool });

const workhorse = createDrizzleAdapter(db, {
  close: () => pool.end(),
});
```

The adapter is a `WorkhorseAdapter`. It has `database`, `queue`, `admin`, `forTransaction`,
`adminForTransaction`, `createWorker`, and `close`. Your request handlers, operator tools, and
worker processes use this one adapter. The core package of Workhorse does not depend on Drizzle.

## Enqueue a task in a Drizzle transaction

Call `forTransaction` with the transaction object that Drizzle gives to your callback. The queue
that it returns sends its SQL through that transaction. Thus the task commits or rolls back with
your Drizzle writes.

```ts
await db.transaction(async (tx) => {
  await tx.insert(account).values({ id: accountId, email });
  await workhorse.forTransaction(tx).enqueue("account.created", {
    accountId,
  });
});
```

If the callback throws an error, Drizzle rolls back the account and the task. Other connections do
not see the account or the task before the commit.

To enqueue a task that is not part of a transaction, use `workhorse.queue`. This queue does not join
the transaction of the caller.

## Keep the transaction queue inside the callback

Drizzle does not tell the adapter when a transaction ends. Thus a queue from `forTransaction(tx)`
does not fail after the transaction. It continues to use the connection that the transaction used.

**Example.** A callback keeps its transaction queue in a variable after the callback returns.

1. The callback enqueues a task through `workhorse.forTransaction(tx)`, and Drizzle commits.
2. Drizzle returns the connection to the pool.
3. Another request starts a Drizzle transaction on the same connection.
4. Your code enqueues a task through the kept queue. The task joins the new transaction.
5. The new transaction rolls back, so the task of step 4 is lost.

Use the queue from `forTransaction(tx)` only inside the callback. If no other transaction uses the
connection, an enqueue through a kept queue commits by itself.

## Create workers from the same adapter

`workhorse.createWorker` uses the default queue and the database connection of the adapter. Thus a
worker process does not need a second configuration.

```ts
const worker = workhorse.createWorker();
worker.handle("account.created", handleAccountCreated);
await worker.run();
```

The worker takes its heartbeat connection and its listen connection from the node-postgres pool of
Drizzle. A listen connection waits for notifications about new tasks.

<details>
<summary>Reference: worker connections</summary>

- `createDrizzleAdapter` finds the node-postgres pool through `$client` of the Drizzle database.
- `DrizzleAdapterOptions` has no `pool` option.
- A dedicated heartbeat connection needs a pool of at least 3 connections. If the pool is smaller,
  the worker does not start unless you set `sharedHeartbeats`.

More detail: [Overview: ORM adapters](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#orm-adapters),
[Overview: Connection budgets per language](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#connection-budgets-per-language).

</details>

## Build a queue without the adapter

If you need your own `Queue` but not the adapter, use `drizzleQueryable`. It converts a Drizzle
database or transaction into the `Queryable` interface of the core package. A `Queue` accepts this
interface.

## Handle database errors

If a database statement fails, the adapter throws `DrizzleQueryError`. The error keeps the SQL
statement, the PostgreSQL error code if there is one, and the original error.

Typed Workhorse conflicts keep their core error classes. Examples are idempotency, checkpoint, and
wait conflicts. Thus your code does not need to unwrap them.

<details>
<summary>Reference: errors and statements</summary>

| `DrizzleQueryError` field | Content                                                |
| ------------------------- | ------------------------------------------------------ |
| `statement`               | The SQL statement.                                     |
| `code`                    | The SQLSTATE that PostgreSQL reported, or `undefined`. |
| `cause`                   | The original error.                                    |

- `DrizzleQueryError` extends `QueryError`.
- `drizzleQueryable` rebuilds each statement as a Drizzle `SQL` value. A `$N` with no matching value
  raises `RangeError`, not `DrizzleQueryError`.

More detail: [Overview: What an adapter must guarantee](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#what-an-adapter-must-guarantee),
[Overview: Drizzle queryable](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#drizzle-queryable).

</details>

## Close the pool that the adapter owns

The adapter does not close the resources of the caller unless you give a `close` callback. Give
this callback only when the adapter owns the pool. `adapter.close` can run when the process stops or
when startup fails. If your application created the pool for other work, close the pool yourself.

## Install the Workhorse schema with the Workhorse tools

Install the Workhorse schema with the deployment tools of the core package. Do not let Drizzle
generate or migrate the Workhorse SQL functions. The Workhorse schema is a versioned protocol, not a
set of application tables. Workhorse is not part of your Drizzle migration graph.
