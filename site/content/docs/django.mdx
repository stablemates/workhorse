When a request changes business data, its task must commit and roll back with that data. Workhorse
can enqueue through the connection that Django already uses inside
`transaction.atomic(using=alias)`. Then Django commits both writes together, or rolls back both.

This page is a maintained recipe. It uses the optional `workhorse.django` module, not the Django
Tasks interface. Requests enqueue tasks, and [separate worker processes](/docs/worker-processes) run
the handlers. For decorated tasks, use the bounded [Django Tasks backend](/docs/django-tasks).

## Install Django with Psycopg 3

The recipe requires the `django.db.backends.postgresql` backend of Django with Psycopg 3. If your
project uses psycopg2, it cannot give its connection to `Queue`.

In your Django environment, install the tested framework and driver:

```sh
pip install 'Django==6.1.1' 'psycopg[binary]==3.3.6' 'stablemates-workhorse[django]'
```

Then set up the database:

1. Configure a database alias, such as `business`, in the `DATABASES` setting of Django.
2. Install the [Workhorse schema](/docs/installation) in that same PostgreSQL database. Use the
   schema commands of Workhorse, outside request handling.

Django continues to own the migrations of your application.

## Enqueue a task inside the atomic block

Call `enqueue_in_atomic` from the `workhorse.django` module inside the atomic block. The helper
requires an explicit `using` alias. It returns an `EnqueueResult`. The maintained recipe is in
`python/examples/django_enqueue.py`.

```python
from django.db import connections, transaction

from workhorse.django import enqueue_in_atomic

alias = "business"
with transaction.atomic(using=alias):
    with connections[alias].cursor() as cursor:
        cursor.execute(
            "INSERT INTO django_orders (id, note) VALUES (%s, %s)",
            [order_id, "accepted"],
        )
    result = enqueue_in_atomic("order.fulfill", {"order_id": order_id}, using=alias)
```

The helper makes `Queue(connections[alias].connection)` for this one enqueue. It does not open a
different connection, and it does not keep the queue. Django owns the commit, the rollback, the
savepoints, autocommit, thread affinity, and the close of the connection. Django also returns the
connection to a pool, if one exists.

Do not change the lifecycle of the borrowed connection:

- Do not enter the context manager of the connection.
- Do not call its lifecycle methods.
- Do not keep a queue for more than one request or more than one atomic block.

The enqueue can be the first statement of the transaction. Until the outer transaction commits, a
different connection cannot see the business row or its task. If an inner savepoint rolls back,
PostgreSQL removes the writes of that savepoint. The earlier writes of the outer transaction stay.
A savepoint release does not commit.

**Example.** A request accepts order 7 and enqueues its task. Then a later statement fails.

1. The request opens `transaction.atomic(using="business")`.
2. The request inserts order 7 and calls `enqueue_in_atomic`. It gets an `EnqueueResult` with a
   task ID.
3. A later statement in the block raises an error.
4. Django rolls back the transaction. PostgreSQL removes the order row and the task.
5. The task ID from step 2 now identifies no task.

An `EnqueueResult` shows that Workhorse accepted the task in the current transaction. It does not
show that the transaction committed. If Django rolls back, the task ID becomes unusable.

If you replay an idempotent enqueue, you get the original task ID and the original outcome. If the
replay has a different payload, Workhorse raises `EnqueueIdempotencyConflictError`.

<details>
<summary>Reference: what `enqueue_in_atomic` checks</summary>

`enqueue_in_atomic(task_type, payload, *, using, options=None)` checks these conditions in this
order, then calls `Queue(connection).enqueue_with_result`:

1. `validate_thread_sharing()` passes for the Django connection.
2. The connection is in an atomic block, and autocommit is off. If not, it raises
   `TransactionManagementError`.
3. The raw connection is a `psycopg.Connection`. If not, it raises `TypeError`.
4. The connection is open, and it did not close in the transaction. If not, it raises
   `TransactionManagementError`.
5. `validate_no_broken_transaction()` passes.

More detail: [ADR 0087: Keep the Django Tasks backend bounded by atomic acceptance](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0087-bounded-django-tasks-backend.md).

</details>

## Use the same alias for all writes

The guarantee applies only to writes on the connection of the selected alias. Thus each business
write must select the same alias as the enqueue:

- For an ORM model, use `Order.objects.using(alias).create(...)`.
- For SQL, use `connections[alias].cursor()`.

A second connection to the same database does not join the transaction.

`enqueue_in_atomic()` rejects a call outside `transaction.atomic(using=alias)`. It also rejects a
call where you turned off autocommit manually without an atomic block. An atomic block on a
different alias does not permit the enqueue. The helper also rejects a broken or closed atomic
connection. It does not repair or open the connection again.

An ordinary `Queue` can enqueue in autocommit mode, but this recipe does not do that. A business
write that already committed cannot roll back with a later standalone enqueue.

## Catch errors outside the atomic block

Workhorse runs its SQL through the raw Psycopg connection, not through the cursor wrapper of
Django. Thus an unexpected database error stays a Psycopg exception, not a Django exception. A known
protocol rejection of Workhorse keeps its structured error class and its original database cause.

1. Let the error leave the atomic block.
2. Catch the error outside that block, so that Django can roll back.
3. To keep the earlier writes of the outer transaction, catch the error outside an inner atomic
   block.

Do not ignore a raw error and continue to query in a broken transaction. Raw execution does not use
the error bookkeeping of Django. Thus Django cannot do its usual checks for a broken transaction
there.

## Call the helper from async code

Keep the transaction synchronous. Wrap the **whole** synchronous function that writes the business
data and enqueues the task. Do not wrap its calls one by one.

```python
from asgiref.sync import sync_to_async

from application.django_enqueue import create_order

result = await sync_to_async(create_order, thread_sensitive=True)(order_id, using="business")
```

The runnable recipe also has `create_order_async()` with this boundary. Do not pass the Django
wrapper, the raw connection, or the queue to a different thread.

This is not an async transaction API, and it is not an `AsyncQueue` adapter. For ASGI requests,
follow the connection policy of Django. The helper does not close connections, and it does not
install request lifecycle hooks.

## Enqueue before the commit, not in `on_commit`

`transaction.on_commit()` runs a callback only after the business transaction commits. If the
enqueue then fails, the callback cannot roll back the business write. Thus `on_commit` controls the
sequence, but it does not make the task acceptance atomic. This recipe enqueues on the connection
of the transaction, before the commit.

## Use the recipe with `ATOMIC_REQUESTS` or several databases

With `ATOMIC_REQUESTS`, the request transaction of the selected alias can be the atomic block of
the enqueue. The explicit alias must still match. Middleware and the iteration of a streaming
response run outside that request transaction. Do not expect them to use it. In other cases, open
an explicit atomic block.

If you use several databases, the guarantee covers only the connection and the PostgreSQL
transaction of the selected alias. It does not cover writes on a different alias or on a separate
Workhorse database. Connect the worker for these tasks to the database of the selected alias.
Workhorse does not add a distributed transaction.

## Make the handlers safe to run again

Handlers run later, outside the request transaction. Their external effects still need
idempotency. This recipe does not give the result semantics of Django Tasks. It does not give
compatibility with the Celery API.

## Run and verify the recipe

To run the standalone example, do these steps:

1. Create this application table in the selected database:

   ```sql
   CREATE TABLE django_orders (id bigint PRIMARY KEY, note text NOT NULL);
   ```

2. Install the Workhorse schema in the same database.
3. Set `DJANGO_SETTINGS_MODULE` to the settings of your application.
4. Run the example from the checkout with an unused order ID:

   ```sh
   DJANGO_SETTINGS_MODULE=application.settings \
     python python/examples/django_enqueue.py --using business --order-id 1
   ```

To run the tests, run `pnpm python:test:django` from a configured repository checkout. The fixture
creates scratch databases from the test database of that checkout, and drops them after the tests.
It uses a real Django model, the runnable example, and an independent observer.

The Python CI job runs `pnpm python:test`. That command collects this full fixture with no
exclusions. CI runs the language suite one time for each change. `pnpm python:test:django` is the
focused local command, not a second CI run.
