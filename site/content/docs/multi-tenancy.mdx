---
title: Multi-tenancy
description: Run many tenants on Workhorse, with one database each or one shared database whose tasks carry the tenant.
---

A tenant is a customer, team, or account whose work you must keep fair and bounded, and sometimes
apart. Workhorse offers two ways to do that, and the difference is who enforces the boundary.

With **isolated tenancy**, each tenant has its own database, and PostgreSQL enforces the boundary.
With **shared tenancy**, tenants share one database, and every task carries its tenant as metadata
that the application keeps consistent. Pick isolated tenancy when a tenant's rows may not sit in
the same tables as another's. Pick shared tenancy when many tenants need fair share and per-tenant
limits rather than data separation.

## Isolated tenancy: one database per tenant

**Example.** Your product serves two hospitals, `north` and `south`. Their records may not share a
table, so each hospital gets its own database with the Workhorse schema installed.

1. **At setup** you install the schema into the `north` database and into the `south` database.
2. **At run time** one worker fleet points at `north`, and a second fleet points at `south`. Each
   worker binds to one database, so no worker ever sees both hospitals' tasks.
3. **On a deploy** you run `workhorse schema migrate` twice, once per database. Each database
   upgrades on its own.

Tasks, queues, schedules, policies, budgets, retention, and the dashboard are separate because the
databases are. Nothing in the schema has to know about tenants.

The cost is operational. Each tenant adds a schema upgrade per deploy and a fleet that holds its own
connections. Telemetry is separate too: the process resource attributes name the tenant, one fleet
at a time.

<details>
<summary>Reference: isolated tenancy</summary>

- PostgreSQL enforces the boundary between databases.
- Every table, policy, budget, schedule, retention window, and dashboard session is separate.
- Each database runs `workhorse schema migrate` independently.
- Each `Worker` binds to one database.
- In isolated tenancy the process resource attributes identify the tenant, one worker fleet at a
  time.

More detail: [Overview: Isolated tenancy](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#isolated-tenancy).

</details>

## Shared tenancy: the tenant rides on the task

Queue `reports` serves every customer in one database. The concurrency policy lets the queue run
forty reports at once, and at most four per tenant. Each tenant's budget caps its active work at
eight across every queue.

1. **At 09:00** tenant `acme` enqueues 60 monthly reports. Four start, and the other 56 wait.
   The other 36 slots stay free, because `acme` has used its four.
2. **At 09:01** tenant `globex` enqueues three reports. They start at once in the free slots. The
   claim passes over the waiting `acme` reports ahead of them.
3. **At 09:02** `acme` also enqueues exports on queue `exports`. Its budget, also named `acme`,
   counts its reports too. Four exports start, and the rest wait while `acme` is at its cap.
4. **At 09:05** an operator filters the dashboard task list by the tag `tenant:acme` and sees only
   `acme`'s work.

In a shared database the tenant is not a column. It is the same identifier written to three enqueue
options that Workhorse already enforces:

- `concurrencyKey` gives the tenant fair share inside a queue. A concurrency policy with
  `maxActivePerKey` caps how many of one tenant's tasks run at once, and a rate policy with `perKey`
  gives each tenant its own token bucket. See [concurrency policies](/docs/concurrency-policies)
  and [rate limits](/docs/rate-limits).
- `budget` caps one tenant's work across every queue. Synchronize one budget per tenant with
  `Queue.syncBudgets`, and each task names its tenant's budget.
- A `tenant:` tag makes the tenant filterable. Dead-letter listing, redrive filters, and the
  dashboard task list accept a tag filter, so an operator can see one tenant's work at a glance.

The claim passes over a tenant at its cap only within a bounded window of the oldest ready tasks.
If one tenant's waiting backlog fills that whole window, the claim reaches no other tenant's work.
[Avoid a blocked queue](/docs/concurrency-policies#keep-a-full-key-from-blocking-other-work) covers that case.

Go applications set `ConcurrencyKey`, `Budget`, and `Tags` on `EnqueueOptions` and synchronize
with `Queue.SyncBudgets`. Python applications set `concurrency_key`, `budget`, and `tags` and
synchronize with `Queue.sync_budgets` or `AsyncQueue.sync_budgets`. Rust applications set the same
snake_case fields and synchronize with `Queue::sync_budgets`. Ruby applications pass the same names
as keywords and synchronize with `Queue#sync_budgets`.

A queue groups work for dispatch, not tenants. Tenants share queues, and the key and budget keep
them fair. A queue per tenant works for a handful of tenants, but it multiplies health rows, worker
queue lists, and policy rows without adding any isolation.

A recurring schedule names its tenant through the `concurrencyKey` in its task definition. Schedule
definitions do not carry tags or a budget yet. A scheduled task therefore has fair share but no
cross-queue cap, until the handler enqueues follow-up work with the full set.

<details>
<summary>Reference: the three tenant fields</summary>

| Field                                    | Bounds                                    | Role                                                                                                |
| ---------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `task.concurrency_key`                   | 1 to 256 UTF-8 bytes, queue-scoped        | `concurrency_policy.max_active_per_key` and the `rate_limit_policy` per-key bucket give fair share. |
| `task.budget_name`                       | 1 to 256 UTF-8 bytes                      | One `budget` row per tenant caps that tenant's active tasks or start rate across every queue.       |
| One `tenant:<id>` element of `task.tags` | At most 20 tags, each 1 to 100 characters | `task_tags_gin_idx` serves the tag filters.                                                         |

**Tag filters**

| Read                                                                           | Match                     |
| ------------------------------------------------------------------------------ | ------------------------- |
| `list_dead_letters_v1` and `redrive_many_v1`, through `DeadLetterFilter.tags`  | Every supplied tag (`@>`) |
| `dashboard_tasks_v1`, `dashboard_tasks_cursor_v1`, and `dashboard_activity_v1` | Any selected tag (`&&`)   |

- The dashboard wire validator accepts at most 20 selected tags.
- `Admin.listTasks` has no tag filter.
- The claim inspects at most the first 100 ready rows of the queue, in priority, sequence, and
  task-identity order. A saturated key's rows stay in that window.
- `sync_budgets_v1` accepts at most 10,000 definitions per call. On the benchmark host, one budget
  per tenant cost about 130 microseconds per tenant to synchronize.
- `schedule_definition` keeps `concurrency_key` and carries neither tags nor a budget.
- `namespace` on schedules, policies, and budgets names the owning deployment, not a tenant.

More detail: [Overview: Shared tenancy](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#shared-tenancy).

## What shared tenancy does not do

Your app enqueues a task with `concurrencyKey: "acme"`, but a bug writes the tag `tenant:globex`.
Workhorse accepts the task. It counts the task against `acme`'s fair share, and an operator who
filters by `tenant:globex` sees it in `globex`'s list.

The boundary is a convention your application keeps. Nothing rejects a task whose key, tag, and
budget disagree.

Retention is per installation. Every tenant's history ages under the same windows. A tenant that
needs its own windows needs its own database.

Operator access is not tenant-scoped. An administrator sees every tenant's tasks, and an authorized
cancel, redrive, or purge acts on any task. A tag filter narrows a view; it does not enforce a
boundary. Workhorse does not yet scope operator access to a tenant. The
[limitations](/docs/limitations) page tracks that gap.

Metrics never carry the tenant. Queue and task type bound the cardinality of every counter and
histogram, and a tag or key would let tenant count multiply the series. A handler that wants the
tenant on its own spans reads it from the payload.

<details>
<summary>Reference: what shared tenancy does not scope</summary>

- No check compares a task's `concurrency_key`, `budget_name`, and tags.
- `retention_policy` is a singleton, so retention windows are per installation.
- No function scopes a read or an operator action to a tenant.
- Metric attributes never include a key or tag.
- Spans carry `workhorse.task.id` and `workhorse.task.type`, not the key or tags.
- [`docs/features.md`](https://github.com/stablemates/workhorse/blob/main/docs/features.md) records
  that tenant-scoped operator access is not supported.

More detail: [Overview: Shared tenancy](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#shared-tenancy).

</details>

## Dispatch cost does not grow with tenant count

Queue `reports` holds work for 100,000 tenants. The 40 tenants at the head of the queue are all at
their per-tenant cap.

1. A worker claims. Workhorse counts each head tenant's active tasks through a partial index on the
   key, so the count never scans other tenants' rows.
2. The claim passes over the saturated tenants' tasks inside a bounded window of ready tasks.
3. It admits the first task whose tenant has room.

A budget's active tasks are counted the same way, through a partial index on the budget name. So
admitting one task never scans the other tenants. The tenant cardinality benchmark loads one queue
with a widening ladder of tenant counts and shows claim latency flat across it.

<details>
<summary>Reference: admission cost and benchmark</summary>

- `claim_v1` counts one key through `task_runtime_active_queue_key_expiry_idx`.
- It counts one budget through `task_runtime_active_budget_expiry_idx`.
- When a per-key limit or budget passes over saturated work, the claim inspects at most 100 ready
  rows.

`pnpm benchmark:tenant-cardinality` loads one queue with 100 through 100,000 tenants. Each tenant
has a key, a tag, and optionally its own budget. The queue has 80 saturated rows at the head of the
window.

| Measurement                        | Across the ladder                                               |
| ---------------------------------- | --------------------------------------------------------------- |
| Median claim latency, no budgets   | 2.2 to 3.5 ms                                                   |
| Median claim latency, with budgets | 3.7 to 4.4 ms                                                   |
| One admission count                | Three buffer hits                                               |
| Dashboard task list by tag         | 1 ms to 94 ms. It tracks total rows, not tenants.               |
| `queue_health_v1`                  | 2.7 s at 200,000 ready rows. It tracks total rows, not tenants. |

The repository's benchmark analysis for 2026-09-16 records the full figures.

More detail: [Overview: Admission cost](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#admission-cost).

</details>
