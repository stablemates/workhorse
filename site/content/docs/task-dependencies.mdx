---
title: Task dependencies
description: Keep a dependent task blocked until its prerequisites reach a terminal state. Then release, cancel, or fail it.
---

Some work is correct only after other work finishes. For example, a notification about an import
must not go out before the import is complete. A task dependency keeps a task out of dispatch until
its prerequisites finish. A prerequisite is a task that must finish first. A dependent is the task
that waits.

## Run a task after another task succeeds

**Example.** Your app imports a contact list and then notifies the user. The notification must not
go out before the import is complete.

1. At 0 s, the app enqueues `contacts.import` and keeps its task ID. The import task is ready.
2. At 0 s, the app enqueues `contacts.notify` with the import as its prerequisite. The import is not
   complete, so the notification task is `blocked`. No worker can claim a blocked task.
3. At 1 s, a worker claims the import and runs it.
4. At 3 min, the import succeeds. In the same transaction, Workhorse resolves the edge with
   `release`. The notification has no other prerequisite, so Workhorse makes it ready.
5. Soon after, a worker sends the notification.

An edge is the link from one dependent to one prerequisite. To make a task wait, give
`EnqueueOptions.dependencies` when you enqueue the task.

<Tabs items={["TypeScript", "Python", "Go", "Rust", "Ruby"]}>

PostgreSQL checks both tasks and creates the dependency in the enqueue transaction. If the
transaction rolls back, neither the task nor its dependency exists.

If the import succeeded before step 2, Workhorse releases the edge immediately. The notification is
not `blocked`. It starts in its usual ready or scheduled state.

Do not use the older `prerequisiteTaskId` option. It is deprecated, because it hides the terminal
policies. Put the prerequisite IDs in `EnqueueOptions.dependencies`.

<details>
<summary>Reference: declaring dependencies</summary>

**`EnqueueOptions.dependencies`**

| Field                 | Rule                                             |
| --------------------- | ------------------------------------------------ |
| `prerequisiteTaskIds` | Required. 1 to 100 unique IDs of existing tasks. |
| `onSuccess`           | Required. `release`, `cancel`, or `fail`.        |
| `onFailure`           | Required. `release`, `cancel`, or `fail`.        |
| `onCancellation`      | Required. `release`, `cancel`, or `fail`.        |

The same `Dependencies` value names the prerequisite IDs in every SDK. TypeScript uses
`prerequisiteTaskIds`. Python, Rust, and Ruby use `prerequisite_task_ids`. Go uses
`PrerequisiteTaskIDs`.

- The deprecated `prerequisiteTaskId` names one prerequisite with `onSuccess: "release"`,
  `onFailure: "fail"`, and `onCancellation: "cancel"`. One request cannot set both fields.
- `enqueue_batch_v1` raises `prerequisite task does not exist` for an unknown ID.
- It locks every prerequisite `FOR KEY SHARE` in the transaction of the caller. Thus, a concurrent
  terminal transition of a prerequisite sees the new edge.
- A batch locks the prerequisites of every member in identity order before its first member runs. A
  batch with a debounce or throttle member does too.
- An update cannot change the endpoints or the outcome policies of an edge. It raises SQLSTATE
  `55000`.
- A live prerequisite makes a `blocked` runtime row and appends `dependency_blocked`.
- A prerequisite that already succeeded releases the edge immediately when `onSuccess` is
  `release`, with `dependency_released.details.reason` `prerequisite_already_succeeded`. A `fail` or
  `cancel` success policy rejects the dependent instead.
- Debounce, throttle, and [fast-tier queues](/docs/fast-tier) reject dependencies.

More detail: [Data model: Declaring dependencies at enqueue](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#declaring-dependencies-at-enqueue), [Data model: Prerequisite locking at enqueue](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#prerequisite-locking-at-enqueue), and [Data model: Edge updates](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#edge-updates).

</details>

## Wait for several prerequisites

A dependent can wait for more than one prerequisite. This shape is a fan-in.

**Example.** A release goes out only after it is published and indexed. The announcement names
both `release.publish` and `release.index` as prerequisites.

1. At 0 s, the announcement is blocked with two unresolved edges.
2. At 1 min, `release.publish` succeeds. Workhorse resolves that edge with `release`. One edge is
   still unresolved, so the announcement stays blocked.
3. At 2 min, `release.index` succeeds, and Workhorse resolves its edge.
4. No edge is unresolved now, so Workhorse makes the announcement ready and appends
   `dependency_released`.

Workhorse keeps a counter of the unresolved edges of each blocked dependent. When an edge resolves,
Workhorse decreases the counter in the same transaction. When the counter is zero, the dependent
leaves `blocked`. Thus, a wide fan-in costs the same for each prerequisite as a single edge.

If the `runAt` of the dependent has arrived, Workhorse makes it ready. If the `runAt` is in the
future, Workhorse makes it scheduled, and the task becomes ready at that time. A repeated completion
cannot release the dependent a second time.

<details>
<summary>Reference: resolution and release</summary>

The outcome trigger `task_outcome_resolve_dependencies_insert` calls
`resolve_dependents_many_v1` in the transaction that inserts the outcome of the prerequisite. The
`task_runtime.pending_prerequisites` column holds the counter. A second statement in the same
resolver call subtracts the resolved edges from it.

| Counter and rejection   | Resolver action                                  |
| ----------------------- | ------------------------------------------------ |
| Above zero              | Stays blocked. One runtime update, no edge scan. |
| Zero, no rejection      | Released to ready or scheduled.                  |
| Zero, after a rejection | Fails or is canceled. See the next section.      |

- A release allocates a ready sequence, appends `dependency_released`, and sends one
  `NOTIFY workhorse_tasks` per queue that gained ready work.
- A scheduled dependent becomes ready through ordinary promotion.
- The resolver materializes an already-passed deadline for each released task.

| `dependency_released.details.reason` | When                                                               |
| ------------------------------------ | ------------------------------------------------------------------ |
| `prerequisite_succeeded`             | After success, when `onSuccess` selects `release`                  |
| `prerequisite_failed_policy`         | `onFailure` selects `release`                                      |
| `prerequisite_canceled_policy`       | `onCancellation` selects `release`                                 |
| `prerequisite_already_succeeded`     | At enqueue, after success, when `onSuccess` selects `release`      |
| `prerequisite_terminal_policy`       | At enqueue, after a failure or cancellation that selects `release` |
| `dependency_counter_repaired`        | A recount found no pending edge                                    |

More detail: [Data model: Resolver counters](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#resolver-counters).

</details>

## Choose what happens when a prerequisite fails

Each edge has three policies: `onSuccess`, `onFailure`, and `onCancellation`. The terminal state of
the prerequisite selects one of them.

**Example.** The announcement from the previous section uses `onFailure: "fail"`. This time, the
index build fails.

1. At 1 min, `release.index` fails after its last retry. Its edge resolves with the policy `fail`.
   Workhorse marks the announcement as rejected. One edge is still unresolved, so the announcement stays blocked.
2. At 2 min, `release.publish` succeeds, and its edge resolves with `release`.
3. No edge is unresolved now. The announcement is rejected, so Workhorse reads its rejecting edges.
4. The `release.index` edge has the policy `fail`, so Workhorse fails the announcement. The
   announcement never runs.

Each policy accepts `release`, `cancel`, or `fail`. `release` satisfies the edge. After all edges
resolve, `fail` has precedence over `cancel`, and `cancel` has precedence over `release`. Thus, the
order in which concurrent outcomes arrive does not change the result.

Workhorse applies the same policies when a prerequisite is already terminal at enqueue.

<details>
<summary>Reference: rejected dependents</summary>

- An edge resolves with `on_success`, `on_failure`, or `on_cancellation`, to match the terminal
  state of the prerequisite.
- A `fail` or `cancel` resolution sets the flag `task_runtime.dependency_rejected`.
- At zero unresolved edges, the resolver reads only the `fail` and `cancel` edges. It chooses
  `fail` before `cancel`, then the lowest prerequisite identity.
- `settle_dependents_v1` deletes the runtime row and appends `dependency_failed` or
  `dependency_canceled`. It inserts a terminal outcome with the error `DependencyFailed` or
  `DependencyCanceled`.

More detail: [Data model: Settlement](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#settlement).

</details>

## Find out why a task is blocked

A blocked task waits in the `blocked` state. It has a durable runtime row, but no worker can claim
it. Its run time does not make it ready.

To find out why a task did not run, call `Admin.getTask` or `Admin.listTasks`. Each task record
gives its `prerequisiteTaskIds` and its `dependencyPolicy`. While the task is blocked, the record
also gives `blockedReason: "prerequisite_pending"`.

To read the edges of a task in both directions, call `Admin.getDependencyLineage(taskId)`. It
returns the edges where the task is a prerequisite or a dependent. Each edge has its policies, its
resolution, and its release time. The result tells you when more edges exist than the response
limit. Each task accepts a bounded number of prerequisites, children, and dependents. Thus, the
default response gives all the direct edges of the task.

<details>
<summary>Reference: blocked state and lineage</summary>

- A blocked row stays in `task_runtime` with `state = 'blocked'`. `task_runtime_ready_idx` and the
  scheduled index exclude it, so claim and promotion do not read it.
- Task records from `Admin.getTask` and `Admin.listTasks` carry `prerequisiteTaskIds`,
  `dependencyPolicy`, and `blockedReason`.
- `Admin.getDependencyLineage(taskId, limit)` returns `{ records, truncated }`. `limit` defaults to
  1,000 (`MAX_TASK_QUERY_PAGE_SIZE`). `truncated` is true when more edges exist.
- One task holds at most 300 direct edges: 100 prerequisites from its enqueue request, 100
  children, and 100 dependents. Thus, the default `limit` returns all of them.
- Each record has `dependentTaskId`, `prerequisiteTaskId`, `onSuccess`, `onFailure`,
  `onCancellation`, `createdAt`, `releasedAt`, and `resolution`.

More detail: [Data model: Columns and bounds](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#columns-and-bounds) and [Data model: Admin reads](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#admin-reads).

</details>

## Cancel a blocked dependent

You can cancel a dependent while it waits for its prerequisites. The prerequisites continue to run.

**Example.** The announcement from the fan-in is still blocked. The team decides not to announce
the release.

1. At 30 s, an operator cancels the announcement with `Queue.cancel`. Workhorse removes its runtime
   row, and the announcement ends as canceled.
2. In the same transaction, Workhorse releases the edges of the announcement. A canceled dependent
   does not wait for its prerequisites.
3. `release.publish` and `release.index` continue to run. Retention no longer keeps them for the
   announcement.

If you cancel a dependent, its prerequisites do not change.

<details>
<summary>Reference: dependent cancellation</summary>

- `cancel_v1` deletes a blocked runtime row and inserts one `canceled` outcome immediately. Work
  that never started emits no attempt history.
- The outcome trigger first sets `released_at` and a `release` resolution on every pending edge
  that enters the canceled task. `release_own_dependencies_v1(task_id)` is the one-task form.
- Deadline materialization of a blocked dependent uses the same path.

More detail: [Data model: Outcome trigger](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#outcome-trigger).

</details>

## Watch dependencies in the dashboard and in queue health

The dashboard and the queue health report show blocked work. An operator can use them to find out
why work waits or why it did not run.

**Example.** An operator looks at the release announcement after `release.index` failed at 1 min.

1. The operator opens the `Blocked` filter in the dashboard. The list shows the announcement, its
   blocked reason, and its unresolved prerequisite `release.publish`.
2. The operator opens the announcement. The task detail shows both edges: `release.index` resolved
   with `fail`, and `release.publish` pending.
3. At 2 min, `release.publish` succeeds, and Workhorse fails the announcement.
4. Later, maintenance removes the resolved edges. Then retention can delete either task identity.

The task detail shows the prerequisites and the dependents of the task, with the policies and the
stored release evidence. Thus, an operator can see why work stays blocked. An operator can also see
why PostgreSQL released, canceled, or failed it.

The `Blocked` filter lists blocked tasks with their `blockedReason` and their unresolved
`prerequisiteTaskIds`. A related ID in the task detail opens that task, and the drawer stays open.

`Queue.health()` reports blocked tasks, pending edges, and stored dependency failures. It also
reports if dependency edges stopped the latest retention pass from deleting tasks. OpenTelemetry
exports the queue pressure without task IDs, prerequisite IDs, or other unbounded labels.

Retention keeps a prerequisite identity while a dependent edge still controls dispatch. When that
edge resolves and the dependent finishes, maintenance removes the edge. Then retention can delete
the task identities. Thus, the dependency lineage can disappear while either terminal task remains.

<details>
<summary>Reference: health, telemetry, and retention</summary>

**`Queue.health().dependencies`:** `blockedTasks`, `pendingEdges`, `failedResolutions`,
`retentionPruneStarved`, and `capped`. Each count scans at most 10,001 rows and reports at most
10,000. `capped` marks a lower bound.

**Metrics:** `workhorse.queue.dependencies.blocked`, `workhorse.queue.dependencies.pending_edges`,
`workhorse.queue.dependencies.failed_resolutions`, and `workhorse.queue.dependencies.capped`, by
queue.

**Retention**

- `prerequisite_task_id` restricts deletion, so retention cannot strand blocked work.
- `prune_released_dependencies_v1` deletes at most 100,000 released edges per call whose dependent
  has a terminal outcome.
- Released-edge compaction runs before terminal-task pruning in the same pass.

More detail: [Data model: Dependency health](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#dependency-health) and [Data model: Pruning released edges](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#pruning-released-edges).

</details>

## Stay inside the graph bounds

Workhorse limits the number of edges of each task. If a request goes above a limit, the request fails.

**Example.** Task `reports.build` makes a nightly report. During the day, each export request
enqueues a `reports.export` task that depends on `reports.build`.

1. During the day, each export request adds one dependent edge to `reports.build`.
2. Later, `reports.build` has the maximum number of dependent edges. PostgreSQL rejects the next
   edge, and the enqueue request fails with a limit error.
3. At night, `reports.build` runs, and then the waiting exports run and finish.
4. Maintenance removes their released edges, and `reports.build` accepts dependents again.

PostgreSQL counts the retained dependents of a prerequisite, not only the unresolved dependents.
Thus, the work to settle that prerequisite stays bounded in the transaction of the worker.
PostgreSQL also limits the unresolved graph below each task. Thus, a failure or a cancellation
cannot cascade through unlimited work in that transaction.

If an edge makes a cycle or goes above a bound, the enqueue request fails with a typed error. Your
code can handle the error without matching database text.

<details>
<summary>Reference: edge bounds and errors</summary>

| Bound                                                                                        | Limit | `limit` value           |
| -------------------------------------------------------------------------------------------- | ----- | ----------------------- |
| Unresolved prerequisite edges into one dependent                                             | 100   | `prerequisites`         |
| Retained dependent edges out of one prerequisite                                             | 100   | `dependents`            |
| Distinct dependents one prerequisite reaches through unresolved edges, direct and transitive | 100   | `unresolved_dependents` |

- PostgreSQL raises these with SQLSTATE `P1005`. `Queue` throws `DependencyLimitExceededError`,
  which carries `taskId`, `limit`, and `max`.
- PostgreSQL raises a cycle with SQLSTATE `P1003`. `Queue` throws `DependencyCycleError`, which
  carries `dependentTaskId`, `prerequisiteTaskId`, `cycleTaskIds`, and `truncated`.
- One request names at most 100 prerequisites (`MAX_TASK_DEPENDENCIES`). The TypeScript SDK
  rejects a longer list with a `RangeError` before it queries.
- `prune_released_dependencies_v1` removes a released edge after its dependent has a terminal
  outcome.

More detail: [Data model: Columns and bounds](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#columns-and-bounds) and [Data model: Edge validation](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#edge-validation).

</details>

## Repair a counter that does not agree with the edges

The counter of a blocked dependent must agree with its unresolved edges. Before a dependent leaves
`blocked`, Workhorse checks that no edge is unresolved.

**Example.** A fault left the counter of the announcement at 1, but two edges are unresolved.

1. At 1 min, `release.publish` succeeds. The counter would go to zero, but one edge is still
   unresolved.
2. Workhorse recounts the edges of the announcement instead. It stores the counter 1 and keeps the
   announcement blocked.
3. Workhorse records a `dependency_counter_repaired` event.

Workhorse also recounts if a resolution would make the counter less than zero. It also recounts a
dependent that is marked as rejected without a rejecting edge. Thus, a wrong counter does not stop
the completion of the prerequisite. It also does not release the dependent too early.

You can also find and repair drift yourself. Drift is a counter or a rejected mark that does
not agree with the edges.

- To find drift, call `Admin.listDependencyDrift`. It lists the drifted blocked dependents and the
  action that a repair does. It writes nothing.
- To repair drift, call `Admin.repairDependencyDrift`. It recounts those dependents and settles each
  dependent whose edges are all resolved.
- The repair requires an actor, a reason, and a request ID. Each repair event records them.
- To use the command line, run `workhorse admin repair-dependencies`. Add `--dry-run` to only read.

```sh
workhorse admin repair-dependencies --dry-run
workhorse admin repair-dependencies --reason "counter drift after restore" \
  --env workhorse_production --yes
```

<details>
<summary>Reference: counter repair</summary>

**Automatic.** The resolver recounts a dependent when its counter is smaller than the edges the call
resolved, or equal to them while a pending edge remains. The `details.source` of the event is
`resolver`. `settle_dependents_v1` recounts a rejected dependent with no rejecting edge, with
`source` `settlement`.

**On demand**

| Surface                                     | Effect                                                                             |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `Admin.listDependencyDrift(limit)`          | Reads drifted rows and the planned action: `recounted`, `rejected`, or `released`. |
| `Admin.repairDependencyDrift(audit, limit)` | Recounts under lock and settles rows with no pending edge.                         |
| `workhorse admin repair-dependencies`       | `--dry-run` reads. Without it, requires `--reason`, `--env`, and confirmation.     |

- `limit` defaults to 1,000 and accepts 1 to 100,000 (`MAX_DEPENDENCY_DRIFT_LIMIT`).
- The repair requires `requested_by` of 1 to 200 characters, `reason` of 1 to 2,000 characters,
  and `request_id` of 1 to 512 UTF-8 bytes.
- The request ID correlates the repair. It is not an idempotency key.
- No maintenance pass calls either function. `queue_health_v1` does not report drift.

More detail: [Data model: Counter repair](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#counter-repair) and [Data model: Governed drift repair (schema version 40)](https://github.com/stablemates/workhorse/blob/main/docs/architecture/data-model.md#governed-drift-repair-schema-version-40).

</details>
