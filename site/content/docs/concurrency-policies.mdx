---
title: Concurrency policies
description: Synchronize durable queue and keyed dispatch budgets that every worker shares.
---

Some capacity belongs to the application, not to one worker process: a database connection budget,
a downstream API's connection limit, a per-tenant fairness rule. `WorkerOptions.concurrency`
limits one process, so adding a worker silently raises the fleet's total. A concurrency policy
stores the budget in PostgreSQL instead, where every competing worker checks it atomically during
claim — scale the fleet and the limit holds.

## Synchronize desired policy

`queue.syncConcurrencyPolicies` is a desired-state call, like schedules: declare the policies a
namespace owns and PostgreSQL reconciles stored state to match.
`Queue.listConcurrencyPolicies` returns the persisted typed rows.

Go applications call `Queue.SyncConcurrencyPolicies` through the same caller-owned executor used
for enqueue. `Queue.ListConcurrencyPolicies` returns the persisted typed rows. Rust applications use
`Queue::sync_concurrency_policies` and `Queue::list_concurrency_policies`.

Python applications call `sync_concurrency_policies` through `Queue` or `AsyncQueue` on their
caller-owned connection. `list_concurrency_policies` returns the persisted typed rows.

<Tabs items={["TypeScript", "Python", "Go", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.syncConcurrencyPolicies("workers", [
      { queue: "mail", maxActive: 20, maxActivePerKey: 3 },
    ]);
    ```
  </Tab>
  <Tab value="Python">
    ```python
    queue.sync_concurrency_policies(
        "workers",
        [ConcurrencyPolicyDefinition(queue="mail", max_active=20, max_active_per_key=3)],
    )
    ```
  </Tab>
  <Tab value="Go">
    ```go
    maxActivePerKey := 3
    policies, err := queue.SyncConcurrencyPolicies(ctx, "workers", []workhorse.ConcurrencyPolicyDefinition{{
    	Queue: "mail", MaxActive: 20, MaxActivePerKey: &maxActivePerKey,
    }})
    ```
  </Tab>
  <Tab value="Rust">
    ```rust
    let policies = queue
        .sync_concurrency_policies(
            "workers",
            &[ConcurrencyPolicyDefinition {
                queue: "mail".into(),
                max_active: 20,
                max_active_per_key: Some(3),
            }],
            false,
        )
        .await?;
    ```
  </Tab>
</Tabs>

Workers need no matching in-memory configuration — admission reads the stored policy, so a policy
change takes effect without redeploying the fleet. Workhorse prunes omitted policies by default, and
PostgreSQL rejects another namespace that tries to replace a queue this namespace owns.

`maxActivePerKey` is optional; omit it (or pass `null`) to keep only the queue-wide limit.

## Attach a queue-scoped key

The key names the group a task competes in — a tenant, a destination host, an account.

<Tabs items={["TypeScript", "Python", "Go", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.enqueue("mail.send", { messageId }, { queue: "mail", concurrencyKey: tenantId });
    ```
  </Tab>
  <Tab value="Python">
    ```python
    queue.enqueue(
        "mail.send",
        {"messageId": message_id},
        EnqueueOptions(queue="mail", concurrency_key=tenant_id),
    )
    ```
  </Tab>
  <Tab value="Go">
    ```go
    _, err := queue.Enqueue(ctx, "mail.send", map[string]any{
    	"messageId": messageID,
    }, workhorse.EnqueueOptions{Queue: "mail", ConcurrencyKey: tenantID})
    ```
  </Tab>
  <Tab value="Rust">
    ```rust
    queue
        .enqueue(
            "mail.send",
            &json!({ "messageId": message_id }),
            EnqueueOptions {
                queue: Some("mail".into()),
                concurrency_key: Some(tenant_id.into()),
                ..Default::default()
            },
        )
        .await?;
    ```
  </Tab>
</Tabs>

Keyless tasks consume queue capacity only. A keyed task also consumes capacity for its key. The same
key text in another queue is independent, and one saturated key does not block the queue: admission
can pass over a full key and claim later ready work for another key, within a bounded window
ordered by priority first and FIFO among equal priorities.

## A dispatch budget, not a mutex

Capacity counts active tasks with unexpired leases. If a worker disappears, its capacity returns
when the lease expires — the queue cannot be starved by a dead process. The flip side: a stale
handler can briefly overlap its replacement after expiry, and fence tokens — not the policy —
prevent that stale generation from recording a result. Handlers keep the ordinary at-least-once
assumptions.

## Share one budget across queues

A policy limits one queue. When several queues call the same downstream resource, a named budget
caps them together without merging them, so each queue keeps its own priority order, pause control,
and health row. `Queue.syncBudgets` stores budgets in PostgreSQL the way policies are stored, and
`Queue.listBudgets` reads them back. Go applications use `Queue.SyncBudgets` and
`Queue.ListBudgets`. Python applications use `Queue.sync_budgets` or `AsyncQueue.sync_budgets`,
and `Queue.list_budgets` or `AsyncQueue.list_budgets`. Rust applications use `Queue::sync_budgets`
and `Queue::list_budgets`.

<Tabs items={["TypeScript", "Python", "Go", "Rust"]}>
  <Tab value="TypeScript">
    ```ts
    await queue.syncBudgets("workers", [{ name: "vendor-api", maxActive: 4 }]);

    await queue.enqueue("invoice.sync", { id: 1 }, { queue: "billing", budget: "vendor-api" });
    await queue.enqueue("contact.sync", { id: 2 }, { queue: "crm", budget: "vendor-api" });
    ```

  </Tab>
  <Tab value="Python">
    ```python
    queue.sync_budgets("workers", [BudgetDefinition(name="vendor-api", max_active=4)])

    queue.enqueue("invoice.sync", {"id": 1}, EnqueueOptions(queue="billing", budget="vendor-api"))
    queue.enqueue("contact.sync", {"id": 2}, EnqueueOptions(queue="crm", budget="vendor-api"))
    ```

  </Tab>
  <Tab value="Go">
    ```go
    maxActive := 4
    budgets, err := queue.SyncBudgets(ctx, "workers", []workhorse.BudgetDefinition{{
    	Name: "vendor-api", MaxActive: &maxActive,
    }})

    _, err = queue.Enqueue(ctx, "invoice.sync", map[string]any{"id": 1}, workhorse.EnqueueOptions{
    	Queue: "billing", Budget: "vendor-api",
    })
    ```

  </Tab>
  <Tab value="Rust">
    ```rust
    let budgets = queue
        .sync_budgets(
            "workers",
            &[BudgetDefinition { name: "vendor-api".into(), max_active: Some(4), rate: None }],
            false,
        )
        .await?;
    queue
        .enqueue(
            "invoice.sync",
            &json!({ "id": 1 }),
            EnqueueOptions {
                queue: Some("billing".into()),
                budget: Some("vendor-api".into()),
                ..Default::default()
            },
        )
        .await?;
    ```
  </Tab>
</Tabs>

A task names its budget at enqueue time with the `budget` option beside `concurrencyKey`. The
budget is an extra check: the task must still pass its queue's own policy. A budget can cap active
tasks, cap the start rate, or both. It has no per-key limit, because keys stay queue-scoped, and a
task that names a budget nobody synchronized is not limited by it. An expired lease returns budget
capacity, a release wakes every queue holding ready work that names the budget, and `claim_v1`
passes over a saturated budget inside the same bounded window it uses for keys.

## Observe pressure

`queue.health()` reports each policy's limit, active count, blocked ready work, and saturated-key
counts, all bounded. Named budgets appear under `budgetPolicies`, and `Queue.budgetStatuses` returns
the same observation on its own, with the budget name as the only telemetry label. OpenTelemetry publishes the same queue-level gauges without raw key values.
If ready work sits behind a full policy, it shows up as `blockedReady` rather than as a mystery
latency.

TypeScript synchronizes desired state with `Queue.syncConcurrencyPolicies` and reads it back with
`Queue.listConcurrencyPolicies`; Python uses `Queue.sync_concurrency_policies` or
`AsyncQueue.sync_concurrency_policies`. Python reads policy state through
`Queue.list_concurrency_policies` or `AsyncQueue.list_concurrency_policies`.
PostgreSQL applies the policy in `claim_v1`, and `Queue.health()` exposes the resulting pressure.
