---
title: SQLAlchemy
description: Enqueue a Workhorse task on the Psycopg connection that a synchronous or asynchronous SQLAlchemy transaction already uses.
---

Your application writes through SQLAlchemy. To enqueue a task in the same transaction, use the
Psycopg connection that SQLAlchemy already uses for that transaction. The application write and the
task then commit together. You do not need a second pool or a second transaction owner.

This page describes a tested recipe, not an ORM adapter package. SQLAlchemy owns the transaction
completion, the savepoints, and the return of the connection to the pool. Install the Workhorse
schema outside your ORM migrations.

## Choose the Psycopg dialect

For synchronous SQLAlchemy, use the Psycopg dialect with `Queue`. For asynchronous SQLAlchemy, do
these steps:

1. Install `SQLAlchemy[asyncio]` and Psycopg.
2. Use the `postgresql+psycopg` dialect with `AsyncQueue`.

The [enqueue page](/docs/enqueue#enqueue-in-an-asynchronous-sqlalchemy-transaction) gives the full
recipe. It tells you which accessor to use, when to flush the session, and how to use the connection
in sequence. It also gives the lifetime rules, the installation, and the tested versions. It links
the runnable example and the integration fixture that CI collects.

## Do not use the asyncpg dialect

This recipe does **not** support the asyncpg dialect of SQLAlchemy. Tests show two problems. The
dialect starts its physical transaction late, and its JSON codecs are not compatible with Workhorse.
Read the [asyncpg limit](/docs/enqueue#do-not-use-the-asyncpg-dialect-of-sqlalchemy) before you
choose that dialect.

Workhorse continues to support asyncpg connections and pools that you own independently.
