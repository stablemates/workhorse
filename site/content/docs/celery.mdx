---
title: Celery migration
description: Move one JSON credit task from Celery to Workhorse while retaining application-owned operation identity and effects.
---

This recipe moves one PostgreSQL application's account-credit task, not an entire Celery installation.
Both handlers consume the same JSON and apply the same account credit.
The application retains the operation request and effect receipt across producer switches and worker restarts.

It is a **documented migration recipe**, not a Celery adapter or broker.
The fixture executes real Celery locally in eager mode and a Workhorse worker against local PostgreSQL.
It does not verify RabbitMQ, Redis, broker acknowledgment, visibility timeout, or production drain behavior.

## Runnable before and after

The repository owns [the example](https://github.com/stablemates/workhorse/blob/main/python/examples/celery_migration.py)
and [its database tests](https://github.com/stablemates/workhorse/blob/main/python/tests/test_celery_migration.py).
Neither file is an installed `workhorse` module.
Celery is a development dependency, not a requirement of `stablemates-workhorse`.

From a configured repository checkout:

```sh
pnpm example:celery-migration
pnpm exec tsx scripts/with-env.ts uv run --project python pytest python/tests/test_celery_migration.py -q
```

The example creates and drops its own scratch database from that checkout's loopback `DATABASE_URL_TEST`.
It never resets the checkout's test database.
Celery uses `task_always_eager=True`, JSON serialization, and the local memory transport.
No live broker, external service, or container is required.
Eager results are inspected only to verify the local fixture; production producers must not wait for a handler inside a request.

The application credits `customer` for the immutable payment reference `payment-001`:

```json
{
  "operation_id": "4c9c24a3-9e84-5997-98cb-ee6191f45667",
  "account_id": "customer",
  "amount_cents": 1500
}
```

`credit_payload()` derives `operation_id` from the operation kind, account, and immutable payment reference.
It does not use a Celery result ID, a Workhorse task ID, or a fresh random ID on retry.
Retain the original payment reference and amount in the application that accepts the business request.
For an existing application, backfill this identity from authoritative business records before switching producers.
If an old delivery has no recoverable business identity, stop and reconcile it rather than inventing a new one.

## Publication and the business effect

`celery_migration.operation` retains the exact account and amount under a unique `operation_id`.
Reusing that ID with a changed request fails closed.
Both handlers call `apply_credit()`.
It verifies the committed operation and inserts its unique `celery_migration.effect` receipt in the same transaction as the account update.
Concurrent deliveries contend on that receipt; only the transaction inserting it increments `credit_cents`.
An effect transaction failure rolls back both writes.

**Before: Celery.** `stage_operation()` commits the business request first.
Then `submit()` calls the real Celery task's `delay(payload)`.
If publication fails or its outcome is unknown, the request remains committed without a proved delivery.
`unresolved_operations()` finds committed requests without effect receipts for reconciliation.
It is an application-owned reconciliation query, not a Celery backlog inspection API.

**After: Workhorse.** Within `connection.transaction()`, `stage_operation()` passes that exact Psycopg connection to `Queue`.
The business request and `Queue.enqueue()` commit or roll back together.
An independent connection sees neither before commit.
The caller owns the transaction, nested savepoints, and connection lifetime.
The Workhorse handler calls the same `apply_credit()` function from a dedicated worker process.

```python
with psycopg.connect(database_url) as connection, connection.transaction():
    staged = stage_operation(connection, payload)
```

The application's persisted route chooses the destination inside that transaction.
`switch_producer()` updates it transactionally and waits for producers already holding its shared row lock.
This lock orders cooperating application producers; it cannot fence an old deployment that bypasses the route.
A producer that selected Celery can still publish after the route switches.
The shared effect ledger protects that overlap, including late old deliveries.

Workhorse enqueue idempotency reduces repeated acceptance within its configured retention window.
The application effect ledger remains necessary after that window, after task history expires, and across both queues.
Keep operation and effect receipts for every period in which either system, an operator, or a business client may replay the request.
Deleting those receipts removes the application's duplicate-effect protection.

## Cutover, verification, and rollback

1. Deploy the shared JSON contract and durable ledger to the **old** producer and handler first.
   Backfill authoritative operation identities for existing deliveries.
   Reject identity conflicts and verify the intended credit before introducing Workhorse.
2. Install a compatible Workhorse schema and run a dedicated worker for `migration.credit` on `celery-migration`.
   Give it its own pool and process lifecycle; never start it from a web request or framework startup hook.
   Exercise one controlled application operation and reconcile its account, effect receipt, and task outcome.
3. Switch all cooperating producers through the persisted route in one committed transaction.
   Track obsolete deployments, scheduled producers, in-flight publication, reserved deliveries, broker retries, and delayed tasks separately.
   Keep the old handler available during overlap.
4. Reconcile every unresolved committed operation using its **existing** ID and payload.
   Under the Workhorse route, submitting it accepts a Workhorse task even if the old publication outcome is unknown.
   A late Celery delivery and a Workhorse delivery then share the same effect receipt.
   Do not discard the old backlog merely because a new task exists.
5. Verify the application ledger and account totals with an independent observer.
   Inspect Workhorse task outcomes and attempts, and use the old broker's real operational tools to assess its backlog.
   An empty visible queue or an empty reconciliation query is **not** proof that no old delivery remains reserved or delayed.
   Retire old consumers only after the application owner has bounded those uncertainties and documented its drain evidence.

If cutover fails before commit, the route, staged business writes, and Workhorse acceptance roll back together.
If the new path fails after cutover, commit `switch_producer(connection, "celery")` to roll back the **producer switch**.
Keep existing Workhorse tasks and both handlers available while reconciling; they may still complete.
Do not generate replacement operation IDs, delete ledgers, or undo already committed credits as part of the switch.
An inverse credit requires a separate authorized business operation.

The fixture proves route rollback, overlapping producers, unknown old publication, late deliveries, and durable reconciliation.
It deliberately does not declare a production broker drained.

## Retries and native controls

The old eager task exercises Celery's `autoretry_for` for an operational failure after the business effect commits.
The Workhorse tests retry the handler before and after that same commit.
They also start a fresh interpreter, commit the effect, exit before queue completion, and run a new handler afterward.
The effect receipt prevents a second credit in every case.
A crash after effect commit may still leave an uncertain queue outcome; reconciliation must inspect both authorities.

Workhorse-native controls include enqueue idempotency, persisted retry policy and attempt limits, concurrency admission, cancellation, deadlines, and named checkpoints/waits.
Configure them through Workhorse APIs and inspect Workhorse outcomes, not through Celery request or result objects.
This example uses bounded attempts and enqueue idempotency; its ledger protects the application effect independently.

This recipe offers **no** Celery result-ID translation, `AsyncResult` backend, `self.retry()` API, task decorator compatibility, Canvas chain/chord semantics, or broker compatibility.
It does not translate every task, serializer, routing option, periodic schedule, or retry policy automatically.
Re-design each additional task explicitly.
Workhorse executes handlers at least once; neither queue's task identity promises an external exactly-once effect.
An HTTP call or email needs a downstream idempotency contract or another application-owned reconciliation design.
The receipt and credit are atomic here because both live in the same PostgreSQL transaction.

## Django boundary

Celery's [`DjangoTask.delay_on_commit()`](https://github.com/celery/celery/blob/v5.6.3/celery/contrib/django/task.py)
registers `delay()` with Django's `transaction.on_commit()`.
It orders publication after a successful database commit; it does **not** make publication and that commit atomic.
A process failure after commit can still leave an unpublished operation.

This example uses ordinary Psycopg and implements no Django connection helper.
The separate [Django recipe source](https://github.com/stablemates/workhorse/blob/184a139a609960d8d5a85b68d67fa0297788acdb/python/examples/django_enqueue.py)
uses the merged `workhorse.django.enqueue_in_atomic()` helper inside Django's transaction.
Adopting that recipe requires a Workhorse version containing that helper and its reviewed connection-ownership policy.
This independent migration does not use or duplicate the helper.

## Tested versions and limits

The local proof uses Python 3.12.14, PostgreSQL 18.6, Workhorse source version 0.6.1,
Celery 5.6.3, Kombu 5.6.2, Billiard 4.3.0, Vine 5.1.0, Psycopg and psycopg-binary 3.3.6, and psycopg-pool 3.3.2.
Celery is pinned exactly for the fixture; driver versions come from this recipe's Python lockfile.
The existing Python CI suite collects the fixture once, without a second framework-specific lane.
