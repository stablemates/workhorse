---
title: Django Tasks
description: Keep your decorated Django tasks, accept each task in the business transaction, and run it in a dedicated Workhorse worker.
---

Django Tasks is the task interface of Django: you decorate a function with `@task` and call
`.enqueue()`. The Workhorse backend lets a Django application keep that interface. The task commits
in the same PostgreSQL transaction as your business writes. A separate worker process runs it. The
backend gives a bounded contract for submission and execution. It does not store Django results.

## Install the backend

The optional `workhorse.django` module is part of the Python distribution. An ordinary Workhorse
installation does not install or import Django. Install the extra in the environment of your Django
application:

```sh
pip install 'stablemates-workhorse[django]' 'psycopg[binary]==3.3.6'
```

The backend requires Psycopg 3, not psycopg2. Install the [Workhorse schema](/docs/installation)
separately, in the same database. Django continues to own the migrations of your application.

## Configure the backend

Give the backend its database alias explicitly. No database router selects the alias for you.

```python
TASKS = {
    "default": {
        "BACKEND": "workhorse.django.WorkhorseTaskBackend",
        "QUEUES": ["default", "urgent"],
        "OPTIONS": {
            "DATABASE_ALIAS": "business",
            "TASK_PATHS": ["application.tasks.greet"],
            "MAX_ATTEMPTS": 3,
        },
    },
}
```

`DATABASES["business"]` must select the PostgreSQL Psycopg backend of Django. `TASK_PATHS` is an
allowlist: it names each task that the backend can run. Each path must be an importable, decorated,
module-level task. All configured paths must resolve when the worker starts.

```python
from django.tasks import task

@task
def greet(name: str, *, punctuation: str = "!") -> dict[str, str]:
    return {"greeting": f"Hello, {name}{punctuation}"}
```

Keep the task modules free of side effects such as request handling or worker startup. The
maintained example `python/examples/django_tasks.py` has the same task and a separate worker entry
point. To run the repository example, configure its allowlist as `django_tasks.greet`.

<details>
<summary>Reference: backend options</summary>

| Setting          | Rule                                                                 |
| ---------------- | -------------------------------------------------------------------- |
| `QUEUES`         | A nonempty list of nonempty queue names. Defaults to `["default"]`.  |
| `DATABASE_ALIAS` | Required. A nonempty string.                                         |
| `TASK_PATHS`     | Required. A nonempty list of unique dotted paths to decorated tasks. |
| `MAX_ATTEMPTS`   | An integer from 1 through 100. Defaults to 25.                       |

An invalid setting raises `ImproperlyConfigured`. The backend enqueues each task with the task type
`django.tasks.<backend alias>`.

More detail: [ADR 0087: Keep the Django Tasks backend bounded by atomic acceptance](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0087-bounded-django-tasks-backend.md).

</details>

## Enqueue a task inside the atomic block

Call `.enqueue()` inside `transaction.atomic(using=DATABASE_ALIAS)`.

```python
from django.db import transaction
from application.tasks import greet

with transaction.atomic(using="business"):
    Order.objects.using("business").create(id=order_id, note="accepted")
    accepted = greet.using(queue_name="urgent").enqueue("Ada", punctuation="?")
```

The backend uses the same guarded connection as the [Django enqueue recipe](/docs/django). It never
commits, never closes the connection, never keeps a queue, and never starts a second transaction. A
standalone submission must also be inside `transaction.atomic(using=DATABASE_ALIAS)`. An atomic
block on a different alias is not sufficient. `on_commit()` does not replace atomic acceptance.

`.using(queue_name=...)` selects an allowed Workhorse queue. `.using(backend=...)` selects a
different configured backend. That backend must allow the same task path and map its own database
alias explicitly. No task can change the retry limits through `.using()`.

## Pass arguments that convert to JSON

The backend converts the arguments with the JSON rules of Django. Then it checks for finite JSON
values and string object keys. A tuple becomes a list, and UTF-8 bytes become a string.

The enqueue fails before acceptance in these cases:

- an argument is an unsupported object;
- the arguments do not match the signature of the function;
- a number is not finite;
- the task is not registered.

## Read the returned `TaskResult` as acceptance, not commit

`.enqueue()` returns a genuine Django `TaskResult`. Its status is `READY`. It has the Workhorse
task ID, the converted arguments, and the submission time. It has no attempts, worker IDs, or
errors.

**Example.** A request submits `greet` in an inner atomic block, and then the outer block fails.

1. The request opens the outer block `transaction.atomic(using="business")`.
2. The request opens an inner atomic block and calls `greet.enqueue("Ada")`. It gets a `TaskResult`
   with a task ID.
3. The inner block ends, and Django releases its savepoint.
4. A later statement in the outer block fails, and Django rolls back the outer block.
5. PostgreSQL removes the task. The task ID from step 2 now identifies no task.

A `TaskResult` shows that Workhorse accepted the task in the current transaction. It does not show
that the transaction committed.

## Run a dedicated worker

Run the worker in a separate process. Do these steps in that process:

1. Initialize Django before you import the tasks of the application.
2. Open a worker pool on the database that `DATABASE_ALIAS` selects.
3. Bind the backend to the worker, then run the worker.

```python
import django
from django.tasks import task_backends
from psycopg_pool import ConnectionPool
from workhorse import Worker

django.setup()
backend = task_backends["default"]
with ConnectionPool(database_url, min_size=3, max_size=3,
                    kwargs={"autocommit": True}) as pool:
    worker = Worker(pool, queues=sorted(backend.queues))
    backend.bind_worker(worker)
    worker.run()
```

The importable worker entry point of the example accepts `--database-url`, `--backend`, and
`--once`:

```sh
PYTHONPATH=python/examples DJANGO_SETTINGS_MODULE=application.settings \
  python -c 'import django; django.setup(); import django_tasks; django_tasks.main()' \
  --database-url "$DATABASE_URL" --once
```

`bind_worker()` resolves only the configured decorated tasks. During execution, an envelope selects
a registered task. The envelope is the JSON payload that names the backend, the queue, the task
path, and the arguments. The worker does not import the path from the payload. If the path is
unknown, if the backend or queue does not match, or if the envelope is invalid, the attempt fails.

Never start this worker from a request, from a Django startup hook, or from a thread of the web
process. [Worker processes](/docs/worker-processes) explains the runtime.

<details>
<summary>Reference: envelope</summary>

The envelope has exactly these keys: `version`, `backend`, `path`, `queue`, `args`, and `kwargs`.

- `version` must be the integer 1.
- `backend` must be the alias of the bound backend.
- `path` must be in the registry that `bind_worker()` built from `TASK_PATHS`.
- `queue` must be in `QUEUES` and must be equal to the queue of the task.
- `args` must be a list. `kwargs` must be an object with string keys.

If a check fails, the handler raises `InvalidTask`.

More detail: [ADR 0087: Keep the Django Tasks backend bounded by atomic acceptance](https://github.com/stablemates/workhorse/blob/main/docs/decisions/0087-bounded-django-tasks-backend.md).

</details>

## Make each task safe to run again

Workhorse retries a raised exception up to the `MAX_ATTEMPTS` of the backend. The native retry
schedule of Workhorse controls the delay. Each attempt calls the function from its start. After the
last attempt, Workhorse records the final failure.

Delivery is at least once, so the external effects of each task must be idempotent. If you change
the code of a registered task in a deployment, the later attempts use the new code.

## Read task outcomes in Workhorse, not in Django

The backend discards return values. The first Django result stays `READY` after success and after
failure. `get_result()`, `aget_result()`, `refresh()`, and `arefresh()` raise
`NotImplementedError`. No process-local cache replaces durable results.

To see what happened to a task, use the native Workhorse task outcomes and operator surfaces. These
are not Django `TaskResult` objects.

## Know what the backend does not support

`supports_get_result`, `supports_priority`, `supports_defer`, and `supports_async_task` stay false.
The backend rejects nondefault priorities, `run_after`, coroutine handlers, and
`takes_context=True`.

`.aenqueue()` comes from Django. It submits through the thread-sensitive synchronous adapter of
Django. It does not make an async transaction, and it does not permit coroutine handlers. Wrap the
**whole** business operation and its atomic block with `sync_to_async(..., thread_sensitive=True)`.
The [Django recipe](/docs/django) shows this.

These features stay native-only: named checkpoints, durable waits, signals, child tasks, progress,
cancellation context, per-task retry policies, idempotency, and other coordination options. If you
need them, use a native Workhorse handler.

## Run the tests

`pnpm python:test:django-tasks` runs the focused backend fixture. `pnpm python:test:django` keeps
all the connection, error, lifecycle, and transaction tests of the shared guarded connection. Both
use scratch databases for each test. They include an independent worker subprocess, and installed
wheel and source-distribution consumers with Django and without Django. CI collects these fixtures
through `pnpm python:test` one time for each change.

The contract follows the released
[Django 6.1 Tasks documentation](https://docs.djangoproject.com/en/6.1/topics/tasks/) and the
[Django 6.1.1 backend source](https://github.com/django/django/blob/6.1.1/django/tasks/backends/base.py).
