The `@stablemates/workhorse-typeorm` package connects Workhorse to TypeORM. With it, your
application enqueues a task in the same transaction as its entity writes. The entity and the task
then commit together, or neither commits.

This prevents two errors. Without a shared transaction, a task can exist for a row that rolled back.
Also, a row can commit and its task can be lost, and no error shows this. TypeORM owns your entities.
Workhorse owns its own schema and its versioned SQL functions.

## Create the adapter

Install the integration together with TypeORM.

```bash
pnpm add @stablemates/workhorse-typeorm typeorm
```

Give an initialized data source to `createTypeOrmAdapter`. The `close` callback is optional. By
default, the adapter does not destroy a data source that the caller owns.

```ts
import { createTypeOrmAdapter } from "@stablemates/workhorse-typeorm";

const workhorse = createTypeOrmAdapter(dataSource, {
  close: () => dataSource.destroy(),
});
```

The adapter is a `WorkhorseAdapter`. It has `database`, `queue`, `admin`, `forTransaction`,
`adminForTransaction`, `createWorker`, and `close`. Your request handlers, operator tools, and
worker processes use this one adapter.

## Enqueue a task in a TypeORM transaction

Call `forTransaction` with the entity manager that TypeORM gives to your callback. The queue that it
returns sends its SQL through that entity manager. Thus the task commits or rolls back with your
entity writes.

```ts
await dataSource.transaction(async (manager) => {
  const account = await manager.save(Account, { email });
  await workhorse.forTransaction(manager).enqueue("account.created", {
    accountId: account.id,
  });
});
```

If the callback throws an error, TypeORM rolls back the account and the task. Other connections do
not see the account or the task before the commit.

To enqueue a task that is not part of a transaction, use `workhorse.queue`. This queue does not join
the transaction of the caller.

## Initialize the data source before you create a worker

When the data source initializes, the PostgreSQL driver of TypeORM creates a node-postgres pool. The
worker takes its heartbeat connection and its listen connection from this pool. A listen connection
waits for notifications about new tasks. Thus, initialize the data source before you create a
worker.

The pool must have space for these two connections and for the claims of the worker. Use the
TypeORM option `extra.max` to set the size of the pool.

<details>
<summary>Reference: worker connections</summary>

- The pool is `dataSource.driver.master`. TypeORM's `PostgresDriver` creates it on `initialize()`.
- The adapter finds the pool when a worker is constructed, not when you create the adapter.
- TypeORM does not document `driver.master`. An integration test pins this accessor.
- `TypeOrmAdapterOptions` has no `pool` option.
- A dedicated heartbeat connection needs a pool of at least 3 connections. If the pool is smaller,
  the worker does not start unless you set `sharedHeartbeats`.

More detail: [Overview: ORM adapters](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#orm-adapters),
[Overview: Connection budgets per language](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#connection-budgets-per-language).

</details>

## Handle database errors

If a database statement fails, the adapter throws `TypeOrmQueryError`. The error keeps the
statement, the original error, and the error code of the PostgreSQL driver.

Typed Workhorse conflicts keep their core error classes. Examples are idempotency, checkpoint, and
wait conflicts.

<details>
<summary>Reference: errors</summary>

| `TypeOrmQueryError` field | Content                                                |
| ------------------------- | ------------------------------------------------------ |
| `statement`               | The SQL statement.                                     |
| `code`                    | The SQLSTATE that PostgreSQL reported, or `undefined`. |
| `cause`                   | The original error.                                    |

- `TypeOrmQueryError` extends `QueryError`. It does not copy parameter values into its message.
- The code search follows `driverError` and `cause`.

More detail: [Overview: Prisma and TypeORM queryables](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#prisma-and-typeorm-queryables).

</details>

## Close the data source that the adapter owns

If you do not give a `close` callback, the adapter leaves the data source initialized. Give this
callback only when the adapter owns the data source. `adapter.close` can run when the process stops
or when startup fails.

## Install the Workhorse schema with the Workhorse tools

Install the Workhorse schema with the deployment tools of the core package. Do not let TypeORM
migrations manage the Workhorse SQL functions. The Workhorse schema is a versioned protocol, not a
set of application entities.
