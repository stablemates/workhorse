title: Installation
description: Add the core package, install its PostgreSQL schema, and check compatibility before a process starts.
---

Workhorse keeps its durable state in your database. Thus, an installation of Workhorse is a schema
change. Do a schema change as a separate deployment step. Do not let the first process that starts
make it. This page tells you how to do two different actions. The installation creates the database
objects one time. The startup check makes sure that the schema is correct, and each runtime process
does it.

## Check the requirements

Each SDK runs on standard PostgreSQL and needs no extension. The schema CLI runs on Node.js during
deployment. This is also true when the application uses Python, Go, Rust, or Ruby.
[Compatibility](/docs/compatibility) gives each supported version. No other page gives them.

Choose the runtime of your application:

- TypeScript needs an ESM application.
- Python can use synchronous or asynchronous drivers.
- Go can use pgx or `database/sql`.
- Rust runs on Tokio with `tokio-postgres`.
- Ruby runs on the `pg` gem. It can use the gem directly, through `connection_pool`, or through
  Active Record.

If the PostgreSQL version is not supported, `installSchema` refuses it before it starts. The error
gives the version of the server. Thus, you do not get a syntax error halfway through the
installation.

Each SDK is a package for the language of your application. Install the SDK. Each package includes
its default PostgreSQL driver.

Add a database adapter only if the process uses that integration. The adapters are
`@stablemates/workhorse-drizzle`, `@stablemates/workhorse-prisma`, `@stablemates/workhorse-typeorm`,
`@stablemates/workhorse-kysely`, and `@stablemates/workhorse-knex`.

Add `@stablemates/workhorse-dashboard` to put the operator interface in your own server. You also
need it to run [the standalone console](/docs/dashboard). Both serve the same packaged application.
The core package treats this package as an optional peer. Thus, an installation with only workers
does not include the browser bundle.

In a TypeScript application, `workhorse init` can write the first configuration for you. It examines
the project, writes a worker configuration, and shows how to mount the dashboard. It does not change
your routes or your package manifest.

```bash
npx --package @stablemates/workhorse workhorse init
```

## Give Workhorse a database

Workhorse creates each object in a schema with the name `workhorse`. The role that connects must
have permission to create this schema. It must also have permission to create the tables, indexes,
partitions, and functions in the schema.

Your process gives the connection through its usual configuration. Usually this is a `pg` `Pool`
that uses `DATABASE_URL`. The CLI reads `--database-url` first, then `WORKHORSE_DATABASE_URL`, then
`DATABASE_URL`.

## Run the schema tool at the version of the application

Only the TypeScript package contains the schema tool. The tool changes the database that your
application reads. Thus, the version of the tool is a part of the deployment. If the tool is older
than the application, the application refuses the schema, and the deployment fails.

A TypeScript project does not need a pinned version, because the binary is its own dependency:

```bash
npm exec --no -- workhorse schema install
```

The `--no` option makes this command safe. The command runs the `workhorse` binary in
`node_modules`, or it fails. It does not download a package. If your package manager is pnpm, use
`pnpm exec workhorse …`. If it is Yarn, use `yarn workhorse …`. The project has only one version of
the tool, so the versions cannot become different.

A Python, Go, Rust, or Ruby project has no `node_modules` that holds the binary. Thus, the command
gives the package and the version:

```bash
npx --package @stablemates/workhorse@0.7.1 workhorse schema install
```

Use the version of the Python package, the Go module, the `workhorse` crate, or the Ruby gem that
your application uses. All the SDKs release together from one commit, so their versions are the
same.

The `--package` option also tells `npx` where the binary comes from. Without it, `npx` looks for a
package with the name `workhorse`, and a different owner has that package.

Each command refuses an unknown option. Each command accepts `--flag value` and `--flag=value`. The
help of a command stops before the CLI connects to PostgreSQL.

## Install the schema in a new database

If the database is new, install the schema from a deployment step. TypeScript deployment code can
call the same step as `installSchema`.

```ts
import { installSchema, Pool } from "@stablemates/workhorse";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
await installSchema(pool);
await pool.end();
```

`installSchema` is for a clean database. If a `workhorse` schema already exists, `installSchema`
continues only if the schema has exactly the current version and no legacy relations. It refuses a
mixed schema, a schema without a version, and an older schema. It never upgrades a schema. To
upgrade, migrate the schema.

## Migrate an installed schema

A migration changes an installed schema to the version of a new release. Run `migrateSchema` from a
deployment step, before the processes of the new release start. It applies the migration steps of
the package in sequence. Each step is immutable and goes only forward.

```ts
import { migrateSchema } from "@stablemates/workhorse";

await migrateSchema(pool);
```

The migration refuses these schemas:

- a missing schema;
- a version below the supported baseline;
- a version after the last step of this release;
- a plan with a gap between two steps.

Each step commits one version in its own transaction and holds an advisory lock. If a step fails,
its transaction rolls back. Thus, when you run the migration again, it continues from the recorded
version. The CLI gives the same step as `workhorse schema migrate`. If the schema is already
current, the migration does not change it. A development schema at a retired version below the
baseline must be reset.

### Upgrade a 0.4.x database offline

The upgrade from 0.4.x to 0.5.0 includes a contract step, so you cannot do it as a rolling
deployment. `workhorse schema migrate` stops before that step. After the step, a 0.4.x worker fails.
Use the CLI of the release that you upgrade to.

1. Stop every worker and every producer.
2. Run `workhorse schema migrate`. It stops at schema version 24 and reports the pending contract
   step.
3. Run `workhorse schema contract --yes`. It applies the contract step and reaches version 25.
4. Run `workhorse schema migrate` again. It applies the additive steps. The schema then has the
   version of the new release, for example version 43 for 0.5.0.
5. Start the new release.

After the upgrade, each queue stays on the full tier. After 0.5.0, a minor upgrade is a usual
rolling deployment again.

## Verify the schema before the new release starts

The migration and the start of the new release are two different steps. Check the schema between
them:

1. Run the migration.
2. Run `schema status --json`.
3. If the command exits with a value that is not zero, stop the deployment.

```bash
npm exec --no -- workhorse schema migrate
npm exec --no -- workhorse schema status --json
```

The command exits with 0 if this build accepts the installed schema. It exits with 1 if this build
refuses the schema, or if the PostgreSQL major version is too old. The JSON output gives the schema
and the PostgreSQL results separately. This part of the output is for a current schema of release
0.7.1:

```json
{
  "schema": {
    "installedVersion": 64,
    "expectedVersion": 64,
    "minimumVersion": 54,
    "state": "current",
    "compatible": true,
    "refusal": null,
    "refusalCode": null
  },
  "postgres": { "supported": true, "level": "supported-tested" }
}
```

Use `schema.compatible` to decide if the deployment continues. Write `schema.refusal` to your log.
`schema.refusalCode` gives the same refusal as a code.
`schema.state` tells you how the installed version compares with the expected version.

The state `ahead` is not a failure. A rolling deployment migrates first. Thus, the processes of the
earlier release find a newer schema until the deployment is complete. They continue to operate,
because inside a major line a migration only adds.

## Create a development database without Node.js

The schema tool is available only on npm. Thus, a Python, Go, Rust, or Ruby developer has no local
command that creates the database. In its place, each `vX.Y.Z` tag attaches the clean-install file
`schema.sql` to its GitHub release. Do these steps:

1. Download the file from the release of the version that your application uses.
2. Apply the file with `psql`.

```bash
curl -fLO https://github.com/stablemates/workhorse/releases/download/v0.7.1/schema.sql
psql "$DATABASE_URL" -f schema.sql
```

The [`v0.7.1` release](https://github.com/stablemates/workhorse/releases/tag/v0.7.1) has the file.
If you use a different version, change the two version numbers together. The file creates the
schema that the SDK of the same release expects.

Use this procedure only for development. The CLI applies the same file, but `psql` does none of the
checks of the CLI. It does not check the PostgreSQL major version. It does not refuse a database
that has a mixed, unversioned, or older `workhorse` schema. It also records no migration history
other than the history that the file writes. For a deployment, use the CLI.

## Check the schema before a runtime starts

An application process or a worker process must check the schema. It must not install the schema.
Thus, no long-running process needs the permission to create database objects. Each SDK has the
check.

<Tabs items={["TypeScript", "Python", "Go", "Rust", "Ruby"]}>
  <Tab value="TypeScript">

    ```ts
    import { assertSchemaCompatible } from "@stablemates/workhorse";

    await assertSchemaCompatible(pool);
    ```

    A refusal throws `SchemaCompatibilityError`, whose `code` names the reason.

  </Tab>
  <Tab value="Python">

    ```python
    from workhorse import assert_schema_compatible

    assert_schema_compatible(connection)
    ```

    An asynchronous application calls the function for its driver, as `AsyncQueue` does. Call the
    function for the type of your connection.

    ```python
    from workhorse import assert_schema_compatible_psycopg

    await assert_schema_compatible_psycopg(connection)
    ```

    ```python
    from workhorse import assert_schema_compatible_asyncpg

    await assert_schema_compatible_asyncpg(connection)
    ```

    A refusal raises `ProtocolCompatibilityError`, whose `code` names the reason.

  </Tab>
  <Tab value="Go">

    ```go
    executor := workhorse.NewPGXExecutor(pool)
    if err := workhorse.AssertSchemaCompatible(ctx, executor); err != nil {
    	return err
    }
    ```

    A refusal is a `*workhorse.CompatibilityError`, whose `Code` names the reason.

  </Tab>
  <Tab value="Rust">

    ```rust
    let queue = Queue::connect(url, "default").await?;
    queue.assert_compatible().await?;
    ```

    A refusal is `workhorse::Error::Compatibility`, whose `code` names the reason.

  </Tab>
  <Tab value="Ruby">

    ```ruby
    queue = Stablemates::Workhorse::Queue.new(PG.connect(ENV.fetch("DATABASE_URL")))
    queue.assert_compatible
    ```

    A refusal is `Stablemates::Workhorse::CompatibilityError`, whose `code` names the reason.

  </Tab>
</Tabs>

The check reads the installed version. It does not create or change anything. If the schema is
missing, the error tells you to install it. If the version is not the version of the runtime, the
error gives the two versions.

You can also read the values directly, for example for a health endpoint. In TypeScript, compare
the result of `readSchemaVersion` with the exported constant `WORKHORSE_SCHEMA_VERSION`.

```ts
import { readSchemaVersion, WORKHORSE_SCHEMA_VERSION } from "@stablemates/workhorse";

const installed = await readSchemaVersion(pool); // number, or null when absent
console.log({ installed, expected: WORKHORSE_SCHEMA_VERSION });
```

To check the PostgreSQL server, call `readPostgresSupport`. It puts the connected PostgreSQL in one
of three classes: supported and tested, supported but not tested, or not supported.
