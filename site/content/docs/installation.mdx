title: Installation
description: Add the core package, install its PostgreSQL schema, and check compatibility before a process starts.
---

Workhorse stores durable state in your database, so installing it is a schema change — and schema
changes deserve a deliberate deployment step, not a side effect of the first process to boot. This
page separates the two actions: installation, which creates database objects once, and the startup
check every runtime process should make instead.

## Requirements

Every SDK runs on stock PostgreSQL without an extension. The shared schema CLI runs on Node.js
during deployment, including when the application itself runs Python or Go.
[Compatibility](/docs/compatibility) names every supported version, and is the only page that does.
Choose the runtime that matches your application:

- TypeScript needs an ESM application.
- Python works through synchronous or asynchronous drivers.
- Go supports pgx or `database/sql`.

`installSchema` refuses an unsupported PostgreSQL up front, naming the server's version, rather
than failing partway through with a syntax error that reads like a Workhorse bug.

## Add the package

Install the SDK. Each package includes its default PostgreSQL driver.

<Tabs items={["TypeScript", "Python", "Go"]}>
  <Tab value="TypeScript">

    ```bash
    npm install @stablemates/workhorse
    ```

  </Tab>
  <Tab value="Python">

    ```bash
    pip install stablemates-workhorse
    ```

    Use the `asyncpg` extra when that is your application's driver instead of Psycopg.

    Your application never installs the schema. A deployment step installs it once, and that step
    runs on Node.js.

  </Tab>
  <Tab value="Go">

    ```bash
    go get github.com/stablemates/workhorse/go
    ```

    Your application never installs the schema. A deployment step installs it once, and that step
    runs on Node.js.

  </Tab>
</Tabs>

Add a database adapter (`@stablemates/workhorse-drizzle`, `@stablemates/workhorse-prisma`, `@stablemates/workhorse-typeorm`,
`@stablemates/workhorse-kysely`) or `@stablemates/workhorse-dashboard` only when that integration belongs in the same
process.

For TypeScript applications, `workhorse init` can scaffold the wiring. It inspects the project,
writes a worker configuration, and prints a dashboard mount — but it leaves your routes and package
manifest alone.

```bash
npx --package @stablemates/workhorse workhorse init
```

## Give Workhorse a database

Workhorse creates every object inside a schema named `workhorse`. The connecting role must be able
to create that schema plus its tables, indexes, partitions, and functions.

Your process supplies the connection through its normal configuration — typically a `pg` `Pool`
built from `DATABASE_URL`. The CLI reads `--database-url`, then `WORKHORSE_DATABASE_URL`, then
`DATABASE_URL`.

## Run the schema tool at the application's version

The schema tool ships only in the TypeScript package, and it changes the database your application
reads. Those two facts make its version part of the deployment: a tool older than the application
leaves a schema the application refuses to start against, and the deploy fails.

A TypeScript project needs no pin, because the binary is its own dependency:

```bash
npm exec --no -- workhorse schema install
```

`--no` is what makes that safe. It runs the `workhorse` in `node_modules` or fails; it never
fetches anything. Use `pnpm exec workhorse …` or `yarn workhorse …` if that is your package
manager. The version cannot drift, because there is only one.

A Python or Go project has no `node_modules` to resolve the binary from, so it names both the
package and the version:

```bash
npx --package @stablemates/workhorse@0.1.0 workhorse schema install
```

Pin that to the version of `stablemates-workhorse` or `github.com/stablemates/workhorse/go` the
application depends on. All three release together from one commit, so the numbers are the same.
`--package` also names where the binary comes from: without it `npx` looks for a `workhorse`
package by that bare name, which belongs to someone else.

Every command rejects unknown options and accepts both `--flag value` and `--flag=value`.
Command-specific help exits before the CLI connects to PostgreSQL.

## Install the schema deliberately

When the target database is new, install from a deployment step. TypeScript deployment code can
call the same step as `installSchema`.

```ts
import { installSchema, Pool } from "@stablemates/workhorse";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
await installSchema(pool);
await pool.end();
```

`installSchema` targets a clean database. If a `workhorse` schema already exists, it proceeds only
when that schema carries exactly the current version and no legacy relations; anything mixed,
unversioned, or older is refused. It never treats installation as an upgrade path.

## Migrate an installed schema

Run `migrateSchema` from a deployment step before processes from the new release start. It applies
the package's immutable, forward-only migration steps in order.

```ts
import { migrateSchema } from "@stablemates/workhorse";

await migrateSchema(pool);
```

The migration refuses a missing schema, a version below its supported baseline, a version beyond
the last step this release carries, or a gap in the ordered plan. Each step commits one version in its own transaction behind an
advisory lock, and a failed step rolls back atomically, so a rerun resumes from the recorded
version. The same step is available from the CLI as `workhorse schema migrate`, and an
already-current schema is left unchanged. Development schemas at retired versions below the
baseline still require a reset.

## Verify before the new release starts

Migrating and starting are two steps, and a deploy should not cross between them on hope. Run
`schema status --json` after the migration and before the first process from the new release
starts, and fail the deploy on a non-zero exit.

```bash
npm exec --no -- workhorse schema migrate
npm exec --no -- workhorse schema status --json
```

The command exits 0 when this build accepts the installed schema, and 1 when it would refuse it or
when PostgreSQL is below the required major. The JSON separates the two questions:

```json
{
  "schema": {
    "installedVersion": 1,
    "expectedVersion": 1,
    "minimumVersion": 1,
    "state": "current",
    "compatible": true,
    "refusal": null
  },
  "postgres": { "supported": true, "level": "supported-tested" }
}
```

Read `schema.compatible` for the gate and `schema.refusal` for the sentence to log. `schema.state`
says where the installed version sits, and `ahead` is not a failure: a rolling deployment migrates
first, so processes from the previous release meet a schema ahead of them until the rollout
finishes, and they keep working because inside a major line a migration only adds.

## Create a development database without Node.js

Every release attaches `schema.sql` to its
[GitHub release](https://github.com/stablemates/workhorse/releases). A Python or Go developer with
no Node.js toolchain can create a database from it directly:

```bash
psql "$DATABASE_URL" -f schema.sql
```

Use this for development only. The file is the same clean-install artifact the CLI applies, but
`psql` applies none of the CLI's guards: it does not check the PostgreSQL major, and it does not
refuse a database that already holds a mixed, unversioned, or older `workhorse` schema. It also
records no migration history beyond what the file itself writes. Deployments run the CLI.

## Check before a runtime starts

Application and worker processes should verify the schema, never install it. That split keeps the
destructive authority to create database objects out of every long-lived process. Every SDK ships
the check.

<Tabs items={["TypeScript", "Python", "Go"]}>
  <Tab value="TypeScript">

    ```ts
    import { assertSchemaCompatible } from "@stablemates/workhorse";

    await assertSchemaCompatible(pool);
    ```

    A refusal throws `SchemaCompatibilityError`, whose `code` names the reason.

  </Tab>
  <Tab value="Python">

    ```python
    from workhorse import assert_schema_compatible

    assert_schema_compatible(connection)
    ```

    Asynchronous applications name their driver, the way `AsyncQueue` does. Call the one that
    matches the connection you hold.

    ```python
    from workhorse import assert_schema_compatible_psycopg

    await assert_schema_compatible_psycopg(connection)
    ```

    ```python
    from workhorse import assert_schema_compatible_asyncpg

    await assert_schema_compatible_asyncpg(connection)
    ```

    A refusal raises `ProtocolCompatibilityError`, whose `code` names the reason.

  </Tab>
  <Tab value="Go">

    ```go
    executor := workhorse.NewPGXExecutor(pool)
    if err := workhorse.AssertSchemaCompatible(ctx, executor); err != nil {
        return err
    }
    ```

    A refusal is a `*workhorse.CompatibilityError`, whose `Code` names the reason.

  </Tab>
</Tabs>

The check reads the installed version without creating or changing anything. If the schema is
missing, it says so and points at the installation step; if the version differs from the runtime's,
it names both.

When you want the raw values instead of an assertion — for a health endpoint, for example —
TypeScript exposes `readSchemaVersion` to compare against the exported `WORKHORSE_SCHEMA_VERSION`
constant.

```ts
import { readSchemaVersion, WORKHORSE_SCHEMA_VERSION } from "@stablemates/workhorse";

const installed = await readSchemaVersion(pool); // number, or null when absent
console.log({ installed, expected: WORKHORSE_SCHEMA_VERSION });
```

For the server side of the same question, `readPostgresSupport` classifies the connected PostgreSQL
as supported and tested, supported but untested, or unsupported.
