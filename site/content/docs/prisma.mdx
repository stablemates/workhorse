---
title: "Prisma: enqueue background tasks in the same transaction"
description: Enqueue Workhorse tasks inside Prisma interactive transactions, so your data and your tasks commit together.
---

The `@stablemates/workhorse-prisma` package connects Workhorse to Prisma Client. With it, your
application enqueues a task inside a Prisma interactive transaction. Your data and the task then
commit together, or neither commits.

This prevents two errors. Without a shared transaction, a task can exist for a row that rolled back.
Also, a row can commit and its task can be lost.

## Check the requirements

- Prisma Client 6.
- PostgreSQL as the Prisma data source.
- The Workhorse schema in the database. [Installation](/docs/installation) tells you how to install
  it.

## Install the package

```bash
pnpm add @stablemates/workhorse-prisma @prisma/client
```

## Create the adapter

Give your Prisma client to `createPrismaAdapter`.

```ts
import { PrismaClient } from "@prisma/client";
import { createPrismaAdapter } from "@stablemates/workhorse-prisma";

const prisma = new PrismaClient();
const workhorse = createPrismaAdapter(prisma);
```

The adapter gives you `queue`, `admin`, `forTransaction`, `adminForTransaction`, `createWorker`, and
`close`.

## Enqueue a task in a Prisma transaction

Call `forTransaction` with the transaction client that Prisma gives to your callback. The task then
uses that transaction.

```ts
await prisma.$transaction(async (tx) => {
  const account = await tx.account.create({ data: { email } });
  await workhorse.forTransaction(tx).enqueue("account.created", {
    accountId: account.id,
  });
});
```

If the callback throws an error, Prisma rolls back the account and the task.

To enqueue a task without a transaction, use `workhorse.queue.enqueue`.

## Run the worker in its own process

Run workers in their own process, not in your web server. A worker needs a node-postgres pool,
because Prisma does not give one. The worker uses this pool for its heartbeat and for wake-up
notifications. Busy handlers then cannot block the heartbeat.

```ts
import { defineWorkerProcess, Pool } from "@stablemates/workhorse";
import { PrismaClient } from "@prisma/client";
import { createPrismaAdapter } from "@stablemates/workhorse-prisma";

const databaseUrl = process.env.DATABASE_URL;
if (!databaseUrl) throw new Error("Set DATABASE_URL");

export default defineWorkerProcess({
  async adapter() {
    const pool = new Pool({ connectionString: databaseUrl });
    const database = new PrismaClient({ datasources: { db: { url: databaseUrl } } });
    return createPrismaAdapter(database, {
      pool,
      close: async () => {
        await database.$disconnect();
        await pool.end();
      },
    });
  },
  workers: [
    {
      options: { queue: "default", concurrency: 1 },
      configure(worker) {
        worker.handle("account.created", async (payload) => {
          // Do the work here.
          return { ok: true };
        });
      },
    },
  ],
});
```

Start the process with `workhorse worker --config <compiled file>`. If `workhorse init` finds
Prisma, it writes this file for you. [Worker processes](/docs/worker-processes) tells you more.

If you cannot give a pool, set `sharedHeartbeats` on the worker. The worker then sends heartbeats
through Prisma and polls for new tasks.

<details>
<summary>Reference: worker connections</summary>

- `createPrismaAdapter` accepts the option `pool`.
- A dedicated heartbeat connection needs a pool of at least 3 connections. If the pool is smaller,
  the worker does not start unless you set `sharedHeartbeats`.

More detail: [Overview: ORM adapters](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#orm-adapters),
[Overview: Connection budgets per language](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#connection-budgets-per-language).

</details>

## Handle database errors

If a database call fails, the adapter throws a `PrismaQueryError`. The error keeps the SQL
statement, the original error as `cause`, and the PostgreSQL error code as `code`. Workhorse
conflicts, such as an idempotency conflict, keep their own error classes.

<details>
<summary>Reference: errors</summary>

- `PrismaQueryError` extends `QueryError`. It does not copy parameter values into its message.
- The code search prefers `meta.code` over the outer raw-query code of Prisma, such as `P2010`.

More detail: [Overview: Prisma and TypeORM queryables](https://github.com/stablemates/workhorse/blob/main/docs/architecture/overview.md#prisma-and-typeorm-queryables).

</details>

## Close the client that the adapter owns

The adapter does not disconnect your Prisma client. Give a `close` callback only when the adapter
owns the client.

## Install the Workhorse schema with the Workhorse tools

Prisma migrations do not manage the Workhorse schema. Install and upgrade the schema with the
Workhorse tools.

## Run the integration tests

This integration is **verified**. Continuous integration runs the Workhorse adapter conformance
suite against Prisma on every change. The suite opens real transactions in PostgreSQL. The
[integrations list](/docs/integrations) shows the Prisma version that the tests use.

To run the suite in this repository, use this command:

```bash
pnpm test:database:typescript typescript/adapter-conformance/test/conformance.test.ts typescript/adapter-conformance/test/integration.test.ts
```
