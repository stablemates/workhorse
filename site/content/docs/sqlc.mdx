title: sqlc (Go)
description: Use the queries that sqlc generates and Workhorse enqueue in one pgx transaction that the caller owns.

sqlc is a tool that generates Go code for your business queries. Workhorse accepts tasks through its
existing Go executor. The generated queries and Workhorse can use the same transaction, so you need
no outbox and no other adapter package. This page is a tested recipe. The
[transactional enqueue](/docs/enqueue) page owns the general commit and rollback rules.

## Give the same transaction to sqlc and Workhorse

The generated `Queries.WithTx(tx)` method of sqlc uses the transaction instead of the original pool.
Give the same `pgx.Tx` to `NewPGXExecutor`.

```go
tx, err := pool.Begin(ctx)
if err != nil {
	return err
}
defer func() { _ = tx.Rollback(context.Background()) }()

order, err := queries.WithTx(tx).CreateOrder(ctx, parameters)
if err != nil {
	return err
}
queue := workhorse.NewQueue(workhorse.NewPGXExecutor(tx), "recipes")
if _, err := queue.Enqueue(ctx, "order.accepted", map[string]any{
	"orderId": order.ID.String(),
}); err != nil {
	return err
}
return tx.Commit(ctx)
```

The [runnable example](https://github.com/stablemates/workhorse/tree/main/go/examples/sqlc) supplies
the imports, the parameters, and the setup instructions. Before you run its CLI, apply its business
schema to a disposable database. That database must already have the Workhorse schema. The example
uses a fixed UUID, so a second run fails unless the business schema is new.

## Own the transaction in your code

Your code owns the transaction lifecycle and the return of the connection to the pool. Workhorse
does not begin, commit, roll back, or close the transaction that it borrows.

- Return each enqueue error before the commit. This includes client-side payload contract
  failures, which do not abort the PostgreSQL transaction.
- Do not keep a transaction-bound queue or generated `Queries` after the transaction ends.
- Do not call the queries of the original pool inside the atomic operation.

## Roll back an inner write with a savepoint

A savepoint is a named point inside a transaction. You can roll back to it and keep the outer
transaction. The fixture tests explicit nested PostgreSQL savepoints on the same transaction.

If you roll back to the inner savepoint, PostgreSQL removes the inner business row and its task.
The outer transaction can continue. If you release both savepoints, the outer rollback still
removes their writes. After an ordinary SQL error, roll back to a savepoint or roll back the
transaction before you send more queries.

## Recover after a cancelled context

The effect of a cancelled context depends on when the cancellation occurs.

- If the context is cancelled before the query starts, the fixture shows that the executor does not
  roll back the transaction.
- If the context is cancelled while a query runs, pgx can abort the transaction or discard its
  connection.

**Example.** A lock blocks an enqueue, and the request context is cancelled.

1. Your code writes the order and starts the enqueue.
2. The enqueue waits for a lock.
3. The context is cancelled while the enqueue waits.
4. Your code rolls back the transaction. PostgreSQL removes the order and the task.
5. Your code repeats the operation in a new transaction, and the new transaction succeeds.

After a cancellation during a query, roll back and use a new transaction. The recipe does not
promise recovery to a savepoint after the wire protocol cancels a query. Use a context that is not
cancelled for the rollback.

## Run workers in a separate process

Run workers in a separate process with their own pool and their own heartbeat connections. Generated
request-side queries do not replace a worker executor.

## Generate the queries and run the fixture

From a configured repository checkout, run these commands:

```sh
pnpm go:sqlc:generate
pnpm go:sqlc:check
WORKHORSE_REQUIRE_DATABASE=1 pnpm exec tsx scripts/with-env.ts \
  go -C go test -count=1 -v ./examples/sqlc
```

The business inputs are `go/examples/sqlc/schema.sql`, `queries.sql`, and `sqlc.yaml`. The output in
`generated/` is checked in. It contains only application queries, never generated Workhorse protocol
calls. Workhorse still uses its own maintained SQL catalogue and its own enqueue validation.

The generate command downloads the official sqlc release archive and verifies it. The check command
generates the code again in a temporary directory and compares it with the checkout. It does not
change the checkout. The static CI lane runs the check one time for each change. The generator adds
no runtime dependency to the SDK.

The fixture installs both schemas in an isolated scratch database and runs the actual CLI.

The Go CI suite of the repository finds the recipe and type-checks the generated queries with it.
The recipe is not a new Workhorse package. It does not certify a PostgreSQL provider.

**Generation.**

- `pnpm go:sqlc:generate` downloads the official release archive. It pins the archive by version and
  by the SHA256 for each platform. Then it verifies the version of the binary.
- `pnpm go:sqlc:check` generates in a temporary directory. It compares the file names and the exact
  bytes and does not rewrite the checkout.
- Supported platforms: Linux and macOS, on amd64 and arm64. A run without a cache needs GitHub
  access and `tar`.

**Fixture coverage.**

- backend PID, transaction identity, and the task `xmin`
- invisibility to an independent connection, joint commit and rollback, and lifecycle ownership
- native UUID, JSONB, nullable text, nullable enqueue reasons, ordered batches, and structured
  errors
- The native driver exposes `P1001`. `Queue` translates it into `EnqueueIdempotencyConflictError`
  with its structured details.
- Ordinary `22012` errors and aborted-transaction `25P02` errors keep their native SQLSTATE.
- A lock in the scratch database blocks a real enqueue. This proves cancellation, joint rollback,
  and recovery in a new transaction.

**Not tested.** The `database/sql` output of sqlc, custom type overrides, other generators, other
drivers, providers, and poolers. Each needs its own proof.
