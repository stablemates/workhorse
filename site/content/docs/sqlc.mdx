title: sqlc (Go)
description: Use generated application queries and Workhorse in one caller-owned pgx transaction.

sqlc generates your business queries; Workhorse accepts tasks through its existing Go executor.
Both can use the same transaction without an outbox or another adapter package.
This page is a tested recipe appendix to [transactional enqueue](/docs/enqueue), which owns commit and rollback guidance.

## Use the tested baseline

The maintained example pins sqlc **v1.31.1**, pgx **v5.11.0**, and the **pgx/v5** generation mode.
The local real-database proof uses Go **1.25.14** and PostgreSQL **18.6**.
The repository's existing Go CI suite discovers and typechecks the generated queries with the recipe.
This is not a new Workhorse package or certification of a PostgreSQL provider.

The business inputs are `go/examples/sqlc/schema.sql`, `queries.sql`, and `sqlc.yaml`.
The checked-in output under `generated/` contains only application queries, never generated Workhorse protocol calls.
Workhorse still uses its own maintained SQL catalogue and enqueue validation.

## Bind both callers to the same transaction

sqlc's generated `Queries.WithTx(tx)` selects the transaction instead of the original pool.
Pass that exact `pgx.Tx` to `NewPGXExecutor` too.

```go
tx, err := pool.Begin(ctx)
if err != nil {
	return err
}
defer func() { _ = tx.Rollback(context.Background()) }()

order, err := queries.WithTx(tx).CreateOrder(ctx, parameters)
if err != nil {
	return err
}
queue := workhorse.NewQueue(workhorse.NewPGXExecutor(tx), "recipes")
if _, err := queue.Enqueue(ctx, "order.accepted", map[string]any{
	"orderId": order.ID.String(),
}); err != nil {
	return err
}
return tx.Commit(ctx)
```

The [runnable example](https://github.com/stablemates/workhorse/tree/main/go/examples/sqlc) supplies imports, parameters, and setup instructions.
Apply its business schema to an explicitly disposable database with Workhorse already installed before running its CLI.
The fixed example UUID makes a repeated run fail unless the business schema is fresh.

The caller owns lifecycle and pool return. Workhorse does not begin, commit, roll back, or close the borrowed transaction.
Return every enqueue error, including client-side contract failures that leave PostgreSQL usable.
Do not keep a transaction-bound queue or generated `Queries` after its transaction ends.
Do not call the original pool's queries inside the atomic operation.

## Preserve savepoint and cancellation boundaries

The fixture tests explicit nested PostgreSQL savepoints on the same transaction.
An inner rollback removes the inner business row and task; the outer transaction can continue.
Releasing both savepoints still leaves their writes subject to the outer rollback.
An ordinary SQL error requires rollback to a savepoint or rollback of the transaction before more queries.

A context cancelled before dispatch is tested without executor-owned rollback.
An in-flight cancellation is different: pgx may abort the transaction or discard its connection.
The caller rolls back and uses a fresh transaction; the recipe does not promise savepoint recovery after wire cancellation.
Use an uncancelled context for owner cleanup.

Run workers in a separate process with their own pool and heartbeat connections.
Generated request-side queries are not a worker executor replacement.

## Reproduce generation and proof

From a configured repository checkout:

```sh
pnpm go:sqlc:generate
pnpm go:sqlc:check
WORKHORSE_REQUIRE_DATABASE=1 pnpm exec tsx scripts/with-env.ts \
  go -C go test -count=1 -v ./examples/sqlc
```

Generation downloads the official release archive pinned by version and platform SHA256, then verifies the binary version.
Check mode regenerates in a temporary directory and compares file names and exact bytes without rewriting the checkout.
Linux and macOS on amd64 and arm64 are supported by this command; a cold run requires GitHub access and `tar`.
The existing static CI lane runs the drift check once per change. The generator adds no SDK runtime dependency.

The fixture installs both schemas in an isolated scratch database and runs the actual CLI.
It checks backend PID, transaction identity, task `xmin`, independent invisibility, joint commit/rollback, and lifecycle ownership.
Native UUID, JSONB, nullable text and enqueue reasons, ordered batches, and structured errors are covered too.
The native driver exposes `P1001`; `Queue` translates it into `EnqueueIdempotencyConflictError` and its structured details.
Ordinary `22012` and aborted-transaction `25P02` errors retain their native SQLSTATE.
A scratch-only lock blocks a real enqueue to prove cancellation, joint rollback, and fresh-transaction recovery.

Only pgx/v5 generation with the pinned types is tested, not sqlc's `database/sql` output or custom type overrides.
Other generators, drivers, providers, and poolers need their own proof.
