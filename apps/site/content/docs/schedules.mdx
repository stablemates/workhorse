---
title: How do I run recurring jobs?
description: Synchronize named cron definitions during deployment and let any matching worker fire them safely.
---

Workhorse treats schedules as desired deployment state. Your application declares a complete
namespace, and PostgreSQL reconciles stored definitions to match it.

## Synchronize the namespace

Call `Queue.syncSchedules` during deployment with every definition the namespace should contain.
Omitted names become disabled when pruning is enabled.

```ts
await queue.syncSchedules("billing-production", [
  {
    name: "invoice-run",
    schedule: billingCron,
    job: {
      type: "invoice.generate",
      queue: "billing",
      payload: { scope: "due" },
    },
  },
]);
```

The namespace prevents one service from changing another service's definitions. Cron validation
happens before the write, so one invalid expression cannot leave a partial deployment.

Use non-pruning synchronization only when you deliberately want an additive update. The normal
deployment path should supply the complete namespace so code remains the owner of intent.

## Let workers evaluate schedules

A `Worker` evaluates only the namespaces in `WorkerOptions.scheduleNamespaces`.

```ts
const worker = new Worker(queue, {
  scheduleNamespaces: ["billing-production"],
});
```

No separate scheduler service or PostgreSQL extension is required. Workers parse cron expressions
and call `fire_schedule_v1` for each planned occurrence.

## Why do competing workers create one job?

Each occurrence has a durable key made from its namespace, schedule name, and planned time. When
several workers race, PostgreSQL makes every call converge on one job identity.

A definition revision protects rolling deployments. If a worker fires an old revision after a
deployment changes the definition, PostgreSQL turns that stale call into a no-op.

If the worker fleet is unavailable, schedules do not fire on time. Catch-up is bounded when workers
return, so schedules provide durable recurring work rather than hard real-time alarms.

## What happens after firing?

The occurrence creates an ordinary Workhorse job with the definition's queue, payload, attempt
budget, and retry policy. Its execution still has at-least-once delivery.

Canceling one occurrence does not disable its definition. Use the next synchronization to disable
future occurrences.

`Queue.schedules` reads stored definitions for operator tools. `Queue.fireSchedule` exposes the
revision-fenced operation for tests and controlled integrations.
