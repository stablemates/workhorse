---
title: How do I use Workhorse with Express?
description: Inject queue access into Express requests and bind co-hosted workers to server shutdown.
---

`@workhorse/express` joins a `WorkhorseAdapter` to one Express process. It exposes queue access as
`request.workhorse` and can own co-hosted worker startup and graceful shutdown.

```ts
import express from "express";
import { ExpressWorkhorse, serveWithWorkhorse } from "@workhorse/express";

const workhorse = new ExpressWorkhorse(adapter);
const app = express().use(express.json()).use(workhorse.middleware());

app.post("/jobs", async (request, response) => {
  const id = await request.workhorse.queue.enqueue("email.send", request.body);
  response.json({ id });
});

const server = await serveWithWorkhorse({ app, workhorse, port });
process.once("SIGTERM", () => void server.shutdown());
```

Dedicated worker processes remain the production default. If `ExpressWorkhorse` has worker
definitions, `serveWithWorkhorse` starts them once, and its idempotent `shutdown` drains HTTP
requests and worker handlers before it closes adapter-owned resources.

The dashboard has its own lifecycle. Mount `dashboardNodeMiddleware` from
`@workhorse/dashboard/server` with `app.use`; mounting needs a database connection but no worker
runtime.

Use `workhorse.contextFor(request)` for a caller-owned transaction. Express's global request type
cannot carry the adapter's transaction type, so this method restores the checked bridge.
