---
title: How do I preserve work across retries and waits?
description: Use named checkpoints and durable waits when a handler must survive another activation.
---

Workhorse restarts a handler from its entry point after a retry or durable wait. Named boundaries let
the new activation reuse completed work instead of relying on a saved JavaScript stack.

## Save completed stages with checkpoints

`HandlerContext.checkpoint` looks for a saved value under the supplied name. If none exists, it runs
the operation and stores its JSON result under the current fenced lease.

```ts
worker.handle("order.fulfill", async (payload: { orderId: string }, context) => {
  const charge = await context.checkpoint("charge", () =>
    payments.charge(payload.orderId, {
      idempotencyKey: `charge:${payload.orderId}`,
    }),
  );

  const shipment = await context.checkpoint("shipment", () =>
    logistics.createShipment(payload.orderId, charge.id),
  );

  return { chargeId: charge.id, shipmentId: shipment.id };
});
```

If another activation reaches `charge`, Workhorse returns the stored value. Reusing the same name
with a different value raises `CheckpointConflictError` instead of changing durable evidence.

A checkpoint commits after its operation finishes. If the process dies between an external effect
and that commit, the effect can happen again, so provider calls still need stable idempotency keys.

## Release a worker slot with a durable wait

`HandlerContext.sleep` stores a named relative timer. `HandlerContext.sleepUntil` stores a named
absolute target.

The durable wait removes active ownership and places the job in `scheduled`. The worker slot becomes
free, while the current logical attempt remains open.

```ts
worker.handle("email.follow-up", async (payload: { to: string; followUpAt: string }, context) => {
  await context.checkpoint("welcome", () => mailer.welcome(payload.to));
  await context.sleepUntil("follow-up-window", new Date(payload.followUpAt));
  await context.checkpoint("follow-up", () => mailer.followUp(payload.to));
  return { deliveredTo: payload.to };
});
```

When the timer becomes due, promotion makes the job ready and a worker calls the handler from the
top. The saved `welcome` checkpoint returns without sending that message again.

## Treat names as immutable program state

Checkpoint and wait names belong to the job's durable control flow. Keep them stable across deploys,
because changing a name creates a different boundary.

A repeated relative wait keeps its original duration and wake target. A repeated absolute wait must
keep its original target, while changing the mode or target raises `WaitConflictError`.

`HandlerContext.getCheckpoint` and `getWait` read one boundary. `Queue.listCheckpoints` and
`listWaits` expose retained evidence to operator code.
