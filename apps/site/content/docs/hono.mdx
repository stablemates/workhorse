`@workhorse/hono` owns Workhorse's lifecycle inside one Hono application process: typed middleware,
worker startup, idempotent graceful shutdown, and an optional dashboard mount.

```bash
pnpm add @workhorse/hono hono @hono/node-server
```

## Minimal application

```ts
import { Hono } from "hono";
import { installSchema } from "@workhorse/core";
import { HonoWorkhorse, serveWithWorkhorse } from "@workhorse/hono";

// Installation is an explicit deployment/startup step.
await installSchema(adapter.database);

const workhorse = new HonoWorkhorse(adapter, {
  workers: [
    {
      options: { concurrency: 4 },
      configure(worker) {
        worker.handle("email.send", async (payload: { to: string }) => ({ delivered: payload.to }));
      },
    },
  ],
  onWorkerError: (error, worker) => logger.error({ error }, "worker loop failed"),
});

const app = new Hono().use(workhorse.middleware()).post("/jobs", async (c) => {
  const id = await c.var.workhorse.queue.enqueue("email.send", await c.req.json());
  return c.json({ id }, 202);
});

const server = await serveWithWorkhorse({ fetch: app.fetch, workhorse, port: 3000 });
process.once("SIGTERM", () => void server.shutdown());
```

`adapter` is any `WorkhorseAdapter`: build it with `createWorkhorseAdapter` from `@workhorse/core` or
`createDrizzleAdapter` from [`@workhorse/drizzle`](/docs/drizzle).

## Typed middleware

`workhorse.middleware()` sets `c.var.workhorse`:

```ts
interface HonoWorkhorseContext<TTransaction> {
  readonly queue: Queue;
  forTransaction(transaction: TTransaction): Queue;
}
```

Enqueue inside a request transaction:

```ts
app.post("/accounts", async (c) => {
  const id = await db.transaction(async (tx) => {
    const account = await createAccount(tx, await c.req.json());
    await c.var.workhorse.forTransaction(tx).enqueue("account.created", { id: account.id });
    return account.id;
  });
  return c.json({ id }, 201);
});
```

## Lifecycle

| Method      | Behavior                                                                  |
| ----------- | ------------------------------------------------------------------------- |
| `start()`   | Starts every configured worker once. Idempotent. Run loops go background. |
| `quiesce()` | Stops new claims and waits for in-flight handlers.                        |
| `stop()`    | Quiesces, then closes provider-owned resources. Idempotent.               |

A stopped runtime cannot be restarted; construct a new one.

`serveWithWorkhorse` starts workers and the Node server together and returns
`{ server, shutdown() }`. `shutdown()` is idempotent and orders operations correctly: stop accepting
connections, quiesce workers, wait for in-flight requests, then close provider-owned resources.

If server startup throws, `serveWithWorkhorse` stops the runtime before rethrowing, so a failed boot
does not leak workers or pools.

## Mounting the dashboard

```ts
import { mountWorkhorseDashboard } from "@workhorse/hono";

mountWorkhorseDashboard(app, {
  workhorse,
  path: "/workhorse", // use "/" to own the host root
  environment: "production",
  authorize: (request) => isAdmin(request),
});
```

The mount owns the configured path: the packaged React application, static assets, oRPC API, and SSE
refresh stream.

<Callout type="warn">
  `authorize` is **required** and must explicitly authorize every dashboard, RPC, asset, and
  event-stream request. Workhorse has no built-in authentication, RBAC, or multi-tenancy.
</Callout>

The mount verifies that the installed schema is compatible and returns `503` when it is not. It never
installs or migrates database objects.

See [Dashboard](/docs/dashboard) for options and the standalone React surface.

## Production caveat

Running workers in your web process is convenient, but it couples job capacity to HTTP replica count
and couples two unrelated drains. For production, prefer a dedicated worker process; see
[Workers](/docs/workers) and [Deployment and operations](/docs/operations).
