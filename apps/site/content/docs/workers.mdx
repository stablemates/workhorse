---
title: How should I run workers?
description: Register handlers, choose process boundaries, control how workers take jobs, and drain active work safely.
---

A `Worker` owns a bounded set of handler executions for one queue. Production deployments should
place workers in a dedicated process so job capacity can scale independently from HTTP traffic.

## Register handlers

`Worker.handle` associates a job type with an async function. The returned worker supports chained
registration, while each handler result must be JSON.

```ts
import { Worker } from "@workhorse/core";

const worker = new Worker(queue, { queue: "email" }).handle(
  "email.send",
  async (payload: { to: string }, context) => {
    await mailer.send(payload.to, { signal: context.signal });
    return { deliveredTo: payload.to };
  },
);

await worker.run();
```

The `HandlerContext` exposes the claimed job, its `AbortSignal`, checkpoints, waits, and progress.
Those methods preserve the current fence, so custom handler code cannot accidentally write as a
stale owner.

## Choose concurrency by policy group

`WorkerOptions.concurrency` limits active handlers in one `Worker`. Replicas multiply that capacity.
Use [concurrency policies](/docs/concurrency-policies) for a fleet-wide active budget and
[rate limits](/docs/rate-limits) for a fleet-wide start budget.

Use one multi-slot worker for handlers that share a queue and operational policy. Add another worker
when work needs a different queue, lease policy, retry override, schedule namespace, or handler set.

Each active job owns its own heartbeat loop and fence generation. The [core concepts](/docs/concepts)
guide owns the lease explanation; the practical consequence is that one failed slot does not transfer
ownership from another.

## Use a dedicated process

`defineWorkerProcess` describes the adapter and worker configurations. `runWorkerProcess` adds signal
handling and process supervision, while the `workhorse worker` CLI loads the compiled definition.

```ts
import { createWorkhorseAdapter, defineWorkerProcess } from "@workhorse/core";

export default defineWorkerProcess({
  adapter: () => createWorkhorseAdapter(adapterOptions),
  workers: [
    {
      options: { queue: "email" },
      configure(worker) {
        worker.handle("email.send", sendEmail);
      },
    },
  ],
});
```

The process owns its database resources, worker loops, optional probes, and shutdown. Compile the
configuration before the CLI imports it because the CLI does not install a TypeScript loader.

## Pause and stop for different reasons

`Worker.pause` stops the local worker from asking for jobs while active handlers continue.
`Worker.resume` lets it ask again, and `Worker.stop` drains active work before `run` resolves.

`Queue.setWorkerPaused` stores an operator request in `worker_registry`. A worker receives it during
registration refresh, so a dashboard can pause a process that runs elsewhere.

When an operator asks a worker to pause, the request belongs to one process incarnation. Use
`Queue.pauseQueue` when a replacement worker must also stop asking for work.

## Read fleet state carefully

`Queue.listWorkers` reads the durable registry, while `Worker.runtimeState` reads the local process.
Registry slot counts are recent observations rather than synchronous views of another event loop.

Unless a process manager guarantees uniqueness, leave `workerId` generated. Reusing one identity
across live replicas creates an ownership collision.
