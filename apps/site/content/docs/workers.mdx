A `Worker` is a bounded-concurrency polling client of the durable protocol. PostgreSQL distributes
ready rows between workers with `SKIP LOCKED`; each instance claims only enough jobs to fill its local
slots.

## Creating a worker

```ts
import { Worker } from "@workhorse/core";

const worker = new Worker(queue, {
  workerId: "email-1",
  queue: "email",
  concurrency: 4,
}).handle("email.send", async (payload: { to: string }, context) => {
  return { deliveredTo: payload.to };
});

await worker.run();
```

`handle()` returns the worker, so registrations chain. A handler's return value must be
JSON-serializable and becomes the job's immutable terminal result.

## `WorkerOptions`

| Option                  | Default               | Meaning                                                            |
| ----------------------- | --------------------- | ------------------------------------------------------------------ |
| `queue`                 | `"default"`           | Queue name used for claims                                         |
| `workerId`              | `worker-<pid>-<uuid>` | Durable lease owner identity; must be unique among live workers    |
| `concurrency`           | `1`                   | Integer 1 to 100; concurrent handler executions in this instance   |
| `leaseMs`               | `30_000`              | Ownership granted by claim and each accepted heartbeat             |
| `heartbeatMs`           | `leaseMs / 3`         | Local heartbeat interval; must be less than `leaseMs`              |
| `pollMs`                | `250`                 | Idle polling delay                                                 |
| `maintenanceIntervalMs` | `1_000`               | Minimum delay between tick/schedule passes; at least 100           |
| `maintenanceTaskPollMs` | `60_000`              | Minimum delay between background maintenance eligibility checks    |
| `onMaintenance`         | –                     | Receives one telemetry event per SQL maintenance phase             |
| `scheduleNamespaces`    | `[]`                  | Namespaces whose schedules this worker evaluates                   |
| `scheduleCatchupLimit`  | `100`                 | Max missed occurrences fired per schedule per pass (1 to 10,000)   |
| `retryDelayMs`          | –                     | Number or `(attempt, job) => number \| undefined` backoff override |
| `failpoint`             | –                     | Test-only deterministic crash hook                                 |

Invalid combinations throw at construction: `heartbeatMs >= leaseMs`, out-of-range concurrency, and
cadences below 100 ms are rejected immediately.

## Handler context

```ts
interface HandlerContext<TPayload> {
  job: ClaimedJob<TPayload>;
  signal: AbortSignal;
  getCheckpoint<T>(name: string): Promise<JobCheckpoint<T> | null>;
  getWait(name: string): Promise<JobWait | null>;
  checkpoint<T>(name: string, operation: () => Promise<T> | T): Promise<T>;
  sleep(name: string, durationMs: number): Promise<void>;
  sleepUntil(name: string, wakeAt: Date): Promise<void>;
}
```

`job` exposes `id`, `type`, `payload`, `attempt`, `maxAttempts`, `retryPolicy`, `deadlineAt`,
`executionTimeoutMs`, `attemptTimeoutAt`, `fenceToken`, and `leaseExpiresAt`.

`signal` aborts with `CancellationRequestedError`, `DeadlineExceededError`, or `ExecutionTimeoutError`.
See [Cancellation, deadlines, and timeouts](/docs/cancellation).

## Leases and heartbeats

A claim grants a lease for `leaseMs`. Each active job runs its **own** heartbeat loop and fence
lifecycle. An accepted heartbeat extends only that job's lease.

Choose values so that:

- `heartbeatMs` is comfortably below `leaseMs` to tolerate event-loop and network jitter;
- `leaseMs` is short enough to meet your recovery objective after a hard process kill.

If a lease expires, bounded recovery closes the old attempt immutably and creates a new one. The old
worker's later writes are rejected by fencing.

## Concurrency

`concurrency` is the number of async handler executions one `Worker` may own concurrently. It is:

- not an OS thread count;
- not a Node worker-thread pool;
- not a process-global limit;
- multiplied by the number of worker instances and process replicas claiming the same work.

A claim pass issues one claim at a time, starts each claimed job in its own slot, never claims beyond
the bound, and stops filling the pass at the first null claim.

```ts
worker.concurrency; // readonly number
worker.runtimeState(); // { concurrency, activeSlots, paused, draining }
```

### Measured behavior

From the 2026-08-02 lifecycle benchmark with roughly 120 ms handlers:

| Concurrency |   Throughput | Maximum overlap |
| ----------: | -----------: | --------------: |
|           1 |  8.08 jobs/s |               1 |
|           4 | 31.83 jobs/s |               4 |
|           8 | 62.85 jobs/s |               8 |

At equal total capacity, `1×8`, `2×4`, and `8×1` all reached about 63 to 64 jobs/s for I/O-like
handlers. One eight-slot worker bounded claim pressure to a single query while preserving the same
handler overlap.

**Recommendation:** use one multi-slot `Worker` per distinct queue or policy group per process, and
scale process replicas for availability and aggregate capacity. Do not create one `Worker` per
concurrency slot.

Add another worker definition only when it needs materially different queue names, handler registries,
lease or heartbeat policy, schedule namespaces, maintenance behavior, or retry overrides.

## Lifecycle controls

```ts
worker.pause(); // stop new claims; active handlers and heartbeats continue
worker.resume(); // reopen claims immediately
worker.stop(); // stop new claims; run() resolves after active handlers drain
worker.isPaused();
await worker.runOnce(); // single claim pass, useful in tests
```

These are **process-local** controls, not a durable worker registry or a cross-worker rate limit.

## Maintenance telemetry

```ts
const worker = new Worker(queue, {
  workerId: "worker-1",
  onMaintenance: (telemetry) => {
    // { loop, phase, rowsAffected, durationMs, skippedLock, error, observedAt }
    metrics.record(telemetry);
  },
});

worker.maintenanceTelemetry(); // latest event per loop
```

`loop` is one of `tick`, `history_partitions`, `history_retention`, or `terminal_storage`.

## Dedicated worker processes

Production deployments should run workers in their own process. Define the process once:

```ts
// src/workhorse.worker.ts
import { createWorkhorseAdapter, defineWorkerProcess } from "@workhorse/core";
import { Pool } from "pg";
import { generateReport, sendEmail } from "./jobs.js";

export default defineWorkerProcess({
  adapter() {
    const pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 10 });
    return createWorkhorseAdapter({
      database: pool,
      adaptTransaction: (transaction: typeof pool) => transaction,
      close: () => pool.end(),
    });
  },
  workers: [
    {
      options: { concurrency: 8, scheduleNamespaces: ["production"] },
      configure(worker) {
        worker.handle("email.send", sendEmail);
        worker.handle("report.generate", generateReport);
      },
    },
  ],
  shutdownTimeoutMs: 25_000,
  probes: { hostname: "0.0.0.0", port: 9090 },
});
```

Run the compiled module with the packaged CLI:

```bash
workhorse worker --config ./dist/workhorse.worker.js --shutdown-timeout-ms 25000
```

The CLI imports JavaScript understood by the current Node.js process. It does not bundle a TypeScript
loader, so production should run compiled output.

Applications that own their own supervision can use the APIs directly:

- `defineWorkerProcess(definition)` type-checks and returns a configuration.
- `startWorkerProcess(definition)` starts workers without installing global signal handlers.
- `runWorkerProcess(definition, options)` installs the standalone Node process lifecycle.

Signal handling, probe endpoints, drain deadlines, and deployment manifests are covered in
[Deployment and operations](/docs/operations).
