`@workhorse/dashboard` is an embeddable React operator dashboard. The package owns the UI, data
contracts, theme, styles, browser bundle, oRPC client, and a provider-neutral server read model. It has
no dependency on the demo application.

## What it shows

- Current tasks with filters, pagination, and a task drawer
- Durable checkpoint progress (a Steps column and a stepper of saved, running, and pending boundaries)
- Terminal results and per-attempt failure evidence
- Recurring schedules and their occurrences
- Queues and the live worker fleet, including audited pause and resume that reach workers in any process
- System health: deadline pressure, retention lag, and PostgreSQL diagnostics

## Mounting

The dashboard host is framework-neutral. It takes a `Request` and returns a `Response`, or `null`
when the request does not belong to its mount path, so unrelated host routes are never taken over.

```ts
import { createDashboardHost } from "@workhorse/dashboard/server";

const host = createDashboardHost({
  path: "/workhorse", // "/" to own the host root
  database: pool,
  environment: "production",
  authorize: (request) => isAdmin(request),
});
```

**Fetch-native hosts** — Hono, Next.js route handlers, SvelteKit, Nitro:

```ts
const response = (await host.handle(request)) ?? new Response("Not found", { status: 404 });
```

**Connect-style hosts** — Express, Connect, Fastify via `@fastify/middie`:

```ts
import { dashboardNodeMiddleware } from "@workhorse/dashboard/server";

app.use(dashboardNodeMiddleware(host));
```

For Hono, `mountWorkhorseDashboard` is a thin binding that registers these routes for you:

```ts
import { mountWorkhorseDashboard } from "@workhorse/hono";

mountWorkhorseDashboard(app, {
  database: pool,
  path: "/workhorse",
  environment: "production",
  authorize: (request) => isAdmin(request),
});
```

<Callout>
  Mounting needs only a database connection. It does **not** need a worker runtime. Workers register
  themselves in PostgreSQL, so the dashboard reports every live worker even when they run in
  separate processes — which is the recommended production topology.
</Callout>

Selected options:

| Option                                                                                    | Purpose                                                                                                                                            |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`                                                                                    | Mount namespace. Defaults to `/workhorse`.                                                                                                         |
| `authorize`                                                                               | **Required.** Authorizes every dashboard, RPC, asset, and stream request.                                                                          |
| `environment`                                                                             | Label shown in the UI                                                                                                                              |
| `configuredWorkers`                                                                       | Optional. Expected worker identities, so a declared worker that has never started is still visible. Live workers are discovered from the registry. |
| `auditActor`                                                                              | Actor recorded for mutations initiated from the dashboard                                                                                          |
| `browserModules`                                                                          | Trusted host-owned ES modules loaded before the dashboard entry                                                                                    |
| `operator`, `queueController`, `taskController`, `workerController`, `scheduleController` | Host-owned control surfaces, used to wrap mutations in your own audit and authorization                                                            |
| `refresh`                                                                                 | Refresh hub to publish into; pair with `listenForDashboardRefresh`                                                                                 |
| `projectDurability`                                                                       | Host projection of durable-step progress                                                                                                           |

## Authorization

<Callout type="warn">
  The dashboard has **no built-in authentication, RBAC, or multi-tenancy**. Host applications must
  authorize every request. `requestedBy` and `auditActor` are attribution, not authorization.
</Callout>

Expose it only to trusted operators, behind your existing session or SSO check.

## Schema safety

The mount verifies that the installed schema is compatible and returns `503` when it is not. It
deliberately never installs or migrates database objects.

## Custom integrations

The React surface remains available for hosts that want to render the dashboard themselves:

```tsx
import { Dashboard, WorkhorseThemeProvider } from "@workhorse/dashboard";
import { createDashboardClient } from "@workhorse/dashboard/client";
import "@workhorse/dashboard/styles.css";

const client = createDashboardClient("/workhorse/rpc");

root.render(
  <WorkhorseThemeProvider>
    <Dashboard client={client} basePath="/workhorse" auditActor="ops@example.com" />
  </WorkhorseThemeProvider>,
);
```

`DashboardProps` accepts `client`, `basePath`, `auditActor`, and `demoTools`. The `demoTools` job
seeding menu is not part of the required client contract; opt in only when a host intentionally
supplies demo fixtures. All sample and seed data stay owned by the demo project, never the package.

Server-side building blocks are exported from `@workhorse/dashboard/server`, including
`createDashboardHost`, `dashboardNodeMiddleware`, `listenForDashboardRefresh`, `dashboardRouter`,
`readDashboardSnapshot`, `dashboardDatabase`, `dashboardAssetsDirectory`, and `DashboardRefreshHub`.

## Standalone console

To look at a queue without wiring the dashboard into an application at all:

```bash
npx workhorse dashboard --port 3000
```

This owns its process, so unlike an embedded mount it takes a connection string. It binds
`127.0.0.1` and is read-only by default, because a standalone server has no session to authorize
against. `--host` publishes it and `--allow-mutations` enables operator actions attributed to
`--actor`; both print a warning, and neither is a substitute for putting it behind your own
authenticated proxy.

## Refresh behavior

The browser refreshes only the active page through its dedicated reader on a bounded polling cadence.
The default is 30 seconds, with 5-second, 15-second, 1-minute, 5-minute, and manual-only options.

To react promptly to work happening in another process, bridge PostgreSQL notifications into the
mount's refresh hub:

```ts
import { listenForDashboardRefresh } from "@workhorse/dashboard/server";

const client = new Client({ connectionString });
await client.connect();
await listenForDashboardRefresh({ client, refresh });
```

This listens on `workhorse_jobs` (the dispatch wake hint, meaning ready work may exist) and
`workhorse_activity` (coalesced operator hints that workers publish when
`WorkerOptions.activityNotifications` is enabled, covering transitions such as completion that
create no ready work). The client must be a dedicated connection, not a pooled one, because
`LISTEN` registers against a specific backend session.

Both channels are liveness optimizations, never a source of truth. A dropped notification only
delays a refresh until the stream's periodic fallback fires.

## Try it locally

The repository ships an end-to-end demo that mounts the packaged dashboard and seeds successful,
retried, failed, durable, deadline, and timeout jobs:

```bash
pnpm install
pnpm db:reset:all
pnpm demo
```

See the
[demo README](https://github.com/stablemates/workhorse/blob/main/demo/README.md) for fixtures,
production-mode, and connection overrides.
