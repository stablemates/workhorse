---
title: How does a job move through Workhorse?
description: Understand the tables, states, ownership, and delivery contract behind every job.
---

A Workhorse job separates immutable identity from live state and terminal evidence. That split keeps
dispatch fast because completed jobs leave the table workers search.

## Where does a job live?

`job` stores the identity, queue, type, payload, attempt budget, and policy. PostgreSQL writes this
row when it accepts the job and never changes its semantic fields.

`job_runtime` exists while the job is `scheduled`, `ready`, or `active`. Workers and SQL functions
change this row as the job becomes eligible, gains an owner, or returns for another attempt.

`job_outcome` appears when the job becomes `succeeded`, `failed`, or `canceled`. PostgreSQL removes
the runtime row and writes the outcome in the same transaction.

A committed job has one runtime row or one outcome row. It never has both, so readers cannot observe
the job as live and terminal at the same time.

## Who owns active work?

A `Worker` calls `claim_v2` when it has a free slot. PostgreSQL checks any durable queue policy, then records the worker ID, an expiry, and
a fence token on `job_runtime`.

The worker calls `heartbeat_v2` while the handler runs. If heartbeats stop, recovery closes the old
attempt and makes the job eligible again.

Every semantic write carries the worker ID and fence token. A stale worker cannot complete, fail, or
change a job after a newer worker has claimed it.

## Why can a handler run again?

The handler runs outside the transaction that grants ownership. A process can finish an external
effect and die before PostgreSQL records success, so recovery must run the handler again.

That is at-least-once delivery. Use stable provider idempotency keys for external effects, and use
`HandlerContext.checkpoint` to reuse completed stages inside a job.

## Where does history go?

`job_event` records lifecycle changes, while `attempt_history` records how each logical attempt
closed. These append-only relations can grow and retire independently of the live dispatch path.

`job_query` gives operator reads their own bounded projection. Queries and the dashboard can inspect
all states without adding broad indexes to `job_runtime`.
