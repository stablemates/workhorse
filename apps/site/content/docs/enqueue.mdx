---
title: How do I enqueue work safely?
description: Accept immediate, delayed, batched, or transactional jobs without separating them from application state.
---

`Queue.enqueue` turns a type and JSON payload into a durable job. Pass an application transaction
when the job must agree with another database write.

## Enqueue immediate or delayed work

Without `runAt`, PostgreSQL places the job in `ready`. A future `runAt` places it in `scheduled`
until `tick_v1` promotes it.

```ts
await queue.enqueue("email.send", { to: "person@example.com" });

await queue.enqueue("invoice.remind", { invoiceId }, { queue: "billing", runAt: reminderDate });
```

`runAt` is a not-before boundary. If someone pauses the queue, or workers become unavailable, a
worker can claim the job later than the boundary.

`EnqueueOptions` also carries tags, a concurrency key, an attempt budget, a retry policy, a deadline,
an execution timeout, and enqueue idempotency. The architecture reference owns their exact bounds and defaults.

## Join an application transaction

Pass the active `Queryable` after the options. PostgreSQL then commits the job and your application
write together, which removes the gap that an outbox normally reconciles.

```ts
const client = await pool.connect();

try {
  await client.query("BEGIN");
  await client.query("INSERT INTO account (id, email) VALUES ($1, $2)", [id, email]);
  await queue.enqueue("account.created", { accountId: id }, {}, client);
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

This transaction covers durable acceptance only. Handlers run later and outside the transaction, so
their external effects still need idempotency.

## Enqueue a batch

`Queue.enqueueMany` validates and writes a bounded group in one statement. Returned IDs preserve
input order, and the whole group commits or rolls back together.

Use several bounded calls when your input exceeds the published limit. Add an idempotency key to
each request if a caller may repeat part of the batch.

## Separate queues without adding priorities

`new Queue(database, defaultQueue)` selects the client default, while `options.queue` overrides one
job. A `Worker` claims from its configured queue.

Workhorse orders ready jobs by FIFO sequence and has no priority layer. Use separate queue names when
different work needs different capacity or worker policy.

Use `options.concurrencyKey` when a synchronized queue policy also limits one application-defined
group. Keys are scoped to their queue and remain part of idempotent enqueue identity.

`Queue.pauseQueue` prevents workers from claiming new jobs without changing them. `Queue.resumeQueue`
lets workers claim again, while `Queue.purgeQueue` removes scheduled work and releases its enqueue
keys.
