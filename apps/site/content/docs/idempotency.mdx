---
title: How do I prevent duplicate jobs?
description: Use scoped enqueue keys so repeated acceptance returns the original durable job.
---

Enqueue idempotency prevents repeated requests from creating repeated job identities. It solves
duplicate acceptance, while handler delivery remains at least once.

## Choose a stable key

Build the key from the business operation that should happen once, such as an order or webhook
delivery. A timestamp or random value cannot identify a replay.

```ts
const jobId = await queue.enqueue(
  "invoice.capture",
  { invoiceId },
  {
    queue: "billing",
    idempotency: {
      key: `capture:${invoiceId}`,
      scope: "invoice-capture",
    },
  },
);
```

If the same scope and key still exist, an equivalent request returns the original job ID. PostgreSQL
does not add another job, event, queue placement, or notification.

Scopes keep unrelated features apart. An omitted scope uses `DEFAULT_IDEMPOTENCY_SCOPE`, which works
well when every key already includes a feature prefix.

## What counts as the same request?

PostgreSQL fingerprints the queue, type, payload, sorted tags, attempt budget, retry policy, key
retention, and an explicit `runAt` value.

If those fields match, the call is a replay. If they differ, `Queue.enqueue` throws
`EnqueueIdempotencyConflictError` and rolls back the statement.

An omitted `runAt` remains omitted in the fingerprint. A later replay of an immediate job therefore
does not conflict with the original acceptance time.

## What is stored?

PostgreSQL stores the scope and a cryptographic hash of the key. Events, errors, and operator views
show only a bounded preview and digest, so the raw key does not become audit data.

Bindings expire under the request policy. After expiry, the same key can own a new job, which makes
enqueue idempotency a replay window rather than a permanent business registry.

Purging a waiting job releases its binding. Maintenance removes expired bindings before it removes
terminal job identity.

## Why do handlers still need idempotency?

One accepted job can run again after a worker dies. Use the job ID or a domain ID as the provider's
idempotency key when repeating an external effect would be harmful.

`HandlerContext.checkpoint` can reuse a completed stage, but a crash can still occur after the effect
and before the checkpoint commit. The system performing the effect must close that final gap.
