---
title: How do I report job progress?
description: Publish a bounded latest-value projection for operators without changing durable control flow.
---

Progress answers what an active handler is doing now. It is mutable operator data, so it cannot tell
Workhorse to skip a stage after a retry.

## Publish the latest value

Call `HandlerContext.setProgress` with a JSON value that your operator surface understands.

```ts
worker.handle("catalog.import", async (payload, context) => {
  await context.setProgress({ phase: "reading" });
  const result = await importCatalog(payload);
  await context.setProgress({ phase: "complete", imported: result.count });
  return result;
});
```

`HandlerContext.getProgress` returns the latest retained value. A custom runtime can use
`Queue.updateProgress` and `Queue.getProgress` with the claimed job and worker identity.

## Why is progress rate-limited?

Every changed value updates one `job_progress` row and appends a small `progress_updated` event. A
tight loop would create database churn without making the interface more useful.

PostgreSQL therefore size-caps and rate-limits changed values. A caller that updates too quickly gets
`ProgressRateLimitError`, including when it may retry.

Repeating an identical value is a no-op. It does not advance the revision or append another event,
which makes harmless retries cheap.

## What survives?

Each accepted update records the attempt, fence token, worker ID, revision, and timestamps. The
latest value survives retries and terminal materialization until retention removes the job identity.

Only the current unexpired owner can change progress. A stale generation receives
`ProgressLeaseLostError`, so old handlers cannot overwrite a newer activation's status.

Progress is not a checkpoint. Use `HandlerContext.checkpoint` when another activation must reuse a
completed result instead of running the operation again.
