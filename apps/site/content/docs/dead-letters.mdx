---
title: How do I run a failed job again?
description: Inspect terminal failures and redrive selected work as fresh, auditable job identities.
---

When a job exhausts its attempts, Workhorse keeps an immutable failed outcome. Redrive creates a new
job from that evidence instead of rewriting the failed job.

## List terminal failures

`Queue.listDeadLetters` reads the cold failure index and supports bounded filters for queue, type,
tags, error name, and finish time.

```ts
const page = await queue.listDeadLetters({
  queue: "billing",
  errorName: "ProviderTimeout",
});

for (const failure of page.items) {
  console.log(failure.jobId, failure.error, failure.redriveCount);
}
```

The cursor uses immutable finish time and job identity. Dead-letter listing stays separate from
ready and active indexes, so a large failure backlog does not slow claims.

## Redrive one failure

`Queue.redrive` requires the actor, reason, and a stable request ID. Your operator layer must
authorize the actor before calling it.

```ts
const result = await queue.redrive(sourceJobId, {
  requestedBy: actor.email,
  reason: "provider incident resolved",
  requestId: incidentId,
});
```

The target copies the queue, type, payload, tags, retry policy, attempt budget, and execution timeout.
It does not copy attempts, errors, checkpoints, waits, cancellation state, or the old deadline.

The source remains unchanged as evidence. `job_redrive` stores the lineage edge, so
`Queue.getRedriveLineage` can trace later copies back to their failures.

## Make operator retries safe

Repeating the same source and request returns the existing target. If attribution changes under the
same request ID, Workhorse throws `RedriveIdempotencyConflictError` instead of losing audit evidence.

PostgreSQL stores a digest rather than the raw request ID. Operator views receive safe diagnostics
without turning incident identifiers into durable payload.

## Work through a backlog carefully

`Queue.redriveMany` processes a bounded page of matching failures in stable order. Its dry-run option
returns eligible sources without creating jobs or lineage.

Start with a narrow dry run, confirm the external dependency has recovered, and then reuse one
incident request across cursor pages. If the tool crashes, repeating the page converges on its
existing targets.

Redrive is another at-least-once execution. Payment, email, and webhook handlers still need provider
idempotency before an operator replays them.
