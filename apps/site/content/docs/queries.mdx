title: Querying and timelines
description: Cursor-based cross-state job listing with bounded payload projection, point lookup, merged lifecycle timelines, and queue health.
---

Operator reads use a dedicated `job_query` projection with its own indexes. They never broaden the
ready, scheduled, active, deadline, timeout, or recovery indexes used by dispatch.

## Point lookup

```ts
const snapshot = await queue.getJob(jobId);
```

`getJob` coalesces the sole live runtime row or the terminal outcome into one stable `JobSnapshot`:

```ts
{
  id, queue, type, payload, tags, state,
  currentAttempt, maxAttempts, retryPolicy,
  deadlineAt, executionTimeoutMs,
  fenceToken,      // bigint; zero before the first claim
  runAt, result, error,
  cancelRequestedAt, cancelRequestedBy, cancelReason,
  createdAt, updatedAt,
}
```

Returns `null` when the identity does not exist. Use this when existence matters.

## Cross-state listing

```ts
const page = await queue.listJobs({
  queue: "billing",
  type: "invoice.capture",
  states: ["active", "failed"],
  createdAfter: new Date("2026-08-01T00:00:00Z"),
  createdBefore: new Date("2026-08-02T00:00:00Z"),
  limit: 100,
  payload: {
    include: true,
    maxBytes: 16_384,
    redactKeys: ["cardNumber", "accessToken"],
  },
});

for (const item of page.items) {
  console.log(item.id, item.state, item.payloadStatus);
}

if (page.nextCursor) {
  const next = await queue.listJobs({ /* same filter */ cursor: page.nextCursor });
}
```

### Ordering, cursors, and limits

- Pages are ordered newest-first by immutable `(createdAt, jobId)`.
- The default limit is 100; the maximum page size is 1,000 (`MAX_JOB_QUERY_PAGE_SIZE`).
- Cursors are signed and **bound to the filter and payload projection** that produced them. Reusing a
  cursor with a different filter is rejected.
- Unknown query fields throw `TypeError`, so typos fail loudly instead of silently widening a scan.

### Payload projection

Payload is **omitted by default**. When you opt in:

- PostgreSQL applies at most 50 unique top-level redaction keys (`MAX_JOB_QUERY_REDACT_KEYS`) before
  checking the response ceiling.
- The ceiling is caller-selected from 1 byte through 1 MiB (`MAX_JOB_QUERY_PAYLOAD_BYTES`), defaulting
  to `DEFAULT_JOB_QUERY_PAYLOAD_BYTES`.
- Each row reports `payloadStatus` as `omitted`, `included`, or `too_large`. An omitted or oversized
  payload is returned as `null`.
- Redaction applies to top-level object keys only. It is not a nested scrubber.

Candidate identities are selected before payload rows are joined, so only the bounded page touches
payload storage.

### Consistency

<Callout type="warn">
  Listing is intentionally **weakly consistent across calls**. New jobs can appear before an
  existing cursor, and concurrent state changes can alter membership in a later filtered page. Use
  `getJob` when identity existence matters.
</Callout>

## Lifecycle timelines

```ts
const timeline = await queue.getJobTimeline(jobId, { limit: 100 });

for (const entry of timeline.items) {
  if (entry.kind === "event") {
    console.log(entry.occurredAt, entry.eventType, entry.details);
  } else {
    console.log(entry.occurredAt, entry.outcome, entry.attempt);
  }
}
```

- Merges retained lifecycle events and closed attempts into one latest-first cursor stream.
- Pages are capped at 1,000 entries.
- Attempt outcomes are `succeeded`, `failed`, `retry`, `lease_expired`, `canceled`,
  `deadline_exceeded`, or `timeout`.

Event and attempt retention are independent, so a known job may have a partial or empty timeline.
Unknown identities and fully retired history both return an empty stream; use `getJob` to tell them
apart.

## Checkpoints and waits

```ts
await queue.getCheckpoint(jobId, "charge");
await queue.listCheckpoints(jobId);
await queue.getWait(jobId, "cooldown");
await queue.listWaits(jobId);
```

These return immutable durable-execution evidence with attempt, fence, worker, and creation-time
provenance. See [Durable checkpoints and waits](/docs/durable-execution).

## Queue health

```ts
const health = await queue.health();
```

`QueueHealth` reports:

| Group           | Fields                                                                        |
| --------------- | ----------------------------------------------------------------------------- |
| Protocol        | `schemaVersion`                                                               |
| Depth           | `counts` per state, `readyDepth`, `scheduledDepth`, `oldestReadyAgeMs`        |
| Durable waits   | `sleepingJobs`, `overdueWaits`, `nextWakeAt`                                  |
| Ownership       | `activeLeases`, `expiredLeases`                                               |
| Timing pressure | `deadlinePressure`, `activeExecutionTimeouts`, `overdueExecutionTimeouts`     |
| Retention       | `retentionPolicy`, `retentionLagMs`, `oldestRetainedAt`                       |
| History         | `eligibleHistoryPartitions`, `defaultHistoryRows`, `defaultHistoryRowsCapped` |
| PostgreSQL      | `relations[]`, `oldestTransactionAgeMs`, `lockWaitCount`                      |

A JSON snapshot is also available from the CLI:

```bash
workhorse-health
```

<Callout>
  Health is assembled from independent read-only queries and PostgreSQL statistics can lag, so it is
  a useful operational signal rather than a transactionally consistent snapshot.
</Callout>
