---
title: Retries and backoff
description: Persisted retry policies, PostgreSQL-owned delay selection, manual overrides, and terminal failure.
---

Retries are decided in PostgreSQL. `fail_v1` increments the attempt, selects the delay, performs the
transition, and records provenance, so every client and language binding behaves identically.

## Attempt budget

`maxAttempts` defaults to **25**. Exhaustion atomically removes the runtime row and creates an
immutable failed outcome.

## Persisted retry policies

Attach a policy at enqueue time or on a recurring schedule's job definition:

```ts
type RetryPolicy =
  | { type: "fixed"; delayMs: number }
  | { type: "exponential"; initialDelayMs: number; multiplier: number; maxDelayMs: number }
  | { type: "decorrelated-jitter"; baseDelayMs: number; maxDelayMs: number };
```

```ts
await queue.enqueue(
  "provider.sync",
  { accountId },
  {
    maxAttempts: 8,
    retryPolicy: { type: "exponential", initialDelayMs: 1_000, multiplier: 2, maxDelayMs: 300_000 },
  },
);
```

PostgreSQL validates and normalizes the policy, selects each delay, performs the retry or recovery
transition, and records policy provenance. Explicit policies apply equally to **handler failure** and
**expired-lease recovery**.

### Bounds

| Constraint   | Rule                                            |
| ------------ | ----------------------------------------------- |
| Any delay    | Integer, 0 through 31,536,000,000 ms (365 days) |
| `multiplier` | Integer, 1 through 100                          |
| `maxDelayMs` | At least `initialDelayMs` / `baseDelayMs`       |

### Deterministic decorrelated jitter

Decorrelated jitter derives from the stable job identity, the attempt, and the persisted previous
delay. Replay and `Queue` recreation cannot change the selected value.

## Default behavior without a policy

Omitting `retryPolicy` preserves compatibility:

- **Handler failure** uses the SQL-owned, Sidekiq-inspired random backoff. For zero-based retry count
  `count` (the first failed attempt is `0`), the delay is
  `(count ** 4) + 15 + floor(random() * 10) * (count + 1)` seconds. With the default 25-attempt budget
  that spreads retries across roughly 20 days.
- **Expired-lease recovery** is immediate.

## Manual overrides

Precedence, highest first:

1. A numeric `retryDelayMs` passed to `Queue.fail(...)`.
2. `WorkerOptions.retryDelayMs`, either a number or `(attempt, job) => number | undefined`.
3. The job's persisted `retryPolicy`.
4. The compatibility default above.

```ts
const worker = new Worker(queue, {
  workerId: "sync-1",
  retryDelayMs: (attempt, job) => {
    if (job.type === "provider.sync") return Math.min(60_000, 1_000 * 2 ** attempt);
    return undefined; // defer to the persisted policy or SQL default
  },
});
```

Returning `undefined` defers to PostgreSQL. An omitted delay in `Queue.recoverExpired(limit)` is passed
as SQL `NULL` so PostgreSQL selects the persisted policy.

<Callout>
  Overrides change **timing** only. PostgreSQL still enforces the attempt budget, deadlines, and
  execution timeouts.
</Callout>

## Observability

Claims and `JobSnapshot` expose the normalized persisted policy. The `retry_scheduled` and
`lease_expired` lifecycle events expose `retry_policy`, `retry_delay_ms`, and `retry_delay_source`, so
you can always tell which layer selected a delay.

```ts
const snapshot = await queue.getJob(jobId);
snapshot?.retryPolicy; // RetryPolicy | null
snapshot?.currentAttempt;
```

## Failure paths

| Path                        | Result                                                                |
| --------------------------- | --------------------------------------------------------------------- |
| Handler throws, budget left | Retry to `ready` or `scheduled` with the selected delay               |
| Handler throws, budget gone | Immutable `failed` outcome plus closed attempt history                |
| Lease expires               | Bounded recovery closes the attempt and requeues or fails             |
| Deadline reached            | Terminal failure without retry                                        |
| Execution timeout           | Distinct timeout evidence; remaining budget schedules a later attempt |
| Cancellation requested      | Cancellation wins over retry; see [Cancellation](/docs/cancellation)  |

Terminal failures land in the cold `job_outcome` relation and are queryable through
[dead letters and redrive](/docs/dead-letters).
