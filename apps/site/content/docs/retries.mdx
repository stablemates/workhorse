---
title: How does a failed job retry?
description: Give jobs an attempt budget and a persisted backoff policy that PostgreSQL applies consistently.
---

When a handler throws, PostgreSQL decides whether another attempt remains. It records failure
evidence before moving the job back to `ready`, `scheduled`, or a terminal outcome.

## Set an attempt budget

`EnqueueOptions.maxAttempts` limits how many logical attempts the job can use. When the budget is
gone, `fail_v1` removes the runtime row and writes an immutable failed outcome.

The database enforces this budget regardless of which client reported the failure. A worker override
can change timing, but it cannot create extra attempts.

## Persist the delay policy with the job

`RetryPolicy` supports fixed, exponential, and decorrelated-jitter policies. PostgreSQL validates the
chosen shape and stores it with the immutable job definition.

```ts
await queue.enqueue(
  "provider.sync",
  { accountId },
  {
    retryPolicy: providerRetryPolicy,
  },
);
```

A fixed policy always uses the same delay. Exponential delay grows toward a ceiling, while
decorrelated jitter spreads a group of failures across different wake times.

Workhorse derives jitter from stable job state. Recreating a `Queue` or replaying the same transition
therefore cannot select a fresh random delay.

## Keep failure and recovery consistent

An explicit policy applies when a handler throws and when recovery finds an expired lease. That
keeps a crashed process from changing the job's backoff behavior.

Jobs without a policy preserve compatibility behavior, which differs between handler failure and
lease recovery. Set a persisted policy when consistent timing matters.

`Queue.fail` and `WorkerOptions.retryDelayMs` can override the next delay. If a worker callback returns
`undefined`, PostgreSQL falls back to the persisted policy or compatibility behavior.

## What survives another attempt?

The job ID, payload, tags, policy, and saved checkpoints remain. PostgreSQL increments the attempt,
and the next claim receives a new fence token.

A retry is another run of the same job. A redrive happens only after terminal failure and creates a
new job identity.

`JobSnapshot.retryPolicy` shows the normalized policy. Timeline events record the selected delay and
its source, which lets an operator explain why a job is waiting.
